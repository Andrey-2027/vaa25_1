# D-R S0: семантическая классификация production-типов артефакта platform-register.
#
# Зачем реестр появился в том же срезе, что и модуль. Порядок «сначала перенести 17 типов, потом
# решить, что из них контракт» уже опробован в D3.3 и дал TEMPORARY_ALL_PUBLIC: состав
# зафиксирован, а решение не принято ни по одному типу, включая реализацию. Здесь роль
# назначается тем же изменением, которое создаёт артефакт. Забор — RegisterSurfaceRoleTest
# в самом модуле: его сборка (buildSteps манифеста) гоняет тесты, поэтому расхождение видно на
# сборке артефакта, а не только в приложении.
#
# Формат: <role> <fqn>
# Роли (ровно одна на production-тип): APP_API | APP_SPI | MODULE_API | INTERNAL
#   APP_API    — поддерживаемый API приложения: приложение называет тип, платформа не наследует.
#   APP_SPI    — приложение реализует или расширяет тип; платформа вызывает обратно.
#   MODULE_API — контракт между platform-модулями: тип нужен следующему срезу (S1 — читатель,
#                S3 — протокол набора владельца), но приложение его не называет.
#   INTERNAL   — реализация без compatibility promise: менять и удалять можно свободно.
# Вложенные типы наследуют роль владельца и отдельной записи не требуют.
#
# Замер, на котором стоят решения, а не привычка: `node scripts/analyze-platform-surface.mjs
# --json` (2026-10-13). Из него следует:
#   · приложение (main) называет 12 типов среза, тесты — ещё четыре; роль по тесту не
#     назначается: тесты движка переезжают вместе со своими срезами (S5);
#   · ни один платформенный модуль типов регистра не называет. Поэтому MODULE_API на S0 не
#     назначен ни одному типу: следующий срез введёт его осознанно, вместе с читателем, а не
#     как «на будущее»;
#   · четыре типа не названы нигде — охранник подчинённой строки, контекст записи набора,
#     валидатор декларации и валидатор среза. Это реализация: обещание строки — поведение, а не
#     имена. Охранник назван аннотацией @EntityListeners на базовом классе подчинённой строки,
#     и в baseline артефакта эта строка видна: забор замыкания считает сигнатурой поля, методы
#     и наследование, а не аргументы аннотаций. Так исключение остаётся прочитанным в диффе,
#     а не невидимым.
#
# Совместимость с D1-реестром приложения (platform-public-surface.txt). Роли сходятся, кроме
# двух записей: D1 записал PeriodicRegisterEntryBase и RecordedRegisterEntry как API по признаку
# «приложение называет тип», здесь роль — APP_SPI по признаку «приложение расширяет тип»
# (NomenclaturePrice extends PeriodicRegisterEntryBase, строки реализуют RecordedRegisterEntry).
# Это два разных вопроса, и один ответ на них склеивать нельзя: D1 считает бюджет доступа
# приложения к платформе, этот реестр — границу обещания совместимости. Расхождение записано
# явно, чтобы следующий срез читателя не унаследовал его молча.
#
# ---- S1 (2026-10-13) добавил 8 типов: реестр объявлений, каталог типов-регистраторов, стартовая
# проверка деклараций, точечный и срезовый читатели, фазы отбора листового списка, фабрика
# читателей и её read-конфигурация. Решения этого среза:
#
#   · APP_API у читателей и реестра — по-прежнему по признаку «приложение называет тип»
#     (сервис пилота, форма списка, конфигурация записи), а не по признаку «тип принадлежит
#     модулю». MODULE_API остаётся пустым осознанно: замер `grep` по platform-*/src/main показал,
#     что ни один платформенный модуль типов регистра не называет. Появится потребитель
#     (S4 — UI-модуль) — роль придётся пересмотреть, и это видно в диффе, а не в комментарии;
#   · RecorderTypeRegistry переехал в S1, а не в S3 вместе с набором владельца: реестр разрешает
#     коды регистраторов, и без каталога реестр перестал бы проверять декларацию. План называл
#     это развилкой S1 («либо каталог типов переезжает вместе с реестром, либо разрешение кодов
#     получает S3-расширение»); выбран переезд, поэтому цена — один тип читающего среза,
#     а не второй способ разрешения кодов;
#   · RegisterStartupValidator — INTERNAL, а не APP_API: приложение его не называет, он объявлен
#     конфигурацией модуля. Обещание здесь — поведение («регистрация падает громко»), а не имя,
#     и это тот же размен, что у валидаторов S0;
#   · RegisterReadConfiguration — INTERNAL по той же причине: имя авто-конфигурации не обещание,
#     обещание — бины, которые она приносит (и их можно заменить своими,
#     @ConditionalOnMissingBean).
#
# ---- S2 (2026-10-13) добавил 10 типов: команды записи по ключу и смены ключа, их именованные
# операции, охранник mapping'а, чтение состояния строки, мьютекс записи, часы порядка подчинённых
# регистров вместе с их сущностью и вторая авто-конфигурация артефакта. Решения среза:
#
#   · APP_API у обеих команд и обеих таблиц именованных операций — по всё тому же признаку
#     «приложение называет тип»: сервис цен вызывает set/delete и смену ключа, форма списка и
#     диалог ключа спрашивают у тех же классов canWriteKey/canChangeKey, чтобы интерфейс и
#     команда отвечали одним решением (ADR-0017);
#   · MODULE_API впервые не пуст, и это не «на будущее»: RecorderOrderClock и его засев нужны
#     следующему срезу — протоколу набора владельца (S3). Оговорка названа честно: пока S3 живёт
#     в приложении, прикладной RecorderSetWriter называет часы порядка напрямую (берёт их из
#     мьютекса и вызывает advance). Это единственное место, где запись не следует букве
#     «приложение его не называет», и оно исчезает вместе с переездом S3, а не в результате
#     решения о роли: обещание здесь — контракт между модулем и следующим срезом, а не
#     прикладная поверхность;
#   · охранник mapping'а, чтение состояния строки, мьютекс и вторая авто-конфигурация — INTERNAL:
#     приложение их не называет, а обещание среза — поведение («поля ключа неизменяемы для
#     обычных путей», «смена ключа только под разрешением команды»), а не имена. Мьютекс и чтение
#     состояния вообще package-private: замыкание API проверено забором, а не глазами;
#   · разделение конфигурации на read (S1) и key-write (S2) — причина появления двух записей в
#     AutoConfiguration.imports: срез привозит только свою часть, а протокол набора владельца (S3)
#     остаётся приложению до своего среза и пользуется теми же часами порядка, а не вторым
#     механизмом.
#
# ---- S3 (2026-10-14) добавил 11 типов и понизил два: протокол набора владельца — процедуры записи
# подчинённых регистров под документом-владельцем, его шов авторизации, участие в canonical
# сохранении и удалении агрегата и третья авто-конфигурация артефакта. Решения среза:
#
#   · RegisterRecords и RecordedRegisterReader — APP_API по всё тому же измеренному признаку:
#     приложение (main) называет их — генерация набора владельца вызывает RegisterRecords, сервис
#     чтения подчинённых строк собирает RecordedRegisterReader. Это первое место, где срез приносит
#     прикладной протокол, а не только движок: процедура набора — часть контракта приложения
#     с платформой (ADR-0019), поэтому её роль APP_API, а не MODULE_API — обещание предъявляется
#     приложению, и понижать его до «внутреннего для модуля» значило бы соврать о том, кто
#     потребитель;
#   · RecorderSetWriteAuthorizer и RecorderSetWriteRequest — APP_SPI: приложение не вызывает
#     авторизатор, а реализует его (в тестах — лямбдой), платформа вызывает обратно перед заменой
#     набора. Обе роли обязаны быть application-facing вместе: Request стоит в сигнатуре
#     Authorizer, и INTERNAL у Request утащил бы за собой весь шов — забор замыкания API поймал бы
#     это на сборке артефакта, а не на ревью;
#   · RecorderSetWriter, участники сохранения и удаления агрегата, исполнитель транзакции,
#     платформенная реализация авторизатора и третья конфигурация — INTERNAL: приложение их не
#     называет, а обещание среза — поведение (набор владельца заменяется целиком под токеном
#     canonical onSave, с retry на границе транзакции и с отдельным решением по каждой строке),
#     а не имена. Шов остаётся заменяемым (@ConditionalOnMissingBean), но имя реализации —
#     не обещание;
#   · RecorderOrderClock и RecorderOrderClockBootstrap понижены из MODULE_API в INTERNAL, и это
#     не косметика: MODULE_API был назначен им затем, чтобы S3 взял часы порядка из другого
#     артефакта. Срез приехал и взял их из своего же артефакта, поэтому обещание «контракт между
#     модулями» стало некому адресованным; измерение (ни один другой модуль эти два типа не
#     называет) превратило его в INTERNAL. MODULE_API = 0 после S3 — снова измеренный факт.
#
# ---- S5(а) (2026-10-16) добавил 1 тип: RegisterNamedOperations — определения именованных
# операций регистра вместе с подписями для человека (ADR-0024 §2.4). Решения среза:
#
#   · APP_API, а не INTERNAL: тип называет приложение — один адаптер к каталогу прав читает этот
#     список как данные и перестаёт держать текст операции на каждый регистр. Обещание здесь
#     предъявляется приложению (форма подписи и состав операций), поэтому «внутренний для модуля»
#     соврал бы о потребителе;
#   · имя регистра для человека приехало атрибутом @RegisterMetadata.displayName(), а не вторым
#     реестром рядом: имя принадлежит декларации, и его отсутствие при включённой именованной
#     операции — отказ валидатора (RegisterMetadataValidator), а не пустая подпись в экране;
#   · атрибут displayName() у APP_API-аннотации и метод displayName() у APP_API-дескриптора
#     отдельными записями не идут: реестр классифицирует типы, а не их члены.
