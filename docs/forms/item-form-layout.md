# Узлы компоновки карточки

AF5.1–AF5.4 подготовили единый движок `ItemFormLayout`. AF5.5 добавляет
`@FormFor`, `layout()` / `adjust()` / `behavior()`. Прежние конструкторы с деревом
или списком полей остаются входами совместимости.

```java
var layout = new ItemFormLayout(List.of(
    new PanelNode("main", "Основное", List.of(
        new FieldNode("journal"), new FieldNode("nomenclature"))),
    new TabSheetNode(List.of(
        new TabDefinition("details", "Реквизиты", List.of(
            new RemainingFieldsNode().except("comment"))),
        new TabDefinition("materials", "Материалы", List.of(
            new SectionNode(PrdSpecMtr.class))))),
    new FieldNode("comment"),
    new CustomNode(() -> new Span("Дополнительная информация"))
));
var form = new ItemForm<PrdSpec>(metadata, fieldFactory, layout);
```

`RemainingFieldsNode` выводит опубликованные через `FieldMetadata`, не скрытые
реквизиты в порядке `order`. Явные `FieldNode` учитываются во всём дереве,
включая более поздние вкладки. Путь для вывода связанного значения (`x.name`)
не считается размещением редактируемого реквизита `x`.

На дерево разрешён один узел остальных полей. `.except(...)` возвращает новый
узел, не меняя исходный; неизвестное имя исключения отклоняется при построении.
Исключение относится только к остальным полям: явный `FieldNode` остаётся на месте.

`SectionNode` указывает класс строки секции из `@TableSections` сущности.
Таблицу создаёт и подключает `TableSectionFactory` после конструктора карточки.
Пока секция не подключена, место скрыто. Фильтр состава секций и режим чтения
продолжают действовать; секции без узла остаются внизу: одна — с заголовком,
несколько — вкладками. Указание секции не включает её принудительно в состав.
Неизвестная секция отклоняется до подключения таблиц, повторное место —
при построении дерева. Все подключённые таблицы остаются в общем жизненном
цикле карточки: родитель, dirty, проверка строк, сохранение.

У `PanelNode` появились `id` и необязательный `title`, у `TabDefinition` — `id`.
Идентификаторы непустые и уникальные в пределах дерева. Они присваиваются
корню панели и содержимому вкладки. Старые конструкторы без идентификаторов
сохранены и не добавляют заголовки или обёртки к прежней компоновке.

`CustomNode(Supplier<? extends Component>)` вызывает фабрику один раз при
построении каждой карточки. Дерево с фабрикой можно использовать при нескольких
открытиях: компоненты будут отдельными. Результат фабрики не может быть null.
Прежний `CustomNode(Component)` и accessor `component()` сохранены; готовый
компонент предназначен для своего экземпляра формы.

## Единый движок конструкторов (AF5.4)

Все прежние конструкторы ItemForm теперь сразу строят одно дерево.
Автоформа по метаданным использует RemainingFieldsNode; фильтр имён и конструктор
строки переводят выбранные поля в FieldNode. Поля доступны после `super(...)`;
обработчики существующих подклассов продолжают подключаться в конструкторе.

`getFormLayout()` всегда возвращает фактическую основную область, в том числе
для явно заданного ItemFormLayout. Добавление собственных компонентов в эту область
сохраняется. Секции и нижние кнопки остаются отдельными соседними областями.

Старый фильтр имён сохраняет порядок метаданных и исключает hidden-поля;
null или пустой список означает все поля. Конструктор с классом и готовым списком
FieldMetadataInfo сохраняет переданный порядок и состав, включая явно переданные
hidden-поля. Его `getMetadata()` по-прежнему возвращает null.

Прикладные формы не мигрировались. Новый API `layout()` / `adjust()` и изменение
момента сборки относятся к AF5.5.

## Описание в классе формы (AF5.5)

```java
@FormFor(Workshop.class)
public class WorkshopItemForm extends ItemForm<Workshop> {
    @Override protected ItemFormLayout layout(Layout l) {
        return l.of(
            l.field("code").setWidth("10em"),
            l.field("name").setWidth("24em"),
            l.remainingFields());
    }
    @Override protected void adjust(FormAdjust a) {
        a.element("branch").setWidth("24em");
    }
}
```

`FormFor` расположен в `org.ipro.form.builder`, `Layout` и `FormAdjust` —
в `org.ipro.form.builder.layout`. Тип результата — прежний `ItemFormLayout`.
Аннотация не делает форму singleton-бином: регистратор сканирует пакеты приложения
и создаёт отдельный экземпляр через Spring на каждое открытие. Дополнительный
`@Component` и прежняя регистрация фабрики этой же формы не нужны.
Двойная регистрация одного `(entity, ITEM, variant)` отклоняется.

Новый защищённый конструктор без аргументов создаёт пустую форму. `FormResolver`
после возврата из конструктора вызывает layout, раскрывает остальные поля,
применяет adjust, проверяет описание и один раз создаёт компоненты. Затем
подключается behavior, старые поведенческие кастомайзеры, табличные части
и первоначальные значения. `layout()` не вызывается из конструктора.
Поля нового API нельзя запрашивать в конструкторе подкласса; это делается
в behavior/кастомайзере после сборки. Старые конструкторы по-прежнему немедленные.

На старте создаётся отдельный пустой экземпляр для проверки описания и
деклараций обработчиков. Это разрешено владельцем при закрытии К1: редакторы,
таблицы и дочерние компоненты на старте не создаются. `layout`/`adjust` должны
описывать форму; компонент для custom передаётся фабрикой, а не создаётся сразу.
Описание пересобирается на настоящем экземпляре при открытии, поэтому фабрика
`this::component` не захватывает стартовый экземпляр.

## Правки, свойства и варианты

`layout()` возвращает `l.of(...)`; без переопределения используется вся автоформа.
`remainingFields()` раскрывается до `adjust()`, поэтому `a.element("branch")`
находит и автоматически добавленный реквизит. Идентификатор поля — его путь;
у группы, вкладки и custom он задаётся явно и уникален во всей форме.

- `field`, `display`, `custom`, `panel`, `tabs`/`tab`, `section`, `remainingFields`
  описывают замкнутый набор узлов.
- `setLabel`, `setTitle`, `setVisible`, `setReadOnly`, `setWidth`,
  `setSelectionVariant` задают свойства этой формы. readOnly и вариант выбора
  относятся к полям; общий label реквизита в метаданных не меняется.
- `addField`, `addDisplay`, `addCustom`, `addTab` добавляют элементы в adjust.
- `placeFirst`, `placeBefore`, `placeAfter`, `placeInto` меняют положение.
  Циклическое перемещение или неверный контейнер отклоняются.
- `remove()` исключает элемент; остальные поля не возвращают его обратно.
  `setVisible(false)` оставляет привязку, скрывая поле вместе с подписью.

```java
@FormFor(value = Workshop.class, variant = "short")
public class WorkshopShortForm extends WorkshopItemForm {
    @Override protected void adjust(FormAdjust a) {
        super.adjust(a);
        a.element("branch").remove();
        a.element("code").setReadOnly(true);
    }
}
```

Цепочка ограничена двумя уровнями классов формы, сущность по цепочке неизменна.
Вариант выбора проверяется после регистрации остальных форм и применяется
локально через FieldFactory, не изменяя FieldMetadataInfo.
Невыведенное обязательное поле даёт предупреждение с классом формы и именем;
явный remove или скрытое, но привязанное поле снимает предупреждение.

## Поведение и загрузка

```java
@Override protected void behavior(FormBehavior b) {
    b.onChange("name", event -> {
        // event.field(), event.value(), event.form()
    });
    b.onLoaded(() -> {
        // Поля уже заполнены; после записи применён весь возвращённый снимок.
    });
}
```

Регистрация обработчиков декларативна; их тела при стартовой проверке не
исполняются. Ссылка onChange на отсутствующее поле отклоняется на старте.
Значения читаются внутри обработчиков, например `b.value("name", String.class)`.
onChange реагирует на ввод и программные изменения из обработчиков, но подавлен
при setEntity, initializeNewEntity и применении результата записи.
onLoaded вызывается после открытия и после записи; aggregate-адаптер применяет
шапку, возвращённые строки и чистую точку отсчёта одной группой через applySavedState.

Новые карточки получают начальный фокус в первом доступном редакторе. Диалог
нового API подбирает высоту по содержимому; старые формы сохраняют прежние размеры.
Для основного Workshop нет демонстрационного запрета «Фин»: он существует только
на тестовом classpath в варианте test-fin. Встроенные списки, связанные значения
и короткое подключение своего редактора относятся к последующим этапам.
