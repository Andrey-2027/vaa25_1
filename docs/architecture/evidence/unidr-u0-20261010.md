# UniDR U0: техническая основа пилота

Начало: 2026-10-09. Завершение: 2026-10-10 (Europe/Moscow).
Режим: технический эксперимент перед пилотным редактором.
Основание: пользователь выбрал позиции накладных и запросил выполнение U0.

## Результат и границы

Путь «реальные сущности позиций → существующее защищённое чтение → два вида
DynamicReports → HTML/PDF/XLSX» подтверждён. Для первой итерации выбран HTML
готового `JasperPrint`. Детали и summary рассчитывает DynamicReports/JasperReports.
Второй агрегатор для браузерной таблицы не нужен.

Добавлены только тестовый эксперимент и скрипт его запуска. Продуктовые классы,
редактор UDR, компилятор UDR, сохранённые шаблоны и постоянная схема не менялись.
U1–U6 не выполнялись. Это завершение U0, а не готовый пользовательский редактор.

Локальный рабочий план: `docs/plans/unidr-pilot-plan.md` (игнорируется Git).
Этот документ и тестовые исходники сохраняют результаты независимо от него.

## Выбранная сборка отчёта

| Возможность | Подтверждённое решение |
| --- | --- |
| 0–3 уровня | Custom groups DR по скрытым полям ID |
| Подпись | Отдельное String-поле; явная регистрация через `report.fields(...)` обязательна для custom expression |
| Summary | `setDetailPrintWhenExpression(false)`, `GroupHeaderLayout.EMPTY`, `subtotalsAtGroupHeader`; подпись и показатели на одной строке |
| Детали | Обычный detail, заголовки групп, `subtotalsAtGroupFooter` |
| Общий итог | `subtotalsAtSummary` |
| SUM / AVG / MIN / MAX | Штатные subtotals по исходному `BigDecimal` |
| Число записей | `sbt.count(exp.value(1), outputColumn)`; marker-поле в источнике и marker-колонка не нужны |
| Экспорт | Один `JasperPrint` → HtmlExporter, PDF, JRXlsxExporter |

Численный пример: позиции `2, 4, 9, 5, 10, 6` дают сумму **36**, среднее **6**,
минимум **2**, максимум **10**, записей **6**. Цех A: `15 / 5 / 2 / 9 / 3`;
цех B: `21 / 7 / 5 / 10 / 3`. Подгруппы A/X и B/X имеют средние 3 и 7,5.
Общий AVG считается по исходным значениям, не по средним подгрупп.

Все восемь сочетаний глубины и видимости detail имеют одинаковый общий итог.
Два разных ID с одинаковой подписью не объединяются. ID не выводятся как колонки.
NULL-ключи образуют группу «Не заполнено». Значения `NULL, 0, 6` дают
`SUM=6, AVG=3, MIN=0, MAX=6, COUNT_ROWS=3`; полностью NULL-значения дают пустые
числовые итоги и корректный count. Представление пустого числа знаком «—» остаётся
за будущим продуктовым форматированием U3.

Проверка 90 позиций подтверждает перенос между страницами без потери деталей,
единственный общий итог и наличие всех страниц в HTML. Текст `<script>`
экспортируется экранированным. PDF содержит кириллицу и встроенный шрифт,
XLSX содержит числовую ячейку `12.5`, а не строку локализованного числа.

## Источник и защита

Использованы настоящие JPA-типы приложения: ReceivingDocumentItem,
ReceivingDocument, Workshop, Nomenclature, UnitOfMeasurement, Journal и Branch.
Одна исходная строка — одна позиция. Запрос не содержит `GROUP BY` и коллекционных
соединений. Всего 14 scalar-проекций, в пределах `MAX_COLUMNS=30`.

```text
ReceivingDocumentItem i
  INNER JOIN ReceivingDocument d ON i.document.id = d.id
  INNER JOIN Workshop r ON d.receivingWorkshop.id = r.id
  INNER JOIN Workshop t ON d.transferringWorkshop.id = t.id
  INNER JOIN Nomenclature n ON i.nomenclature.id = n.id
  INNER JOIN UnitOfMeasurement u ON n.unitOfMeasurement.id = u.id
  INNER JOIN Journal j ON d.journal.id = j.id
WHERE d.date BETWEEN :periodFrom AND :periodTo AND u.id = :unitId
[AND r.id = :recipientId]
ORDER BY r.name, r.id, n.code, n.id, d.date, i.id
```

Проверен `ReportTemplate` без сохранения и без бэндов, с явными `orders`.
Выборка выполняется исключительно через `ReportQueryAssemblyService` и полный
конструктор `ReportQueryExecutor` с guard и authorizer; bypass отключён.
Прямой JDBC используется только для создания/удаления тестовой схемы PostgreSQL.

Фикстура содержит три доступные накладные, закрытый журнал, закрытого приёмщика,
закрытого сдатчика, другой период и другую единицу измерения. Возвращаются ровно
шесть нужных позиций, ID уникальны. Их порядок и все количества проверены.
Один и тот же dataset формирует оба представления с общим итогом 36.

Реальные grants: C5 ENTITY-read всех использованных типов, `JOURNAL`, `BRANCH`
и существующий CHECK_ONLY `ENTITY:ReceivingDocument`. SQL содержит ограничения
журнала и обоих цехов документа, фильтры независимо присоединённых Workshop
и Journal. Grant с доступом к типу не заменяет построчные ограничения.

При отзыве ENTITY-read Workshop сборка запрещается до SQL источника. При смене
субъекта после сборки executor повторно проверяет права и запрещает исполнение.
Проекция защищённого FK без независимого JOIN запрещается как
`RLS_ASSOCIATION_JOIN_REQUIRED`. Лимит проверен дополнительной строкой: запрос
6 строк при лимите 5 обнаруживает превышение; запрос 7 при лимите 6 подтверждает
полную выборку из 6. Продуктовое сообщение об отказе при превышении относится к U2.

## Найденные особенности существующего пути

1. `PERIOD` резолвится в `nameFrom/nameTo`, но `parameterNamesOf` объявляет только
   `name`. Поэтому guard отказывает. Для UniDR одно поле периода адаптируется
   к двум обязательным SCALAR-параметрам `LocalDate`; это проверено отдельно.
2. ORDER BY по SELECT aliases вызывает `UnsupportedOperationException` в
   `SqmAliasedNodeRef.accept` при обходе C5 на Hibernate 7. Проверены явные пути
   полей из серверного описания источника. Пользовательский текст сюда не попадает.
3. Корень `ReceivingDocument` с обратным соединением Item не удовлетворяет
   требованию независимого JOIN защищённой связи `Item.document`. Корень Item
   и JOIN Document по ID проходит guard и сохраняет фильтры Hibernate.
4. CHECK_ONLY `ENTITY:ReceivingDocument` по-прежнему проверяется существующим
   путём чтения дополнительно к C5 ENTITY-read. Пилот учитывает действующий контракт.

Изменять старые guard/compiler ради эксперимента не потребовалось.

## Предпросмотр и оставшиеся ограничения

Выбран HTML печатного результата. Кириллица, экранирование, поля, отступы,
фиксированная ширина и страницы пригодны для пилота. В SecurityConfig уже разрешён
same-origin frame (`X-Frame-Options: SAMEORIGIN`); новая политика не добавлялась.
В U3/U4 нужно встроить защищённый ресурс во фрейм, изолировать HTML, настроить
масштаб/прокрутку и проверить реальную Vaadin-сессию. На этом этапе браузерная
проверка выполнена на локальных экспортированных файлах, не на новом маршруте.

`HtmlExporter.setRemoveEmptySpaceBetweenRows(true)` сообщает, что опция
не поддерживается; она исключена. Скрытие detail и размещение итогов задаются
в DR-макете, поэтому от этой опции не зависят. XLSX сохраняет структуру печатного
отчёта, включая строки групп и итогов; отдельная плоская выгрузка не реализована.
Скорость и память на 5000 строках, worker, квоты, сохранение и UI проверяются
на последующих этапах, не следуют из успешного U0.

## Воспроизведение и материалы

Предусловия: закреплённые зависимости подготовлены, JDK 21, Maven.
В PowerShell из корня проекта:

```powershell
$u0Maven = 'C:\Program Files\JetBrains\IntelliJ IDEA Community Edition 2025.2.3\plugins\maven\lib\maven3\bin\mvn.cmd'
$u0Java = 'C:\Program Files\Axiom\AxiomJDK-21'
./scripts/bootstrap-local-dependencies.ps1 -ValidateOnly -Offline
./scripts/run-unidr-u0.ps1 -MavenCommand $u0Maven -JavaHome $u0Java
./scripts/run-unidr-u0.ps1 -MavenCommand $u0Maven -JavaHome $u0Java -Postgres
```

PostgreSQL-режим явно включается `-Postgres`, читает локальный конфигурационный
файл без вывода пароля и создаёт только новую схему `unidr_u0_<UUID>`. Hibernate
использует её как default schema, JDBC — как currentSchema. После тестов схема
удаляется; shutdown hook повторяет cleanup при аварийном завершении JVM.
Принудительное убийство процесса может потребовать удаления оставшейся тестовой
схемы. Рабочие таблицы не используются как фикстура.

Исходники: `src/test/java/org/ip/unidr/spike/` (два теста, DR helper, sandbox).
В `outputs/unidr-u0/` сохраняются:

- `h2-and-render-test.log`, `postgresql-test.log`, `prepare.log`, `compile.log`;
- `baseline-validation.log`, `render-test.log` — исходная проверка и общий отказ testCompile;
- `receiving-items-query.hql`, `receiving-items-sql-h2.log`, `receiving-items-sql-postgresql.log`;
- `postgresql-environment.txt`, `postgresql-cleanup.txt`;
- `groups-{0,1,2,3}-{details,summary}.{html,pdf,xlsx}`, файлы текстовых значений;
- `receiving-items-{h2,postgresql}-{details,summary}.html` — оба вида реальной выборки;
- PNG для визуальной проверки и `html-browser-check.json`.

Следующий этап — U1: простая конфигурация и личные варианты. U0 не требует
пересмотра пользовательской модели отчёта или объединения с редактором UDR.
