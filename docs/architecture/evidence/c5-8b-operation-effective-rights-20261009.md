# C5.8b: эффективные права для операционных измерений — 2026-10-09

- План: [C5.4–C5.10](../c5-operation-permissions-plan.md), пакет C5.8 («Администратор и первичная
  выдача»), остаток «эффективные права для операционных измерений».
- Решения: [ADR-0017](../decisions/ADR-0017-c5-single-operation-authority.md) §1 (решение — одно
  место), §3 (носитель права — строка `access_grant`: точный ключ, глобальная строка,
  `canUpdate` решает CREATE/UPDATE/EXECUTE, `canDelete` — DELETE), §10 (решение и его источники);
  [ADR-0019](../decisions/ADR-0019-owner-named-row-operation.md) §1, §5.
- Предшественник: [c5-8-named-operation-issuance-20261008.md](c5-8-named-operation-issuance-20261008.md) —
  операцию стало чем выдать, но диалог «Эффективные права» показывал её не тем движком.
- Метод: одна additive-точка в `platform-rls`, правка композиции в приложении, целевые прогоны,
  намеренная перезапись одного baseline.

## 1. Что было не так

`AccessGrantAdminService.collectEffective` — источник диалога «Эффективные права» в
[AdminView](../../../src/main/java/org/ip/views/admin/AdminView.java). Для C5 read-ключей он давно
берёт решение C5 (`C5ReadDecisionService`), а для **операционных** измерений складывал ответ из
RLS-свёртки `AccessService.effectiveGrants` — то есть из другого движка, чем тот, что решает
сервер.

Свёртка и решение расходятся ровно там, где расхождение опасно:

| Строка `access_grant` | RLS-свёртка | Решение C5 (сервер) |
| --- | --- | --- |
| `dimension = '*'`, update | «Изменение: Да» | отказ |
| `dimension = ACTION:...`, `dimensionValueId = 42`, update | «Изменение: Да» | отказ |
| точный ключ, глобальная строка, update | «Изменение: Да» | «Да» |

Первые две строки — это `'*'` (семантика RLS, ADR-0017 §3 её сохраняет для построчного доступа) и
value-scoped строка. Для операции они не авторизуют ничего, но диалог показывал по ним право:
администратор видел «Да» там, где canonical write и именованная операция отказывают. Это тот же
класс ошибки, что и в самом решении, но на другом конце — не разрешение лишнего, а **показ**
лишнего.

## 2. Что сделано

**Одна subject-aware форма решения (platform-rls).**
`C5PermissionDecisionService.decideForSubject(SubjectType, subjectKey, key, operation)` — полное
эффективное решение для пользователя **или роли**: перечисляет **все** источники allow, а не первый
достаточный (для enforcement таким остаётся `decide(...)` с его ранним выходом). Правила — те же,
что спрашивает enforcement, а не второе чтение хранилища: точный ключ с глобальной строкой
(`dimensionValueId == null`), отображение флага по ADR-0017 §3, и только назначенные роли. Чтение
делегирует `C5ReadDecisionService` — уже subject-aware.

Почему в платформе, а не в приложении: субъектом диалога бывает и роль, а у операции
subject-aware формы не было вовсе (у чтения — была, `C5ReadDecisionService.decide(dimension,
subjectType, subjectKey)`). Собрать её в приложении значило бы переписать правило хранения
(`точный ключ + глобальная строка + флаг`) второй раз — ровно то дублирование, из которого
расхождение и растёт. Baseline `platform-rls.api` перезаписан намеренно: диффом видно ровно одну
добавленную строку (106 → 107 insertions, deletions 7 → 7).

**Композиция ответа (app).** В `collectEffective` операционные измерения собираются
`operationEffectiveGrant`: спрошены ровно объявленные определением операции, `CREATE/UPDATE/EXECUTE`
складываются во флаг «изменение», `DELETE` — в «удаление», источники — объединение источников
разрешивших решений. C5 read-ключи теперь идут той же subject-aware формой
(`c5EffectiveGrant` → `decideForSubject`), поэтому чтение и операции объясняются одним движком.

**Столбец «Чтение» короткого `ENTITY:<Имя>`-ключа оставлен у того, кто им владеет.** Это
единственное исключение, и оно названо. Определение операций не объявляет `READ` — у типа это
`CREATE/UPDATE/DELETE`, у именованной операции `EXECUTE`. Для `ACTION:...` столбец чтения поэтому
всегда «—»: флага чтения у операции нет вовсе. Для короткого `ENTITY:...` «чтение» — прежний гейт
видимости плитки подсистемы, и сервер спрашивает его **через RLS**
(`AccessService.hasAnyAccess`, см. `SubsystemHomeView`), а не через C5. Взять его у C5 значило бы
показать «права нет» субъекту, который плитку видит, — новое расхождение вместо снятого. Снятие
дублирующего гейта — шаг C5.7; до него правило разведено по владельцу столбца, как и в срезе
выдачи.

## 3. Проверки

| Проверка | Результат |
| --- | --- |
| [`OperationEffectiveRightsIT`](../../../src/test/java/org/ip/security/OperationEffectiveRightsIT.java) — диалог и сервер отвечают одинаково: выдача/отзыв именованной операции; wildcard и value-scoped строки **не** показаны правом (`'*'` при этом в свёртке остаётся «Да» — расхождение зафиксировано тем же тестом); роль показана источником только пока назначена; у короткого `ENTITY`-ключа столбцы записи совпадают с решением C5, а столбец чтения — с гейтом плитки | 5/5 |
| `C5PermissionDecisionServiceTest` — отдельно форма решения: полный список источников против раннего выхода enforcement, решение роли по её собственной строке, отказ на необъявленной операции, read-ключ и legacy `ATTR`-ключ, пустой субъект | 24/24 |
| `C5PermissionDecisionServiceJpaTest` — на настоящем хранилище: `'*'` и value-scoped строка не дают `decideForSubject` права | 5/5 |
| Соседи, которых срез касается напрямую: `C5GrantAdminParityIT` (read-путь диалога), `RlsAutoConfigurationSmokeTest` (`collectEffective` покрывает все настраиваемые измерения), `NamedOperationGrantAdminIT`, `PlatformRlsModuleTest` | 7 + 17 + 6 + 5, 0 отказов |
| `PlatformApiBaselineTest` — после намеренной перезаписи `platform-rls.api` | 3/3 |
| Прочие целевые классы `platform-rls`: `C5ReadDecisionServiceTest`, `C5OperationPermissionRegistryTest` | 11 + 10, 0 отказов |
| `PlatformVaadinSurfaceTest` | 6/6 |
| `PlatformCoreSurfaceTest` | 5/6; падает на **чужом** untracked `PilotSecurityQueryMeasurementIT.java` (`org.ipro.crud.MetadataDrivenAggregateSaveService`), не по этому срезу |

Построение шло `mvn -o -f platform-build/pom.xml -pl :platform-core,:platform-vaadin -am install`:
рабочее дерево содержит чужие untracked platform-типы (`CanonicalSaveLifecycleScope`,
`AggregateSaveLifecycleScope`, `FormMessages`, `FormTypeCustomization`), без которых прикладной
модуль не компилируется вовсе. Это состояние дерева, а не следствие среза; ничего из этого не
менялось, а только установлено из текущих исходников.

Чего право не делает и это тоже проверено: показанное решение не заменяет решение — определение
по-прежнему спрашивается до чтения грантов (`requireSupports`), а незарегистрированный ключ
остаётся ошибкой конфигурации, а не отказом.

## 4. Остаток

- **Клики по отрисованному диалогу** не проверялись: проверен сервис, которым диалог получает
  данные (`collectEffective`), а не состояние конкретной сетки на странице. Заголовок столбца
  «Изменение» в диалоге для именованной операции остаётся прежним — администратор объясняет
  строку по её названию («Переименование значения атрибута — операция (…»), а не по заголовку
  столбца; это формулировка, а не решение, и она не менялась.
- **Отчёт «определение зарегистрировано, грантов нет»** не сделан (см. предыдущий срез).
- **Снятие дублирующего гейта плитки** (`SubsystemHomeView.isEntityVisible` → `hasAnyAccess`) —
  C5.7; до него столбец «Чтение» короткого `ENTITY`-ключа честно показывает RLS-ответ.
- PostgreSQL и полный прогон — за C5.9.
