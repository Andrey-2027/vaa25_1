# AF6 — этап 2: ленивое встраивание, родитель и чтение (08.11.2026)

## Реализация

Добавлен внутренний per-opening EmbeddedListHost. Он хранит собственное состояние
и не участвует в FormBindingRegistry, dirty или aggregate-save родительской карточки.
ItemForm создаёт лёгкий host при сборке описания, а ListForm — только при показе
выбранного места в присоединённой к UI карточке. Для вложенных вкладок учитывается
весь выбранный путь. Редакторы остальных полей продолжают строиться сразу.

Новый родитель без id показывает подсказку без фабрики/чтения списка. После первой
записи список создаётся, если его вкладка открыта; иначе ждёт первого перехода.
Повторные переходы используют тот же экземпляр. Смена id удаляет предыдущий
список; при возврате к новому объекту снова показывается подсказка. При отсоединении
карточки смена родителя не создаёт новый список до следующего показа.

Синхронизация выполняется после успешного заполнения полей и onLoaded, включая
setEntity, initializeNewEntity и завершение целого applySavedState. Она использует
сохранённый parent/peek-состояние и значения биндингов без getEntity/applyAllToEntity.
Явно скрытые вкладки не раскрываются при загрузке/записи.
Фабрика обязана возвращать отдельный список; повторное использование ранее
выданного компонента запрещено даже после его отсоединения.

## Права чтения

EmbeddedListFactory.canRead проверяет C5PermissionEvaluator.isEntityReadPermitted
для любого типа, затем RlsReadGate для текущего аутентифицированного субъекта.
Это те же входы, что использует canonical reader. Проверки есть при создании host,
обновлении родителя, активации и в самом стандартном адаптере перед созданием списка.
При отсутствии права список не создаётся, элемент скрывается; если в его вкладке
не осталось другого содержимого, скрывается и вкладка. Смешанная вкладка сохраняется.
Построчные ограничения JOURNAL/BRANCH остаются в штатном серверном чтении.

Отрицательная интеграционная проверка уточнила результат исследования: одного
RlsReadGate недостаточно — он обращается к C5 только для типов с CHECK_ONLY,
а canonical reader требует entity-read и для ReceivingDocument без этого измерения.
Ранний вариант адаптера провалил эту проверку; он исправлен добавлением общего
C5PermissionEvaluator. Модули platform-rls/core и их политики не изменялись.
Creation-only адаптер этапа 1 не получает неявного разрешения: default canRead
выдаёт именованную ошибку композиции, пока read-вход не предоставлен явно.

## Контекст и границы этапа

Перед фактическим созданием вычисляются проверенные фильтры Self/Constant/FieldValue
и передаются стандартному FormNavigator как ограничения открытия до присоединения
списка к UI. Пустой источник l.value показывает подсказку, не снимает связь молча.
Явный read-only узла применяется без снятия read-only нижнего слоя.
Список принадлежит отдельной сущности и не наследует запрет записи родителя.

Полный контракт реакций на контекст, сценарии CatalogOwner/сохранённых видов,
команды и их заголовки остаются этапом 3. Непустая настройка команд узла пока
отклоняется при активации явно: запрос скрыть действие не должен игнорироваться.
Встроенный список без таких настроек использует штатные команды/ActionPolicy.
Рабочие WorkshopItemForm и ReceivingDocumentListFormConfig не менялись;
пилот и визуальная приёмка остаются последующими этапами, эскиз не считается принятым.
