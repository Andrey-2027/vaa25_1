# AF5.2: построение всех карточек приложения

Дата: 06.11.2026. Полный прогон не выполнялся по указанию владельца.

## Проверка

Добавлен `src/test/java/org/ip/form/ItemFormConstructionTest.java` с настоящим
Spring-контекстом приложения. Тест получает типы из ManagedEntityCatalog,
добавляет типы ItemFormCustomization и классы строк табличных частей.
Для каждого конкретного типа с контрактом IdentifiableEntity строится default,
затем все именованные ITEM-варианты из FormRegistry.

Фабрики не перечислены вручную: новая сущность или зарегистрированный вариант
попадёт в обход автоматически. Непустой состав и наличие как зарегистрированных,
так и автоматических форм проверяются отдельно от построения.

Каждое открытие — отдельный DynamicTest с полным именем типа и вариантом.
Используется FormResolver, поэтому исполняются настоящие фабрики, конструкторы
подклассов и кастомайзеры, а затем подключаются таблицы через TableSectionFactory.
Ошибка неизвестного поля или пути при построении не перехватывается и проваливает
соответствующий случай. Дополнительно сверяются объявленный класс реализации
(где он указан) и фактически подключённые секции с учётом фильтра состава формы.

Каждый случай получает отдельный UI с восстановлением предыдущего UI в finally.
Записи не открываются и не сохраняются; события ввода и сохранения в этот этап
не входят. Полная поведенческая проверка и сравнение двух движков — другие этапы.

## Границы зависимостей

DataInitializer заменён mock, чтобы не создавать демонстрационные записи.
LookupService также заменён mock с пустыми результатами: фабрики Nomenclature
и User запрашивают словари прямо в конструкторах. Это аналог локального источника
данных ExplorerFormPreview; проверка компоновки не требует выдавать права на чтение
словарей и не проверяет работу их запросов. FieldFactory, metadata, реестр,
резолвер, фабрики форм и фабрика секций остаются настоящими.

Первый запуск без такого источника обнаружил отказы READ для AttributeType и Role;
это исправлено в окружении теста, код разрешений и прикладных форм не менялся.

В overlay `platform-vaadin-surface.txt` разрешён новый тестовый потребитель
FormRegistry и FormResolver. Производственные классы и API не менялись,
отпечатки платформенных модулей и эталон настроек не обновлялись.

## Объём и воспроизведение

Целевой запуск: ItemFormConstructionTest, FormSettingsSnapshotTest,
PlatformVaadinSurfaceTest. Лог — `outputs/verification/af52-targeted-final.log`.
В каждой строке `AF5.2` записаны тип, вариант, фактический класс формы и число секций.

Итог: **48 тестов прошли, ошибок и пропусков нет**:

- 38 открытий для 32 типов в ItemFormConstructionTest;
- 4 проверки FormSettingsSnapshotTest: снимок P2 совпал без перезаписи;
- 6 проверок PlatformVaadinSurfaceTest: дополненный overlay согласован с исходниками.

Использован изолированный Maven-кэш предыдущих проверок и собранный JAR AF5.1:
из classpath Surefire исключён старый `org.ipro:platform-vaadin`, новый JAR
добавлен через `maven.test.additionalClasspath`. Кэш работающего приложения
не заменялся. Приложение не перезапускалось.

Тест охватывает также варианты строк `accounting-correction-row`, `attributeValue`,
`material`, `product` и варианты спецификации `full`, `materials-only`.
Устаревшие конструкторы карточек и автоматические формы проверяются в одном
контексте с существующими прикладными подклассами.

Визуальная приёмка новых экранов не требуется этим изменением: AF5.2 добавляет
проверку построения, компоновка приложения не меняется. AF5.3 и последующие
этапы не выполнялись.
