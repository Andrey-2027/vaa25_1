# AF5.8 — связанные поля (07.11.2026)

## Объём и решения владельца

Владелец отложил миграцию AccountingObjectCorrection и поручил отдельно связанные
поля AF5.8. Корректировка сохраняет текущую реализацию; HasValue/setEditor не
вводятся ради её миграции. Общие изменения проверяются на совместимость со старой
формой. ReceivingDocument и остальные задачи AF5.6 не включены в этот шаг.

О5 остаётся открытым: у Nomenclature есть только основная единица. Реализуются общий
механизм связей и пилот основной единицы; отбор дополнительных единиц остаётся
явным остатком до выбора модели. К4 этим шагом не закрывается.

## Реализация

- Закрытый словарь SelectionValue: константа, l.value(path), l.self(). Неизменяемые
  FieldRelations передаются в ElementNode после remainingFields/adjust.
- setSelectionFilter(path,value) действует в автокомплите и в диалоге. Параметр берётся
  из текущего редактора при каждом поиске; диалог также вычисляет его заново на каждый
  запрос, не сохраняя значение первого открытия.
- Источник меняется из UI или кода — неподходящее выбранное значение очищается.
  setClearInvalidSelection(false) сохраняет его. Пустой источник по умолчанию снимает
  условие; setAllowEmptySelectionSource(false) даёт пустой набор выбора.
- setFillFrom(path) работает только на USER. setFillOnlyIfEmpty(true) сохраняет ручное
  значение. Числа Long передаются в модельном типе без потери разрядности; неявные
  преобразования несовместимых типов подстановки не разрешаются.
- Путь подстановки, вложенный параметр и данные для проверки текущего выбора сами
  расширяют LOOKUP/DETAIL/ROW через механизм AF5.6. UI не перечитывает выбранную
  сущность вручную и не строит EntityGraph.
- ValueChangeSource различает USER, HANDLER, INITIAL_LOAD, SAVED_STATE. b.onChange
  получает ввод и изменения из обработчиков; автоматическая подстановка — только ввод.
  Старые пользовательские слушатели EntityField сохраняют своё поведение.
- Загрузка, копирование и применение результата записи не подставляют и не очищают
  записанные значения. Изменения, выполненные связью, не сбрасывают clean baseline.

Пути, присутствие источника на форме и совместимость типов проверяются до создания
редакторов, в том числе при стартовой проверке @FormFor. Runtime читает значения
через getter там, где он есть: это важно для инициализированных JPA-прокси.

## Пилот PrdSpecMtr

Material: отбор typeNom=Материал находится на элементе nomenclature, unit получает
setFillFrom(nomenclature.unitOfMeasurement). Product: unit получает
setFillFrom(prdSpecMtr.nomenclature.unitOfMeasurement). Единственный оставшийся
обработчик в behavior() product-формы записывает nomenclature строки, у которой в
этом варианте нет редактора; он также ограничен USER. Его вход nomenclature объявлен
явно через setLookupPaths, зависимость единицы выведена из setFillFrom.

PrdSpecMtrFormCustomization удалён. Составы и порядок видимых полей сохранены.
Общий default-вариант по-прежнему использует remainingFields(). Модель и схема БД
не менялись. Пример API: [связанные поля](../../forms/related-fields.md).

## Проверки

Все 240 целевых проверок прошли без ошибок и пропусков: 55 в platform-vaadin и
185 в приложении. Итоговые журналы: target/af58/platform-tests.log и
target/af58/regression.log. Предварительный набор приложения (48 тестов) также
прошёл; в итоговом наборе эти проверки повторены, поэтому отдельно не суммируются.

Покрываются пользовательский выбор/очистка, программные изменения, начальная
загрузка, копирование, authoritative saved state, два режима подстановки, очистка/
сохранение выбора, self и пустой источник, неверные пути/типы, Long, реальные SQL
запросы обоих каналов, повторный запрос одного диалога после смены источника,
отсутствие старого бина и обратная совместимость обработчиков/форм.

П.2 и отдельный снимок требований чтения AF5.6 проверяются без обновления эталонов.
Полный прогон, frontend и C/D harness не запускались. Визуальная приёмка К4 не
объявляется: видимая компоновка не менялась; проверяются компоненты, значения и чтение.

## Граница параллельной работы

Во время проверки в общем рабочем дереве появились изменения API команд списка.
Они не входят в AF5.8 и не включаются в его коммиты. Целевой прогон приложения
использовал platform-vaadin, собранный и установленный до появления этих правок.
Отпечаток AF5.8 фиксирует именно этот состав (HEAD пакета 1 плюс файлы AF5.8),
а не незавершённые параллельные изменения. Общий bootstrap поэтому проверяется
отдельно и не служит заявлением о проверке совместного рабочего дерева.

Отпечаток проверенного состава platform-vaadin: 265 файлов,
`de60da8ce7c0bd938ac12bed9443a0e936561b2fcf0b376ad692fe74043cca36`.
При расчёте сохранены фактические окончания строк исходного рабочего дерева;
обратная проверка исходного состава воспроизводит прежний эталон пакета 1.
Строгий bootstrap -ValidateOnly останавливается на параллельном изменении
platform-vaadin (265 → 269 файлов). Диагностический проход -AllowSourceDrift
завершён; кроме него виден только ранее известный platform-report-vaadin
(33 → 34 файла), его эталон не менялся.
