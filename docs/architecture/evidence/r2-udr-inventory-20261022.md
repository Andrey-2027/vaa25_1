# R2: инвентарь UDR, архив формата и карта ID (2026-10-22)

- Дата: 2026-10-22.
- Основание: §R2 плана разделения query/report
  ([план](../../plans/query-report-separation-plan.md)); реестр сценариев
  ([R2 inventory](../r2-udr-scenario-inventory.md)); закрытие создания UDR

- Срез: первый шаг R2 — измеренный инвентарь окружений, решение по S8 (формат и
  конвертер), закрытие S3, карта старых ID и правила переноса данных.

PostgreSQL 17.10.

| `DBVaa25` | 6 |

| `accounting_object_pilot_local_v1/v2/v3` | 0 |
| `navigation_pilot_6dd935094b1448d98f627a56dcd85d1f` | 0 |

Все шесть шаблонов — `DRAFT`, автор `admin`, созданы 2026-08. Это локальный
срез, а не производство; прод-инвентарь остаётся входом владельца (§2).

`maxRows=5000`, `timeoutMs=30000`.

**Найденный дефект данных.** У шаблонов 2 и 4 корневые `GROUP_HEADER` записаны
с `parent_id = id` (в шаблоне 4 — два таких бэнда). Старая модель трактует это
как «корень», но в обменном JSON это самоссылка. Архив сохраняет её как есть, а
читатель считает такие бэнды корневыми и показывает их число
(`selfParentBands()`). Переписывать данные задним числом в этом срезе нельзя:
архив должен отражать то, что реально сохранено.

## 2. Инвентарь владельца

Решение по каждому шаблону — не техническое: «пересобрать в UniDR», «архив» или
«не нужен». Форма решения — таблица
[`r2-udr-id-map.csv`](r2-udr-id-map.csv): `proposed_decision` заполняется
инженерной стороной, `owner_decision` и `owner` — владельцем и его именем.

Предложено по локальному срезу:

| id | Предложение | Почему |
|---|---|---|
| 1 | `ARCHIVE` | локальный тест: жёсткий фильтр `LEFT(a.code,6)="А12.24"`, псевдоколонка `col3` |
| 2 | `ARCHIVE` | имя `434434`, тестовое содержимое |
| 3 | `ARCHIVE` | имя `435435`, тестовое содержимое |
| 4 | `REBUILD_UNIDR` | единственный сценарный: спецификации по журналу, две группы, итоги `COUNT/SUM`, параметр-сущность |
| 6 | `ARCHIVE` | имя `Тест1`, запрос с `typeNom` |
| 7 | `ARCHIVE` | имя `Проь`, тестовое содержимое |

**Решение владельца 2026-10-23.** Ни один UDR-отчёт не нужен: все шесть шаблонов
— тестовые. Поэтому ни один не пересобирается, архив не ведётся как рабочий,
перенос данных и таблица соответствия ID не нужны. Все строки
`r2-udr-id-map.csv` получили `owner_decision=NOT_NEEDED`; предложение
`REBUILD_UNIDR` для шаблона 4 отменено владельцем. Прод-инвентарь по шаблонам
при этом решении не запрашивается: отсутствие нужных UDR-отчётов — решение обо
всей подсистеме, а не о конкретной БД.

JSON-примеры остаются фикстурами формата и проверки читателя, а не архивом
рабочих отчётов: удалять их не нужно, но и восстанавливать по ним отчёты никто
не обязан.

**Если решение изменится.** В этом чекауте производственных БД нет, поэтому
инвентарь здесь не снимается. Процедура для такого случая:

1. На каждом окружении выполнить `scripts/r2-udr-inventory.sql` и сохранить
   вывод рядом с решением (дата, БД, исполнитель).
2. Выгрузить каждый шаблон через `scripts/r2-udr-export-json.sql` (см. §3) —
   файл становится проверяемым архивом, даже если шаблон потом удаляется.
3. Внести строки в копию `r2-udr-id-map.csv`: `old_id`, имя, привязка,
   `owner_decision`, `owner`, комментарий.
4. Для `REBUILD_UNIDR` — завести UniDR-определение, заполнить `new_unidr_id` и
   `verified_at` после сверки данных/вывода.

Сейчас условие «нет строки без решения» выполнено: у всех шести строк есть
`owner_decision=NOT_NEEDED`.

## 3. S8: формат заморожен, конвертер не пишется

**Формат.** [`udr-template-json-format.md`](../udr-template-json-format.md)
описывает `ipro-report-template/3`: конверт, шаблон, параметры, бэнды, поля,
сортировки, перечисления и политику версий. Документ не зависит от кода
`org.ipro.reportstudio.transfer`, который удаляется в R3.

**Примеры.** Шесть файлов в [`r2-udr-json-samples/`](r2-udr-json-samples)
выгружены из `DBVaa25` запросом `scripts/r2-udr-export-json.sql` (JSONB-сборка
по тем же именам полей, что у `ReportTemplateExchange`). Они проверяются
тестом, а не считаются «примерно верными».

**Читатель.** `org.ip.archive.UdrTemplateArchive` (`src/main/java/org/ip/archive`)
не импортирует отчётный DOM: он читает конверт, проверяет `format`,
`schemaVersion`, уникальность ключей бэндов, ссылки `parentKey`, обязательные
поля `COLUMN`/`ENTITY`, известные значения перечислений и печатает сводку.
Запуск: `UdrTemplateArchive <file.json>...`; код 2 — если архив не прочитан.

**Решение по конвертеру.** Автоматический UDR→UniDR конвертер **не пишется**:

- единственный повторяющийся набор в локальных данных — табличный отчёт с
  группировкой и итогами, и UniDR уже умеет его собрать (S1);
- шесть локальных шаблонов — тестовые черновики, автоматизировать их перенос
  значит закрепить случайные формы (`EXPRESSION` с `{a.code}`, `TEXT`, self-parent);
- у единственного сценарного шаблона (id 4) перенос проверяется на данных:
  автоматический конвертер без такой проверки создал бы ложное обещание
  паритета.

Правило плана «конвертер только для подтверждённого повторяющегося подмножества»
означает: если в прод-инвентаре окажется много однотипных шаблонов, решение
пересматривается отдельно, с примерами и тестами.

## 4. S3: предпросмотр запроса закрыт

Сценарий S3 («предпросмотр ≤20 строк и readonly JPQL») закрыт в Q3/T1:

- `/queries` показывает снимок с явным лимитом (`QuerySnapshotService`, N+1) и
  сортировкой/фильтром по снимку, а не «тихий» предпросмотр;
- текст сгенерированного запроса остаётся readonly в редакторе визуального
  конструктора, ручной JPQL — редактируемым;
- guard и RLS выполняются на том же пути, что и запуск, — предпросмотр не
  открывает второй путь чтения.

Ограничение «≤20 строк» заменено явным полем лимита: константа не защищала от
перегрузки, а скрывала, сколько строк реально запрошено.

## 5. Данные: карта ID и правила переноса

Карта — [`r2-udr-id-map.csv`](r2-udr-id-map.csv). Правила R2 №7:

1. **Старый числовой ID не переиспользуется.** Переезд UDR id 4 в UniDR с id 4
   не означает соответствия: старые ссылки (`/report-editor?id=…`,
   сохранённые закладки) не перенаправляются на совпавший числовой ID. Молчаливый
   редирект показал бы чужой отчёт.
2. **Соответствие хранится построчно.** `new_unidr_id` заполняется только после
   создания UniDR-определения; `verified_at` — после сверки данных и PDF/XLSX.
   Строка без `new_unidr_id` при `REBUILD_UNIDR` означает незавершённый перенос.
3. **Архив — до удаления.** Для каждого шаблона JSON-файл создаётся до R3;
   файл и строка карты проверяются читателем. Физическая таблица
   `report_template` удаляется отдельной процедурой (по образцу DB1), а не
   вместе с кодом.
4. **Архив не равен нейтральному формату.** Это формат старой модели; новые
   отчёты в нём не создаются. Для чтения после R3 остаются документ, примеры и
   `UdrTemplateArchive`.

## 6. Проверки

```text
scripts/r2-udr-inventory.sql       выполнен на DBVaa25: 6 строк, 6 в состоянии DRAFT
scripts/r2-udr-export-json.sql     выполнен для id 1,2,3,4,6,7; 6 файлов в samples/
UdrTemplateArchiveTest             Tests run: 7, 0 failures / 0 errors
```

Дополнительно примеры один раз проверены настоящим DTO: `ReportTemplateExchange`
десериализует все 6 файлов с `FAIL_ON_UNKNOWN_PROPERTIES` (6/6,
`ipro-report-template/3`). Это подтверждает, что JSON собран по тем же именам
полей, что и штатный экспорт, а не только «похож на формат». Постоянная
проверка — независимый `UdrTemplateArchiveTest`: он переживёт удаление DTO в R3.

Тест читает именно файлы из `docs/architecture/evidence/r2-udr-json-samples`:
формат, имена, вложенные группы шаблона 4, привязка печати шаблона 1, self-parent,
а также отказы на неизвестный формат/версию, висячий `parentKey` и `COLUMN` без
`queryField`.

## 7. Что осталось в R2

**R2 закрыт 2026-10-23** после решения владельца: нужных UDR-отчётов нет.

- Прод-инвентарь и пер-шаблонные решения не требуются (§2): все шесть строк —
  `NOT_NEEDED`.
- Пересборка шаблона 4 в UniDR отменена; `new_unidr_id`/`verified_at` остаются
  пустыми намеренно — это не незавершённый перенос, а отменённый.
- R2-D2 (`PERIOD`/`CONTEXT`/`COMPUTED`) и R2-D4 (`headerLayout`/`titleWidth`/
  «нет данных») закрыты как «не требуется»: эти возможности нужны были только
  для переноса UDR-шаблонов. R2-D5 (срок хранения архива) снят вместе с
  архивом рабочих отчётов. R2-D3 (печать из карточки) уже реализован для UniDR
  в S5 и остаётся включённым.
- Дальше — **R3**: удаление UDR-редактора, модели, компилятора, run/store и
  transfer, очистка каталога/печати/меню/capabilities. S8-документ, примеры и
  `UdrTemplateArchive` переживают R3 как описание старого формата, а не как
  обязательство по данным.
