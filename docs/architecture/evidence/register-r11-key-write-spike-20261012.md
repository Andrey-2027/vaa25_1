# Р11: PostgreSQL-спайк записи по ключу (set / upsert / delete)

Дата: 2026-10-12. Статус: спайк закрыт — 20 / 20 на реальном PostgreSQL, BUILD SUCCESS.
Решение по контракту — [ADR-0023](../decisions/ADR-0023-register-key-write.md). Интеграция в
canonical write pipeline остаётся следующим пакетом Р11 и этим протоколом не заявляется.

## Что именно проверялось и чем это не является

Спайк — [RegisterKeyWriteConcurrencyPostgresIT](../../../src/test/java/org/ipro/register/RegisterKeyWriteConcurrencyPostgresIT.java):
тестовый **прототип** контракта (не публичный API), работающий с реальными PostgreSQL-транзакциями
по объявленному регистру-фикстуре. Фикстура проходит настоящую валидацию декларации
(`RegisterDescriptor.describe`): самостоятельный периодический регистр, ключ `(измерение, период)`,
физический UNIQUE — то есть проверяется не «похожая таблица», а форма, которую даёт декларация
регистра.

Чего в спайке намеренно нет: C5/RLS-решений, canonical write record, row lifecycle, durable
аудита телеметрии и публичного API. Всё это — предмет реализации, а не спайка. Аудит здесь
представлен собственной строкой в той же транзакции: этого достаточно, чтобы проверить
неудвоение побочного эффекта при повторе.

## Окружение и воспроизведение

PostgreSQL 17.10, Windows x86_64, READ COMMITTED, JDK 21 (AxiomJDK-21), Maven из рабочего
проекта. Команда из корня проекта:

```powershell
.\scripts\register-r11-postgresql.ps1
```

Скрипт берёт параметры подключения из `config/application-local.properties`, создаёт новую
изолированную базу `g3_register_test_r11_<guid>`, передаёт её URL в набор и восстанавливает
переменные окружения. Рабочая база не затрагивается, тестовая остаётся для диагностики.

Прогон 2026-10-12: **20 / 20** (12 сценариев, четыре из них — `RepeatedTest(3)` ради повторяемости
гонок), failures 0, errors 0, skipped 0, время класса 11.76 с, BUILD SUCCESS.
[Протокол прогона](../../plans/register-r11-postgresql-spike-20261012.log).

**Инертность.** Без изолированной базы класс пропускается и не влияет на обычные прогоны:
`Tests run: 20, Skipped: 20, BUILD SUCCESS` при отсутствии переменной окружения. Это проверено
отдельным запуском после закрытия спайка.

Локальный репозиторий Maven — обычный (`~/.m2`), тот же набор артефактов, что у H2-приёмок; по
причине, описанной в [протоколе Р9](register-r9-postgresql-20261012.md), закреплённый
`.local-maven-repository` не использовался.

## Результаты по сценариям

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Гонка вставки одного отсутствующего ключа (×3) | Победитель `CREATED` (одна строка, версия 0, аудит один), проигравший `CONCURRENT_INSERT` |
| Тот же проигравший с бюджетом 3 (×3) | Попытка 1 `CONCURRENT_INSERT`, попытка 2 `UPDATED`; в базе одна строка с ресурсом второго писателя; ровно две записи аудита — откатанная попытка не оставила следа |
| Проверяемая версия, две транзакции с версией 0 (×3) | Победитель `UPDATED` (версия 1), проигравший `VERSION_CONFLICT`; повторов нет (попыток ровно 1) |
| Правило PostgreSQL: `23505`, затем следующий оператор | Отказ `25P02` — транзакция испорчена; проверено отдельной пробой на сервере, без участия ORM |
| Та же последовательность через ORM | Продолжение отказано, попытка не завершается успешно; ни строки, ни аудита |
| Полный откат попытки | Строка и аудит исчезают вместе |
| Resource-only | Повтор тех же ресурсов — `UNCHANGED` без роста версии; другой ключ — другая строка (ID первой сохранён); проверяемый `set` на отсутствующем ключе — `ABSENT` |
| Удаление по ключу | Без версии — `VERSION_REQUIRED`; несовпадение — `VERSION_CONFLICT`; успех — `DELETED`; повтор — `ABSENT` |
| Набор ключей в обратном порядке (×3) | Оба набора коммитятся, deadlock нет; итог — целиком набор одного из конкурентов. Вставки в непересекающиеся ключи обе успешны |
| Исчерпание бюджета (конкурент забирает ключ перед каждой попыткой) | Два настоящих `23505`, вердикт `RETRY_EXHAUSTED`, попыток ровно 2, ни строки, ни аудита от нашей команды |
| Классификация по SQLState | 23505 / 40001 / 40P01 / 55P03 / 25P02 и `VERSION_CONFLICT` разобраны; повторяются только транзиентные, `LOCK_TIMEOUT` и конфликт версии — нет |

## Что выяснилось (и попало в ADR)

1. **Авторитет гонки отсутствующего ключа — физический UNIQUE.** Блокировка отсутствующей строки
   ничего не защищает: второй писатель не ждёт «свободный ключ», он ждёт индекс. Наблюдаемое
   ожидание подтверждено через `pg_blocking_pids`, а не по времени.
2. **После ошибки оператора транзакция непригодна (25P02).** Значит bounded retry не может быть
   «докручиванием» той же транзакции: каждая попытка — новая транзакция. Это подтверждено
   дважды — на уровне сервера и на уровне ORM.
3. **Сходимость повтора возможна только на безверсионном пути.** Проигравший вставку, увидев
   строку во второй попытке, обновляет ресурсы — это и есть upsert. Проверяемая версия так
   повторяться не может: чужое решение не затирается, конфликт версии возвращается вызывающему.
4. **Число попыток не связано с числом записей.** Побочный эффект живёт в транзакции попытки,
   поэтому откат уносит строку и аудит вместе, а исчерпание бюджета не оставляет частичного
   результата.
5. **Порядок захвата — часть контракта.** Два набора одних ключей в обратном порядке успешно
   коммитятся только потому, что прототип сортирует ключи канонически.

## Что не проверено

- Интеграция в canonical pipeline: права C5/RLS, canonical write record, row lifecycle, durable
  аудит телеметрии, формы и REST-каналы.
- H2-равноценность и поведение под `SERIALIZABLE`: `40001` и `40P01` классифицируются на
  синтетических SQLState, но воспроизвести реальный сериализационный конфликт в READ COMMITTED
  нельзя — нужен отдельный сценарий с явным уровнем изоляции.
- Другие серверные СУБД.
- Полный общий прогон приложения и платформы; этим протоколом выполнялся один класс.
