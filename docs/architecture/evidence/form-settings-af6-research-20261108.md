# AF6 — исследование и этапы (08.11.2026)

Статус: исследование исходников; производственный код не изменялся, новые тесты
не запускались. К4 принят владельцем; AF5.7 отложен до уточнения целевого Explorer.
Эскиз Workshop предложен, его компоновка и сокращённые колонки ещё не подтверждены.
Имена новых типов ниже — предложения, не существующий API.

Уточнение по результату этапа 2: read-вход использует и C5PermissionEvaluator
для любого типа, и RlsReadGate, как canonical reader. Одного RlsReadGate
недостаточно для типов без CHECK_ONLY. См. отчёт этапа 2.

## 1. Что уже есть

| Задача | Существующая опора |
| --- | --- |
| Создать полноценный список без отдельной вкладки Workspace | `FormNavigator.createListForm`, реализация `FormCoordinator.createListForm` подключает сервис, действия, выбор, сохранённые виды и callback обновления после записи |
| Задать неснимаемое пользовательскими фильтрами ограничение | `ListForm.setOpeningContextFilters`, отдельная карта `openingContextFilterValues`; `applyViewState` меняет визуальные фильтры, не эту карту |
| Заполнить новую накладную | `ListForm.getRequiredContextValues` включает прямые ограничения открытия; координатор передаёт их в `initialValues` новой карточки |
| Скрыть/разместить команду конкретного списка | `ListCommandLayout`, `ListForm.configureCommands`; экземплярный слой поверх платформы, семейства, сущности и варианта |
| Сократить колонки без изменения основного списка | `ListFormVariants.addColumns` для именованного варианта, разрешение колонок до конструктора списка |
| Разделить сохранённые виды | `FormCoordinator.createListForm`: ключ настроек включает сущность и вариант |
| Найти владельца подчинённого справочника | `CatalogOwnerForms.ownerOf`, валидированный `CatalogOwnerDescriptor` |
| Проверить чтение типа | `RlsReadGate.canRead` и `RlsCurrentUser`; тот же вход применяется навигацией приложения |

Для пилота не нужны новая сущность, таблица БД, свой repository, второй CRUD
или ручная выгрузка накладных. Серверное чтение сохраняет штатные ограничения RLS.

## 2. Чего не хватает и где менять

### Описание и проверка формы

`platform-vaadin/.../form/builder/layout/Layout.java`, `LayoutNode.java`:
добавить `l.list(Entity.class)` и узел списка с неизменяемыми параметрами:
вариант, ограничения, read-only и настройки команд. Нужен идентификатор элемента
для повторного использования одного типа списка в разных местах формы.
Фильтр `setFilter(path, l.self())` проверяется относительно целевой сущности;
тип ссылки должен принимать родительскую сущность. Для `@CatalogOwner` путь
выводится из дескриптора, с проверкой типа владельца.

`ItemFormCustomizationRegistrar.validateNodes`: проверка целевого типа, варианта,
путей, идентификаторов и команд при старте, без списка, редакторов и запросов.
`FormReadDependencies`: вложенный список читает собственные данные через LIST;
его колонки не должны становиться зависимостями DETAIL родительской карточки.

### Сборка и ленивая загрузка

`ItemForm.renderTabSheet` сейчас немедленно обходит всех детей всех вкладок.
Требуется отложить именно создание встроенного списка до первого показа;
редакторы карточки на остальных вкладках сохраняют существующий жизненный цикл.
Узел списка вне вкладок активируется при показе соответствующего места формы.

Предлагается отдельный внутренний host встроенного списка и узкий типизированный
порт фабрики. Передать порт до `prepareDescription/buildDescription` через
`FormResolver`/`FormContext`, подключить в `FormAutoConfiguration`.
`ItemForm` не получает `ApplicationContext` или конкретный `FormCoordinator`.
Существующий `FormNavigator` уже позволяет создавать списки; адаптер может
делегировать ему, не дублируя сборку координатора. Конкретный способ передачи
порта уточняется в первом этапе; бизнес-параметры не используются для инфраструктуры.

### Родитель, запись и ограничения

`ItemForm.setEntity` и `applyPersistedEntity` вызывают `entityStateListeners`,
но `initializeNewEntity` этот список слушателей не вызывает. Все три пути
должны обновлять состояние host: новый объект → подсказка; сохранённый → список;
первая запись → подсказка заменяется списком, если место уже открыто.
При смене родителя не сохранять ограничение предыдущего id.
Не вызывать `getEntity()` ради обновления списка: он применяет биндинги к модели.

Ограничения передавать при создании списка через существующий вход параметров
открытия, а не после отображения. `ListForm` вызывает `filterGrid.build()` уже
в конструкторе; `FormResolver.prepareListForm` накладывает ограничения позднее.
На этапе интеграции проверить первый реальный запрос и группировку. По исходникам
обвязки нельзя утверждать, что внешняя библиотека FilterGrid до установки контекста
не делает чтений. Если проверка выявит раннее чтение — обеспечить отложенный запуск
данных на границе сборки списка; не переписывать все конструкторы заранее.

Состояние списка не входит в `FormBindingRegistry`, dirty и aggregate-save родителя.
Запись накладной обновляет вложенный список существующим callback координатора.
Режим просмотра родительской карточки и read-only вложенного списка следует
разделить: отдельные права на накладные обязательны, запрет изменения цеха сам
по себе не является запретом создания накладной. Явный read-only узла ограничивает
действия вложенного списка через существующую политику.

### Права и пустые состояния

Ссылка плана AF6.3 на `ActionContextProvider.classPermissionOf` неточна:
этот метод возвращает право создания, а не чтения. Для скрытия элемента использовать
решение чтения типа на основе `RlsReadGate` и текущего субъекта. Построчные
ограничения остаются в серверном чтении. Отсутствие права и пустой разрешённый
список — разные состояния; запрещённый список не создаётся.
Если вкладка содержит только запрещённый элемент, не оставлять пустую вкладку;
если есть другие элементы — сохранить их.

### Команды

Переиспользовать `ListCommandLayout` и экземплярную настройку списка для
состава/расположения. У `CommandOverride` пока нет заголовка, а у
`CommandBar.Command.title` поле final. Добавить заголовок как свойство слоя
и применять к кнопке/меню согласованно; не переименовывать только Vaadin Button.
Объявленное действие брать из `ActionRegistry`, решение — из `ActionPolicy`;
включение команды местом встраивания не может разрешать запрещённое действие.
Никаких новых бинов suppress или отдельного механизма прав.

### Пилот Workshop

`WorkshopItemForm`: вкладки «Основное» и «Входящие накладные»;
встроенный ReceivingDocument с `receivingWorkshop = self`.
`ReceivingDocumentListFormConfig`: именованный вариант, например `workshop-incoming`,
для сокращённых колонок и собственного ключа сохранённых видов.
Пользовательские журнал/период можно наследовать из действующей панели;
receivingWorkshop показывается фиксированным, без второго редактируемого поля.
Существующий required-журнал блокирует создание, не просмотр всех доступных журналов.

Обычный список и его команды/колонки/сохранённые виды сохраняются.
Форма накладной и серверная запись используют существующий путь; ограничение
списка заполняет начальное значение новой накладной. Запрет последующего изменения
цеха в карточке накладной сам по себе не следует из AF6 и здесь не добавляется.

## 3. Пять этапов реализации

| Этап | Объём | Проверяемый результат |
| --- | --- | --- |
| 1. Контракт и описание (AF6.1) | Узел, DSL, типизированная фабрика, подключение до сборки, стартовая проверка; согласование границ эскиза | Описание без UI/SQL; ошибочные тип, путь и вариант отвергаются; старые формы и конструкторы совместимы |
| 2. Встраивание и состояние (AF6.1–AF6.3) | Ленивый host, вкладки, три пути установки сущности, первая запись, read-гейт и скрытие пустой вкладки | До открытия вкладки список не создаётся; новый объект не читает накладные; после записи появляется список; без права чтения UI/чтений списка нет |
| 3. Контекст и действия (AF6.2, AF6.4) | Неснимаемые ограничения, CatalogOwner, начальные значения, read-only, слой команд и заголовки | Сброс/вид не снимают связь; создание получает родителя; запрет ActionPolicy сохраняется; кнопка и меню имеют один заголовок |
| 4. Пилот (AF6.4) | Workshop, вариант накладных, панель журнала/периода, состояния списка | Реальная накладная создаётся с цехом/журналом, повторно читается и видна в списке; родитель не становится dirty; обычный список не изменён |
| 5. Проверки и приёмка AF6 | Целевые модульные и прикладные проверки, актуальные API/отпечатки, запуск и визуальная приёмка | Зафиксирован результат AF6.1–AF6.4 и чек-лист §3.2; AF6 закрывается после подтверждения владельцем |

## 4. Проверки

- Модуль: расширить `ItemFormDescriptionTest`, `ItemFormLayoutNodesTest`,
  `FormReadDependenciesTest`; добавить проверки host на счётчиках фабрики/запросов,
  путях setEntity/initializeNewEntity/applyPersistedEntity и смене родителя.
- Контекст: опираться на `FilterPanelIntegrationTest`, `CatalogOwnerListSelectionTest`,
  `CatalogOwnerFormsTest`; проверить сохранённый вид, сброс, initialValues и независимость
  двух одновременно открытых карточек.
- Команды: расширить `ListCommandLayoutTest`, `FormResolverListCommandsTest`,
  `ListFormDeclaredActionTest`, `CommandMenuRegressionTest`; запреты, обработчики,
  заголовки кнопки/меню и изоляция экземплярного слоя.
- Приложение: новый интеграционный тест с реальным Workshop/ReceivingDocument,
  SQL обоих состояний доступа, запись/повторное чтение, первый запрос уже с ограничением,
  независимость dirty/save, неизменность default-списка. Учесть actual RLS JOURNAL/BRANCH.
- После изменения платформы: целевая установка, API/surface и test-usage,
  fingerprints/bootstrap с раздельным учётом существующих параллельных правок.
- Визуально: обычное/узкое окно, компактный список, пустое состояние, новый цех,
  фокус/клавиатура, видимость фиксированного ограничения, доступность команд.

Полный прогон приложения не запускается без изменения действующего указания владельца.
Рабочее дерево уже содержит параллельные изменения ItemForm/ListForm/команд/резолвера;
перед реализацией зафиксировать состав проверяемой версии, не откатывать чужие правки.

Основная работа — platform-vaadin. В приложении ожидаются настройка Workshop,
вариант списка накладных и интеграционные проверки. Изменения core/БД заранее
не требуются; возможное вмешательство в запуск FilterGrid решается по проверке
первого запроса, а не по предположению.
