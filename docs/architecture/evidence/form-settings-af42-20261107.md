# AF4.2 — чтение конфигураций колонок из исходников

Дата: 07.11.2026, Europe/Moscow. Основание: основной план О1/Р19/AF4.2,
рабочий план §8 и пакет 1 (§1.1). Полный прогон не выполнялся по указанию владельца.

## Результат и API

ProjectSources индексирует источники статических конфигураций одновременно
с типами и снимком полей для автоматического состава. JavaEntityReader читает
основные колонки из @FormConfigurationFor(Entity.class), @ListColumns и
@SelectionColumns. Приоритет конфигурации над массивом сущности совпадает
с MetadataResolver. Исходники нужно индексировать от Java source root,
включая пакеты сущностей и конфигураций, например src/main/java.

ExistingEntity получил listColumns() и selectionColumns() типа ExistingFormColumns:

- mode — AUTO, EXPLICIT или UNKNOWN;
- declaredPaths — исходное намерение (пусто для AUTO);
- resolvedPaths — окончательный порядок колонок;
- sourceTypeId / sourcePath / sourceSha256 — адрес и хэш прочитанного объявления;
- resolutionComplete — удалось ли статически разрешить окончательный состав.

Прежние сигнатуры конструкторов ExistingEntity сохранены; без новых данных
они возвращают UNKNOWN. Из одинаковых колонок режим не выводится.
У старого AUTO с неизвестным grid-порядком режим остаётся AUTO,
resolutionComplete=false и resolvedPaths пуст; предположительный порядок не выдаётся.
Прежние признаки публикации читаемых полей при этом сохраняются.
Новый AUTO, который требует неразбираемых grid-настроек, получает адресный отказ.

Непустой value аннотации — EXPLICIT даже при совпадении с AUTO. Пустое value,
{} и аннотация только с properties — AUTO. Разрешённый AUTO учитывает
унаследованные и затенённые поля, grid.order и стабильный порядок при равных
значениях. Стандартные поля code/name, number/date и period берутся из
известного платформенного контракта, а прикладные — из исходников.

Новые ListColumns и SelectionColumns независимы. Отсутствующая SelectionColumns
сохраняет старый fallback только из EntityMetadata.listColumns; она не наследует
новое ListColumns. Явная SelectionColumns с AUTO использует grid, включая случай,
когда на сущности ещё есть старый явный массив списка. Эти различия проверены
на настоящем MetadataResolver и Spring-коллекторе.

Поддерживаются одиночная строка, массив литералов, повторяемые аннотации и их
контейнеры Declarations, литеральные variant/title/properties, вложенные пути,
полностью квалифицированные имена и импорты. Все найденные варианты проверяются;
в ExistingEntity возвращается основной вариант. Properties проверяются отдельно
и не расширяют состав. Вложенная ссылка разрешается с импортами класса,
который объявил поле, включая унаследованное поле из другого пакета.

## Отказы и промежуточная граница патчера

Новая неразбираемая запись вызывает SourceRefusal с классом, строкой и свойством,
например FORM_COLUMNS_UNSUPPORTED p.Config:1#value. Константы, конкатенация
литералов (в том числе свёрнутая парсером), условия и вызовы методов не исполняются.
Отказываются также неоднозначная/отсутствующая статическая привязка,
наследование конфигурации, вложенные конфигурации, прямые условия Spring и
условные мета-аннотации, доступные в исходниках. Полная модель регистрации
бинов Spring и интерпретация configure() в читатель не добавлялись.

Дубли роли/варианта дают FORM_COLUMNS_CONFLICT с обоими источниками.
Проверяются пути всех вариантов, пустые/повторные пути, константы в свойствах
и свойства колонок вне разрешённого состава. Конфигурация с понятной привязкой
к другой сущности не мешает чтению текущей; неразрешимая привязка даёт отказ,
поскольку принадлежность объявления неизвестна.

Читатель не загружает классы. Тест с падающими статическим блоком и конструктором
конфигурации успешно читает её аннотации без выполнения этих блоков.

Полная работа патчера с внешним составом остаётся AF4.3. На промежуточном этапе
добавление поля при внешнем основном объявлении колонок адресно отклоняется
MODIFICATION_UNSUPPORTED. Изменение подписи разрешено; sourceSha256 прочитанных
основных конфигураций включается в ModificationPlan.dependencyHashes,
поэтому изменение конфигурации после построения плана не остаётся незамеченным.
Файлы конфигураций патчер не пишет.

GeneratedFormColumnsReaderTest создаёт реальные файлы через EntityJavaGenerator
для standard-catalog-v3, standard-document-v2, independent-register-v3 и
independent-register-v4 с RLS. Читатель возвращает те же явные составы,
режимы, хэш конфигурации и собственные поля сущности. Генерируемые fixtures
не перезаписывались читателем; старые рецепты не менялись.

JavaEntityReaderParityTest теперь сравнивает не только признаки полей, но и
точный порядок разрешённых колонок и режим. Индекс включает весь src/main/java,
а не только модель. Прочитаны 29 типов модели: 70 полей, 28 заблокированы
по прежним причинам; отчёт — target/entity-reader-parity-report.txt.

SourceFormColumnsPlatformParityTest компилирует десять независимых конфигураций
во временном source root, регистрирует их с настоящим FormColumnDeclarationsCollector
и сравнивает результат читателя с MetadataResolver и заданными ожиданиями.
Проверены AUTO, EXPLICIT с теми же колонками, иной порядок, properties без value,
legacy fallback, независимый выбор, повторяемые объявления, варианты и вложенные пути.
БД, UI-экземпляры и бизнес-чтение этому тесту не требуются.

Два пропуска относятся к прежнему ModificationApplyTest: создание symlink
недоступно текущей учётной записи Windows, тест POSIX-прав к Windows не применим.
Две проверки применения в EntityModificationTest сначала не смогли заменить
свои временные файлы в песочнице; итоговый целевой запуск вне песочницы прошёл.
Во всех запусках приложения использован явный Mockito -javaagent.
Снимок П.2 совпал без перезаписи.
