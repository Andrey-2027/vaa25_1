# M2.2 preflight: что именно упирается в приложение (2026-10-24)

- Дата: 2026-10-24.
- Основание: [M2 плана](../../plans/query-report-separation-plan.md), второй срез —
  UI каталога/печати и UniDR; продолжение [M2.1](m2-1-report-layer-jr-20261024.md).
- Срез: инвентарь и границы перед физическим переносом. Код не перемещался:
  слепой `git mv` этих файлов ломает сборку на трёх прикладных точках, перечисленных ниже.

## 1. Объём

```text
src/main/java/org/ip/unidr/**            34 production-файла
src/main/java/org/ip/views/unidr/**      15 production-файлов
src/main/java/org/ip/views/reportstudio/** 8 production-файлов (каталог/печать/параметры)
src/test/java/org/ip/unidr/**            25 тестовых файлов
src/test/java/org/ip/views/unidr/**       9 тестовых файлов
```

Пакеты `model`, `source`, `store`, `render`, `run`, `query` замыкаются друг на
друга (model ↔ source), поэтому делить backend на «чистые» и «прикладные» пакеты
нельзя: `UniDrQueryService` и `UniDrRunService` — одна цепочка с `UniDrReferenceService`.

## 2. Три прикладные точки, которые нужно снять до переноса

### 2.1. Реестр ссылок и app-сущности

`UniDrReferenceService` одновременно:

- статически отображает `fieldId` → класс сущности:
  `Workshop`, `Nomenclature`, `ReceivingDocument`, `UnitOfMeasurement`;
- ищет варианты и выбранное значение через `EntityLookup`.

Статический `referenceType(...)` вызывают `UniDrQueryAdapter`, `UniDrFilterSupport`
и UI. Простой перенос в модуль потянет `org.ip.model.*` — запрещённую обратную
зависимость.

**Нужен порт** `UniDrReferenceCatalog` в модуле:

```text
Class<?> referenceType(String fieldId)
List<Option> options(String fieldId, String term, int limit)
Option selected(String fieldId, long id)
String entityType(String entityClassName)
```

Приложение реализует его поверх своих сущностей (`Workshop` и т.д.) и
`EntityLookup`; `UniDrQueryService`/`UniDrQueryAdapter`/`UniDrFilterSupport`
получают порт вместо конкретного класса. UI получает тот же порт через
`UniDrConfiguration`.

### 2.2. Пилотный источник

`UniDrReceivingItemsSource` описывает именно прикладной срез «позиции накладных»
(JPQL-поля `d.number`, `r.name`, `i.quantity`). По плану он остаётся приложению:
`UniDrConfiguration` регистрирует его в `UniDrSourceCatalog`, а модуль знает
только `UniDrSourceDefinition` и механизм регистрации. Переносить файл в модуль
нельзя — это вернёт в артефакт прикладную модель.

### 2.3. UI-мосты каталога и печати

`ReportCatalogView`, `ReportPrintDialog`, `ContextualReportLauncher`,
`ReportPrintAction`, `ItemFormReportActions` напрямую знают:

- `UniDrFileStore` (load/copy/export/import/delete/currentUser);
- `UniDrRunDialogFactory` (открыть параметры и запуск);
- `ReportParamEditor`/`ReportQueryDialog`/`ReportParamForm`/`FormEntitySelection`
  (UI запроса и параметров).

Для `platform-report-vaadin` нужны два узких порта:

```text
UniDrCatalogGateway  load/copy/exportJson/inspectImport/importJson/delete/currentUser
UniDrRunLauncher     open(UniDrDefinition snapshot, ReportContext context)
```

Приложение реализует их над своим `UniDrFileStore`/`UniDrRunDialogFactory`.
UI запроса остаётся в `platform-query-vaadin`; `ReportParamEditor`/`ReportQueryDialog`
переносятся в отчётный UI-модуль вместе с параметрами, а не остаются в приложении.

## 3. Предлагаемый порядок

| Срез | Содержание | Выход |
|---|---|---|
| M2.2.1 | `platform-unidr`: model/source/store/render/run/query, порт `UniDrReferenceCatalog`; пакет `org.ipro.unidr`; тесты без прикладных сущностей | модуль собирается без `org.ip`; приложение подключает его и даёт адаптер ссылок |
| M2.2.2 | `platform-report-vaadin`: каталог/печать/параметры/диалог запроса + порты `UniDrCatalogGateway`/`UniDrRunLauncher`; UI UniDR | модуль без `org.ip`, `reportstudio`, UniDR-сущностей |
| M2.2.3 | cutover приложения: `UniDrConfiguration` и прикладные адаптеры; обновление BOM/manifest/гейтов; runtime-проверка | M2 закрыт, затем A1 |

Пакет переименовывается один раз в M2.2.1 (`org.ip.unidr` → `org.ipro.unidr`) —
до переноса UI, иначе мосты и тесты придётся править дважды.

## 4. Что не входит

- `UniDrReceivingItemsSource` и прикладные имена/JPQL остаются в приложении.
- Переход файлового store на JPA, новые сценарии и изменение JSON v1/v2 не входят.
- `dynamicreports-defaults.xml` переезжает в `platform-unidr` вместе с рендером,
  но только в M2.2.1; app-тема и frontend не трогаются.

**M2.2 начат с preflight.** Следующий допустимый шаг — M2.2.1; без порта ссылок
перенос backend невозможен.
