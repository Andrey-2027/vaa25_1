# C5.8: выдача права на именованную операцию — 2026-10-08

- План: [C5.4–C5.10](../c5-operation-permissions-plan.md), пакет C5.8 («Администратор и первичная
  выдача»).
- Решения: [ADR-0017](../decisions/ADR-0017-c5-single-operation-authority.md) §3 (носитель права —
  строка `access_grant`; `canUpdate` решает CREATE/UPDATE/EXECUTE), §5 (реестр определений);
  [ADR-0019](../decisions/ADR-0019-owner-named-row-operation.md) §1, §5.
- Предшественник: [c5-6b-named-row-operation-20261008.md](c5-6b-named-row-operation-20261008.md) —
  операция объявлена и работает, но выдать её человеку было нечем.
- Метод: правка пути выдачи в приложении (админ-сервис и экран), одна additive-точка в
  `platform-rls`; целевые прогоны, намеренная перезапись одного API-baseline.

## 1. Что было не так

Определение `ACTION:ATTRIBUTE_VALUE:RENAME` регистрировалось как измерение `CHECK_ONLY`, поэтому
ключ **уже** попадал в выпадающий список админ-экрана — но выдача обращалась с ним как с
построчным доступом:

- предлагались три флага «Чтение / Изменение / Удаление», причём «Изменение» было заблокировано,
  пока не отмечено «Чтение»;
- сохранение нормализовало `canRead = read || update || delete`, то есть выдача **записывала**
  право чтения для операции, которая им не решается;
- ключ показывался сырым (`ACTION:ATTRIBUTE_VALUE:RENAME`) — администратор не мог объяснить, что
  именно выдаёт.

Итог: право выдать было можно, но полученная строка не говорила то, что значит, а объяснить её
было нечем. C5.8 требует обратного: «экран показывает операции из определений», а «администратор
объясняет решение».

## 2. Что сделано

**Не бросающий запрос определений (platform-rls).** `C5OperationPermissionRegistry.operationsOf(key)`
возвращает операции объявленного определения или пустое множество. Это запрос для путей, которые
**показывают и выдают** права: там незнакомый ключ — вопрос «есть ли определение», а не ошибка
конфигурации. Решение о доступе по-прежнему спрашивает `requireSupports` и падает на
незарегистрированном ключе: показ и выдача не заменяют решение. Baseline `platform-rls.api`
перезаписан намеренно — диффом видно ровно одну добавленную строку.

**Строгий путь выдачи — только для именованной операции (app).**

| Метод | Что делает |
| --- | --- |
| `isNamedOperationDimension` | Ключ объявлен определением с единственной операцией `EXECUTE` |
| `expressibleFlags` | Флаги, которые измерение вообще может выражать: у операции — объявленные, у C5 read — только чтение, у остальных `CHECK_ONLY` — прежние три |
| `saveSingleOperationGrant` | Пишет ровно объявленные флаги: у операции это `canUpdate`, а `canRead` не нормализуется из остальных |
| `currentOperationGrant` | Показывает решения определения: флаг, которого определение не выражает (наследство прежней выдачи), показывается как «права нет» |
| `requireDeclared` | Отказ на флаг, которого определение не выражает, — с ключом и операциями в сообщении |

**Почему строгий режим не распространён на короткий ключ типа `ENTITY:<Имя>`.** Этот ключ несёт две
роли сразу: решение C5 об операциях (`canUpdate`/`canDelete`) и прежний гейт видимости плитки
подсистемы (`SubsystemHomeView.isEntityVisible` → `AccessService.hasAnyAccess` → `canRead`).
Перестать писать там `canRead` значило бы спрятать плитку у субъекта, которому только что выдали
запись. Это подтвердили два существующих теста
([C5GrantAdminParityIT](../../../src/test/java/org/ip/security/C5GrantAdminParityIT.java),
[RlsAutoConfigurationSmokeTest](../../../src/test/java/org/ip/security/RlsAutoConfigurationSmokeTest.java)):
первая версия среза уронила их именно на этом, и правила разведены по роли ключа, а не по удобству.
Снятие дублирующего гейта — шаг C5.7, и до него правило для `ENTITY`-ключа остаётся прежним.

**Экран (AdminView).** Чекбоксы строятся по `expressibleFlags`, а не по собственному условию: у
именованной операции виден один флаг, подписанный «Выполнение:» (у остальных — «Изменение:»), и
требования «Чтения» нет; сохранение отправляет только выражаемые флаги, поэтому скрытый чекбокс не
записывает флаг, которого определение не решает.

**Владелец объявляет название.** `NamedOperationOwner` (приложение) даёт владельцу рядом с
определением сказать, как операция называется для человека;
[`AttributeValuePermissions`](../../../src/main/java/org/ip/application/catalog/AttributeValuePermissions.java)
объявляет `RENAME_TITLE = «Переименование значения атрибута»`. Без названия экран показывает сырой
ключ — точный, но необъяснимый; название не участвует в решении и прав не меняет.

## 3. Проверки

| Проверка | Результат |
| --- | --- |
| [`NamedOperationGrantAdminIT`](../../../src/test/java/org/ip/security/NamedOperationGrantAdminIT.java) — экран предлагает операцию с одним флагом; выдача через админ-сервис открывает переименование, отзыв закрывает; строка содержит `canUpdate` и не содержит `canRead`; флаг, которого нет в определении, отвергнут; устаревшая строка с чужим флагом показывается как «права нет»; сам bean экрана поднимается с объявленным списком владельцев | 6/6 |
| `AttributeValueWriteBoundaryIT` (вооружённый тип), `C5GrantAdminParityIT`, `RlsAutoConfigurationSmokeTest` | 5 + 7 + 17, 0 отказов |
| [`C5OperationPermissionRegistryTest`](../../../platform-rls/src/test/java/org/ipro/rls/c5/C5OperationPermissionRegistryTest.java) — `operationsOf` не бросает, а решение на том же ключе по-прежнему падает | 10/10 |
| `PlatformApiBaselineTest` — после намеренной перезаписи baseline `platform-rls` | 3/3 |
| `PlatformVaadinSurfaceTest` | Падает на **чужом** untracked файле `AccountingObjectRegisterView.java` (`org.ipro.form.FormBindingRegistry`), не по этому срезу |

Чего право не делает и это тоже проверено: операции мало — переименование читает исходное
состояние, поэтому без read-ключа оно остаётся закрытым.

## 4. Остаток

- **Эффективные права для операционных измерений** по-прежнему собираются RLS-свёрткой
  (`collectEffective` → `AccessService.effectiveGrants`), а не решением C5. C5.8 просит «решение и
  его источники берутся тем же engine» — это следующий шаг, и он касается и ролей.
- **Отчёт «определение зарегистрировано, грантов нет»** не сделан: сегодня закрытая операция
  видна только тому, кто сам догадается посмотреть её ключ на экране.
- **Проверка руками в UI** не делалась: проверены сервис, которым экран выдаёт, и проводка
  самого bean'а экрана, а не клики и не включённость чекбоксов на отрисованной странице.
- **Выдача по умолчанию** не вводилась: право не выдаётся никому при старте — его выдаёт
  администратор, как и остальные операционные права. Пилотный сценарий (документы учёта,
  справочники) значения атрибутов не заводит, поэтому первичная выдача именно этой операции в
  его фикстуру не входит.
- PostgreSQL и полный прогон — за C5.9.
