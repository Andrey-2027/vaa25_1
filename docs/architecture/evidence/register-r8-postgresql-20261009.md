# Р8: PostgreSQL-конкуренция и пользовательская проба

Дата: 2026-10-09. Статус: итоговый PostgreSQL-прогон успешно завершён;
пользовательская оценка пока не получена.

## Окружение и воспроизведение

PostgreSQL 17.10, Windows x86_64, Java 21, Hibernate / Spring из рабочего проекта.
Используется READ COMMITTED. Команда из корня проекта:

```powershell
.\scripts\register-r8-postgresql.ps1
```

Скрипт читает параметры подключения из локальной конфигурации, создаёт новую
`g3_register_test_r8_<guid>` базу, передаёт её URL в три тестовых класса и
восстанавливает переменные окружения. URL рабочей базы не передаётся в create-drop.
Тестовая база остаётся для диагностики. Пароли в протокол не выводятся.

Первый запуск остановился на testCompile из-за старого установленного platform-rls:
исходники уже используют C5PermissionEvaluator в RlsReadGate. Актуальный локальный
модуль пересобран; production-исходники RLS в рамках этой проверки не изменялись.
Второй запуск выявил отсутствие явного имени key column в новой тестовой модели;
исправлен @Column(name="item_key"). Эти запуски не считаются успешной приёмкой.
Затем исправлена подготовка строк старого replacement API: ему требуется явно
передать recorder, в отличие от add API. Production-код не изменялся.
Отдельный прогон новых сценариев завершён: 21 / 21, без ошибок и пропусков,
14:18:08 МСК. [Протокол](../../plans/r8-postgresql-concurrency-fourth-20261009.log).

## Проверяемые гонки

Каждый новый сценарий повторяется трижды. Два потока используют разные транзакции
и persistence context. Первый поток удерживает блокировки до разрешения теста;
тест наблюдает реального waiter через pg_stat_activity / pg_blocking_pids,
после чего разрешает первому потоку завершиться. Все ожидания ограничены.

| Сценарий | Проверяемый результат |
| --- | --- |
| Две смены ключа с одной исходной версией | Один успех; второй отказ по версии; тот же ID и ресурс; документ не изменён |
| Смена ключа → replacement | После обоих commit один новый полный набор документа |
| Replacement → смена старого ключа | Старый ID больше не редактируется; новый набор сохраняется |
| Смена ключа → удаление документа | Нет документа и осиротевших строк |
| Удаление документа → смена ключа | Отказ для удалённой строки; данные не восстанавливаются |
| Два append одного владельца | Свежий owner state под блокировкой; номера 1/2/3, прежние ID / порядок сохранены |
| Две независимые строки претендуют на один ключ | UNIQUE допускает одного победителя; вторая строка / ресурс не затираются |

Ожидаемый конфликт отличают от произвольного исключения: допустимы stale version,
отсутствующая запись и UNIQUE; deadlock / lock timeout не считаются успешным исходом
новых сценариев. Append проходит через настоящий aggregate onSave и RegisterRecords,
не через самостоятельно изготовленный lifecycle token.

Узкие fixtures используют настоящие PostgreSQL / Hibernate и команды регистров;
permissions / read-port в них подменены. Реальные проверки прав, формы и lifecycle
двух прикладных документов проверяются отдельным AccountingObjectPilotIT на той же
изолированной PostgreSQL-базе. RecorderSetWriterPostgresIT дополнительно проверяет
прежние replacement / delete / retry / rollback.
