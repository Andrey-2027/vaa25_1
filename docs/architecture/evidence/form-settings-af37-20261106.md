# AF3.7: подписи конструктора запросов, 06.11.2026

**О4 решён:** каталог конструктора использует подписи реквизитов из
`FieldMetadataInfo.getLabel()` (`@FieldMetadata.label` с прежним fallback).
Заголовки колонок списка больше не становятся дополнительными псевдонимами поля.
Совместимость сохранённых визуальных запросов и отчётов проверена до изменения
установленного модуля и после него.

## Что именно использовало псевдонимы

- `QueryBuilderMetadataCatalog.describe` уже задавал основную `Field.caption`
  через `f.getLabel()`. Отдельный `gridHeaderAliases` добавлял заголовки колонок
  списка в `Field.aliases`, сопоставляя их по последнему сегменту пути.
  Вложенный заголовок мог таким образом стать псевдонимом одноимённого поля корня.
- Единственный производственный читатель `Field.aliases()` —
  `NaturalLanguageQueryParser.resolveField`: это дополнительные слова при разборе
  нового текстового запроса. В сохранение/компиляцию JPQL этот путь не входит.
- `VisualQueryDefinition.SelectField` хранит технический `path` и явный `resultName`;
  JOIN, группировка, отборы и сортировка тоже используют технические пути.
  `VisualQueryDefinitionJsonCodec` и `VisualQueryPackageJsonCodec` не сохраняют
  каталог и его `Field.aliases`.
- `VisualQueryCompiler` разрешает пути по `Field.name` и сохраняет явные имена
  SELECT/агрегатов. Подписи результата и до изменения читались из `Field.caption`.
  Эти имена результата не являются удаляемыми поисковыми псевдонимами.
- `ReportQueryAssemblyService.resolveExecutableJpql` компилирует сохранённый JSON
  либо использует ручной JPQL; `ReportQueryLanguage` использует технические пути.
  Они не вызывают естественно-языковой парсер и не читают `Field.aliases`.
- UniDR сохраняет определение в файловом хранилище, включая `query.visualQueryJson`.
  JR хранит JPQL в XML `queryString`, а БД — каталожные метаданные шаблона.
  Каталог псевдонимов в эти форматы не входит.

Публичный компонент `Field.aliases` и возможность явных псевдонимов парсера оставлены
для совместимости API. Удалён только автоматический источник из настроек списка.
Новый текстовый ввод больше не получает синонимы из заголовков формы;
имена полей, подписи реквизитов и явно заданные псевдонимы парсера остаются.

## Локально сохранённые отчёты

Проверено настроенное файловое хранилище `reports/unidr`: 9 определений,
из них 7 VISUAL и 2 со стандартным источником `receiving-items`.
Ни одно не содержит каталожного `aliases`. Все 7 визуальных определений
сохранены как регрессионные фикстуры:
[af37-saved-visual-queries.json](../../../src/test/resources/query/af37-saved-visual-queries.json).

До установки изменённого `platform-query` эти 7 запросов скомпилированы на прежнем
артефакте с реальным каталогом приложения в H2-срезе. Эталон включает исполняемый
JPQL, имена, подписи и Java-типы выходных полей:
[af37-saved-compiled.txt](../../../src/test/resources/query/af37-saved-compiled.txt).
После установки нового артефакта тот же тест сравнил результаты с эталоном —
**все 7 совпали полностью**. Запросы не исполнялись, пользовательские файлы не менялись.

SHA-256 эталона: `a9ac033157cdaa3c803ecf2d25b6b30c29f0382edf86cde3491aa01235c734b2`.
Инвентаризация: [UniDR](../../../outputs/verification/af37-stored-inventory.json),
[JR](../../../outputs/verification/af37-jr-inventory.json).
Настроенная локальная папка `jrxml-files` отсутствует: существующих JRXML для
перекомпиляции на этом стенде нет. Другие пользовательские хранилища и базы
не обследовались; вывод о формате JR основан на коде его хранилища и исполнителя.

## Изменение и проверки

В `QueryBuilderMetadataCatalog` удалены чтение колонок списка и `gridHeaderAliases`.
Корни, поля и ассоциации продолжают строиться из прежнего набора метаданных,
с прежними правилами скрытых полей, технических полей регистра и RLS.
Основные подписи полей и связей остаются `FieldMetadata.label`.

99 целевых проверок прошли без падений и пропусков:

- `platform-query`: 30 — новые `QueryFieldLabelsTest` (3), границы backend,
  стандартный каталог, JSON и компиляция простых, JOIN и пакетных запросов.
- `platform-query-vaadin`: 54 — парсер, черновик, дерево источников,
  анализ редактора и границы UI.
- Приложение: 15 — каталог с семью сохранёнными запросами, сборка отчётного запроса,
  снимок П.2, API baseline `platform-query` и документированные измерения.

Новые модульные тесты задают отличающиеся подписи списка и реквизитов, включая
вложенную колонку. Проверяют независимость подписей каталога от формы,
распознавание подписи реквизита и отсутствие синонима из формы, а также одинаковую
компиляцию сохранённого запроса с прежними и новыми псевдонимами каталога.

Снимок П.2 не переписывался, MD5 `4c089da0fea2aecf2eb30c96f2b28dff`.
Публичные сигнатуры не менялись; API baseline проверен без перезаписи.
Полный прогон и отдельная браузерная проверка не выполнялись: основной текст
подписей уже брался из модели, изменение касается дополнительных слов парсера.

Модуль `platform-query` установлен в изолированный и обычный Maven-кэши;
обновлён только его отпечаток (128 файлов). Bootstrap ValidateOnly сохраняет
ранее известный дрейф внешнего filtergrid (177 → 178 файлов, SHA
`f8c677d23f4f0cb04ff97c7049a3eb2897934fb4be5b6ab127258410cbc573ba`).
Логи — `outputs/verification/af37-*.log`. AF3.8 не начинался, модели не мигрировались,
изменения не закоммичены.
