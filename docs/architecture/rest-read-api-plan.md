# Входящий REST API чтения сущностей: план

- Статус: этапы 1–4 и локальная read-приёмка завершены; внешняя публикация имеет отдельные C5/C, consumer и deployment gates
- Дата: 2026-10-01; актуализировано 2026-10-06 по итоговой приёмке 4.7
- Область: `GET list` и `GET detail` для явно опубликованных ресурсов приложения

## 1. Контекст и место в roadmap

Внешнему потребителю нужны, например, список спецификаций с объявленными фильтрами и
карточка спецификации по id. Третий потребитель может появиться в любой момент: для нового
клиента того же контракта не должны требоваться новый контроллер, сериализатор и повторная
реализация проверок доступа.

Уже есть `EntityDataAccess.list/detail`, `EntityDescriptor` с read capabilities,
`CanonicalReadExecutor`, FetchPlan и RLS. Их повторно использует REST-адаптер. Builder
и REST-каталог реализованы в первых двух срезах; mapping-замечания второго этапа
исправлены. Серверный read pipeline, C5 read-подмножество, HTTP-пакеты 4.0–4.7
и общие локальные build gates приняты. JSON/Problem/OpenAPI v1, реальные HTTP/H2
пилоты и итоговый стабильный source/JAR snapshot закреплены в [evidence 4.7](rest-read-api-stage4-47-evidence-20261006.md).
Полный C5/C и внешняя публикация остаются отдельными gates.
`EntityDataAccess` не принимает дополнительные пути загрузки,
хотя внутренние `PageRead`/`DetailRead` и `ScenarioFetchGraphResolver` их поддерживают.

Актуальное состояние: З0–З5/Gate 3A/3B и [этап 4](rest-read-api-stage4-http-plan.md)
завершены. Полный стандартный bootstrap: 1830 application tests, failures/errors 0,
6 PostgreSQL-only skipped; HTTP/H2 + compatibility 50/50 без skipped. Frontend/package
и strict validation проходят. Команды, fingerprints и JAR receipts — в [evidence 4.7](rest-read-api-stage4-47-evidence-20261006.md).

Roadmap запрещает открывать generic entity REST до завершения этапа C. Этот план не
объявляет C завершённым и не меняет приоритеты этапов. Его предмет — **входящий** API,
публикующий локальные сущности; `F-INT-2` описывает противоположный канал — чтение
внешнего источника через REST-провайдер, и не служит спецификацией этого API.

### Что означает утверждение границ

Предлагается утвердить отдельный условный срез `F-REST-READ`: платформа публикует только
явно объявленные `list/detail` локальных root-сущностей через optional адаптер, а
приложение владеет внешним контрактом каждого ресурса. Это решение о границе работ,
а не фиксация wire-контракта `v1` и не открытие маршрутов. Проработка ресурса и read SPI
не зависит от G/Studio; C5 ставится в отдельную очередь как общий security-контур для
UI и REST. Публикация API требует завершения этапа C и приёмки первого пилота.

Вместе с builder согласуются публичный ключ первого ресурса, поля `list/detail`
(default и максимум), фильтры и сортировки. Перед HTTP-адаптером отдельно фиксируются
envelope и формат ошибок с примерами `200/400/401/403/404`. API-review закрепляет
read SPI и способ регистрации прав C5.
Пилот `PrdSpec` проверяет RLS, `Nomenclature` — обязательное API-право без RLS.
Оба контракта пока примеры, а не опубликованные схемы. Синхронизация, запись и
owned-секции остаются отдельными задачами.

Первый реализуемый REST-срез — **прикладной builder декларации**, его immutable результат
и локальные проверки декларации. Контракт `PrdSpec` проектируется вместе с builder:
реальный ресурс проверяет, что API выражает поля, aliases, default/maximum, фильтры,
сортировку и версию без прикладного контроллера. Каталог со сквозной startup-проверкой,
read SPI и HTTP-адаптер подключаются следующими шагами. Builder не регистрирует маршрут
сам по себе.

## 2. Цель и границы первого среза

Платформа предоставляет один повторно используемый optional REST-адаптер. Приложение
явно публикует ресурс и его версионируемый контракт. Ничего не открывается по одному
факту присутствия класса в JPA metamodel, `EntityDescriptorCatalog` или каталоге форм.

В первом срезе поддерживаются:

- `GET /api/v1/{resource}` — ограниченный постраничный список;
- `GET /api/v1/{resource}/{id}` — одна запись по id;
- отдельные разрешённые поля, фильтры и сортировки для каждой операции;
- аутентификация, право на API-операцию, entity read permission и RLS;
- проверки декларации при старте и единые HTTP-исходы.

Вне этого плана: создание и изменение, синхронизация и журнал изменений, `lookup/search`,
произвольный filter DSL, PATCH, webhooks, owned-секции и частные бизнес-команды.
`detail` первого среза означает шапку root-сущности. Секции не загружаются и не
сериализуются автоматически; позднее для них понадобится отдельный контракт чтения
через aggregate boundary.

## 3. Разделение ответственности

| Участник | Ответственность |
| --- | --- |
| `platform-rest` (optional add-on) | Прикладной builder и immutable описание ресурса, каталог, проверка деклараций, маршруты, разбор и валидация параметров, лимиты, сериализация только объявленной схемы, HTTP-ошибки, контракт OpenAPI, тестируемая интеграция с canonical read path и общим механизмом прав. Не зависит от Vaadin и не обращается к repository/`EntityManager` в обход canonical path. |
| Приложение | Какие типы опубликовать, публичные ключ и версию, имена/типы/источники полей, default и максимальный набор полей для `list` и `detail`, допустимые фильтры/сортировки и их операции, предметные вычисления при необходимости. |
| Администратор | Гранты объявленных API-операций и entity/attribute permissions пользователям, ролям либо именованным сервисным учётным записям. Публикация ресурса в коде сама никому не выдаёт доступ. |
| Клиент | Выбирает только подмножество разрешённых полей, передаёт только объявленные фильтры и сортировку, соблюдает пагинацию. Не передаёт Java/JPA-пути или готовый `Specification`. |

Обычный ресурс требует декларации, а не прикладного контроллера и ручного DTO-класса.
Декларация сама является источником внешней схемы. Для предметного вычисления возможен
типизированный projector SPI с явными зависимостями чтения; platform default не угадывает
бизнес-смысл.

Полный пример builder — в
[`rest-read-api-stage1-builder-plan.md`](rest-read-api-stage1-builder-plan.md), §3.
`nomenclatureCode` в нём — публичный alias пути, а не произвольная Java-лямбда.
Вычисляемое предметное поле потребует отдельного projector и объявленных зависимостей,
чтобы исключить случайные lazy-запросы.

Рекомендуемая форма регистрации: приложение объявляет Spring bean типа
`RestResourceDefinition<?>`, полученный через builder. Builder остаётся Spring-neutral;
будущий каталог собирает только такие явные bean-объявления, без scan JPA-типов.
Форма регистрации входит в API-review первого среза и проверяется прикладным fixture.

`platform-rest` включается в platform BOM и bootstrap manifest, но не добавляется в
существующие backend/Vaadin starters как транзитивная зависимость. Приложение
подключает optional артефакт явно. Первый срез артефакта не содержит web-адаптера.

## 4. Ключ, версия и схема ответа

Ключ REST-ресурса принадлежит внешнему API и не выводится из `FormRouteCatalog`.
`specifications` может отличаться от опубликованного ключа формы `prd-spec`; совпадение
имён допустимо, но не создаёт зависимости между контрактами. Число в builder и
`/api/v{major}/{resource}` — **major-версия контракта данного ресурса**, а не
самостоятельная глобальная версия REST-протокола. Идентичность — `(resource, major)`;
`/api/v1/specifications` и `/api/v2/specifications` могут сосуществовать с
`/api/v1/nomenclature`. Общий envelope также входит в версию каждого затронутого
ресурса. Несовместимое изменение получает новый major и отдельное решение о сроке
поддержки прежнего.

Для первой версии действует консервативная политика: имена, типы и смысл полей,
nullability/форматы, максимальные и default-наборы `list/detail`, фильтры,
сортировки и envelope закреплены за major. Изменение любого из них, включая
добавление доступного поля или фильтра, требует нового major. В пределах того же
major допустимы исправления реализации и документации без изменения видимого
контракта. Это создаёт новые API-гранты при выпуске v2 намеренно: право на v1 не
расширяется до новых данных или способов их отбора автоматически.

Для `list` и `detail` объявляются:

- стабильное публичное имя поля, тип, nullability, формат и источник значения;
- отдельно максимальный разрешённый и default-наборы полей;
- явное представление ссылки (например, id и разрешённые скалярные поля), без
  рекурсивной сериализации JPA-сущности;
- обязательный `id` в каждом результате.

`id` — обязательное публичное поле, явно объявленное с типом и источником. Оно
входит в максимальный и default-наборы обеих операций; `fields` не может убрать
его из ответа. Право на API и чтение сущности разрешают обязательный `id`
и остальные опубликованные поля без attribute grants
([ADR-0016](decisions/ADR-0016-rest-resource-field-access.md)).
Каталог проверяет соответствие типа объявленного `id` JPA-идентификатору.

При отсутствии `fields` возвращается default-набор соответствующей операции.
`fields=a,b` может только уменьшить результат в пределах максимального набора.
Неизвестное поле даёт `400`; отсутствие права на операцию или чтение сущности —
`403`. Сервер не добавляет молча поля из `@EntityMetadata`, формы или JPA.
Схема версии, default-ответ и выборка `fields` закрепляются contract-тестом;
переименование alias всегда означает новый major.

Пример запроса для предполагаемой декларации `PrdSpec`:
`GET /api/v1/specifications?journalId=12&fields=codeSpec,draft&page=0&size=50`.
`id` остаётся в каждой строке. Точная форма envelope (список, страница, общее число,
ссылки) фиксируется в контракте v1 до реализации и после этого не меняется молча.

## 5. Запросы `list` и `detail`

### `list`

Имя параметра фильтра, тип, операция и внутренний путь объявлены приложением.
Платформа компилирует только такую декларацию в `Specification<T>`, передаваемую
canonical read path. Неизвестный фильтр, операция, невалидное значение и
неподдержанная сортировка дают `400` до запроса к БД. Первый HTTP-пилот поддерживает
`EQUALS` по скаляру root и по локальному FK association-id (`journalId`) после
проверки, что запрос не обходит защиту целевой сущности. Сортировка первого пилота
ограничена скалярами root и `id`. Переход через to-one к другим полям для фильтра
или сортировки (`nomenclature.typeNom`) требует отдельного решения по правам,
SQL-форме и стоимости; builder может описать такой путь, но каталог не допускает
его к исполнению в профиле первого пилота. To-many-пути и произвольный filter DSL
не поддерживаются; предметный предикат оформляется типизированным SPI, при
необходимости — через `EXISTS`.

Размер страницы ограничен сервером, unpaged-режима нет; сортировка разрешена только
по объявленным ключам и дополняется детерминированным `id`. Сервер также ограничивает
окно offset-пагинации (`page * size + size`), проверяя арифметику до business SQL.
Реализована настройка `platform.rest.read.max-window`: default 10 000 строк,
positive int, не меньше default page size опубликованного ресурса. За окном —
`INVALID_REQUEST`; запланированный HTTP mapping в этапе 4 — `400`. Авторизация
API/root entity может выполнить grant SQL до отказа. Видимый total не обрезается.
Границы подтверждены на H2 в З1; итоговая стоимость проверяется в З4. Ресурс
сохраняет меньший page size; отдельное меньшее окно в builder пока не вводится.
Offset paging достаточен для обычного списка
и не объявляется протоколом синхронизации или стабильным снимком при одновременных
изменениях.

### `detail`

Платформа разбирает id по заявленному типу, проверяет право `DETAIL` и вызывает тот же
canonical read path. Отсутствующая запись и строка, скрытая RLS, дают один `404`, без
различимых деталей ответа. Классовый RLS read deny, который canonical path выражает
пустым чтением, также даёт `404`. Отсутствие права на саму API-операцию обрабатывается
раньше чтения и даёт `403`. Неизвестный/неопубликованный ресурс даёт `404`;
для `list` классовый RLS deny, выраженный пустым canonical чтением, даёт пустую страницу.

Граница `/api/v{major}/**` сначала требует аутентификацию: анонимный запрос получает
`401` независимо от существования ресурса. После аутентификации неизвестная пара
`(resource, major)` даёт `404`; известный ресурс без API-гранта даёт `403` до данных.
Это отдельная матрица HTTP-приёмки, не выводимая из поведения Vaadin deep link.

### Формат HTTP-ошибок

Для отказов REST-контур возвращает `application/problem+json` по
[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html). Клиент различает случаи по
HTTP-статусу, стабильным `type` и прикладному расширению `code`, а не разбирает текст
`title` или `detail`. Для ошибок `400` валидации параметров добавляется публичное имя
параметра; внутренние JPA-пути, имена классов и детали прав в ответ не попадают.
Точный словарь кодов и пример каждого исхода входят в wire-контракт пилота и OpenAPI.

Отсутствующая запись и скрытая RLS запись получают одинаковые статус, `type`, `code`
и текст ошибки. `401` формируется также на границе аутентификации, до поиска ресурса;
`403` не раскрывает данные записи. Контракт тела ошибок проверяется вместе с матрицей
HTTP-исходов. Ошибки декларации при `build()` остаются отдельной диагностикой старта,
а не HTTP-ответом.

## 6. Модель доступа

На каждый запрос последовательно действуют независимые границы:

1. HTTP-аутентификация: нет подтверждённого субъекта — `401`. Адаптер не полагается
   на legacy-значение `"system"` у `RlsCurrentUser` и не выбирает за приложение
   транспорт учётных данных. Платформа предоставляет интеграционный контракт и
   fail-closed wiring; приложение подключает механизм аутентификации.
2. Право использовать канал: для опубликованной тройки `(resource, major, LIST|DETAIL)`
   платформа выводит отдельный стабильный permission id; нет гранта — `403`. Major входит
   в id, чтобы выпуск v2 не давал существующим субъектам новый контракт автоматически.
3. Entity capability и C5 entity read permission: `LIST`/`DETAIL` должны быть
   разрешены типу, а субъекту — чтение сущности. Отсутствие пользовательского
   entity read permission даёт `403` до запроса данных; capabilities типа не являются
   пользовательскими правами.
4. RLS на данных: canonical path применяет действующие class/row gates и predicates.
   Право на API не расширяет видимые строки, в том числе при фильтре по `journalId`.
5. Декларация REST определяет разрешённые поля, фильтры и сортировки.
   Отдельные attribute permissions не требуются. Для используемых ссылок
   сохраняются C5 entity read целевой сущности и её применимые RLS gates.

Декларация ресурса определяет требуемые права, а гранты назначаются через общий
административный механизм пользователям, ролям и сервисным учёткам. API permission
отличается по смыслу от entity read permission: возможность читать запись внутри
приложения не означает разрешения экспортировать её по HTTP. Оба решения должны
использовать общую инфраструктуру C5, а не две независимые базы грантов.

Нынешний `REPORTS:JPQL_PREVIEW` с `AccessService.hasAnyAccess` и CHECK_ONLY — узкий
работающий образец. Он не делает C5 завершённым и не фиксирует CHECK_ONLY как
универсальное представление API-прав. Временный CHECK_ONLY-грант не заменяет C5 для
общего REST-адаптера. Он не открывается до готовности требуемого серверного механизма
прав и выполнения gate этапа C.

## 7. Проекция и canonical read path

Публичная схема не обязана совпадать с `FetchScenario.LIST`/`DETAIL` формы. Для каждой
операции ресурс при старте выводит самостоятельный immutable REST fetch profile
из полных persistent source paths **всех** maximum-полей, включая root scalars,
reference terminals и обязательный id. Запрошенное клиентом подмножество меняет JSON,
но в первом срезе не пересобирает JPA-граф на каждом запросе. Наборы для `list` и
`detail` различаются. Крупные графы — ошибка конфигурации/стоимости, а не повод
грузить коллекции в постраничный список.

Пути проверяются при старте по persistence/metamodel и правилам публикации. REST
не наследует UI FetchPlan, `@Lookup.fetch`, InstanceName или display metadata и
не вызывает их deepen. Capability intent остаётся `LIST`/`DETAIL`; новый
`FetchScenario.API` не вводится. Узкий core SPI/read request передаёт полный профиль
**внутрь** canonical executor, где единственная graph boundary выполняет
`fixed source paths → validate/normalize → explicit graph`. UI/compatibility readers
сохраняют `scenario plan ∪ extras → validate → display deepen once → graph`.
Существующие extras overloads не подменяют новый контракт независимого профиля.

Каждая выбранная to-one получает explicit subgraph до scalar/id terminal; общие
prefixes объединяются. Association-only `fetchRequirements()` каталога не является
полным профилем. Scalar-only и id-only ресурсы получают явный root graph: content и
detail всегда используют `jakarta.persistence.fetchgraph`, count остаётся без него.
Пустой/невалидный полный профиль не включает UI/default fallback. Fetch graph не
заменяет права и не гарантирует SQL column redaction; реальный loaded state и SQL,
включая незаявленные EAGER-связи, проверяются на используемом Hibernate/DB.

Решение закреплено в [ADR-0007 §4.1](decisions/ADR-0007-canonical-data-access-path.md#rest-fixed-fetch-profile)
и [детальном контракте третьего этапа, §4.2.1–§4.2.3](rest-read-api-stage3-security-read-plan.md).
SPI не передаёт `EntityGraph`, `EntityManager` или RLS-предикат прикладному коду.
Выбор точной Java-сигнатуры — отдельный API-review до coding gate.

Чтение и преобразование в ответ выполняются в одной управляемой read-транзакции.
Проверки RLS и загрузка данных остаются у canonical path. REST не обращается
напрямую к repository и не сериализует JPA-объект. Переход через отдельно защищённую
ссылочную цель требует явного правила авторизации; в первом generic-срезе такой
путь не публикуется без подтверждённой проверки. Наличие пути в структурно
проверенной декларации builder само по себе такой проверкой не является.

## 8. Порядок реализации и gate

Детализация первого шага —
[`rest-read-api-stage1-builder-plan.md`](rest-read-api-stage1-builder-plan.md).
Детализация второго —
[`rest-read-api-stage2-catalog-plan.md`](rest-read-api-stage2-catalog-plan.md).
Детализация третьего —
[`rest-read-api-stage3-security-read-plan.md`](rest-read-api-stage3-security-read-plan.md):
серверный C5 read-контур, узкая canonical read-граница, защищённые ссылки и
транзакционная scalar projection без HTTP endpoints. Подготовка плана не закрывает
замечания второго этапа, полный C5 или gate C.

Детализация четвёртого — [HTTP-адаптер и итоговая read-приёмка](rest-read-api-stage4-http-plan.md).
Это последний функциональный этап первого read-среза; пункты «Пилоты» и «Приёмка»
ниже входят в его DoD. Общий C5/C и deployment gate остаются условиями публикации.

Реализация третьего этапа и corrective pass выполнены; Gate 3A имеет evidence,
полная приёмка остаётся открытой. Текущий порядок завершения и критерии закрытия —
[`rest-read-api-stage3-completion-plan.md`](rest-read-api-stage3-completion-plan.md):
окно страниц, согласованное администрирование C5 read grants, реальные роли,
SQL/graph приёмка обоих ресурсов и strict build gates.

1. **Builder и первый контракт.** На `PrdSpec` спроектировать прикладной builder в
   optional `platform-rest` и immutable описание ресурса: ключ/версия, объявленные
   поля и их источники, default/maximum для `list/detail`, фильтры, сортировки и лимиты.
   Локально отвергать дубли и неполную декларацию; зафиксировать примеры внешнего
   контракта. Перед стабилизацией прикладного API проверить, что тем же builder
   описывается `Nomenclature`. Наличие builder не открывает HTTP-маршрут.
2. **Catalog.** Собрать immutable каталог из описаний ресурсов, валидировать версии
   и коллизии ключей, `STANDARD_ROOT`/capabilities, поля, ссылки, фильтры, сортировки
   и fetch paths по metamodel на старте. Необъявленный тип не получает URL.
3. **Security и read contract (параллельно первым двум шагам).** Уточнить permission id
   и гранты в рамках C5, привязку HTTP-субъекта к `RlsCurrentUser`, порядок
   `401/403/404` и отрицательные сценарии. Зафиксировать API-review узкого core read
   SPI, затем реализовать передачу требований загрузки в canonical path, серверное
   применение read-прав и внутренние пилоты с projection/SQL-проверками.
   Это read-потребность в общем C5; его write/action/UI/admin остаток закрывается
   по отдельной очереди C5. HTTP authentication chain относится к следующему шагу.
4. **Read adapter.** Добавить optional `platform-rest-web` без Vaadin-зависимости:
   `GET list/detail`, строгий parsing после API/entity authorization, Basic/TLS,
   request-scoped RLS integration, JSON/Problem Details и generated OpenAPI из
   того же контракта. Ограничения окна/размера, фильтры и проекция исполняются
   существующим server read pipeline через reviewed MODULE_API gateway.
   `platform-rest` сохраняет отсутствие MVC зависимостей; оба starters не
   подключают web add-on автоматически.
   Наличие модуля без деклараций не публикует entity endpoints.
   Подготовка HTTP-контракта и изолированных частей адаптера допустима после
   стабилизации read API параллельно приёмке третьего этапа. Приёмка сквозного
   HTTP-чтения требует закрытых Gate 3A/3B; весь write/action/UI/admin остаток C5
   не является условием разработки адаптера. Публикация маршрутов сохраняет общий gate C5/C.
5. **Пилоты.** Проверить `PrdSpec` с RLS по `JOURNAL` и тип без RLS (например,
   `Nomenclature`) с обязательным API-правом. У обеих сущностей есть owned-секции;
   контракт пилота возвращает только выбранные поля шапки.
6. **Приёмка.** Нужны проверки анонимного входа, отсутствия API- и entity-грантов,
   двух субъектов с разными RLS-грантами, скрытого и отсутствующего id, отсутствия
   автоматической публикации JPA-типа, отказа invalid fields/filters/sort до SQL,
   размера и окна страницы, deterministic paging, query count/N+1, неизменности
   схемы v1 и отсутствия REST routes без optional add-on. Отдельно проверить
   матрицу «анонимный + неизвестный ресурс → 401; аутентифицированный + неизвестный
   ресурс → 404» и приоритет security chains: новый `/api/v{major}/**` не перехватывает
   существующий `@Order(1)` `/api/report-jpql/**`. Wire-контракт первого ресурса
   сверяется с предполагаемым потребителем перед открытием маршрутов. На странице
   из 50 записей с разрешённым to-one alias число SQL-запросов измеряется и
   сопоставляется со страницей из одной записи: оно не должно расти пропорционально
   числу строк. Отдельный count-запрос допустим; состав fetch paths и SQL проверяется
   на реальном пилоте. Проверяются также формат и коды `400/401/403/404`, включая
   неразличимость отсутствующего и скрытого RLS id.

Приёмка серверного read-контура и разработка HTTP-адаптера не привязаны к PostgreSQL.
Реальные JPA/Hibernate-проверки третьего этапа допускаются на H2; перед развёртыванием
тот же набор и schema/grant migrations проверяются на выбранной серверной СУБД.
При её смене эта проверка повторяется; SQL/cost измерения H2 не переносятся автоматически.

Первый gate не включает записи, owned-секции и синхронизацию. Следующий consumer
того же ресурса получает учётку и гранты без нового контроллера. Новый ресурс
получает декларацию; предметный запрос, не выражаемый разрешёнными операциями,
получает типизированный прикладной read service поверх той же security/HTTP-границы.

## 9. Оставшиеся решения и проверки

Узкая canonical read-граница, точные API/entity/attribute keys, scalar/reference
профиль и независимый fixed fetch graph определены и реализованы в этапе 3.
Серверные C5/admin parity, реальные роли, graph/SQL/window budgets и З5 приняты;
HTTP, JSON/Problem/OpenAPI v1, stateless isolation и общие локальные gates закрыты
в [этапе 4](rest-read-api-stage4-http-plan.md), подробности — [evidence 4.7](rest-read-api-stage4-47-evidence-20261006.md).
Остаются внешние условия:

- Общий C5/C и выбор deployment окружения/СУБД с повтором schema/grant/data/security/cost проверок.
- Отдельная consumer учётка, точные grants, HTTPS и включение HTTP opt-in после приёмки.
- Согласование v1 schema, полей/фильтров, int64/nullable и конечного окна с потребителем.
- CI на чистом checkout с versioned/released внутренними зависимостями как отдельный инфраструктурный gate.
- Запись, синхронизация и публикация owned-секций — отдельные срезы.

Эти вопросы не разрешаются автоматически текущими UI-метаданными или `F-INT-2`.
