# F-REST-READ-1: builder декларации ресурса — подробный план

- Статус: проект плана первого среза; реализация и публикация REST ещё не выполнены
- Дата: 2026-10-02
- Родительский план: [`rest-read-api-plan.md`](rest-read-api-plan.md)
- Результат среза: прикладной Java API, создающий структурно проверенное неизменяемое описание
  ресурса; HTTP-маршрутов в этом срезе нет

## 1. Зачем начинать с builder

Прикладной программист должен описать внешний ресурс один раз: стабильный ключ и
версию, набор полей, фильтры и сортировку. Платформа позднее использует одно описание
для каталога, авторизации, чтения, сериализации и OpenAPI. Поэтому форма декларации
определяет границу между платформой и приложением и проверяется до разработки
HTTP-адаптера. Первый опыт — `PrdSpec`; тот же API должен выразить `Nomenclature`.

Этот срез отвечает на вопрос «что приложение публикует». Он не решает, кто получает
грант, как выполняется SQL-запрос и как выглядит HTTP envelope.

## 2. Границы и зависимости

### Входит

- Новый optional артефакт `platform-rest` с прикладным builder и его immutable
  результатом. На этом шаге у артефакта нет Spring Web/Vaadin-зависимостей,
  контроллеров и auto-configuration маршрутов. Он входит в platform BOM и bootstrap
  manifest, но не в зависимости существующих starters; приложение подключает его явно.
- Поля с публичным именем, внешним скалярным типом, nullability/форматом и источником
  значения; один каталог полей внутри декларации, отдельно состав максимальных и
  default-полей для `list` и `detail`. `RestFieldType` принадлежит REST-контракту,
  без зависимости от JPA/Hibernate и UI `FieldType`.
- Именованные фильтры с оператором и источником, разрешённые ключи сортировки,
  сортировка по умолчанию и границы страницы.
- Локальная проверка структуры при `build()` и типизированная диагностика со
  стабильным кодом, ключом ресурса и конкретным элементом декларации.
- Два прикладных примера, проверяющих выразительность API без контроллера и DTO:
  `PrdSpec` с to-one alias и фильтром по журналу; `Nomenclature` с прямыми полями.
- Обозначение публичных API/SPI/internal типов и минимальные сборочные проверки нового
  артефакта в принятом для модулей платформы порядке.

### Следующие срезы

- Каталог всех объявлений и проверка по JPA metamodel/`EntityDescriptorCatalog`:
  существование пути, типы, `STANDARD_ROOT`, read capabilities, to-one ограничения,
  коллизии `(major, resource key)` между объявлениями и защищённые ссылки.
- C5 и HTTP-аутентификация; узкий core read SPI; компиляция фильтров; REST-маршруты,
  DTO-проекция, OpenAPI и интеграционные проверки RLS.
- Запись, синхронизация, owned-секции, произвольные вычисляемые поля, filter DSL и
  автоматическая публикация сущностей.

Builder не назначает гранты и не регистрирует URL. Наличие `platform-rest` в classpath
на этом шаге не меняет HTTP-поведение приложения.
`Nomenclature` в этом срезе проверяет только выразительность декларации;
обязательное API-право для типа без RLS проверяется позднее, вместе с C5 и HTTP.

## 3. Предлагаемый прикладной контракт

Псевдокод для обсуждения имён методов, **не существующий Java API**:

```java
RestResources.publish("specifications", 1, PrdSpec.class)
    .field("id", LONG, path("id"), NOT_NULL)
    .field("codeSpec", STRING, path("codeSpec"), NOT_NULL)
    .field("draft", STRING, path("draft"), NULLABLE)
    .field("comment", STRING, path("comment"), NULLABLE)
    .field("nomenclatureCode", STRING, path("nomenclature.code"), NOT_NULL)
    .field("journalId", LONG, path("journal.id"), NOT_NULL)
    .listFields("id", "codeSpec", "draft", "nomenclatureCode")
    .listDefaultFields("id", "codeSpec", "draft")
    .detailFields("id", "codeSpec", "draft", "comment", "journalId", "nomenclatureCode")
    .detailDefaultFields("id", "codeSpec", "draft", "comment")
    .filter("journalId", EQUALS, LONG, path("journal.id"))
    .sortBy("id", "codeSpec")
    .defaultSort("id", ASC)
    .pageSize(50, 200)
    .build();
```

`field` объявляет поле один раз; `listFields`/`detailFields` ссылаются на его публичное
имя и задают максимальные наборы, `*DefaultFields` — подмножества для запроса без
`fields`. Внешний alias `nomenclatureCode` не является JPA-путём. Фильтр может иметь
то же публичное имя, что и поле (`journalId`), но регистрируется отдельно: возможность
показать поле не включает автоматически право фильтровать по нему. Значение `id`
объявляется явно, входит в максимальный и default-наборы обеих операций и
присутствует в ответе независимо от клиентского `fields`. Его внешний тип и путь
проверит каталог, а C5 attribute read для обязательного `id` проверяется перед
чтением: при запрете вся операция получает `403`.

Рекомендуемая форма регистрации в приложении — `@Bean` с результатом
`RestResourceDefinition<?>`; builder не зависит от Spring. Будущий каталог собирает
такие bean-объявления, а не JPA-типы из classpath. Первый срез закрепляет эту
форму как прикладной контракт и проверяет её fixture с Spring context без
web-сервера. Второй ресурс создаётся таким же способом и не требует нового SPI.

Пилоты проверяют `String` и `Long`; модель внешних типов и ID не исходит из того, что
все сущности имеют `Long` id. В первом срезе фильтр использует только `EQUALS`;
другие операторы добавляются после определения их серверной семантики. Путь
`nomenclature.typeNom` можно хранить в отдельном syntax-fixture, но в первом
HTTP-пилоте фильтр через to-one поле не исполняется. Пути `journal.id` и
`nomenclature.code` иллюстрируют синтаксис декларации: каталог ещё должен проверить
их JPA-смысл, стоимость и права на ссылочную цель. Поэтому исходная декларация
пилота может быть сужена перед публикацией без изменения API builder. Числа страницы
и состав полей в примере не становятся опубликованным `v1` без согласования с
потребителем. Публичные alias и default/max-наборы после публикации входят в
версионируемый wire-контракт; их изменение требует нового major.

## 4. Модель результата builder

`build()` возвращает типизированный `RestResourceDefinition<T>` с:

| Часть | Что хранится |
| --- | --- |
| Идентичность | Публичный ключ, положительная версия, Java type token |
| Поля | Упорядоченные определения: alias, внешний тип, nullability, формат, путь-источник |
| `list` / `detail` | Раздельные максимальные и default-наборы публичных полей |
| Фильтры | Внешнее имя, оператор, тип значения и внутренний путь |
| Сортировка | Разрешённые имена полей и сортировка по умолчанию |
| Страница | Default и максимальный размер |

Результат не хранит Spring bean, `EntityManager`, `Specification`, `EntityGraph`,
сериализатор или security callback. Коллекции копируются; изменение исходных списков
или повторное использование builder не меняет уже построенное описание. Порядок
декларации сохраняется для схемы и диагностики, а сравнение и диагностический вывод
детерминированы. Заявленная nullability до проверки каталогом остаётся утверждением
автора контракта: `build()` не знает JPA mapping и не подтверждает существование
пути, его тип или обязательность всей цепочки to-one ссылок. Scalar `field(...)`
сохраняет своё значение при будущих расширениях; объектная ссылка, если понадобится,
получит отдельный аддитивный метод после предметного примера.

## 5. Проверки первого среза

`build()` проверяет то, что можно определить без JPA и контекста приложения:

Предлагаемый публичный тип отказа — `RestResourceDeclarationException` с устойчивым
кодом, ключом ресурса и именем проблемного элемента. Прикладной код обычно даёт
стартапу упасть; тип и код нужны прежде всего для стабильной диагностики и тестов,
а не для продолжения работы с неполной декларацией. Это ошибка декларации на старте;
формат HTTP-ответов `application/problem+json` относится к последующему REST-адаптеру.

Предлагаемая грамматика: ключ ресурса — `^[a-z][a-z0-9-]*$`, публичное имя
поля/фильтра — `^[A-Za-z][A-Za-z0-9_]*$`, внутренний путь — непустые Java-имена
свойств, разделённые точками. Синтаксис `[]`, `*`, вызовы методов и выражения
запрещены. Окончательные пределы длины и совместимость формата с внешним типом
закрепляются при API-review.

`RestFieldFormat.UUID`, `DATE` и `DATE_TIME` относятся к формату OpenAPI/JSON Schema
для внешнего JSON-типа `string`; они задают формат контракта и сами по себе не
преобразуют Java-значение и не подключают serializer. Поэтому builder принимает их
только для `RestFieldType.STRING`.
Поддержка Java `UUID`, `LocalDate` и `Instant` требует отдельного согласования codec и
покрытия чтения/фильтрации на следующем этапе.

| Проверка | Ожидаемый отказ |
| --- | --- |
| Пустой/небезопасный ключ, неположительная версия, `null` type token | Ошибка декларации с именем ресурса |
| Повтор публичного имени поля/фильтра/ключа сортировки в своём наборе | Ошибка с именем элемента |
| Пустой или синтаксически неверный путь; поле без типа/источника | Ошибка конкретного поля/фильтра |
| Неизвестный оператор или формат, несовместимый с внешним типом | Ошибка конкретного элемента |
| Поле в `list`/`detail` не объявлено; `id` отсутствует в объявлении, maximum либо default любой операции | Ошибка операции |
| Default-набор не является подмножеством максимального; пустой набор | Ошибка операции |
| Сортировка ссылается на неизвестное или не разрешённое для `list` поле | Ошибка сортировки |
| Фильтр конфликтует с системными параметрами (`fields`, `page`, `size`, `sort`) | Ошибка имени фильтра |
| Размер страницы вне положительных границ, выше платформенного потолка либо default больше maximum | Ошибка страницы |

На следующем срезе каталог проверяет содержательное разрешение путей и типов,
заявленную nullability, `STANDARD_ROOT`/capabilities, to-many traversal, коллизии
разных деклараций и допустимость перехода к отдельно защищённой ссылочной цели.
До этой проверки описание нельзя считать безопасным для выполнения запроса.
Builder не принимает готовый `Specification`, произвольный Java callback или путь
от HTTP-клиента. Ошибка `build()` имеет один типизированный контракт с кодом и
контекстом; формулировка сообщения предназначена человеку и может уточняться.

## 6. Порядок работ

1. **Утвердить форму API на двух примерах.** Составить декларацию `PrdSpec` из реальных
   путей `codeSpec`, `draft`, `comment`, `journal.id`, `nomenclature.code` и
   `nomenclature.typeNom` (последний — только syntax-fixture); затем декларацию
   `Nomenclature` с `id`, `code`, `name`, `typeNom`. Зафиксировать major-версию
   ресурса, форму `@Bean`-регистрации, обязательный `id`, независимый `RestFieldType`,
   default/max и платформенный потолок размера страницы. Сначала проверить явные
   списки; сокращающие маркеры на поле добавлять лишь при подтверждённой сложности.
2. **Оформить артефакт.** Добавить `platform-rest` в реестр локальных зависимостей и BOM,
   определить его проверяемые зависимости и публичную поверхность. Не подключать его
   транзитивно через существующие starters. Срез не должен вводить зависимость
   `platform-core` → `platform-rest` или платформы → `org.ip`. Корневой POM приложения
   не агрегирует platform-модули: новый артефакт строится своим `verify` и включается
   в порядок bootstrap, а не считается проверенным после одного root `mvn verify`.
3. **Реализовать builder и immutable definition.** Отделить изменяемое состояние
   построения от результата; сохранить исходные пути как декларативные значения,
   без JPA-запросов, сериализации и регистрации маршрутов.
4. **Добавить локальную валидацию и диагностику.** Все ошибки из §5 выявляются при
   `build()` с устойчивым кодом и контекстом «ресурс → операция/поле → причина»;
   не исправлять неверную декларацию молча.
5. **Проверить прикладное использование.** Позитивные fixture для двух типов, проверки
   отрицательных случаев из §5, неизменяемости результата, `@Bean`-регистрации и
   отсутствия HTTP-маршрутов. Пример прикладного кода требует одну декларацию на
   ресурс и ноль контроллеров/DTO.
6. **Провести API-review.** Зафиксировать роли API/SPI/internal, контракт ошибок
   декларации и список содержательных проверок следующего среза. Согласовать с D3.9 новую
   поверхность `platform-rest`; новый core read SPI и обновление
   `platform-core-surface.txt`/`platform-core.api` относятся к последующему срезу.

## 7. Gate завершения F-REST-READ-1

- Оба примера собираются только с опубликованным builder API, без копирования
  инфраструктурного кода в приложение; один builder описывает оба ресурса. Fixture
  регистрирует `RestResourceDefinition<?>` как Spring bean без веб-сервера.
- `build()` выдаёт неизменяемое **структурно** проверенное описание и ошибки с кодом
  и контекстом для матрицы §5. Содержательная JPA/security-проверка остаётся открытой.
- `platform-rest` есть в `platform-bom/pom.xml` и `scripts/local-dependencies.json`
  с корректными зависимостями, fingerprint и собственным набором тестов; его нет
  в dependency closure существующих starters. Bootstrap `-ValidateOnly` и модульный
  `verify` проходят с зафиксированным результатом.
- Maven Dependency Plugin пишет разрешённый compile-граф `platform-rest` и runtime-граф
  приложения и каждого starter-модуля в JSON до test-фазы. Module composition test проверяет
  весь compile-граф REST (включая транзитивные зависимости); оба starter-теста проверяют
  разрешённое runtime-замыкание своего артефакта; приложение дополнительно проверяет runtime
  ветку Vaadin starter. В starter-графах нет `platform-rest`, в приложении REST остаётся прямой
  опцией. Текстовые проверки POM и импортов дополняют этот gate, а не заменяют разрешение
  зависимостей Maven.
- `platform-rest-surface.txt` классифицирует каждый production-тип модуля; общий
  `platform-rest.api` фиксирует публичные сигнатуры. Типы, названные приложением, также
  получают роли в `platform-public-surface.txt`. Исполняемые surface/dependency-тесты
  подтверждают отсутствие Vaadin, Spring Web, `org.ip`, обратной зависимости из core и
  REST-маршрутов. D3.9 не объявляется закрытым этим срезом.
- Следующий срез получает неизменный API builder и описание ресурса; fixture с
  ссылочными путями может быть сужен после JPA/security-review до публикации v1.
- Известные внешние проблемы общей сборки записаны отдельно, без объявления этапов
  C/F завершёнными. Права на `Nomenclature` здесь не считаются проверенными.

После этого среза остаются обязательными C5, каталог с JPA/startup-проверками,
canonical read SPI и HTTP-приёмка. `F-REST-READ-1` сам по себе не публикует данные.
