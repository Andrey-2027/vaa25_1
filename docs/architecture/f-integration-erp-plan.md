# Этап F: внешние read models и ERP-capabilities

- Статус: запланировано после обязательных gates этапа D; UI-предпосылка — E1
- Дата фиксации: 2026-09-20; трек F-QRY добавлен 2026-11-13
- Область: projection/read-model UI, внешние источники, списки и таблицы по запросу,
  owner semantics, интернированные композиции, бизнес-факты, проведение и регистры

## 1. Контекст и граница решения

Архитектурный разбор мини-приложения по мотивам 1С и интеграции с T-FLEX выявил
пять подтверждённых потребностей платформы:

1. read-only формы над данными, не являющимися локальными JPA-сущностями;
2. владелец как контекст самостоятельной сущности;
3. неизменяемая интернированная композиция owned-строк;
4. бизнес-факт без generic CRUD;
5. ledger проведения с неизменяемыми движениями, остатками и оборотами.

Эти потребности не входят в D3: этап D меняет физические границы и поставку модулей,
но не должен одновременно вводить новое прикладное поведение. До завершения D они
учитываются только как ограничения границ:

- `platform-core` не зависит от Vaadin, `ProjectionFilterGrid`, HQL/JPA `Tuple` или
  конкретной внешней системы;
- projection/report/integration зависимости остаются опциональными и не попадают в
  базовый starter;
- публичный API `platform-vaadin` не закрепляет `Tuple`, HQL либо транспорт внешнего
  источника;
- обычный entity path и projection path не объединяются спекулятивным рефакторингом.

На D3.9 этот план и связанные роли API/SPI должны быть сверены с фактическим составом
артефактов. Реализация начинается после DoD этапа D. D4 reference application служит
приёмочным потребителем готовых возможностей, но не местом их проектирования.

## 2. Предпосылка E1 — capability-aware действия

До внешних read models и ERP-типов стандартные действия форм переводятся на единый gate:

```text
capability типа + resource/RLS decision + обязательный контекст
```

Минимальный контракт поведения:

- `Создать` и `Копировать` требуют `CREATE`;
- `Изменить` требует `UPDATE`;
- при `DETAIL` без `UPDATE` используется действие `Открыть` и read-only форма;
- `Удалить` требует `DELETE`;
- отсутствие обязательного owner/context запрещает создание с явным `blockReason`;
- состояние кнопки не заменяет server-side authorization и capability check.

Это часть E1 «Декларативные действия», а не отдельная ERP-функция. E2/E3 не являются
предпосылкой всего этапа F; диагностика E3 расширяется по мере появления новых
descriptor'ов.

## 3. Трек F-INT — внешние read models

### F-INT-1. Пилот на существующей projection-механике

Первый production-потребитель строится поверх существующего `ProjectionFilterGrid` и
локальной read-only реплики либо отдельного JPA persistence unit:

- `ProjectionListForm` и `ProjectionSelectionForm` дают список, фильтры, сортировку,
  paging, сохранённые виды и выбор строки без CRUD-действий;
- выбор возвращает стабильный составной ключ, а не `Tuple`;
- локальная `ExternalObjectRef` хранит `sourceSystem`, `objectType`, `externalId`,
  `revision` и небольшой display-snapshot;
- способ доступа (`LOCAL_REPLICA`, соседняя БД, позднее REST) не входит в идентичность
  ссылки и предметную модель;
- T-FLEX остаётся владельцем исходных данных; локальная реплика классифицируется как
  `INTERNAL_STORE` и не становится локальным справочником.

Пилот не переделывает `ListForm`/`SelectionForm` и canonical entity path. Общими остаются
UX, `FilterNode`, контекст открытия и сохранённые виды; различаются идентичность строки и
исполнитель чтения.

`ProjectionListForm` и идентичность строки — общая основа F-INT-1 и трека F-QRY (§4).
Первым её строит F-QRY (`platform-query-vaadin`); F-INT-1 переиспользует форму и добавляет
`ProjectionSelectionForm` и `ExternalObjectRef`. Второй projection-список не строится.

### F-INT-2. Storage-neutral projection API

Этот срез начинается только при появлении второго реального backend, которому недостаточно
HQL/JPA. Тогда существующий projection contract разделяется на:

- storage-neutral schema: параметры, колонки, ключ строки и поддерживаемые возможности;
- neutral row: чтение значения по ключу колонки и стабильный row key;
- read request: контекстные параметры, исходный `FilterNode`, paging и sort;
- source/provider, который сам компилирует фильтр в HQL, SQL, REST-запрос либо
  in-memory predicate и явно объявляет неподдерживаемые операции.

Порядок адаптеров: совместимый HQL adapter → JDBC → REST. REST не проектируется по
возможностям HQL: для него отдельно определяются paging, поддержка фильтров, ошибки,
недоступность источника, типы данных и security policy. Generic entity REST из этого
контракта не следует.

## 4. Трек F-QRY — списки и табличные отчёты по произвольному запросу

Источник — обсуждения 2026-11-13 и 2026-11-14. Администратор без выпуска версии создаёт
список на основе произвольного запроса («динамический список» 1С) с типовыми командами
сущности и публикует его в меню. Пользователь строит табличный отчёт **UTR**
(UserTableReport, «Табличный отчёт») по своему запросу. Разработчик встраивает списки по
запросу в формы. Production-пилот для каждого среза выбирается при его старте; без пилота
срез не начинается. Детальный план — локальный `docs/plans/f-qry-work-plan.md`
(редакция 3: пакеты FQ-0–FQ-11, решения Д-Q0–Д-Q9 утверждены 2026-11-14, замечания ревью
2026-11-14).

Порядок срезов: основа (исполнитель с RLS, преобразование в проекцию, форма списка,
хранилище UTR) → F-QRY-3 (UTR) → F-QRY-1 (публикация списка) → F-QRY-2 (команды). Пункт
меню — после СМ-1б и СМ-3; встраивание в формы — после коммитов СМ-0.

### Модель: один запрос, три уровня доверия

| Автор запроса | Хранение | Provenance | Потребитель |
|---|---|---|---|
| Разработчик | код модуля (`QueryListDeclaration`) | `DECLARED` | формы (встраивание), F-INT-1 |
| Администратор | опубликованный документ UTR (JSON) | `REGISTERED` после проверки | F-QRY-1, F-QRY-2 |
| Пользователь | документ UTR (JSON) с видимостью «только я / все» либо разовый запрос на `/queries` | `REGISTERED` после проверки | F-QRY-3 |

Правила модели:

- описание запроса — `QueryDefinition` из `platform-query` (текст либо визуальный
  конструктор); хранимые табличные отчёты и списки — собственный JSON-документ UTR:
  запрос, колонки, отборы `FilterNode`, сортировка, группировка, итоги, режим загрузки,
  видимость, необязательная публикация. Таблицы в БД нет;
- UTR берёт идеи UniDR (строгий JSON-конверт, автор, ревизия, атомарная запись, движок
  общего каталога отчётов), но от UniDR не зависит: печатный рецепт и редактор UniDR
  сделаны под DynamicReports, UniDR не меняется;
- модули `platform-utr` и `platform-utr-vaadin` опциональные, флаг `app.utr.enabled`;
  направление «отчёты → запросы» сохраняется. При выключенном UTR хранилище, каталог и
  маршруты не регистрируются, пункты меню на опубликованные списки становятся
  «устаревшими», а формы с запросами из кода работают;
- проверка одна — `ReportQueryGuard` и C5 `ReportReadAuthorizer`: только SELECT,
  параметры, entity-read и RLS-измерения по всем типам запроса, **только скалярные колонки
  результата**. Выборка сущности целиком допускается лишь после преобразования в
  скалярную схему (идентификатор + представление) с повторной проверкой получившегося
  текста. Подпись представления добавляется после чтения, поэтому у каждой колонки в
  схеме свои возможности: фильтр, сортировка, группировка, агрегат;
- допуск проверяется **на каждое чтение** по текущему пользователю и `AccessGrantVersion`,
  как в `ReportQueryExecutor`; кэшируется только разбор запроса по ревизии документа.
  Строки, загруженные в память, отдаются, пока не изменились пользователь и версия прав;
- исполнение одно по безопасности: RLS-обвязка `RlsFilterActivator.ensureRlsEnabled`,
  readOnly, timeout и maxRows в **той же сессии и транзакции**, что и запрос.
  `HqlExecutor` и `ProjectionGroupValuesService` в `filtergrid-projection` сейчас этого не
  делают, поэтому платформенный исполнитель — обязательная часть основы, а не оптимизация;
- смысл результата сохраняется: отбор сетки склеивается с исходным условием в скобках
  (сейчас `HqlQueryParts` дописывает `AND` без скобок, и исходный `OR` меняет отбор), а
  для запросов с `GROUP BY` / `HAVING` применяется к производной таблице, а не до
  агрегации. Матрица FQ-0 сверяет ожидаемые строки, группы и итоги на H2 и PostgreSQL;
- `Tuple` и HQL не входят в публичный API `platform-vaadin` (ограничение §1);
  преобразование в `ProjectionDefinition` остаётся внутренним;
- `USER_INPUT` намеренно запрещён в `ProjectionDefinition.validate()`, и это правило
  FilterGrid не меняется: сырой текст пользователя в projection-определение не попадает,
  платформа создаёт определение только после проверки. Пользовательские запросы уже
  выполняются на экране `/queries` через guard, C5, RLS и лимиты; UTR добавляет серверные
  отбор, сортировку и группировку, а не новый доступ.

### Ограничение для текущих работ по главному меню

Хранение меню нейтрально: `navigation_entry.function_key` — строка. Виды функций `LIST`,
`LIST_VARIANT`, `CREATE`, `ACTION` уже есть; F-QRY добавляет `QUERY_LIST`
(`query:<ключ списка>`) после СМ-1б и СМ-3. Это смена контракта: `NavigationFunction`
сейчас требует `entityClass`, а диспетчер `ApplicationNavigationCommands` решает и
исполняет по нему. Для `QUERY_LIST` решение даёт допуск запроса текущему пользователю,
исполнение открывает список по ключу. По модели меню М1–М7 пункт кладут в основное и
именованные меню, виден он при наличии допуска. Работы СМ под F-QRY ничего не строят и
соблюдают один принцип: идентичность функции меню не равна классу сущности. Функции из кода
строятся один раз при старте; списки, которые меняет администратор, читаются при
построении меню через кэш индекса публикаций.

### F-QRY-1. Опубликованный список администратора

- список — документ UTR с разделом публикации (ключ, заголовок, основная сущность,
  колонка объекта команды, режим загрузки — по умолчанию `LAZY`). Публикует только
  администратор: роль
  проверяется на сервере при каждой записи раздела; публикуется только свой общий
  документ; импорт с публикацией без права отклоняется;
- представление — общая `ProjectionListForm` с отборами, сортировкой, группировкой и
  сохранёнными видами; открытие по ссылке `query-list/<ключ>`; экран администратора
  «Списки по запросу» с состоянием проверки;
- пункт меню — функция `query:<ключ>`; снятая публикация или выключенный UTR оставляют
  пункт в существующем состоянии `stale`;
- права: в первой версии своего права на список нет — пункт и форма видны, если запрос
  разрешён пользователю; данные защищены entity-read, C5 и RLS при каждом чтении;
- дрейф схемы: при старте и по требованию документ проверяется guard, C5 и
  преобразованием; невалидный список недоступен с диагностикой вместо ошибки при открытии.

Security tests до production path: пользователь без доступа к затронутой сущности получает
отказ; при частичном доступе строки, count, итоги, группы и distinct отфильтрованы, в том
числе через join, подзапрос, CTE и производную таблицу; отзыв прав при открытой форме
действует со следующего чтения; timeout и maxRows срабатывают; H2 и PostgreSQL.

### F-QRY-2. Типовые команды по основной сущности

- объект команды — отдельная проверенная колонка «идентификатор типа X»: из анализа
  известно, что колонка — `alias.id` сущности X. Она может не совпадать с ключом строки
  (строка накладной → накладная);
- Создать / Открыть / Изменить / Удалить — существующие формы элемента и gate E1
  (`CREATE`/`UPDATE`/`DELETE`); ручная привязка «команда → поле результата» не вводится;
- перед выполнением объект перечитывается каноническим чтением с RLS; не виден — отказ;
- колонка-ссылка с типом сущности даёт команду «Открыть <тип>»; для этого `DataType.REF`
  и `ColumnMeta` получают тип сущности (сейчас REF — строка);
- нет колонки объекта — команды над объектом недоступны с явным `blockReason`;
  «Создать» строки не требует;
- запись идёт только через canonical write path сущности, не через проекцию; после команды
  список перечитывается, и отсутствие строки в результате запроса — штатное поведение.

### F-QRY-3. Табличный отчёт пользователя (UTR)

- отдельный продукт «Табличный отчёт»: экран, где сетка сама служит редактором колонок,
  отборов, группировки, сортировки, итогов и режима загрузки; запрос и параметры —
  существующий редактор и конструктор запроса; входы — `/queries` («Открыть как табличный
  отчёт») и общий каталог отчётов, где UTR — отдельный движок;
- кто пишет запросы — действующее правило `/queries` (любой аутентифицированный
  пользователь, права на данные проверяют guard и C5); отдельное право на текст запроса —
  самостоятельное решение владельца, не часть F-QRY-3;
- лимиты обязательны: timeout, maxRows, лимит колонок, readOnly;
- режим загрузки по умолчанию — `LAZY` и для отчёта, и для опубликованного списка: строки,
  счётчик, итоги, группы и distinct считаются по всей отфильтрованной выборке. `HYBRID` —
  только по явному выбору для тяжёлых агрегирующих запросов: при усечении он показывает
  не больше N строк, а итоги и группы считает по всей выборке, и экран пишет об этом явно.
  `IN_MEMORY` — по явному выбору для сложного долгого запроса: он выполняется один раз,
  а отбор, сортировка, группировка и итоги идут в памяти по полному набору. FilterGrid
  требует для этого режима загрузки без предела, поэтому предел строк ставит платформа:
  сверх предела — отказ с предложением сменить режим, а не тихое усечение; доступны только
  отборы, вычислимые в памяти. Квота запусков — для материализации `HYBRID` и `IN_MEMORY` и
  для выгрузки, не для страниц `LAZY`; глубина группировки
  ограничена, потому что ленивое дерево делает отдельные `countDistinct` и `fetchDistinct`
  на каждый узел;
- ключ строки выводится, только если уникальность доказуема по анализу запроса: корень
  `FROM` — сущность и все соединения к одному → её идентификатор; запрос с `GROUP BY` →
  колонки группировки (NULL — допустимое значение группы). Соединение к многим повторяет
  идентификатор сущности, поэтому ключа нет. Без ключа отчёт только для чтения, порядок
  страниц — по всем колонкам, счётчики групп — `COUNT(*)` (сейчас FilterGrid считает по
  первой колонке ключа и пропускает NULL);
- личные отчёты — видимость «только я»: чужой не виден ни в каталоге, ни по ссылке, ни в
  копии и выгрузке; уникальность названий — раздельно для общих и личных;
- выгрузка XLSX и CSV — собственная, серверным запросом по всей отфильтрованной выборке
  с пределом строк и явным сообщением при превышении. Рендер UniDR не используется: он
  работает с печатным рецептом и поддерживает только PDF и XLSX.

### Встраивание в формы

- Список по запросу — второй вид встроенного списка рядом с AF6: в карточке
  `l.queryList(id, ключ)` с привязкой параметров (`l.self()`, `l.value(path)`), в форме
  списка — подчинённая панель по текущей строке. В описании формы — ключ и привязки, а не
  текст запроса: публичный API `platform-vaadin` не закрепляет HQL и `Tuple`.
- В первой версии форма ссылается только на запросы, объявленные в коде
  (`QueryListDeclaration`): так она не зависит от UTR и от правок администратора.
  Программный вход для произвольных экранов — `QueryLists.create(ключ)`.
- Строка — один объект сущности → встроенный список сущности AF6; строка — агрегат,
  соединение или внешние данные → список по запросу.

## 5. Трек F-ERP — предметные platform-driving сценарии

### F-ERP-1. Справочники с владельцем

Владелец вводится как отдельная capability, а не как новый `EntityExposure` и не как RLS:

- один обязательный типизированный owner в первой версии;
- owner неизменяем после создания;
- нумерация и уникальность кода могут быть scoped по owner;
- owner-context даёт fixed filter, initial value и обязательный контекст создания;
- dependent reference constraints одинаково действуют в autocomplete, selection form
  и canonical write;
- удаление владельца учитывает существующие обратные ссылки;
- владение не выдаёт права автоматически и не включает cascade delete по умолчанию.

Пилоты: операция и карта комплектации принадлежат матрице; компонент принадлежит карте.

### F-ERP-2. Неизменяемые интернированные композиции

ADR-0008 расширяется подтверждённым сценарием `НаборРаспространений`:

- композиция канонизируется предметным кодом и создаётся через `findOrCreate`;
- порядок строк не влияет на идентичность;
- head и owned-строки создаются атомарно один раз;
- generic `UPDATE`/`DELETE` отсутствуют, изменение реализуется copy-on-write;
- новый явный section mode описывает create-once/immutable семантику; стандартный
  `replaceAll` для неё запрещён;
- digest может ускорять поиск, но совпадение canonical payload остаётся обязательной
  проверкой от коллизии.

Механизм вводится на живом пилоте и затем применяется к существующим аналогичным случаям;
универсальный DSL предметной канонизации не создаётся.

### F-ERP-3. Бизнес-факты без generic CRUD

Уточнение ET6 (2026-10-26): [ADR-0029](decisions/ADR-0029-entity-semantic-classification.md) разрешает действующий
INFORMATION_REGISTER только из проверенного RegisterDescriptor. Ограничение ниже
на production-примеры больше не блокирует runtime kind; требования к предметным
операциям и статус пилотов сохраняются. Прежний текст ниже описывает исходное решение.


Связь «Операция использует карту комплектации» сначала реализуется как конкретный
`INTERNAL_STORE` с типизированным сервисом:

```text
attach / detach / replace / find
```

Операции идемпотентны, `replace` атомарен, а принадлежность операции и карты одной матрице
проверяется на сервере и ограничениями схемы. Generic формы и canonical CRUD для записи
не выдаются.

Общий `EntityKind.INFORMATION_REGISTER` и универсальная metadata-модель не вводятся по
единственному случаю. Повышение до платформенного регистра сведений требует второго
production-примера с совпадающей семантикой. Если у связи появляются собственные атрибуты,
период действия или независимый lifecycle, она становится обычной ассоциативной сущностью.

### F-ERP-4. Проведение и ledger

Проведение и регистры накопления являются отдельной подсистемой рядом с entity CRUD:

- документ-регистратор получает posting capability и состояния `DRAFT`/`POSTED`;
- `PostingBatch` и движения неизменяемы;
- `post`, `unpost` и `repost` идемпотентны по command id и выполняются атомарно с
  изменением состояния документа;
- отмена создаёт reversal batch, а не удаляет историю;
- хранятся хозяйственное время (`effectiveAt`) и время записи (`recordedAt`);
- read API предоставляет остатки на дату и обороты за период;
- RLS и resource permissions применяются до агрегации;
- проведённый документ нельзя менять или удалять обычным canonical write path;
- материализованные остатки не являются источником истины и добавляются только после
  профилирования с возможностью полного восстановления из движений.

Ledger получает собственный descriptor/engine. Движение не становится обычным новым
`EntityKind`: отсутствие generic CRUD здесь является частью модели, а не UI-настройкой.
Первый пилот — `ЗапускВПроизводство`; точные измерения и ресурсы сверяются с исходной
конфигурацией до schema migration.

## 6. Порядок и gates

Внутри каждого трека порядок строгий; F-INT и F-ERP могут развиваться независимо после E1
и DoD этапа D. F-QRY опирается на закрытый E1 и опциональные query-модули; старт принят
владельцем 2026-11-13 — этап D он считает фактически завершённым (Д-Q0 детального плана).
Внутри F-QRY пункт меню ждёт СМ-1б и СМ-3, а встраивание в формы и
команды — коммитов СМ-0:

```text
D завершён
  -> E1 capability-aware actions
  -> F-INT-1 (переиспользует форму F-QRY) -> F-INT-2 при втором backend
  -> F-ERP-1 -> F-ERP-2 -> F-ERP-3 -> F-ERP-4

E1 + query-модули (Д-Q0)
  -> основа: исполнитель с RLS, преобразование, форма списка, хранилище UTR
  -> F-QRY-3 табличный отчёт UTR -> F-QRY-1 публикация списка -> F-QRY-2 команды
  (пункт меню — после СМ-1б и СМ-3; встраивание в формы — после коммитов СМ-0)
```

Каждый срез:

- начинается с одного production-пилота и формулирует минимальный платформенный контракт;
- имеет behavioural, security и architecture tests до переключения production path;
- не добавляет ERP-классы и имена внешних систем в platform modules;
- не расширяет generic CRUD для типов, которыми владеет специализированная подсистема;
- при изменении схемы включает миграцию и проверку конкурентных сценариев;
- фиксирует AppDev-first impact и не требует ручной инфраструктурной регистрации для
  стандартного случая.

## 7. Отложено осознанно

- единая форма, автоматически выбирающая entity/projection backend;
- универсальный REST-конструктор запросов;
- пользовательские запросы (`USER_INPUT`) к внешним источникам F-INT;
- запись данных из projection-строки в обход canonical write path сущности;
- ручная привязка произвольных команд к полям результата запроса;
- импорт рецептов UniDR в UTR и перевод UniDR на общее с UTR файловое хранилище;
- ссылка формы на опубликованный администратором список (в v1 — только запросы из кода);
- полиморфные и множественные владельцы;
- общий information-register framework до второго подтверждённого случая;
- материализованные остатки до измеренной потребности;
- автоматическое удаление осиротевших интернированных композиций;
- перенос терминологии и устройства 1С в `EntityKind`/`EntityExposure` без собственного
  платформенного поведения.
