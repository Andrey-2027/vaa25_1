# Командный интерфейс — пользовательская проба КИ-5

Пилот использует настоящее приложение, PostgreSQL и обычный вход с паролем.
Учётки, профили и тестовая вложенность создаются отдельным opt-in launcher из
`scripts/navigation-pilot/java`; этих классов нет в приложении при обычной сборке.
`platform.navigation.enabled` в стандартных настройках остаётся `false`.

## Запуск

Нужны Java 21, Maven, PostgreSQL 17 с доступом к созданию БД, Node.js и уже
установленные frontend-зависимости. Параметры PostgreSQL берутся из локального
игнорируемого `config/application-local.properties`: URL должен быть локальным,
без query-параметров. Настроенная там рабочая БД не является целью записи.

Из корня репозитория в PowerShell:

```powershell
./scripts/run-navigation-pilot.ps1
./scripts/run-navigation-pilot.ps1 -Action Status
```

При первом запуске создаётся новая `navigation_pilot_<UUID>`, применяется
`platform-navigation/src/main/resources/db/navigation-postgresql.sql`, остальная
схема создаётся Hibernate `update`. После сообщения `NAVIGATION_PILOT_READY` в
`outputs/navigation-ki5/server.log` запуск готов. `Status` фиксирует успешную
подготовку; последующие старты используют `ddl-auto=validate`.
Сборка/запуск пишут журналы в `outputs/navigation-ki5`; первый dev-старт Vaadin
может занять несколько минут. Скрипт не скачивает Maven-зависимости (`-o`).

Откройте [пилот](http://127.0.0.1:8087/). Учётки: `ki-admin`, `ki-a`, `ki-b`.
Общий случайный пароль находится только в локальном игнорируемом
`config/navigation-pilot.password.local`. Получить его для входа:

```powershell
Get-Content ./config/navigation-pilot.password.local
```

Пароль и PostgreSQL-реквизиты не включаются в документацию, launch args или
состояние в репозитории. Не добавляйте локальные config-файлы в Git.
Доступен только loopback `127.0.0.1`, не сетевой интерфейс компьютера.

```powershell
./scripts/run-navigation-pilot.ps1 -Action Restart -SkipBuild
./scripts/run-navigation-pilot.ps1 -Action Stop
```

Read-only сверка исходных восстановленных назначений и одинаковых прав:

```powershell
./scripts/run-navigation-pilot.ps1 -Action Verify
```

После собственных экспериментов с назначениями сначала верните профили А/Б
из таблицы ниже: Verify намеренно проверяет именно эту исходную конфигурацию.

Перезапуск сохраняет данные и изменения администратора. Stop проверяет, что PID
принадлежит именно этому launcher, и останавливает только его. БД сохраняется.
Если нужно пересобрать исходники, опустите `-SkipBuild`. Пути Java/Maven/Node/PG и
порт можно передать параметрами скрипта. Скрипт не заменяет существующую БД.

Для проверки выключенного режима после успешной подготовки:

```powershell
./scripts/run-navigation-pilot.ps1 -Action Restart -SkipBuild -NavigationDisabled
# После проверки вернуть профильное меню:
./scripts/run-navigation-pilot.ps1 -Action Restart -SkipBuild
```

## Данные и права

А и Б имеют одну роль `KI_READER` и одинаковые grants чтения единиц измерения,
спецификаций и строк JOURNAL. Операции изменения им не выдаются. На приходные
документы не выдано чтение, хотя оба профиля явно требуют SHOW этого пункта.
У администратора есть явное чтение User/Role для штатного поиска и назначения.
Создание Role/User/единицы проходит `EntityDataAccess` от отдельного субъекта
подготовки с явными read/operation/password/role grants. Финальная граница
записи включена. Навигационные профили и назначения создаются защищённым API.

UI-пилот отключает отдельный REST web adapter и использует предусмотренный
`RlsReadableIdsResolver`, делегирующий штатному `AccessService` без session cache:
это позволяет готовить данные до первого HTTP-запроса. C5/RLS не обходятся.
REST API не входит в эту приёмку.

| Учётка | Профиль | Единицы | Спецификации | Тестовый потомок |
| --- | --- | --- | --- | --- |
| ki-a | Пилот А — справочники | SHOW | HIDE | SHOW, включая скрытую developer default плитку |
| ki-b | Пилот Б — производство | HIDE | SHOW | HIDE родителя блокирует SHOW плитки |

«Тест вложенности» — только метаданные с непустыми родителем и потомком;
тестовые плитки не открывают CRUD-форм. Это не изменение прикладной принадлежности
сущностей. Существующая «Документы / Производство» пуста и по правилам удаляется
из итогового меню. Бизнес-проба использует настоящие «Справочники»/«Производство».

## Сценарий

1. Войти как `ki-admin`, открыть «Администрирование → Интерфейс». Проверить
   профили и предпросмотр; он явно показывает состав **до** прав пользователя.
2. Открыть два независимых входа: `127.0.0.1:8087` для А и `localhost:8087` для Б
   (разные host cookies). Для третьей сессии администратора можно использовать
   `localhost.:8087` — этот вариант также проверен в браузере. Проверить различие
   плиток по таблице и отсутствие «Приёмно-сдаточных накладных» у обоих.
   У обычного пользователя нет админ-вкладки.
3. У А открыть «Тест вложенности»: видны обе группы. У Б — только родитель;
   скрытый потомок отсутствует и в меню, и на странице предка.
4. У Б открыть разрешённую прямую ссылку на единицы: скрытие не запрещает данные.
   Прямая ссылка на приходные документы должна показать отказ чтения.
5. Администратором создать профиль, изменить видимость, сохранить, назначить
   пользователю из поиска. После обновления его страницы меню меняется;
   второй уже открытый UI сохраняет свой снимок и назначение.
6. Снять назначение: после обновления работают defaults. Повторно назначить.
   Сбросить профиль к настройкам разработчика: overrides исчезают, назначение
   сохраняется. После пробы вернуть исходные настройки таблицы.
7. Перезапустить приложение; войти снова и проверить оба меню и назначения.
   Запуск проходит `validate` ранее созданной PostgreSQL-схемы.
8. Проверить выключенный режим и вернуть включённый. Остальные служебные и
   legacy-пункты не регулируются профилем — это граница первого пилота.

Результаты конкретного прогона: [evidence КИ-5](evidence/command-interface-ki5-20261010.md).
Изменения применяются после обновления страницы или нового входа. Проба не
обещает live-update, массовые назначения, удаление профилей, миграции ID или
готовность для промышленного развёртывания.
