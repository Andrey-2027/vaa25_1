# ADR-0026: payload команды доходит до lifecycle-хуков поддержанным механизмом платформы

Дата: 2026-10-16. Статус: принято, реализовано и проверено срезом S5(б) плана выноса — измерения и
протоколы в [evidence](../evidence/register-s5b-command-payload-20261016.md).

- Область: граница lifecycle-контракта (`EntityLifecycle`, `EntitySaveContext`) — как команда
  доносит свой payload (позиции документа) до `beforeSave`/`onSave` своей сущности.
- Связанные решения: [ADR-0005](ADR-0005-entity-lifecycle-and-application-behavior.md) (единая
  точка `EntityLifecycle`), [ADR-0007 §5](ADR-0007-canonical-data-access-path.md)
  (canonical write pipeline), [ADR-0019](ADR-0019-owner-named-row-operation.md) и
  [ADR-0020](ADR-0020-register-recorder-procedures.md) (набор владельца, процедуры),
  [ADR-0025](ADR-0025-row-lifecycle-on-recorder-set.md) (хуки строки, тождество callback'а).
- Этап плана: [план выноса §5, S5(б)](../information-register-extraction-plan.md) — последний
  прикладной долг среза S5; ADR-0024 §2.4 (имена операций) закрыт предыдущим заходом того же дня.

## Что было и почему требуется решение

`EntityLifecycle` обещает прикладному коду точки `beforeSave`/`onSave`, но у контракта нет
поддержанного способа донести до них payload команды: `EntitySaveContext` несёт сущность и
`EventContext` — и всё. Aggregate-путь знает позиции документа (`MetadataDrivenAggregateSaveService`
собирает `eventSections` из подключённых секций и контрибуций) и отдаёт их только
`beforeAggregateSave` — редкому хуку уровня всего агрегата. Хуки самой сущности остаются без данных
команды, хотя именно они порождают строки регистра.

Приложение компенсировало это своим механизмом: `AccountingObjectSaveScope` — ThreadLocal, открываемый
командой (`AccountingObjectSaveService.save`), с двумя проверками: `require(document)` по тождеству
экземпляра в `beforeSave` и `lines(document)` в `onSave`, где тождества уже недостаточно и
добавляются сравнение `id` и Hibernate-класса («update возвращает managed copy»).

| # | Замер | Значение |
| --- | --- | --- |
| M1 | прикладной механизм | `AccountingObjectSaveScope` — 37 строк: ThreadLocal, тождество, сравнение `id` + `Hibernate.getClass`; рядом `AccountingObjectContribution` (12 строк) с `Line(nomenclatureId, accountingTypeId)` — копией строк секции |
| M2 | кто знает позиции | команда (передаёт секцию) и платформа (`MetadataDrivenAggregateSaveService` строит `eventSections`); `EntityLifecycleRegistry` (platform-events) строит `EntitySaveContext` и знает только сущность и `EventContext` |
| M3 | какие экземпляры видит хук | `beforeSave` — экземпляр команды, `onSave` — результат `entityManager.merge` на обновлении (`CanonicalWriteExecutor:543`); поэтому приложение и сравнивает `id` с Hibernate-классом |
| M4 | существующий механизм тождества | `AggregateSaveLifecycleScope` (52 строки) и `CanonicalSaveLifecycleScope` (52 строки): недоказуемый извне токен, проверка по тождеству сущности **и** экземпляра `EventContext`, закрытие в порядке открытия, истечение; `RegisterRecords.forRecorder` — единственный владелец права записи |
| M5 | цена «внутри команды» | `AccountingObjectPilotIT.genericHeaderAndRegisterWritesAreClosed` подаёт прямой `aggregateSave.save(document, секция с позициями, EventSource.UI)` и ждёт отказа с текстом про команду: вето означает «внутри команды», а не «есть позиции» |
| M6 | прикладных lifecycle-хуков | 12 (ADR-0025 M1); все они получают `EntitySaveContext` без payload |

## Рассмотренные варианты

1. **Оставить прикладной ThreadLocal.** Отклонён: механизм дублируется в приложении; корректность
   держится на том, что каждая команда вспомнит открыть scope; эвристику (`id` + Hibernate-класс)
   пишет сторона, которая managed copy не создавала, хотя знает о ней единственная платформа; новый
   документ с позициями копирует обвязку целиком.
2. **Платформа выводит payload из секций операции.** Отклонён измерением M5: прямой aggregate save
   с подключённой секцией позиций обязан быть отвергнут — если payload считать из секций, вето молча
   ослабнет до «есть позиции» и перестанет отличать команду от прямого сохранения. Позиции в секции
   и позиции команды совпадают не всегда (форма передаёт свои строки), поэтому вывод «по наличию»
   был бы догадкой, а не свидетельством.
3. **Протащить payload параметром сохранения.** Отклонён по цене: поле в `EntitySaveContext` заполняет
   `EntityLifecycleRegistry` (platform-events), который не может зависеть на platform-core, значит его
   пришлось бы тянуть через SPI или через все вызовы сохранения (50 вызовов `.save(` в production-коде);
   пути repository-aspect и flush-listener (последний рубеж) payload не несут вовсе. Ребро контракта
   дороже, чем польза на одном пути.
4. **Объявление команды через механизм scope'ов.** Выбран этот вариант.

## Решение

1. **Команда объявляет payload один раз, платформенным API.** `AggregateCommandPayload.open(owner, sections)`
   возвращает handle, у которого приложение не может ничего, кроме `close()`: ни прочитать, ни подменить
   владельца, ни связать копию. Ни ThreadLocal, ни эвристик в приложении не остаётся (закрывает M1).
2. **Платформа владеет тождеством.** Хук читает payload как `AggregateCommandPayload.of(context)`.
   Payload виден только для объявленного владельца и — на aggregate-пути — для managed copy, которую
   произвела сама платформа: `MetadataDrivenAggregateSaveService` связывает результат `merge` с открытым
   объявлением (`bindManagedCopy`) сразу после сохранения корня. Приложение не сравнивает ни `id`, ни
   Hibernate-класс (закрывает M3).
3. **Механизм обобщён, а не размножен.** Дисциплина callback-scope'ов crud-пути (поток-владелец,
   закрытие в порядке открытия, вложенность, истечение, чтение по тождеству) вынесена в одну
   реализацию, которой пользуются оба scope'а: объявление payload и свидетельство владельца
   (`AggregateSaveLifecycleScope`). `CanonicalSaveLifecycleScope` остаётся вторым применением той же
   дисциплины в своём пакете — это названная граница, а не третий ThreadLocal.
4. **Семантика вето сохраняется дословно.** `beforeSave` документа по-прежнему отвергает сохранение вне
   команды тем же текстом; тест M5 остаётся зелёным без ослабления, потому что объявление открывает
   только команда.
5. **Payload — read-only данные, а не право.** Права записи требует `RegisterRecords.forRecorder`
   (токен, `entityManager.contains`, активная транзакция, истекающий handle) — payload этого не даёт и
   не заменяет. Хуку строки регистра payload не виден: тождество сверяется с владельцем объявления.
6. **Приложение перестаёт дублировать позиции.** `AccountingObjectContribution.Line` и сам
   `AccountingObjectContribution` удаляются: команда собирает payload и секцию из одного и того же
   списка позиций, а `onSave` читает их из payload. Расхождение «объявленные позиции ≠ сохранённые
   строки» становится невозможным по построению, а не по договорённости.

## Приёмка

| Критерий | Чем доказано |
| --- | --- |
| payload виден хукам своей операции, включая обновление с merge | платформенный тест объявления и app-IT пилота: обновление документа меняет набор строк ровно один раз |
| вне операции payload пуст | тест: чтение после `close`, без объявления и на чужой сущности — пусто |
| «внутри команды» остаётся отличающим признаком | `AccountingObjectPilotIT.genericHeaderAndRegisterWritesAreClosed` (прямой aggregate save с позициями отвергнут) |
| managed copy связывает платформа, а не приложение | платформенный тест связи + app-IT обновления; в приложении нет ни сравнения `id`, ни Hibernate-класса |
| закрытие не в порядке открытия — отказ | платформенный тест: внешний scope после внутреннего → `IllegalStateException` |
| вложенность: внутренний перекрывает, внешний восстанавливается | платформенный тест вложенных объявлений |
| payload неизменяем | платформенный тест: `sections()` и строки секции read-only |
| приложение без своего механизма | замер: файл scope'а удалён, `ThreadLocal` и `Hibernate.getClass` в пилоте — 0 |

## Границы

Не решается здесь: payload для ключевого пути (`RegisterKeyWrites`/`RegisterKeyChanges`) — у него нет
позиций документа, хуки там получают пусто; `afterCommit` — cкоуп закрыт к моменту commit, payload
остаётся свидетельством внутри транзакции; `AggregateSaveContribution` не заменяется и не отменяется —
это серверный payload для записи секций, участников и отката, у него своя роль; перебазирование
`CanonicalSaveLifecycleScope` на общую реализацию названо, но не входит в срез; payload виден хукам
владельца, а не строкам, — правило строки и её контекст решены ADR-0025.
