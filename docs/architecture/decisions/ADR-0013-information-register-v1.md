# ADR-0013: информационный регистр v1 — минимальный контур на примере `ЦеныНоменклатуры`

> Уточнение 2026-10-05: текущая реализация использует LocalDateTime и календарную периодичность.
> Временной контракт и переход схемы: [период и периодичность](../information-register-periodicity.md).
> Ниже сохранено описание соответствующего этапа до этого уточнения.

- Статус: принято; реализация v1.0 завершена с оговорками проверки ниже
- Дата: 2026-10-03
- Область: декларация регистра (`@RegisterMetadata`), стартовая валидация, сущность-пилот, чтение точкой
- Связанные решения: ADR-0004 §1 (kind зарезервирован, семантика «не имитируется обычным CRUD
  заранее»), ADR-0008 (две оси: kind и capability — регистр не интернированный тип), ADR-0007
  (canonical data path), `f-integration-erp-plan.md` F-ERP-3 (см. §6)

## Контекст

ADR-0004 зарезервировал `INFORMATION_REGISTER` без семантики. Чтобы проектировать срез последних,
виртуальный источник конструктора, запись и регистр накопления, нужен первый реальный регистр.
Составной пилот (`ИзмененияКомпонентовПоРаспространениям`: измерение — интернированный набор
распространений, чтение через диапазоны номеров) отложен: он проверяет сразу слишком много.
Пилотом выбран простой собственный регистр `ЦеныНоменклатуры`: в модели нет поля цены, конфликтовать
не с чем.

## Решение

### 1. Объём v1.0

Входит: модель регистра (`NomenclaturePrice`), декларация, стартовая валидация (код и unit-тесты),
охранник неизменяемости ключа, запись обычным CRUD, чтение точкой `getLast(измерения, asOf)` и тест
против наивного расчёта в памяти («оракул»).

Не входит и не обещается: `upsert` и конкурентная запись (владелец транзакции, ретрай конфликта —
отдельный ADR после спайка на PostgreSQL), срез как источник конструктора и параметр LIST,
условия по ресурсам «до среза», регистратор и движения, регистр накопления, RLS-измерения,
валюта и тип цены.

### 2. Декларация

```java
@RegisterMetadata(dimensions = "nomenclature", period = "period", resources = "price")
```

Ключ записи — измерения, затем период (если он задан). Имена — имена Java-полей. Технический `id` из
`BaseEntity` сохраняется; бизнес-уникальность ключа обеспечивает `@Table(uniqueConstraints)`.
В v1 поддерживается JPA field access; property/mixed access отклоняется явно.

### 3. Правила валидации

| Код | Правило |
|---|---|
| `NOT_ENTITY` | тип — `@Entity` |
| `UNSUPPORTED_ACCESS` | JPA использует доступ через поля, без property/mixed access |
| `NO_DIMENSIONS` / `NO_RESOURCES` | есть хотя бы одно измерение и один ресурс |
| `FIELD_MISSING` / `DUPLICATE_FIELD` | поля существуют и названы один раз |
| `FIELD_NOT_PERSISTENT` | поле объявлено в `@Entity`/`@MappedSuperclass` и не является static, Java transient или `@Transient` |
| `PERIOD_TYPE` | период — `LocalDate` |
| `KEY_COLUMN_NAME` | колонка поля ключа названа явно (naming strategy не угадывается) |
| `KEY_NULLABLE` | колонка ключа явно объявляет `nullable = false`; primitive-тип и `optional = false` не заменяют это правило |
| `KEY_UPDATABLE` | поле ключа `updatable = false` |
| `UNIQUE_MISSING` | есть `uniqueConstraint` ровно по колонкам ключа в порядке «измерения, период»; тот же индекс обслуживает будущий срез |

Валидатор проверяет декларации аннотаций, а не фактическую схему БД: наличие физических
ограничений и индексов должно проверяться при внедрении сущности и схемы. `updatable = false`
исключает колонку из JPA UPDATE; запрет попытки изменить ключ на сервере и поведение формы
существующей записи проверяются отдельно при реализации записи.

### 4. Запись в v1.0

Дополнение Р8, 2026-10-09: [ADR-0021](ADR-0021-register-key-change-command.md)
вводит отдельную opt-in команду смены измерений / периода с сохранением ID.
У opt-in регистров JPA ключ writable, обычный UPDATE остаётся закрыт lifecycle
и Hibernate snapshot guard. Правило updatable=false ниже сохраняется по умолчанию
для регистров без этой capability; неизменяемые похожие сущности не расширяются.

Обычные ListForm/ItemForm и canonical CREATE/UPDATE. Дубль ключа ловит unique-индекс;
общий ItemForm преобразует SQLState `23505` / `DuplicateKeyException` в понятное сообщение,
сохраняя исходную причину ошибки. NOT NULL не классифицируется как дубль. Гарантий
конкурентной записи v1.0 не даёт и не декларирует.

Неизменяемость ключа охраняет `NomenclaturePriceLifecycle.beforeUpdate`: колонки ключа
`updatable = false`, и без охранника правка номенклатуры или периода в форме «сохранялась» бы только
в памяти (UPDATE этих колонок не содержит). Охранник — lifecycle-точка, поэтому действует одинаково
для canonical записи из формы, REST и импорта. Если отдельного исходного снимка нет,
сохранение отклоняется: сравнение managed-объекта с самим собой не подтверждает неизменяемость
ключа. Схему создаёт Hibernate (`ddl-auto=update`), отдельного SQL нет.

### 4a. Чтение точкой

`RegisterReader<T>.getLast(Map<String, ?> измерения, LocalDate asOf)` требует полный набор
измерений и периодический регистр: измерения равны, `period <= asOf`, сортировка по периоду по
убыванию, первая строка. Конструктор проверяет декларацию через `RegisterMetadataValidator`:
ошибка декларации не даёт поднять бин, который читает регистр.

Чтение идёт через публичный canonical `EntityDataAccess.list`: сохраняются C5, RLS, экспозиция
типа, FetchPlan и телеметрия. Прямой `JpaSpecificationExecutor.findBy` сохранял бы repository
RLS, но обходил бы остальные проверки canonical read. Текущий paged API выполняет выборку с
лимитом 1 и отдельный count-запрос; оптимизация до одного запроса требует отдельного bounded
canonical API, а не обхода границы доступа.

Прикладной вход — `NomenclaturePriceService.getLast / priceOn`. Критерий закрытия проверяет
`NomenclaturePriceRegisterOracleTest`: краевые случаи и 284 пробы случайной истории против
расчёта в памяти, detached-измерение и отказ C5 без права чтения. У `NomenclaturePrice` нет
RLS-измерений; для нового защищённого регистра нужно отдельно проверить, что видимость одинакова
у всех версий одного набора измерений.

### 5. Размещение

Инфраструктура живёт в `org.ip.register`, сущность — в `org.ip.model`, охранник — в
`org.ip.application.register`. Общая диагностика дубля изменена в `platform-vaadin`,
обновлён только его source fingerprint; публичные сигнатуры и package matrix не менялись.
Использование существующего публичного
`EntityDataAccess` добавлено в `platform-public-surface.txt`, счётчики D1 обновлены.
Инфраструктура использует
`jakarta.persistence`, JDK, Spring Data и публичный `EntityDataAccess`; сущность и охранник —
существующие API/SPI платформы и Spring.
Платформенная природа инфраструктуры в прикладном пакете — осознанный временный долг. Вынос в
платформу — отдельный срез; первоначальная дата «после v1.2» заменена решением Р4 ниже.

#### Уточнение размещения Р4 (2026-10-04)

После закрытия Р2–Р3 общая инфраструктура перенесена в `org.ipro.register` корневого артефакта:
декларация, валидатор, reader, неизменяемый descriptor и registry. Registry использует существующий
`ManagedEntityCatalog`; стартовая проверка подключена через `RegisterAutoConfiguration`.
Предметная сущность, lifecycle и price service остаются в `org.ip`.
Policy чтения регистра принадлежит `org.ipro.reportstudio.query.register` и подключается
автоконфигурацией reportstudio. Общий пакет регистра не зависит от отчётов или UI.

Это размещение типов, а не повышение до `EntityKind.INFORMATION_REGISTER` или выделение
`platform-register`. Требование F-ERP-3 о production-примерах сохраняется.

Замер замыкания 2026-10-13 подтвердил, что цена выноса — перемещение, а не рефакторинг: движок
не называет ни одного прикладного типа (все 14 однопачечных целей — платформенные модули и
внешние артефакты), прикладная зависимость существует только в обратную сторону (50 файлов
потребителей, 30 контрактных типов) и в тестах движка. Предлагаемые срезы S0–S3,
условия их гейтов и открытые вопросы — [замер и срез контрактов](../information-register-extraction-slice.md).
Контракт descriptor описывает проверенные аннотации, а не подтверждённую физическую схему БД.
Прикладной reader получает descriptor через managed registry; самостоятельный конструктор
без registry сохраняет прежнюю проверку декларации. `getLast` продолжает canonical paged read.

#### Реализация Р5 (2026-10-04)

Добавлены нейтральные `SliceSpec` / `SliceSpecValidator` и report-адаптер подготовки источника
с чистым CTE-генератором. `LATEST` использует включительную дату, отбор измерений до MAX
и отбор ресурсов/периода после выбора. Ссылки сравниваются по проверенному persistent id;
обе фазы сохраняют независимые target JOIN для RLS. Композиция нескольких срезов выполняется
обычным visual package; данные, bindings и допуск остаются в существующем report pipeline.
[Контракт, проверки и ограничения Р5](../information-register-r5-generator.md).
Это реализация генератора; полноценная приёмка v1.1 и PostgreSQL-стоимость остаются Р6.

#### Реализация Р6 и уточнение приёмки СУБД (2026-10-04)

Рецепт сохраняемого отчёта цен использует общий CTE-генератор, named LocalDate-параметр
и штатные template/transfer/assembly/execution services. LEFT JOIN сохраняет отсутствие
истории, ресурсный фильтр применяется к результату последней записи. Дата, сохранение,
импорт, права и реальное выполнение входят в функциональную приёмку v1.1.
[Контракт и evidence Р6](../information-register-r6-report.md).

По уточнению пользователя замер PostgreSQL не является обязательным gate Р6:
сервер БД может меняться. Совместимость подтверждается на конкретной СУБД;
планы, индексы и стоимость измеряются отдельным этапом для выбранного deployment-сервера.
При смене СУБД эти проверки повторяются; H2-приёмка не объявляет поддержку всех серверов.

### 6. Связь с планом F (F-ERP-3)

Уточнение ET6 (2026-10-26): [ADR-0029](ADR-0029-entity-semantic-classification.md) разрешает действующий
INFORMATION_REGISTER только из проверенного RegisterDescriptor. Ограничение ниже
на production-примеры больше не блокирует runtime kind; требования к предметным
операциям и статус пилотов сохраняются. Прежний текст ниже описывает исходное решение.


`f-integration-erp-plan.md` F-ERP-3 решает для `СвязьОперацияКартаКомплектации`: общий
`EntityKind.INFORMATION_REGISTER` и универсальная metadata-модель не вводятся по единственному
случаю; повышение требует второго production-примера с совпадающей семантикой; связь с периодом
действия становится обычной ассоциативной сущностью.

Это решение v1.0 не нарушает, и граница проведена явно:

- `NomenclaturePrice` остаётся `PLAIN`: `kind = INFORMATION_REGISTER` не объявляется, Explorer
  группирует её как «Прочие сущности»;
- регистр объявляется отдельной аннотацией (с Р4 — `org.ipro.register`), без нового `EntityKind`;
- пилот не является production-примером в смысле F-ERP-3: это песочница для проверки механизма.

Если после v1.2 пилот и второй реальный регистр (например, периодический
`ИзмененияКомпонентовПоРаспространениям`) совпадут по семантике, повышение до платформенного kind —
отдельный ADR, который снимет или уточнит F-ERP-3. До этого решения F-ERP-3 в силе.

## Последствия

- Добавлены декларация, валидатор, сущность-пилот, охранник ключа и `getLast` с тестами.
- `RegisterStartupValidator` проверяет все типы с `@RegisterMetadata` из
  `ManagedEntityCatalog.managedEntityClasses()` до завершения refresh. Второго classpath scan нет.
  Ошибки собраны в отчёт с типом, полем и кодом; наличие читателя не требуется.
- В Р4 добавлен immutable descriptor; startup и прикладной reader используют единый managed registry.
- v1.1 (срез как источник конструктора через `SliceSpec`, двухэтапный CTE) и v1.2 (параметр «На
  дату» в LIST) описаны в переписке и получат собственные ADR после результатов v1.0.

## Критерий закрытия v1.0

Валидатор зелёный на `NomenclaturePrice`, форма создаёт и показывает записи, `getLast` совпадает
с оракулом на: пусто до первой записи, `asOf` равен периоду записи (включается), несколько
версий, несколько номенклатур.

### Evidence завершения Р1, 2026-10-03

- Контекстные тесты стартовой проверки: 4 прошли, включая некорректный регистр без читателя,
  агрегированную диагностику и обычные сущности. Фикстуры имеют реальные JPA mapping и `@Id`.
- Интеграционные тесты generic ItemForm и default dispatcher: 4 прошли. Проверены две версии,
  история, повторное открытие и изменение ресурса, запрет изменения обоих полей ключа,
  понятная ошибка дубля и отсутствие лишней строки после rollback.
- Persistence: 7 тестов прошли, в том числе три native INSERT с NULL, обходящие Bean Validation.
  Это подтверждает unique и NOT NULL в созданной схеме H2, не схему внешней PostgreSQL.
- Owner-модуль `platform-vaadin`: 21 целевой тест прошёл; проверенный JAR установлен локально.
  Логи: `.local-maven-repository/register-v1-completion/`.
- Итоговый объединённый прогон пропущен по просьбе пользователя. Добавленный после предыдущего
  запуска тест `canonicalDeleteRemovesOnlyTheSelectedVersion` ещё не запускался.
  Программная приёмка компонентов формы не заменяет ручную проверку браузерного интерфейса.
- UPDATE managed-объекта без независимого исходного снимка по-прежнему отклоняется; рабочий
  сценарий формы использует detached payload. Р9 (2026-10-11) закрывает долг контрактом, а не новой командой: объявлены поддерживаемые каналы (canonical create/update с собственным исходным чтением и detach, форма/detached payload, команда смены ключа), a managed payload без независимого исходного снимка отклоняется fail-closed; `Session.getEntityEntry` и очистка чужого persistence context не используются. [Протокол Р9](../evidence/register-r9-batch-and-r8-parity-20261011.md).
  Исторические архитектурные ошибки третьего патча этим этапом не исправлялись и не перепроверялись.
