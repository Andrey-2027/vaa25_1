# ADR-0019: именованная операция владельца на строке — переименование значения атрибута

- Статус: принято 2026-10-08.
- Область: canonical data path (`platform-core`), C5 (`platform-rls`), приложение (`org.ip.service`), форма типа атрибута.
- Родительское решение: ADR-0017 — §2 (ACTION в объёме), §3 (хранилище и флаги), §5 (определения владельца), §8 (порядок решения), §9 (финальная граница записи).

## Контекст

По коду, а не по замыслу:

- `AttributeValue` объявлен CREATE-only намеренно: `EntityCapabilityOverride` в
  [EntityClassificationConfig](../../../src/main/java/org/ip/config/EntityClassificationConfig.java)
  публикует `writes = {CREATE}` с причиной «значение атрибута бессмертно; переименование —
  отдельная typed операция, generic update/delete запрещены».
- [AttributeValueService](../../../src/main/java/org/ip/service/AttributeValueService.java) пишет
  тип напрямую в пяти местах: четыре — создание строки (`getOrCreateRef`,
  `getOrCreateScalarInCurrentTransaction` и две интернирующие ветви `NaturalKeyCreateSupport` —
  `getOrCreateScalar` и `getOrCreateRefRow`), одно — `renameValue(...)`, где managed-строка меняет
  код и наименование и сохраняется `repository.save`.
- Переименование — это UPDATE-семантика без решения об UPDATE. Вооружённая финальная граница
  записи (C5.6, ADR-0017 §9) отклоняет его: замер 2026-10-08 даёт по `AttributeValue` 8 тестов
  ([evidence](../evidence/c5-6-flush-boundary-20261007.md) §10).
- Механизм именованных операций существует и до сих пор не имеет production-потребителя:
  `C5PermissionDefinition.action(id)` даёт ключ `ACTION:<id>` с единственной операцией
  `EXECUTE`; `C5PermissionDecisionService.decideAction(username, id)` решает;
  `C5OperationPermissionRegistry.requireSupports(...)` требует зарегистрированное определение
  **до** чтения грантов; отказ — `ACTION_PERMISSION_DENIED` (ADR-0017 §10); хранилище — та же
  строка `AccessGrant`, где `EXECUTE` разрешает флаг `canUpdate` (ADR-0017 §3). В тестах
  платформы операция называется `RegisterWrite`; в ADR-0017 §5 назван второй потребитель — гейт
  записи регистра, а `REPORTS:JPQL_PREVIEW` обозначен как ACTION, в который переводится его
  нынешнее CHECK_ONLY-измерение.
- Вне предмета: `renameValue` дополнительно пересобирает `displayName` наборов и сохраняет
  `SklNomOpa`. Этот тип не публикует generic-записи вовсе (нет canonical write handle), поэтому
  обслуживается владельцем и границей не затронут.

## Принятые решения

### 1. Переименование — именованная операция владельца, а не UPDATE

Ключ: `ACTION:ATTRIBUTE_VALUE:RENAME`
(`C5PermissionKeys.action("ATTRIBUTE_VALUE:RENAME")`), определение —
`C5PermissionDefinition.action(...)`, то есть единственная операция `EXECUTE`. Идентификатор
стабилен, выведен из владельца и операции и не зависит от подписи или имени bean'а: форма
`<AREA>:<OPERATION>` уже названа в ADR-0017 §5 для `REPORTS:JPQL_PREVIEW`, и гейт записи
регистра получит парный `REGISTER:WRITE`.

Хранилище не расширяется: право выражается одной exact-строкой на этот ключ, а `canUpdate` в ней
разрешает `EXECUTE` — по тому же отображению флагов, что в ADR-0017 §3. Схема, форма ключа и вид
измерения не меняются; новых флагов и новых семейств ключей не вводится.

### 2. Решение принимает платформенный seam, а не прикладной сервис

На canonical data path появляется вход именованной операции на строке — решение фиксируется так
же, как у остальных write-намерений, и **до** пользовательского кода:

```
<T extends IdentifiableEntity> T executeNamed(
    Class<T> type, String permissionId, Object id, Consumer<T> mutation)
```

Порядок внутри (сохраняет ADR-0017 §8):

1. тип имеет canonical handle — иначе отказ, как у остальных намерений;
2. `requireSupports(C5PermissionKeys.action(permissionId), EXECUTE)` — ключ не пишется руками;
   незарегистрированное определение есть ошибка конфигурации, а не allow;
3. `decideAction(username, permissionId)` — отказ `ACTION_PERMISSION_DENIED` **до** загрузки
   строки и до SQL;
4. загрузка текущей строки, доступной субъекту (canonical read, то есть C5-чтение; RLS исходного
   состояния — если тип им покрыт);
5. мутация владельцем: доменные правила переименования (нормализация по типу значения, запрет
   слияния, запрет для `REF`, независимая подпись ENUM) остаются в `AttributeValueService`, а не
   переезжают в платформу;
6. фиксация авторизации записи тем же журналом, что у canonical write (`recordCanonicalWrite`),
   поэтому финальная граница на flush её потребляет (ADR-0017 §9);
7. validation, hooks и события — как у остальных canonical write.

Существенно, что вход принимает **мутацию на загруженной строке**, а не сущность для слияния: это
и отличает именованную операцию от `update`. Ни `save`, ни `update` не должны уметь доходить до
этого входа. Имя метода может быть уточнено при реализации; контракт (решение до загрузки, мутация
на строке, потребление на flush) фиксируется здесь.

### 3. Capability типа не расширяется

`writes` у `AttributeValue` остаётся `{CREATE}`: определение операции регистрирует владелец
(ADR-0017 §5), а не descriptor. Именованная операция не появляется в
`descriptor.capabilities().writes()` и не делает законным `access.update(AttributeValue.class, …)`
— отклонение generic update/delete остаётся проверяемым обещанием (`CanonicalWriteBoundaryIT`).

### 4. Четыре создания уходят на canonical create

Прямые `repository.save` в путях создания заменяются на canonical create: тип уже публикует
CREATE. Сохраняются дедуп по `codeUp`/`refId`, пессимистичная блокировка типа, гонка на создании
(`NaturalKeyCreateSupport`: уникальное ограничение, `REQUIRES_NEW`, повторный SELECT победителя) и
нормализация `AttributeValueLifecycle`. Repository остаётся только для чтения и блокировок
(`findByAttrTypeAndCodeUp`, `findByAttrTypeAndRefId`, `findByIdForUpdate`).

Следствие, которое нужно выдать вместе со сменой: создание значения начинает требовать право
CREATE на ключ типа (`ENTITY:AttributeValue`, флаг `canUpdate`). Сегодня создание идёт мимо
решения, поэтому первичная выдача обязательна — это часть C5.8, а не этой записи.

### 5. UI и выдача идут тем же решением

Кнопка «Переименовать» в форме типа атрибута сегодня проверяет только доступность формы и тип
значения — гейта операции у неё нет. Включение операции закрывает E1.2b для этого действия:
доступность кнопки берётся из того же `decideAction`, а не из собственного условия формы, чтобы
отказ UI и отказ сервера совпадали.

Выдача: сегодня переименование достижимо субъекту с правом на `ENTITY:AttributeType`; после смены
ему нужна строка на `ACTION:ATTRIBUTE_VALUE:RENAME`. Первичная выдача ACTION-строк вместе с
включением enforcement — C5.8. Фикстура `RlsTestFixture` выдаёт гранты по зарегистрированным
определениям, поэтому новый ключ подхватывает автоматически.

## Отклонённые варианты

| Вариант | Почему отклонён |
| --- | --- |
| Открыть generic UPDATE у `AttributeValue` | Публикует возможность, которую тип закрывает намеренно: любой generic путь смог бы менять любое значение, а обещание «значение неизменяемо» пришлось бы снять вместе с тестом границы. |
| Оставить прямой repository, «прикрыв» его грантом на `ENTITY:AttributeValue` | Грант CREATE не авторизует UPDATE-семантику, а обход canonical path остаётся — ровно то, что закрывает C5.6b. |
| Новое семейство ключей (`ATTRVAL:...` вне `ACTION`) | Расширяет пространство ключей, зафиксированное ADR-0017 §3/§5, без потребителя. |
| Одна generic-операция `ACTION:RENAME` на все типы | Платформе пришлось бы знать доменные правила владельца; ADR-0017 §5 отдаёт определение владельцу вместе с конкретным потребителем. |

## Проверяемые последствия

1. Без строки-гранта переименование отклоняется с `ACTION_PERMISSION_DENIED` до загрузки строки и
   до SQL; грант его открывает.
2. `access.update(AttributeValue.class, …)` и `delete` продолжают отклоняться с прежними
   причинами.
3. Создание значения проходит через canonical create: с правом CREATE — успех, без него — отказ;
   гонка и дедуп сохранены.
4. При вооружённом `AttributeValue` прямой `repository.save` managed-строки отклоняется на flush:
   замер 2026-10-08 (8 тестов по `AttributeValue`) сходится к нулю.
5. Незарегистрированное определение — отказ при старте, не allow.

## Границы и известный долг

- Гейт записи регистра (`REGISTER:WRITE`) — второй потребитель того же seam; он остаётся в C5.6b и
  этим решением не делается.
- Первичная выдача ACTION-строк для существующих баз — C5.8; без неё переименование молча исчезает
  у тех, кто имел его через `ENTITY:AttributeType`.
- `REPORTS:JPQL_PREVIEW` переводится из CHECK_ONLY-измерения в ACTION отдельным шагом
  (ADR-0017 §5).
- Права на поля не затрагиваются (ADR-0018); PostgreSQL-шаг не закрывается.
- Третий потребитель не появляется без прикладного сценария (городьба ADR-0017 и плана C5).
