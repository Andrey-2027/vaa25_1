# ADR-0015: регистратор периодического регистра сведений

- Статус: принято по обсуждению 2026-10-05; основы каталога и моделей начаты, сквозной контракт не завершён.
- Область: запись подчинённых регистров, полиморфная ссылка на документ, равные периоды,
  права, граница транзакции.
- План работ: [Г0–Г8](../information-register-recorder-plan.md).
- Связанные решения: ADR-0003 (aggregate save), ADR-0005 (lifecycle), ADR-0007
  (canonical data path), ADR-0013 (самостоятельный регистр v1), ADR-0014 (C5 и видимость).

## Контекст

Один периодический регистр может получать записи от разных документов. У подчинённой
строки должны оставаться собственные идентификатор и номер строки регистратора,
а история всего регистра должна читаться независимо от наличия доступа к документу.

Если две строки имеют одинаковые измерения и нормализованный период, одного
максимального периода недостаточно для `getLast` и среза. Выбор нельзя оставлять
порядку строк БД, identity id документа или скрытой сортировке генератора.

## Принятые решения

### 1. Recorder reference

Каждая строка подчинённого регистра ссылается ровно на один документ. Ссылка состоит
из стабильного кода типа документа и текущего `Long id`. Тип объявляет код один раз;
регистр объявляет разрешённые типы. Переименование Java-класса, таблицы или URL формы
само по себе код ссылки не меняет.

Каталог типов строится на существующем `ManagedEntityCatalog` и metadata resolver.
Разрешён effective `EntityKind.DOCUMENT`; наследование от `StandardDocumentEntity`
не требуется, если тип корректно объявлен и поддерживает нужный lifecycle и version.
Код Java/FQCN от клиента не является способом загрузить произвольный тип.

Пара хранится без полиморфного FK на таблицы разных документов. Существование
регистратора и очистка его записей обеспечиваются транзакционным протоколом write/delete.
Текущие генераторы `Long` документов не меняются.

### 2. Row key, dimensions и period — разные вещи

Дополнение Р8, 2026-10-09: [ADR-0021](ADR-0021-register-key-change-command.md)
разрешает отдельной opt-in команде изменять dimensions / period существующей строки.
Recorder, lineNumber и recordingOrder сохраняются. Документ не пересохраняется,
а generic UPDATE и неизменяемые типы сохраняют прежние ограничения.

Для строки подчинённого регистра row key — `(recorder_type, recorder_id, line_no)`.
Колонки обязательны; сочетание уникально; `line_no` положителен и не меняется у
сохранённой строки. Технический `BaseEntity.id` остаётся.

`period` не входит в обязательную row uniqueness подчинённого регистра. Он задаёт
временной отбор и первичный порядок в срезе. Dimensions задают бизнес-группу среза.
RecorderRef автоматически в dimensions не добавляется. Текущий ключ самостоятельных
регистров (dimensions + period) сохраняется.

Поддерживаются независимые capabilities `PeriodicRegisterEntry` и
`RecordedRegisterEntry`: без period/recorder остаются самостоятельные режимы;
обе capability вместе задают периодический подчинённый режим. Поля принадлежат
общим mapped superclasses, technical id/version/audit — `BaseEntity`.

### 3. Последняя запись при равном периоде

Принято правило **последняя запись регистрационного набора побеждает**.

Для одной группы dimensions candidate rows сортируются по возрастанию периода,
затем по возрастанию сохранённого `recording_order`, затем по `line_no`.
Побеждает последний элемент этого порядка при условии `period <= asOf`.
Иными словами, лексикографический победитель — максимум `(period, recording_order,
line_no)` среди подходящих строк.

- `recording_order` обозначает порядок успешных операций замены набора для данного
  регистра. Он хранится в строках регистра, чтобы одинаковое правило применялось
  к Hibernate point read, canonical LIST, отчётному CTE и oracle.
- Строки одной замены набора получают общий order; если одна запись заменяет
  несколько строк с той же группой и периодом, больший `line_no` побеждает внутри набора.
- Если набор документа не передавался в операции сохранения, он не заменяется и его
  порядок не продвигается. Явная повторная замена считается новой операцией записи.
- Откат транзакции не оставляет видимых строк с новым порядком. Удаление документа
  удаляет его набор; среди сохранившихся документов снова побеждает последний доступный
  по записи.
- Business document date/number, type code, document id, wall-clock времени и
  генерируемый id строки сами по себе не являются winner order.

`recording_order` — порядок записи набора, а не момент проведения документа.
Требования учитывать дату документа, posting sequence или запрет задних дат потребуют
отдельного бизнес-контракта; этим порядком их не подменяем.

### 4. Запись и конкурентность

Полный набор одного регистратора меняется одной прикладной командой в той же
транзакции, что и согласованная операция документа. Отсутствующий вход означает
«этот набор не менять»; явно переданный пустой набор означает очистить его.
Обычные generic CRUD операции для подчинённых строк закрыты.

Операция замены повышает recorder version. Устаревший payload получает version conflict.
Замена и удаление документа используют общий lock/version protocol, чтобы insert
не прошёл вслед за проверкой существования уже удалённого документа.

Технический кандидат: per-register `recording_order` clock, блокируемый и увеличиваемый
внутри транзакции на каждую замену набора. Блокировка удерживается до commit, поэтому
для двух конкурирующих замен порядок соответствует сериализованному commit-порядку.
Это переносимый JPA row-lock подход, а не PostgreSQL advisory lock. Он последовательно
блокирует записи разных групп одного регистра; спайк Р Г3 должен измерить задержку и
проверить конкурентность на PostgreSQL. Замена allocator не меняет принятый API-порядок.

### 5. Права на регистр и документ независимы

Чтение истории, выбор победителя, slice и count проходят собственные C5/RLS/field
проверки регистра. Невозможность открыть документ не меняет состав истории и победителя.
Проверка подписи и навигация к документу используют права самого документа.

Право сохранить документ не даёт общего права редактировать произвольный регистр.
Производная запись допускается только отдельной объявленной серверной authority
конкретной команды, с указанием recorder scope и доступных регистров. Переданный
клиентом флаг не создаёт authority.

Замена целого набора проверяет и сохраняемые, и удаляемые строки. Не полностью
видимый по регистровым правам набор нельзя незаметно заменить частью. Успешное
удаление документа транзакционно очищает только принадлежащие ему наборы через
внутренний lifecycle path. Эта очистка нужна, чтобы не оставить строки без
регистратора; она не раскрывает поля регистра и не даёт пользовательского права
читать или отдельно менять его строки. Право на запись набора из права редактирования
документа не выводится.

Срез сохраняет принятую ADR-0014 group-invariant visibility. RLS по RecorderRef
не включается автоматически: фильтр по версии регистратора может изменить победителя.

Матрица прав и результата:

| Операция | Право регистра | Право документа | Результат |
| --- | --- | --- | --- |
| История / getLast / slice / count | Допускает строки | Нет доступа к документу | Данные и winner доступны; поля и переход к документу скрыты |
| Caption / navigation | Допускает recorder-проекцию | Нет доступа к документу | Общая закрытая подпись, перехода нет |
| Замена набора | Нет register write authority | Есть право редактировать документ | Отказ записи; права документа недостаточно |
| Замена набора | Есть command-scoped register write authority | Документ доступен и version совпадает | Атомарная замена ровно этого recorder set |
| Удаление документа | Нет прав читать/менять register rows | Есть право удалить документ | Документ и его наборы очищаются атомарно; register fields не выдаются |
| Прямой generic CREATE/UPDATE/DELETE строк | Любое | Любое | Отказ; нужен set command или lifecycle cleanup |

### 6. Граница модели

Подчинённый регистр не является обычной `TableSectionMetadata`: у него несколько
типов регистраторов, самостоятельная история и срез, отдельные права и запрет
generic write. Переиспользуются доказанные aggregate transaction, lifecycle,
validation, event и rollback механизмы через выделенную set capability.

Запись набора изменяет текущее состояние строк регистратора. Она не вводит posting,
`DRAFT/POSTED`, reversal или неизменяемый бухгалтерский ledger. Эти контракты
остаются отдельным треком F-ERP.

## Проверяемые последствия

До публикации writer и slice необходимы:

1. JPA mapping для двух разных типов с одинаковым Long id; fail-fast на повтор кода
   и неподдерживаемый тип регистратора.
2. UNIQUE `(recorder_type, recorder_id, line_no)`, нормализация period и единое
   winner predicate `(period, recording_order, line_no)`.
3. Доказательство point/slice/count/oracle parity на одинаковом period у документов
   разных типов и у нескольких строк одного набора.
4. PostgreSQL тест concurrent replace/replace и replace/delete, включая rollback,
   устаревшую version и сохранение полного набора.
5. Проверка, что отказ открыть документ не удаляет строки/счётчик/победителя;
   подпись и link при отказе не раскрывают поля документа.
6. Измерение стоимости общего clock row. Если throughput не принят, до выпуска нужен
   более узкий сериализатор с тем же транзакционным порядком, а не best-effort id sort.

Исполняемая работа размечена Г0–Г8 в плане регистратора. Production-пилот выбирается
для Г7, когда есть потребитель и согласованы dimensions/resources. До этого контракт
проверяется на DOCUMENT fixtures без выдуманного прикладного смысла. Это ADR
фиксирует порядок победителя и общие ограничения. Реализация идёт по этапам Г0–Г8;
этот ADR сам по себе не означает, что writer, recorder slice executor или DDL уже готовы.
