## Контекст

E3.0 дал типу адрес. Но сама карточка «Структура сущности» в это время не была правдивой: колонка
«Источник» печатала **путь к `.java`-файлу класса сущности** для каждой строки обзора, полей и
колонок. У части фактов это совпадало с истиной (декларация поля действительно живёт в файле
сущности), у остальных — нет: «Экспозиция» приходит из каталога дескрипторов, «Ссылка item/list» —
из каталога маршрутов, «Тип сущности» — из стандартного базового класса, «Внешний ключ» — из
регистрации alias. То есть карточка называла точное место там, где места не знала, и раздел
«источники» приходилось проверять чтением кода.

Ограничения, снятые измерением (E3.1, §0 плана среза):

1. `EntitySummaryPanel` строил ячейку из `row.key().entityClass()`; различимым было одно состояние —
   `FactSource.OVERRIDE` («переопределение»).
2. `TableSectionMetadataInfo.getTitle()` и `ColumnPath.getLabel()` **сами** подставляют fallback.
   Сравнение итоговой строки с fallback назвало бы явно заданное значение «вычисленным» — то есть
   происхождение нельзя выводить из значения.
3. Пустой `listColumns` выводит колонки из полей грида, пустой `selectColumns` — из колонок списка,
   а `ColumnPath.resolve` не несёт подписей для путей через точку: состав колонок тоже нуждается в
   происхождении, а не только их заголовки.
4. `FieldMetadataInfo` уже знает `getRequiredOrigin()`/`getTypeOrigin()`, а
   `EntityMetadataInfo.getEntityKind()` возвращает только итог: знание о ветке есть, но в сводку не
   попадало.
5. `EntityLifecycle` — интерфейс с default-методами, handler может быть Spring-proxy,
   `EntityLifecycleRegistry.find` требует `IdentifiableEntity`: «хук не переопределён» доказуемо
   только после разворачивания класса.
6. Диагностики существуют на старте (`MetadataConsistencyStartupCheck`) и адресуются строками
   FQN+поле; реестр `ADX-*` — документ, в рантайме его нет.
7. `FacetResolver` в продуктивной конфигурации — no-op, все значения `CODE`: ось переопределения в
   UI показать честно нельзя, её можно только проверить тестом.

## Решение

### 1. Два раздельных признака вместо одного «источника»

`ResolvedValue(value, source, origin, symbol)`:

- `source` — **слой** действующего значения (`CODE` или `OVERRIDE`);
- `origin` — **происхождение кодового значения**: почему код такой;
- при `OVERRIDE` происхождение описывает **кодовый дефолт, который переопределён**, а не сам
  override: иначе «действует переопределение» и «действует платформенный дефолт» читались бы
  одинаково.

Признаки разделены потому, что отвечают на разные вопросы: «что победило» и «откуда взялось то, что
победило». Слияние их в одно поле сделало бы невозможным случай, когда действует переопределение
поверх платформенного дефолта.

### 2. Символ — часть факта, а не украшение

`symbol` — точный Java-идентификатор: `org.ip.model.Nomenclature`, `org.ip.model.Nomenclature#code`,
для хука `org.ip.application.catalog.NomenclatureLifecycle#beforeSave`. Путь к `.java` и наличие
source JAR не кодируются и не обещаются: символ проверяется по classpath (`checkedSymbol` в
сборщике), а переход к файлу — дело IDE.

Пустой символ **допустим** и не превращает известное происхождение в `UNKNOWN`: для регистраций
каталог может не хранить место, и тогда честный ответ — «происхождение известно, место нет».

### 3. `UNKNOWN` — только из явного списка

`UNKNOWN` появляется ровно там, где источник действительно не сообщает ветку: совместимый
двухаргументный конструктор `ResolvedValue(value, source)` и прежняя фабрика `code(String)` вне
Explorer. В таблице ветвей §2.2 `UNKNOWN` не используется: предполагаемый файл или «платформенный
дефолт» по умолчанию запрещены, и «удобный» `UNKNOWN` ловится тестом.

`FactOrigin` получает `REGISTRATION`, `DERIVED`, `UNKNOWN` к действующим пяти; эффективные
`kind`, `exposure`, `key` и `linkability` публикуются вместе с происхождением, а не только итогом.

### 4. Происхождение живёт там, где знание

Аксессоры ставятся в источнике: `FieldMetadataInfo` (готово), `TableSectionMetadataInfo.getTitleOrigin`,
`ColumnPath.getLabelOrigin`, `EntityMetadataInfo.getEntityKindOrigin/getEntityKindSymbol`,
типизированные `EntityDescriptor.exposureOrigin/exposureSymbol` и
`PublishedFormRoute.keyOrigin/keyReason/keySymbol`. Сборщик не восстанавливает ветку сравнением
строк и значений: совпавшее явное значение было бы названо выводом.

### 5. Пять состояний handler'а, и ни одно не читается как «правил нет»

| Состояние | Происхождение | Что публикуется |
| --- | --- | --- |
| handler найден и класс развёрнут | `REGISTRATION`, symbol = целевой класс | строка handler'а + шесть строк хуков (`EXPLICIT` для переопределённых, `PLATFORM_DEFAULT` для default-методов) |
| handler найден, класс не развёрнут (Java-proxy вне Spring) | `PLATFORM_DEFAULT` | только handler-строка: «происхождение хуков не подтверждено» |
| handler не зарегистрирован | `PLATFORM_DEFAULT` | только handler-строка |
| тип не `IdentifiableEntity` | `DERIVED`, symbol = класс сущности | только handler-строка: «lifecycle не применим» |
| реестр lifecycle не подключён | `PLATFORM_DEFAULT` | только handler-строка: «реестр lifecycle не подключён» |

Строки хуков публикуются **только** в первом состоянии: «хук не переопределён» и «переопределение не
подтверждено» — разные факты, и второй не выдаётся за первый. Пятое состояние существует, потому что
совместимый семиаргументный конструктор сборщика передаёт `null` вместо реестра: без этой ветки
`summarize` падал бы на NPE, а тихое «handler не зарегистрирован» было бы неправдой.

### 6. Разворачивание proxy — у владельца реестра

`EntityLifecycleInspection` живёт в `platform-events` (пакет `org.ipro.lifecycle`) и отвечает
`Optional<Assessment>`: целевой класс через `AopUtils.getTargetClass` (JDK- и CGLIB-proxy Spring) и
`declared` по каждому хуку. `spring-aop` объявлен в модуле явно, reviewed-бюджет осознанно меняется
(типы 3 → 4, compile-зависимости 5 → 6): разворачивание proxy — исполнение контракта, а не деталь
реализации, и не должно держаться на транзитивной зависимости. UI-модуль о Spring AOP не знает, и
классификация хуков не зависит от того, кто её показывает.

`Optional.empty()` (Java-proxy, созданный вне Spring) — это «не подтверждено», а не «все хуки
default». Порядок хуков фиксирован явным списком, незнакомое имя падает при загрузке класса, а
guard-тест сверяет набор имён с публичными методами `EntityLifecycle` без `entityType`: новый хук не
может появиться в UI молча.

### 7. Причина адресуемости — у одного владельца

Причины `NotLinkable` и отсутствие опубликованного ключа приходят в карточку строками `ENTITY_KEY` и
`LINKABILITY` сводки. Локальная строка «у этого типа нет публичного адреса», которую рисовала вкладка
Explorer с E3.0, снята вместе с зависимостью вида от `FormRouteCatalog`: две копии одной причины
расходились бы молча, а закрытие карточки не меняет конфигурацию.

### 8. Неадресованные диагностики — в каталоге, а не в карточке

Диагностики стартового скана читаются из одного snapshot без повторного запуска валидатора. Запись
поля привязывается по коду к грани, запись строки секции показывается у root-владельца, остальные
остаются в общем списке, который живёт в каталоге Explorer и не зависит от выбранной карточки:
запись, видимая только внутри открытой карточки, исчезала бы вместе с её закрытием. Пустой список не
рисует раздел — «записей нет» и «раздел не открыт» разные состояния.

### 9. Что карточка показывает и чего не показывает

- Колонка «Источник» собирается из трёх признаков: слой, подпись происхождения, Java-символ.
  `OVERRIDE` показывается как `переопределение (код: <происхождение>)`.
- Пустое место остаётся пустым: путь из класса сущности не выводится.
- Происхождение обязательности и типа поля показывается рядом со своими фактами («да ·
  bean-валидация», «Строка · JPA-маппинг»), а `overview.detail` и `column.note` несут причину и
  состав («metadata-driven root», «выведены из полей грида»).
- UI показывает **текст происхождения**, а не отрендеренный `FacetKey`, и не рисует
  `DiagnosticRow.caption` отдельной колонкой: подпись составлена из уровня и кода, которые в той же
  строке уже есть, — второй вид тех же данных читался бы как второй факт.
- Ось `OVERRIDE` в продуктивной конфигурации ещё не наблюдаема (`FacetResolver` — no-op): она
  подтверждается тестом, а не подделкой переопределения в UI.

### 10. Граница API платформы: `ResolvedValue` — APP_API

Шаг 5 сделал происхождение видимым, и вместе с ним видимой стала граница: приложение теперь называет
`FactOrigin`, `MetadataDiagnostic` и `ResolvedValue`. Первые две роли в D1-реестре
(`platform-public-surface.txt`) получили строки API; `ResolvedValue` в D3.3-реестре
(`platform-core-surface.txt`) был `MODULE_API`, и `PlatformCoreSurfaceTest` отверг расхождение:
«контракт модулей не может быть уже достигнут приложением». Роль переведена в `APP_API`
(бюджет 30/4/44/16 → 31/4/43/16) по правилу самого реестра «D1-роль API → APP_API», с причиной в
шапке: значение приходит приложению типом из опубликованной `EntitySummary`, а его собственный
компонент `FactSource` уже был `APP_API`. Замеры: `api-types` 125 → 128,
`named-platform-types` 213 → 216.

## Последствия

- Карточка перестала заявлять точность, которой не имеет: у каждого показанного значения есть
  происхождение, а место либо точное, либо пустое.
- Изменения опубликованных типов разделены по замеру, а не по замыслу: относительно закоммиченного
  baseline отличаются ровно два файла.
  - Аддитивно: новый публичный тип `EntityLifecycleInspection` (`platform-events.api`, +21 строка —
    сам тип, `Assessment`, `Hook`).
  - Аддитивно, со сохранением прежних конструкторов: `OverviewRow`, `FieldRow`, `ColumnRow`,
    `FormRow` — их поверхность от baseline не отличается; новые признаки (`detail`, `note`,
    `requiredOrigin`/`typeOrigin`, `origin`/`symbol`) доступны через новые сигнатуры, старые
    делегируют. `platform-core.api` не менялся вовсе: `ResolvedValue` с совместимым двухаргументным
    конструктором и `FactSource` были в baseline уже до среза.
  - Ломающе, с названной ценой: `LifecycleRow` — конструктор `(hook, declared, value, note)` заменён
    на `(key, hook, declared, value, note)`, добавлен `key()`. Совместимого конструктора нет
    намеренно: `FacetKey` строится из класса сущности и вида грани, а класса в прежних аргументах
    нет — пустышка вместо ключа была бы опубликованным ключом, которого не существует. Миграция —
    единственный вызов в сборщике; `platform-vaadin.api` регенерирован намеренно (одна строка
    конструктора и `key()`).
- Реестры, которые срез действительно изменил: `platform-public-surface.txt` (три D1-роли),
  `platform-core-surface.txt` (`ResolvedValue`: `MODULE_API` → `APP_API`, бюджет 30/4/44/16 →
  31/4/43/16), `d1-surface-measurements.md` (`api-types` 125 → 128, `named-platform-types` 213 → 216,
  `platform-artifact-files` 394 → 395), `scripts/local-dependencies.json` (файлы среза в
  `platform-events` и `platform-vaadin`).
- Цена: пять состояний handler'а вместо двух читаются текстом; `UNKNOWN` виден в UI как
  «происхождение неизвестно» и не исчезнет — он честен там, где источник молчит.
- Долг среза закрыт измерением, а не предположением: два падавших теста (`EffectiveMetadataSnapshotTest`
  — baseline распределения origin'ов, `NumberingMetadataRegistryTest` — унаследованное `@Numbered`
  фикстуры) исправлены в шаге 4; три красных guard'а шага 5 закрыты в шаге 6 — `PlatformPublicSurfaceTest`
  (два падения: три типа модели без D1-роли и замер `named-platform-types`), `WorkspaceManifestTest`
  (отпечаток `platform-vaadin` после правки адреса) и `PlatformCoreSurfaceTest`, который отверг
  расхождение D1- и D3.3-классификаций `ResolvedValue`.
- `platform-persistence.api`, `PlatformPackageDependencyMatrixTest` и reportstudio-контроль `bands`
  остаются чужими падениями: они были в входном baseline среза и не выдаются за успех.

## Что этот ADR не обещает

1. Что правило, вызванное делегатом или другим listener'ом, видно снаружи: оговорка стоит в строке
   handler'а, и это граница метода, а не недоделка.
2. Что у каждого факта есть символ: для регистраций каталог может не хранить место.
3. Что UI показывает `FacetKey`: агрегат — поверхность чтения, а не редактор словаря.
4. Что ось `OVERRIDE` проверена в интерфейсе: сегодня она подтверждена тестом.
5. Что `UNKNOWN` исчезнет: закрыть его можно только источником знания, а не оформлением.
6. Ничего про `actions`/`plans`/`RLS`-факты, дерево по resolved kind, вкладки аспектов, якоря
   секций и `ADX-10`/`ADX-11` — это E3.2 и отдельный срез долга.
