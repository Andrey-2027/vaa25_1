# ADR-0004: семантические типы сущностей и стандартные базовые классы

- Статус: принято
- Дата: 2026-09-11
- Область: entity model, metadata, numbering, owned sections, developer experience

## Контекст

Сейчас большинство прикладных классов наследуются непосредственно от `BaseEntity`.
Этот класс корректно задаёт техническую идентичность сущности (`id`, `version`,
equality), но не сообщает платформе её предметную природу. Справочник, документ,
строка табличной части, системная запись и будущая запись регистра для generic-механизмов
выглядят одинаковыми сущностями. Различия затем восстанавливаются вручную в сервисах,
формах, поиске, нумерации и обработчиках сохранения.

Для типового enterprise-приложения полезны opinionated defaults, аналогичные идее
стандартных объектов 1С. У обычного справочника почти всегда есть код и наименование,
у обычного документа — номер и дата. Если каждый прикладной класс заново объявляет эти
поля, UI metadata, Bean Validation, instance name, поиск и нумерацию, платформа не
выполняет свою задачу по сокращению механической работы.

Отдельный вопрос — табличные секции. Наличие `@ManyToOne`-ссылки на сущность не означает,
что ссылающаяся запись принадлежит агрегату: это может быть обычная ссылка, независимый
объект или проекция. Поэтому платформа не должна обнаруживать owned sections обратным
сканированием всех JPA-связей.

## Решение

### 1. Техническая и предметная природа разделяются

`BaseEntity` остаётся минимальной технической основой и не получает полей документа,
справочника или коллекций секций.

В платформенной metadata-модели вводится семантический тип сущности:

```text
PLAIN
CATALOG
DOCUMENT
INFORMATION_REGISTER
```

`INFORMATION_REGISTER` резервирует отдельный архитектурный archetype. Его полная
семантика — dimensions, resources, period, recorder, uniqueness и slice queries —
проектируется только при появлении соответствующего этапа ERP/registry work и не
имитируется обычным CRUD заранее.

### 2. Golden path предоставляется наследуемыми стандартными классами

Платформа предоставляет как минимум:

```text
StandardCatalogEntity extends BaseEntity
  code
  name

StandardDocumentEntity extends BaseEntity
  number
  date
```

Оба класса являются `@MappedSuperclass` и содержат реальные общие данные и инварианты,
а не служат пустыми маркерами. Они могут нести стандартные Bean Validation/JPA/UI
metadata поля, но не должны фиксировать неподходящую всем сущностям область уникальности
или конкретную последовательность нумерации.

Семантический тип выводится из стандартного базового класса автоматически. Прикладной
разработчик не обязан одновременно наследоваться от `StandardDocumentEntity` и повторять
`kind = DOCUMENT` в metadata.

### 3. Нестандартные сущности остаются допустимыми

Сущность без стандартной структуры наследуется непосредственно от `BaseEntity` и явно
объявляет semantic kind либо остаётся `PLAIN`. Это штатный escape hatch, а не ошибка.

Примеры:

- обычные `Nomenclature`, `Workshop`, `Warehouse` — кандидаты на
  `StandardCatalogEntity`;
- `ReceivingDocument` — кандидат на `StandardDocumentEntity`;
- `PrdSpec` имеет owned sections, но из этого не следует, что это документ: без
  документной семантики номера/даты/проведения он может остаться нестандартным
  каталогом/агрегатом на базе `BaseEntity`;
- security, link и system entities могут оставаться `PLAIN`.

Существующие классы мигрируются только там, где стандартная семантика естественна.
Массовое переименование полей (`codeSpec` в `code`, `shortCode` в `code`) ради
наследования не выполняется.

### 4. Нумерация является policy, а не жёстким свойством базового поля

Стандартные поля получают семантические роли `catalog code`, `document number` и
`document date`. Конкретная policy задаётся metadata конкретного типа:

- ручная, автоматическая или смешанная генерация кода справочника;
- scope номера документа;
- период нумерации;
- prefix/pattern;
- внешний номер без генерации.

В B3.1 это реализовано как роли `NumberingRole.CATALOG_CODE` и
`NumberingRole.DOCUMENT_NUMBER` на унаследованных нумеруемых полях. Обычная сущность
получает platform default без деклараций. Исключение задаётся одной повторяемой
class-level аннотацией `@NumberingPolicy(role = ...)`; затенять приватное поле базового
класса новым `code`/`number` запрещено архитектурным смыслом контракта. Эффективные
параметры материализуются в `NumberingDefinition` и одинаково используются save-hook,
движком, admin UI и metadata explorer. Scope, периодическое поле даты, тип поля,
дублирующая или неприменимая роль проверяются при построении metadata registry.

Глобальный `unique = true` для номера документа не задаётся в mapped superclass:
уникальность часто относится к журналу, организации, типу документа или периоду.
Database constraint обязан соответствовать effective numbering policy конкретной
таблицы.

### 5. Секции являются независимой capability

Не вводится обязательный базовый класс `EntityWithSections`. Секции могут принадлежать:

- стандартному документу;
- нестандартному агрегату;
- при подтверждённом сценарии — справочнику.

Головная сущность явно перечисляет owned sections через `@TableSections` либо его
будущий семантически усиленный эквивалент `@OwnedSections`/`@AggregateRoot`. Платформа
не ищет секции по обратным `@ManyToOne`-ссылкам.

Metadata должна однозначно выражать как минимум:

- row class;
- parent field;
- ownership;
- persistence mode (`mutable replace-all`, а позднее при необходимости
  `write-through`, `immutable`, `create-once`);
- line number policy;
- порядок и заголовок секции.

Если часть декларации остаётся на root, а часть на row class, startup validation
проверяет симметрию и отклоняет неоднозначную либо противоречивую конфигурацию.

В B3.2 `TableSectionMetadataInfo` является resolved descriptor этого контракта.
`SectionMetadataRegistry` строит при старте детерминированный каталог только из явно
объявленных `@TableSections` и проверяет обратную декларацию строки, единственного
owner, JPA entity/identity, `@ManyToOne` parent field, тип line number и compatibility
явного service class. Базовый режим `SectionPersistenceMode.MUTABLE_REPLACE_ALL`
фиксируется в metadata; добавление enum-значения без отдельной реализации не считается
допустимым fallback.

В B3.3 `GenericOwnedSectionService` использует этот descriptor как единственный
контракт persistence секции: связывает новые строки с root, проверяет owner/type,
`minRows` и Bean Validation, назначает line numbers, загружает declared fetch graph,
выполняет replace-all и delete lifecycle. Root authorization по-прежнему проверяет
обычный root `BaseService`, а aggregate lifecycle events координирует
metadata-driven save service. Для стандартных секций application services/repositories
не требуются; typed application service остаётся только для реальной предметной
семантики или нестандартной persistence policy.

### 6. Entity kind задаёт defaults, capabilities их уточняют

`CATALOG` по умолчанию получает list/item/selection, instance name, поиск по
стандартным display fields и catalog-code policy. Иерархия, owner и sections являются
дополнительными capabilities.

`DOCUMENT` по умолчанию получает number/date semantics, copy lifecycle и стандартную
границу сохранения. Sections и будущая posting capability необязательны: документ без
строк остаётся документом, а сущность с секциями не становится документом автоматически.

Выбор поведения платформы строится через резолвнутый entity descriptor и registry/policy,
а не через разрастающийся `if (SomeEntity.class)` type switch.

## Developer-experience contract

Минимальные контрольные сценарии:

1. Обычный справочник наследуется от `StandardCatalogEntity` и без прикладных
   repository/service/search/display-name классов получает стандартные формы, поиск,
   instance name, validation и выбранную code-numbering policy.
2. Обычный документ наследуется от `StandardDocumentEntity`; документ без секций
   сохраняется стандартным entity path.
3. Документ с одной owned mutable section является минимальным aggregate sample и
   сохраняется атомарно без save-specific классов.
4. Документ с двумя секциями подтверждает универсальность механизма: `ABSENT`,
   `ATTACHED + empty`, rollback и persisted result обрабатываются независимо для каждой
   секции.
5. Нестандартная сущность на базе `BaseEntity` может явно описать отличия без
   наследования от неподходящего archetype.

Количество секций не является условием принадлежности к `DOCUMENT`: одна секция —
минимальный пример, две — проверка универсальности, ноль — допустимый документ.

## Последствия

Положительные:

- стандартные справочники и документы становятся короткими и единообразными;
- platform defaults получают надёжный semantic signal вместо эвристик по именам классов;
- общие поля, validation и UI metadata не копируются в каждой модели;
- секции не путаются с произвольными JPA-ссылками;
- B3 может выбирать стандартный aggregate save по descriptor/capabilities, не зная
  конкретных прикладных типов;
- будущие document actions и register semantics получают явную точку расширения.

Ограничения и риски:

- mapped-superclass поля влияют на схему каждой наследующей сущности;
- неподходящую глобальную уникальность или numbering policy нельзя помещать в базовый класс;
- автоматический kind inference и явный metadata override должны проверяться на конфликт;
- миграция существующих моделей может потребовать schema migration и выполняется адресно;
- базовые классы не должны разрастись в универсальный `god object`.

## Рассмотренные альтернативы

### Оставить одну `BaseEntity` для всех типов

Отклонено как единственный golden path: техническая унификация сохраняется, но
прикладной код продолжает повторять стандартные поля и вручную восстанавливать семантику.

### Ввести только `EntityWithSections`

Отклонено: класс не несёт общей структуры, не перечисляет секции и ошибочно связывает
семантический тип объекта с одной независимой capability.

### Определять секции обратным сканированием JPA-ссылок

Отклонено: ссылка не доказывает ownership, cascade, порядок сохранения или участие в
атомарной границе.

### Сделать стандартные базовые классы обязательными для всех объектов типа

Отклонено: нестандартные каталоги, документы с внешними идентификаторами и системные
сущности должны иметь явный, поддерживаемый escape hatch через `BaseEntity` + metadata.

## Связь с другими решениями

ADR конкретизирует developer-experience postulate ADR-0003 и задаёт semantic descriptor,
на который опирается metadata-driven save этапа B3. Полная семантика действий документов,
проведения и регистров относится к последующим этапам E/F.
