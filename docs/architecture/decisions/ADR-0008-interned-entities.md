# ADR-0008: интернированные сущности (натуральный ключ и create-only запись)

- Статус: принято
- Дата: 2026-09-14
- Область: entity model, идентичность, service contract, транзакции и гонки создания

## Контекст

В приложении появился третий тип жизненного цикла рядом со справочником и документом.
Действующий прецедент — набор значений атрибутов КСУ (`SklNomOpa`): его нельзя создать
свободно, идентичность задаёт комбинация «номенклатура + канон значений», редактирования
нет вообще, а единственная операция — «найти или создать». Следующий случай уже назван
предметно: составной ключ внешнего производственного плана (заказ + ДСЕ + пара цехов).

Фактически таких типов **два, и оба уже дублируют друг друга**: кроме `SklNomOpaService`
ту же роль играет `AttributeValueService` (пять вариантов `getOrCreate`, значения словаря
тоже неизменяемы после создания). Машинерия разрешения гонки скопирована между сервисами
дословно: `MAX_ATTEMPTS = 3`, собственный `TransactionTemplate` с `REQUIRES_NEW`,
одинаковая форма «повторный SELECT → иначе INSERT» и побайтово одинаковый классификатор
уникального нарушения вместе с javadoc. Больше в платформе `REQUIRES_NEW` не использует
никто, кроме `NumberingCounterService` — и там противоположное решение (пессимистичная
блокировка строки счётчика).

Симптом отсутствующего контракта виден прямо в коде: оба сервиса вынуждены наследовать
широкий generic-контракт записи и затем гасить неприменимые методы исключением
(`AttributeValueService` — два, `SklNomOpaService` — четыре). Это не «забыли реализовать»,
а следствие того, что платформа не предлагает узкой формы для такого типа.

## Решение

### 1. Это не третий archetype, а две независимые оси

ADR-0004 §6 уже зафиксировал: `EntityKind` задаёт defaults, а capabilities их уточняют.
Интернирование лежит именно в capability-слое, а не в kind:

- **профиль записи** выражается capability типа (`descriptor.capabilities().writes()`).
  Причём профили у живых случаев разные: `AttributeValue` — `CREATE`, а `SklNomOpa` —
  пустой набор, потому что создание принадлежит канонизации, а не generic-пути. Один
  новый kind не смог бы выразить это различие;
- **идентичность** — то, что описывает маркер `InternedEntity`.

Общих колонок у этих типов нет и не появится (набор значений против «тип + значение»
против «заказ + ДСЕ + цеха»), поэтому структурный golden path вводить нечего.

### 2. Маркер поведения, а не `@MappedSuperclass`

`org.ipro.crud.InternedEntity` объявляет только `interningKey()`. `StandardCatalogEntity`
и `StandardDocumentEntity` — это `@MappedSuperclass`, потому что у справочника и документа
есть общий набор полей; у интернированного типа общность только поведенческая.

### 3. Один общий механизм интернирования

`org.ipro.crud.NaturalKeyCreateSupport` владеет всем, что одинаково у любого интернирования:

1. тело попытки выполняется в **своей** транзакции (`REQUIRES_NEW`) — на PostgreSQL
   отменённая транзакция помечает соединение как aborted, и продолжать работу в
   вызывающей транзакции после уникального конфликта нельзя;
2. повторный SELECT внутри транзакции попытки возвращает строку победителя гонки;
3. уникальное нарушение классифицируется по цепочке причин (Hibernate может пробросить
   JPA-обёртку, своё исключение напрямую или Spring `DataIntegrityViolationException`);
4. исчерпание попыток — отказ, называющий ключ, с исходным нарушением в `cause`.

### 4. Канонизация ключа остаётся в типе

Платформа владеет поведением интернирования, но не составом ключа. Живые случаи уже
разные: у значения словаря ключ ветвится по `refId` (два уникальных индекса схемы),
у набора — свёртка отсортированных `typeId:valueId`. Общий «canonical key DSL» с
рефлексией по полям не вводится: канонизация — предметная функция, и подменять её
общим механизмом значит потерять предметные правила (нормализация чисел, отсев пустых,
проверка принадлежности значения типу).

### 5. Граница с обычным справочником проходит по схеме

`StandardCatalogEntity` глобальную uniqueness намеренно не задаёт: строки справочника
ведёт пользователь, и код — натуральный ключ по смыслу, но не по ограничению. Интернированный
экземпляр — наоборот: дедупликация обязана быть гарантирована базой, иначе гонка даст
дубль, который не поймает ни retry, ни канонизация. Это различие проверяется забором
(`InternedEntityContractTest`): интернированный тип обязан объявить `@Table(uniqueConstraints)`
и не может быть `@MappedSuperclass`.

### 6. Что осознанно не вводится

- новый `EntityKind` (у `INFORMATION_REGISTER` уже есть цена «объявлено без семантики»);
- новый реестр или classpath-скан: регистрация берётся из `ManagedEntityCatalog`;
- собственные `InstanceName`/`FetchPlan`: используются границы C3/C4;
- «canonical key DSL» с рефлексией по полям (см. §4).

### 7. Срок службы узкого сервисного шва

Узкая service-форма для таких типов (`InternedEntityService`: только чтения и один
`getOrCreate`, без `update`/`delete` в интерфейсе вообще) вводится **после** волны E C4.6
и вместе с удалением `AbstractBaseService`, на canonical-шве ADR-0007 §1. Причина
порядка: `AbstractFindOrCreateService extends AbstractBaseService` завёл бы нового
наследника compatibility-базы ровно тогда, когда C4.7 её удаляет, и список
`CompatibilityMigrationArchitectureTest` — который по правилу можно только уменьшать —
пришлось бы расширить.

### 8. `displayName` у интернированного типа — производный кэш

«Неизменяемость» означает отсутствие пользовательского редактирования содержимого и
идентичности, а не «нет UPDATE вообще». `SklNomOpa.displayName` пересобирается той же
транзакцией, что и переименование значения словаря, и остаётся persisted-представлением
для отчётов, печати, сортировки и RLS-каталога значений. Перевод его в read-time
`InstanceName` — отдельное решение: оно затрагивает запросы отчётов, `displaySortFields`
и каталог значений, поэтому делается только при подтверждённой потребности.

## Последствия

- Оба живых сервиса сократились до предметной канонизации и вызова одного компонента;
  `AttributeValueService` и `SklNomOpaService` больше не содержат своей копии retry.
- Третий случай (составной ключ плана) получает разрешение гонки бесплатно, а не
  копированием кода.
- Диагностика отказа стала предметной: называется ключ, исходное ограничение остаётся
  в `cause`. Ранее в обоих сервисах после последней попытки повторно бросалось исходное
  нарушение без контекста, а строка `IllegalStateException("Недостижимо")` была
  недостижимой.
- Новый интернированный тип обязан объявить уникальный индекс: маркер без гарантии схемы
  теперь не проходит забор.
- Профиль записи по-прежнему задаётся не маркером, а capability типа, поэтому «create-only»
  и «без generic-записи вообще» продолжают различаться.

## Рассмотренные альтернативы

### Новый `EntityKind` (третий archetype)

Отклонено: kind выражает структурный golden path (поля, нумерация, колонки UI), а у этих
типов общих полей нет; к тому же один kind не выразил бы разные профили записи живых
случаев. ADR-0004 §6 уже допускает уточнение capabilities и делает новый kind избыточным.

### `@MappedSuperclass` с общими полями

Отклонено: полей для общего наследования нет. Единственное общее — поведение.

### Оставить разрешение гонки в каждом сервисе

Отклонено: код уже продублирован дословно, и третий случай гарантированно скопировал бы
его снова, вместе с классом ошибок вида «aborted-транзакция ломает внешнюю».

### Трактовка как DDD value object

Отклонено: value object не имеет идентичности, а здесь есть и идентичность, и внешние
ключи на строку, и уникальный индекс. Верная аналогия — интернирование экземпляров
(пул строк), и именно поэтому существует retry: интернирование без конкурентного
разрешения не работает.

## Связь с другими решениями

- ADR-0004 §6 — kind задаёт defaults, capabilities уточняют: интернирование добавляет
  capability и поведение, не новый kind.
- ADR-0007 §1 — canonical composition boundary: узкий service-шов интернирования строится
  на нём, а не на compatibility-базе (§7 этого ADR).
- ADR-0007 §3 — судьба generic CRUD-баз: удаление `AbstractBaseService` — условие порядка
  для service-шва интернирования.
