# ADR-0022: стандартный список регистра и отдельный редактор ключа

Дата: 2026-10-09. Решение реализовано для двух пилотов; PostgreSQL-проверки
конкурентной записи пройдены (55 / 55). Пользовательская проба ещё предстоит.
[Протокол PostgreSQL](../evidence/register-r8-postgresql-20261009.md).

## Исходное состояние и проблема

Общая ListForm обеспечивает колонки, отборы, сохранённые виды, действия и
навигацию. Подчинённый пилот использовал отдельное окно истории / среза:
два интерфейса и отдельный путь чтения. RegisterRecords и RegisterKeyChanges
предоставляют серверные команды, но сами по себе не дают UI смены ключа.
Обычный ItemForm записывает все bindings; одного backend-запрета недостаточно
для удобства. Старый GridViewState не сохранял режим / дату списка.

## Варианты и выбор

1. Отдельные формы двух регистров: повторение интерфейса и проверок.
2. Знания о регистрах внутри platform-vaadin: зависимость общего UI от
   прикладного пакета регистров, нарушение направления модулей.
3. Общий SPI настройки семейства форм с адаптером регистров в приложении.

Выбран третий вариант. FormTypeCustomization применяется перед настройками
конкретной сущности. UI-модуль получает общие контракты формы и чтения страниц;
RegisterRegistry и правила победителя остаются вне UI-модуля.

## Чтение и состояние

- RegisterFormCustomization поддерживает только типы RegisterRegistry. Для
  периодического типа добавляются «История / Срез последних» и DateTimePicker
  «На дату», шаг 1 мс. Непериодический тип показывает историю.
- ListPageReader получает specification, структурное дерево условий, контекст,
  pageable и fetch paths. История и срез читаются тем же BaseService / canonical
  LIST, что и обычный список. ENTITY / RLS сохраняются; ATTR не вводятся.
- RegisterListFilterPhases относит измерения и их вложенные пути к фазе до
  выбора победителя, ресурсы и период — к фазе после. AND разделяется; смешанное
  OR отвергается с понятным сообщением. Непрозрачный specification контекста
  допустим в истории, в срезе требует явного отказа.
- Победитель определяется прежними правилами period / recordingOrder /
  lineNumber. Колонки, сортировка, fetch и count остаются общими.
- Группировка грида для семейства выключена в этой итерации: прежние отдельные
  group/count запросы не учитывают победителей. Сортировка, отборы и страницы работают.
- Библиотека сначала валидирует дерево; адаптер компилирует scalar-сравнения
  с сохранением JPA-типа выражения. Cast к интерфейсу Comparable не используется:
  Hibernate не поддерживает его как SQL-тип.
- GridViewState.options хранит режим, asOf и контекст. Старые конструкторы /
  JSON продолжают читаться. Ссылки хранят ID; access.detail при открытии повторно
  проверяет доступность каждого элемента. Миграции таблиц нет.
- Ссылка списка содержит ограниченный Base64URL state, который не даёт прав.
  Маршрут и чтение проходят обычные проверки. Для ITEM state запрещён;
  старые адреса сохраняются. Повторное открытие восстанавливает режим / дату / отборы.
- Представления регистратора читаются пакетно существующим сервисом; недоступный
  документ маскируется без удаления строки регистра.

## Редактирование

Bindings измерений / периода блокируются после появления ID. Блокировка
сохраняется при переключении режима карточки и исключает запись этих bindings
даже при программной подстановке UI-значения. Ресурсы независимого регистра
редактируются обычным путём согласно правам. Generic CRUD подчинённого закрыт.

Действие «Изменить ключ записи» существует только при keyChangeAllowed.
Доступность использует RegisterKeyChangePermissions; сервер повторяет проверки.
RegisterKeyDialog содержит только измерения / период, создаёт отдельный черновик
и передаёт ID, ожидаемую версию, IDs ссылок и период в RegisterKeyChanges.
Отмена не меняет выбранную строку; успех обновляет список и снимает выделение.
Регистратор / технические поля не редактируются; документ не сохраняется.
Типы вне RegisterRegistry, включая похожие неизменяемые сущности, сценарий не получают.
Понятные отказы имеют кнопку копирования сообщения.

## Формирование при сохранении документа

AccountingObjectDocumentLifecycles вызывает AccountingObjectRegisterGeneration
в onSave: прикладная валидация, затем clear / add один раз. Прежний contribution
participant снят. Пересохранение документа заменяет ручное исправление его строк
согласно принятой политике этого пилота.

Команда объявляет позиции документа (ADR-0026), и это объявление — вето для beforeSave:
документ сохраняется только из команды, объявившей его позиции. Managed-копию, которую
возвращает merge на обновлении, связывает с объявлением платформа, поэтому приложению
не нужны ни сравнение ID и Hibernate-класса, ни свой scope. Право RegisterRecords
по-прежнему даёт подлинный активный canonical callback, а не объявление команды.
ObjectProvider откладывает получение генератора до callback и исключает цикл
инициализации lifecycle / canonical write / read service.

## Контракты и последствия

FormTypeCustomization — APP_SPI; FormMessages, ActionDecision и
FormBindingRegistry — APP_API. FormBinding — MODULE_API, поскольку он входит
в сигнатуры registry. ListPageReader — MODULE_API; остальные helpers — INTERNAL.
Состав и signature baselines фиксируются целевыми gates. Новое EXECUTE назначается
явно, согласно ADR-0021. Таблицы не меняются; общий posting engine в пакет не входит.
