# ADR-0006: сценарные FetchPlan и единый InstanceName

- Статус: принято; реализация начинается с этапа C3
- Дата: 2026-09-13
- Область: platform API/SPI, read pipeline, fetch-политика, отображаемое имя сущности
- Связанные документы: [`JMIX_GitVaa_Roadmap_v2.md`, C3](../../../JMIX_GitVaa_Roadmap_v2.md#c3-fetchplan--instancename-pilot),
  [`c3-fetchplan-instance-name-plan.md`](../c3-fetchplan-instance-name-plan.md),
  [`appdev-first-audit.md`](../appdev-first-audit.md) (`ADX-07`, `ADX-09`)

## Контекст

Платформа уже имеет metadata-driven формы, RLS enforcement, атомарное сохранение
агрегатов и каталог управляемых сущностей. Однако загрузка графа данных и
формирование отображаемого имени сущности остаются разрозненными:

- fetch-графы собираются вручную в нескольких местах (`AbstractBaseService`,
  `GenericOwnedSectionService`, `LookupService`), а прикладной UI задаёт собственные
  depth-константы, вычисляет association paths и перечитывает сущности, чтобы избежать
  `LazyInitializationException` после закрытия persistence context (`ADX-07`);
- отображаемое имя сущности формируется параллельно через `HasDisplayName`,
  `toString`, `displaySortFields`, `selectColumns` и отдельные объявления display fields
  глобального поиска (`ADX-09`);
- нет общего контракта, который сообщает, какие attribute paths нужны для вычисления
  имени и для сценарного отображения, поэтому эти зависимости не попадают в план
  загрузки автоматически.

При этом C3 не должен превратиться в новый универсальный data-access слой: попытка
сделать одну абстракцию для fetch, RLS, persistence и telemetry создаст god object и
продублирует уже существующие границы.

## Решение

### 1. FetchPlan и InstanceName — два специализированных компонента

Вводятся ровно два platform-компонента с разными обязанностями:

- **FetchPlan resolver** определяет граф загрузки по ключу `(entityClass, scenario)`;
- **InstanceName resolver** формирует отображаемое имя уже загруженной entity.

Они не объединяются в общий registry framework, не образуют фасад C4 и не заменяют
существующие platform-механизмы. Универсальный data-access facade остаётся предметом
C4 и должен строиться поверх проверенных правил, а не вместо них.

### 2. Одна read orchestration boundary, разные collaborators

FetchPlan и RLS подключаются к существующему read pipeline, но остаются разными
компонентами:

| Обязанность | Владелец |
|---|---|
| Определить и применить ограничения доступа | `RlsPolicyEnforcer` |
| Определить граф загрузки сценария | FetchPlan resolver |
| Выполнить запрос | существующий repository/query adapter |
| Сформировать имя загруженной entity | InstanceName resolver |

FetchPlan не становится частью RLS policy, RLS не вычисляет fetch paths,
`AbstractBaseService` не превращается в универсальный data-access object. Новая третья
точка входа в persistence не создаётся.

### 3. `ManagedEntityCatalog` — единственный источник набора управляемых сущностей

Все компоненты C3 получают набор управляемых сущностей из `ManagedEntityCatalog`.
Собственный classpath scanner для FetchPlan или InstanceName запрещён. Дополнительно
не создаётся второй сканирующий каталог: если компоненту нужен набор сущностей,
каталог предоставляет его как read-only представление уже построенного metamodel-снимка.

### 4. Metadata не дублируется; приоритет резолюции фиксирован

FetchPlan и InstanceName используют существующую per-entity metadata как исходные
факты. Новая декларация добавляется только как **явный override** для сценарного
отличия, которое нельзя однозначно вывести из Java type, JPA, Bean Validation и
существующей UI metadata. Четвёртое независимое семейство описаний сущности не
создаётся.

Приоритет резолюции отображаемого имени:

```text
явный InstanceName override
  -> metadata-derived default (эффективная metadata сущности)
  -> HasDisplayName compatibility (только для немигрированных сущностей)
```

`HasDisplayName` остаётся compatibility adapter'ом на время миграции, но не является
новым рекомендуемым API и не применяется к уже мигрированным пилотным сущностям.

Миграция является opt-in: единый источник включается декларацией `@InstanceName` на
сущности. Внутри декларации явные attribute paths имеют приоритет, а их отсутствие
означает вывод состава из metadata (`displaySortFields`). Сущность без декларации
сохраняет прежний источник до отдельной миграции, поэтому внедрение резолвера не меняет
представление немигрированных сущностей. Это согласует общий приоритет резолюции с
требованием C3.2 «непилотные сущности сохраняют текущее поведение».

### 5. Сценарный FetchPlan и fail-fast диагностика

Ключ плана — `(entityClass, scenario)`. Стандартный план выводится из эффективной
metadata; явный plan используется только как override для отличающегося сценария.
Invalid path является **startup error**, а не runtime fallback. Стандартный план не
рекурсивно загружает весь `@Lookup`-граф: обязательны ограничение глубины, защита от
циклов, детерминированный порядок путей и диагностируемая причина включения каждого
пути.

### 6. Startup validation зависимостей instance name

InstanceName объявляет attribute paths, необходимые для вычисления имени. FetchPlan
включает эти зависимости в соответствующие `LOOKUP` и `DETAIL` планы, а старт
приложения валидирует их. Вычисление instance name после закрытия persistence context
не инициирует lazy load и не выполняет скрытых repository-запросов.

### 7. Public API, SPI и internal разделяются с первого среза

Публичными остаются только контракты, необходимые прикладному коду для декларации или
явного расширения поведения. Registry implementation, кэши, сборка defaults и
startup-validation являются internal implementation. Новый тип не становится `public`
только ради удобства wiring или тестирования.

### 8. Каждый новый механизм заменяет старый код

Код C3 не считается завершённым, пока пилотные формы продолжают использовать ручные
`EntityGraph` hints, fetch-depth constants, reload detached entity или обработку
`LazyInitializationException` как штатный путь. Новый API не остаётся вторым
поддерживаемым путём рядом со старым.

### 9. Зависимости сценария выбора объявляются на ссылающемся поле

Если форма после выбора значения сразу читает связи цели (типовой случай — автозаполнение
поля из выбранной номенклатуры), эта зависимость объявляется в metadata поля через
`@Lookup(fetch = {...})`, а не перечитыванием сущности по ID в форме. Такое объявление
является декларацией намерения: оно объясняет, почему связь нужна этому месту
использования, валидируется при старте и попадает в план `LOOKUP` цели.

Плана и сущности недостаточно, чтобы выразить такую зависимость: она принадлежит
конкретному месту использования, а не самой сущности и не её имени. Обратная сторона
решения — план `LOOKUP` сущности собирается как объединение объявленных зависимостей всех
ссылающихся полей, то есть возможна небольшая перегрузка графа. Это сознательный размен в
пользу детерминированного и кэшируемого ключа `(entityClass, scenario)`: план не зависит от
того, из какого поля открыт выбор, и не смешивается с планами других сценариев.

### 10. Сценарии `DETAIL` и `LIST` независимы

`findById` для формы загружает `DETAIL`, а список — `LIST`. Эти планы обслуживают разные
представления и не обязаны совпадать: ссылка, нужная только в гриде, не должна автоматически
утяжелять форму. После сохранения список обновляется отдельным чтением через `LIST`; вставка
экземпляра, загруженного по `DETAIL`, в список без повторного чтения не является контрактом.

Registry валидирует каждый план отдельно и не требует `DETAIL ⊇ LIST`. Дополнительные пути
динамического вида расширяют базовый план потребителя, не заменяя его. Это сохраняет
корректность отображения и не связывает глубину формы с настройками таблицы.

### 11. Ранняя write-авторизация на границе сервиса

Решение об авторизации write-операции принимается **на входе** в
`create/update/delete/save`, а не при вызове `repository.save`: иначе запрещённая
операция успевает запустить bean-валидацию, бизнес-правила, lifecycle hooks и
before-события. Пользовательский расширитель платформы не должен получать управление до
решения о правах — валидация раскрывает бизнес-информацию, а хук может выполнить внешний
побочный эффект, который откат транзакции не отменит. Для `delete` это ещё и вопрос
объёма: удаление owned sections уходило в БД до проверки права.

Гейт не выводит политику заново: он вызывает тот же `RlsPolicyEnforcer`, что и
`RlsRepositoryEnforcementAspect`, поэтому раннее решение и repository-граница не могут
разойтись. Двойная проверка авторизованного пути допустима осознанно: aspect
пересчитывает capability по состоянию **после** хуков (хук может изменить значение
измерения), а flush-listener `RlsWriteEnforcementListener` остаётся последним рубежом
для каналов в обход сервиса и commit-time dirty checking. Кеширование решения внутри
операции не вводится до подтверждённой проблемы производительности.

Контракт закреплён поведенчески (`RlsServiceWriteBoundaryIT`): отказ приходит до
валидации, before-события, lifecycle-хука и удаления owned sections, а проверки
не-вакуумные — на разрешённом пути те же шпионы обязаны фиксировать вызовы.

### 12. Единственный механизм отображаемого имени

Публичный контракт — `InstanceNameProvider` с одним методом `resolve(Object)`; всё
остальное (`InstanceNameResolver` с составом имени и диагностикой) — детали реализации,
нужные fetch-планам и startup-валидации. Лестница разрешения ровно одна: `null` → пустое
представление; неинициализированный proxy → `Type#id`; объявленное `@InstanceName` →
вычисленное имя (пустое объявленное имя тоже даёт ссылку, **а не** откат на legacy); нет
декларации, но есть `HasDisplayName` → legacy-имя; иначе `Type#id`. Последняя ступень
намеренно не `toString()`: `Class@hash` ничего не говорит пользователю.

Статический `InstanceNameBridge` сохраняется только как адаптер для static-контекстов
(форматирование значения грида, снимок аудита) и **не содержит своей лестницы**: он
делегирует провайдеру. Регистрации контекстов сосуществуют, вместо того чтобы
перезаписывать друг друга: в одной JVM живёт несколько контекстов (приложение,
кэшированные и вытесняемые Spring тест-контексты, частичные контексты
auto-configuration), и при перезаписи закрытие любого из них обнуляло глобальное
состояние для остальных — наблюдаемая порядко-зависимость набора тестов была
проявлением этого дефекта. Установка вынесена в lifecycle-managed
`InstanceNameBridgeInstaller`; пользовательский `InstanceNameProvider` выигрывает у
платформенного как провайдер рендеринга, но анализ состава имени остаётся у платформы —
иначе пользовательский провайдер унёс бы с собой и fetch-планы.

Активная регистрация выбирается **по объявлению типа**, а не по очереди установки: для
отображаемого значения берётся самая поздняя регистрация, которая знает его тип; для
`declaredName`, `instanceNamePaths` и `instanceNameFetchPaths` тот же выбор делается по
запрошенному классу. Только если подходящей регистрации нет, используется последняя
установленная. Правило «всегда последняя» делало авторитетным любой контекст, поднявшийся
позже, включая частичный, чей набор metadata не содержит объявлений: имя терялось в UI и
аудите, а fetch-анализ мог потерять декларацию, хотя живой контекст её знал. Класс прокси
определяется через lazy initializer без его инициализации; отдельный расчёт типа или
резолюции имени в bridge не дублируется.

## Последствия

Положительные:

- сценарная загрузка перестаёт зависеть от знания Hibernate session в UI;
- ошибочный путь загрузки обнаруживается при старте, а не при открытии формы;
- lookup, search и audit используют одно представление сущности;
- RLS enforcement и fetch-политика не смешиваются;
- `ManagedEntityCatalog` остаётся единственной точкой разрешения сущностей.

Ограничения и риски:

- FetchPlan может выродиться в eager-load всего графа — контролируется сценарными
  правилами, depth/cycle guards и измерениями query count/размера графа;
- instance name может обратиться к lazy association — контролируется объявленными
  зависимостями и detached-render тестами;
- публичная поверхность может вырасти автоматически — требуется явная классификация
  API/SPI/internal в каждом срезе;
- C3 может незаметно расшириться до C4 — в C3 нет generic CRUD и нового обязательного
  data-access facade.

## Рассмотренные альтернативы

### Один универсальный «data access» компонент для fetch, RLS и имени

Отклонено: смешивает security enforcement, persistence и представление; создаёт god
object и дублирует уже существующие границы (`RlsPolicyEnforcer`, repository/query
adapter). Противоречит AppDev-first: прикладной код получил бы новый обязательный слой
вместо декларации намерения.

### Новый classpath scan для FetchPlan/InstanceName

Отклонено: `ManagedEntityCatalog` уже является единственной строгой границей
разрешения управляемых сущностей; второй сканер означал бы два независимых набора
сущностей и расхождение при старте.

### Объявлять отображаемое имя через новый интерфейс вместо metadata

Отклонено как единственный механизм: metadata уже содержит display-состав
(`selectColumns`, `displaySortFields`), и его дублирование в интерфейсе вернуло бы
`ADX-08`. Явный override остаётся, но только там, где metadata не выражает формат.

### Оставить `HasDisplayName` основным контрактом и не вводить override

Отклонено: не даёт объявить fetch-зависимости имени, поэтому UI продолжит вручную
гидратировать сущности, а форматы lookup/search/audit будут расходиться.

### Строить фасад C4 сразу в C3

Отклонено: непроверенные FetchPlan и InstanceName в одном фасаде скрыли бы их ошибки и
смешали бы ответственность за доступ и за загрузку. C3 сначала доказывает компоненты
по отдельности на пилоте.

## План реализации

1. C3.0 — расчистка периметра: снятие доказанного повторного RLS write/delete
   enforcement, отдельная autoconfiguration C3, использование `ManagedEntityCatalog`
   без нового сканирования.
2. C3.1 — общий контракт зависимостей instance name и его startup validation.
3. C3.2 — InstanceName resolver и пилот на одной lookup-сущности и `ReceivingDocument`.
4. C3.3 — FetchPlan registry (`LIST`, `DETAIL`, `LOOKUP`, `ROW`) с depth/cycle guards и
   диагностикой причин.
5. C3.4 — подключение к существующей read-границе.
6. C3.5 — пилотная миграция `ReceivingDocument`, `PrdSpec`/`PrdSpecMtr`/`PrdSpecOper` и
   удаление ручного fetch-кода из `PrdSpecMtrFormCustomization`.
7. C3.6 — приёмка и измерения.
8. C3.7 hardening — стабилизационный этап без нового пользовательского функционала, в
   котором уточняется то, что C3.0–C3.6 оставили за скобками: ранняя write-авторизация,
   действительно единый механизм имени и закрытие оставшихся обходов fetch-планов.
   Выделен после ревью C3: утверждение «незакрытых пунктов нет» было слишком сильным —
   ранняя проверка `checkRlsWrite/checkRlsDelete` снималась в C3.0 как «дубль», но дублем
   она не была (см. п. 11), а у имени оставались две лестницы разрешения (см. п. 12).

## Прогресс реализации

- Срез C3.0 (2026-09-13): расчистка периметра — снят повторный RLS write/delete
  enforcement, введена отдельная autoconfiguration C3 и read-only доступ к набору
  управляемых сущностей.
- Срез C3.1–C3.2 (2026-09-13): `@InstanceName` с startup-валидацией и
  `InstanceNameResolver`; пилот — `ReceivingDocument` и `Nomenclature`.
- Срез C3.3–C3.5 (2026-09-13): `FetchPlanRegistry` (`LIST`/`DETAIL`/`LOOKUP`/`ROW`),
  `@Lookup(fetch = ...)`, план `LOOKUP` подключён к `LookupService.search` и
  `SelectionFormAssembler`; `PrdSpecMtrFormCustomization` декларативна, `ADX-07` закрыт
  (`ApplicationFormFetchBoundaryTest`), каналы отображения имени унифицированы,
  `ADX-09` закрыт по пилоту.
- Срез C3.4 (завершение, 2026-09-13): все четыре сценария потребляются существующей
  read-границей — `LIST` и `DETAIL` в `AbstractBaseService` (список и загрузка формы),
  `ROW` в `GenericOwnedSectionService` и `ItemTable`; локальное перечисление ссылочных
  полей из границы удалено, явные пути остались только как override. Приёмка
  поведенческая (`FetchPlanReadBoundaryIT`).
- Срез C3.6 (2026-09-13): измерения сняты в тесте (`FetchPlanMeasurementIT`): состав
  плана не теряет ни одного пути прежнего графа, план не дороже по количеству запросов,
  detached-рендер не инициирует lazy load, а `DETAIL` не грузит зависимости чужого
  сценария и коллекции вне сценариев.
- Срез C3.7 hardening, блок 1 (2026-09-13): ранняя write-авторизация
  (`authorizeWrite`) в `create/update/delete/save` — до нормализации, валидации,
  lifecycle hooks и before-событий (п. 11). Проверка поведенческая и не-вакуумная:
  `RlsServiceWriteBoundaryIT` (12 тестов), включая проверку того, что на разрешённом
  пути те же шпионы срабатывают. Регрессия воспроизводилась обратным экспериментом:
  при снятом гейте запрещённое удаление доходит до `publishDeleting`.
- Срез C3.7 hardening, блок 2 (2026-09-13): единый `InstanceNameProvider` (п. 12) —
  у bridge больше нет своей лестницы, добавлен lifecycle-managed
  `InstanceNameBridgeInstaller`, регистрации контекстов не перезаписывают друг друга,
  пустое объявленное имя не откатывается на legacy, добавлены недостающие тесты
  фактического UI-пути (`bridge.displayName(proxy)`, detached proxy). Исправлено условие
  auto-configuration: резолвер требует `ManagedEntityTypes`, поэтому частичный контекст
  получает backoff, а не `UnsatisfiedDependencyException`.
- Срез C3.7 hardening, блоки 3–5 (2026-09-13): стандартные list read-overloads
  применяют `LIST`, `LookupService.findAll/search/findById` — `LOOKUP`, а selection grid
  передаёт явный сценарий `LOOKUP`; динамические fetch paths расширяют сценарий. `ItemTable`
  перечитывает строки секции одним запросом с `ROW` и переносит гидратированные ссылки без
  потери несохранённых правок. Правило `DETAIL ⊇ LIST` снято (п. 10). Порядок управляемых
  типов, lookup-деклараций, путей и диагностических причин стабилизирован; добавлены
  граничные тесты для стандартных overload и независимости планов.
- Срез C3.7 hardening, блок 6 (2026-09-13): закрытие порядко-зависимости набора тестов.
  Авторитет регистрации моста для рендеринга и анализа fetch-путей определяется типом
  сущности (п. 12). Аудит перестал быть
  заимствованным: `AuditConfig` подключается к точке входа явно (`@Import`), поэтому его
  инфраструктура есть в каждом контексте, маппящем `BaseEntity`, включая slice-контексты
  (`JpaAuditingSliceContractTest`); раньше slice-контекст настраивался JVM-глобальным
  AspectJ-аспектом из чужого контекста и падал (`IllegalStateException: … has been closed
  already`) при его закрытии, а пока тот был жив — писал аудит «по доверенности».
  Отдельно устранён дефект сборки: два тест-файла, из-за которых компилятор тестов на
  каждом билде сносил и пересобирал сотни классов, что давало массовые падения прогонов.
  Приёмка — полный набор в default order и два случайных порядка, включая зерно,
  на котором набор до исправления заканчивался ошибками аудита.
- Распространение `@InstanceName` на остальные сущности остаётся отдельной миграцией и
  не блокирует завершение C3.7.

## Связь с другими решениями

ADR опирается на AppDev-first (ADR-0003), семантические archetypes (ADR-0004), единую
точку lifecycle (ADR-0005) и security boundary C2. Он уточняет, как сценарная загрузка
и отображаемое имя подключаются к существующему read pipeline, не создавая новый
обязательный прикладной слой и не смешиваясь с RLS.
