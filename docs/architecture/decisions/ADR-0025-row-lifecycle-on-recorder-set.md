# ADR-0025: lifecycle строки регистра на пути набора владельца — хуки вызываются

Дата: 2026-10-15. Статус: принято, реализовано и проверено — измерения, реализация и протокол
прогонов в [evidence](../evidence/register-adr0025-row-lifecycle-20261015.md).

- Область: путь замены набора подчинённых строк документом-владельцем (`RecorderSetWriter` и
  процедуры `RegisterRecords.forRecorder`), то есть четыре операции записи строк набора и
  очистка при удалении владельца.
- Связанные решения: [ADR-0005](ADR-0005-entity-lifecycle-and-application-behavior.md) (единая
  точка `EntityLifecycle`), [ADR-0013 §4](ADR-0013-information-register-v1.md) (регистр v1),
  [ADR-0015](ADR-0015-information-register-recorder.md) и
  [ADR-0020](ADR-0020-register-recorder-procedures.md) (набор владельца, процедуры),
  [ADR-0019](ADR-0019-owner-named-row-operation.md) (операция строки принадлежит владельцу),
  [ADR-0023](ADR-0023-register-key-write.md) (запись по ключу — второй путь тех же строк).
- Этап плана: [план выноса §3 и S3](../information-register-extraction-plan.md); долг назван
  открытым в [evidence S3](../evidence/register-s3-extraction-20261014.md) и
  [evidence S4](../evidence/register-s4-extraction-20261015.md).

## Что было и почему требуется решение

`EntityLifecycle` обещает (javadoc контракта): «Платформа вызывает callbacks из всех стандартных
save/delete путей, независимо от UI-канала». Замер показывает, что это обещание верно не везде:
строки подчинённого регистра пишутся тремя путями, и один из них не вызывает ни одного хука.

| Путь записи строки | Кто вызывает | Хуки строки |
| --- | --- | --- |
| запись по ключу (upsert, самостоятельный регистр) | `RegisterKeyWrites.set/delete` | `beforeSave`, `beforeUpdate`, `onSave`, `beforeDelete` вызываются |
| команда смены ключа | `RegisterKeyChanges.change` | `beforeSave`, `beforeUpdate`, `onSave` вызываются |
| **набор владельца** (документ-регистратор) | `RegisterRecords.forRecorder` → `RecorderSetWriter` | **не вызываются**: строки идут `persist`/`remove` напрямую |

Дефект именно в этом: правило строки, написанное для подчинённого регистра, молча не исполняется,
при том что диагностика (`EntitySummaryAssembler.lifecycleRows`) показывает handler по типу и
ничего не говорит о пути.

## Замеры, на которых принимается решение

| # | Что измерено | Значение |
| --- | --- | --- |
| M1 | прикладных `EntityLifecycle` handler'ов | 12: `User`, `Role`, `AttributeType`, `AttributeValue`, `Nomenclature`, `NomSklAttribute`, `PrdSpec`, `ReceivingDocument`, `GridFormView`, `AccountingObjectInstallation`, `AccountingObjectCorrection`, `NomenclaturePrice` |
| M2 | из них на строку регистра | ровно один — `NomenclaturePriceLifecycle` (`beforeUpdate`), и он про **самостоятельный** регистр `NomenclaturePrice extends PeriodicRegisterEntryBase`, который пишется по ключу, где хуки уже вызываются |
| M3 | записи через набор владельца | единственный регистр — `NomenclatureAccountingObject extends PeriodicRecordedRegisterEntryBase` (`recorderTypes = {AccountingObjectInstallation, AccountingObjectCorrection}`), и handler'а строки у него **нет** |
| M4 | порядок в платформенных путях | хуки **до** Bean Validation: `RegisterKeyWrites` (`lifecycles.beforeSave` → `validate`), `RegisterKeyChanges` (`beforeSave`/`beforeUpdate` → `validator.validate`), canonical/save-контракт — тот же |
| M5 | где валидируются строки набора сегодня | внутри `prepareRows`, то есть до присвоения окончательного порядка записи и до любой точки, куда можно было бы вставить хук без перестановки |
| M6 | диагностика | `lifecycleRows` описывает handler **типа** (пять состояний E3.1); оси «путь записи» у неё нет — состояние «этот путь хуки не вызывает» пришлось бы добавлять |

M3 меняет оценку дефекта, и это важно для решения: **сегодня ни одно прикладное правило не
пропускается молча** — пропускается сама возможность его написать. Владелец (документ) в этом
сценарии уже полностью покрыт lifecycle: строки порождает его `onSave`, и он вызывается. То есть
дефект — не наблюдённая потеря правила, а расхождение обещания контракта с машиной.

## Рассмотренные варианты

1. **Вызывать хуки на пути набора** — тем же набором и в том же порядке, что у записи по ключу.
   Выбран этот вариант.
2. **Не вызывать, но сделать видимым**: диагностика сообщает «путь записи не вызывает хуки
   строки». Отклонён, цена измерена: (а) диагностике нужна шестая ось — состояние про путь, а не
   про handler типа (M6), при этом ни один handler из M1 не выигрывает от этой надписи: у
   единственного регистра с регистратором handler'а нет вовсе (M3); (б) контракт `EntityLifecycle`
   пришлось бы переписать с «все стандартные пути» на список исключений, то есть решение
   закрепило бы расхождение вместо его устранения; (в) правило строки для подчинённого регистра
   нельзя будет написать в принципе — а именно этого ждёт владелец, генерирующий строки.
3. **Сопоставлять строки старого и нового набора по ключу и вызывать `beforeUpdate`** для пар.
   Отклонён по замеру: у строки набора нет стабильной идентичности между попытками — замена
   снимает старые строки и вставляет новые экземпляры (новые id, номера строк и порядок записи),
   а ключ самостоятельного регистра не является ключом подчинённого. Введение «это та же строка»
   изменило бы протокол ADR-0019/0020 (идентичность строки, номера, порядок), то есть вышло бы
   далеко за предмет ADR-0025. Названо как отдельное решение, если понадобится.

## Решение

1. **Хуки строки вызываются на всех операциях набора.** `beforeSave`, `onSave` — для каждой
   вставляемой строки; `beforeDelete` — для каждой удаляемой строки, и при замене набора, и при
   очистке, и при удалении одной строки, и при очистке на удалении документа-владельца.
2. **Порядок — платформенный, а не местный:** подготовка строки (тип, отсутствие id, уникальность
   экземпляра, принадлежность регистратору, номер строки) → нормализация периода
   (`RegisterPeriodListener.normalize`, правило S2) → присвоение порядка записи под замком →
   **`beforeSave`** → **Bean Validation** → авторизация набора (`RecorderSetWriteAuthorizer`) →
   `beforeDelete` для удаляемых → `remove`/flush → `persist`/flush → **`onSave`**.
   Хук видит строку в окончательном виде (номер и порядок записи уже присвоены), а валидация
   видит последствия мутации из хука: порядок «хук → валидация» тот же, что в M4, и не перевёрнут
   молча ни на этом пути, ни на соседних.
3. **`beforeUpdate` на этом пути не вызывается — и это проверяемое свойство, а не умолчание.**
   У пути нет семантики обновления: строки всегда новые экземпляры (см. вариант 3). Тест
   фиксирует отсутствие вызова явно, поэтому «хук не вызван» здесь отличимо от «хук забыли».
4. **`beforeAggregateSave` не вызывается:** агрегат — документ-владелец, а не строка.
5. **Вето откатывает операцию владельца целиком.** Хук бросает `ValidationException` — весь набор
   не записывается, транзакция сохранения документа помечается на откат; частично применённого
   набора не остаётся.
6. **Ровно один раз на затронутую строку.** Хук не вызывается для строк, которых операция не
   касается: при добавлении — для уже существующих строк набора, при замене — сверх старого и
   нового набора, при удалении одной строки — для остальных.
7. **События и аудит строк на этом пути не публикуются** — граница решения, названная явно.
   Событийный поток документа уже несёт вложенные секции (`attachedSections`), а построчный
   журнал и аудит — контракт записи по ключу (ADR-0021/0023). Добавление построчных событий здесь
   изменило бы телеметрию и аудит, а это отдельное решение со своей приёмкой.
8. **Права записи владельца у хука строки нет.** Хук получает `EntitySaveContext` строки, а не
   документа; токен владельца (`AggregateSaveLifecycleScope`/`CanonicalSaveLifecycleScope`)
   сверяется по тождеству сущности, поэтому `RegisterRecords.forRecorder(...)` из хука строки
   отвергается с `REGISTER_OWNER_WRITE_CONTEXT_REQUIRED`. Это проверено тестом, а не обещано
   комментарием.
9. **Контекст хука — контекст строки, и он различает пути:** имя операции
   `set-register-recorder-set:<Регистр>` / `delete-register-recorder-set:<Регистр>` (у записи по
   ключу — `set-register-key:` / `delete-register-key:`), `aggregateType` = тип строки,
   `aggregateId` = null у новой строки на `beforeSave` и id после `persist` на `onSave`.
10. **Выключателя хуков нет.** Реестр `EntityLifecycleRegistry` — обязательный участник писателя
    набора: ни один конструктор не подставляет «пустой реестр» по умолчанию, поэтому «забыли
    передать» и «приложение не объявило правил» различимы, а вернуть тихий обход нельзя.
11. **Повтор операции доставляет хуки заново** — как и на пути по ключу: повтор идёт новой
    транзакцией (`RecorderSetTransactionExecutor`), и её строки — новые строки.

## Приёмка

| Критерий | Чем доказано |
| --- | --- |
| «хук ровно один раз на вставленную строку» | счётчик вызовов по каждой строке при добавлении, замене и очистке |
| «и ни разу на неизменённую» | счётчик по строкам, которых операция не коснулась (существующие строки при добавлении; строки других регистраторов и других регистров) |
| порядок «хук → валидация» | хук, портящий обязательное поле: отказ приходит из валидации после хука, а не до него |
| вето и откат | хук, бросающий `ValidationException`: документ и набор не сохраняются ни в одной части |
| `beforeUpdate` не вызывается | явный счётчик на нём |
| у хука нет прав владельца | попытка `RegisterRecords.forRecorder` из хука строки отвергается |
| поведение соседних путей не изменилось | прогоны записи по ключу, смены ключа и набора: H2 64/64, PostgreSQL 48/48 на одноразовой базе (числа — в evidence; пилотный прогон там же назван непокрытым и почему) |

## Границы

Не решается здесь: построчные события и аудит на пути набора (пункт 7); сопоставление строк
«та же строка» по ключу (вариант 3); перенос тестов движка в модуль — это S5; `EntityKind`
`INFORMATION_REGISTER` и F-ERP-3 — отдельное решение плана.
