# ADR-0020: процедуры записи регистра из lifecycle регистратора

- Дата: 2026-10-08.
- Статус: первый пакет процедур реализован и проверен на H2; следующая часть Р8 продолжается.
- Основание: согласованный план ListForm / смены ключа и запрос на простые процедуры
  очистки, добавления и удаления записей по регистратору.
- Связанные решения: ADR-0015, ADR-0017; план
  `docs/plans/information-register-r8-listform-key-commands.md`.

## Текущее положение

`RecorderSetWriter` заменял весь набор одного документа. Отдельная очистка была
доступна только закрытому участнику удаления документа. Прикладному коду нельзя
было добавить строки с сохранением существующих ID или удалить одну строку.

Открытый CRUD строк разрушил бы принадлежность регистратору и порядок записи.
Контекст с произвольным `RecorderRef` также не доказывает допуск к сохранению владельца.

## Решение

Прикладной контракт — `RegisterRecords.forRecorder(EntitySaveContext)` внутри
canonical `onSave`. Выданный handle предоставляет `clear`, `add`, `delete` и живёт
только в данном callback, потоке и транзакции. Его конструктор закрыт.

Canonical executor и aggregate save owner открывают свои package-scoped lifecycle
scopes после сохранения. MODULE_API scopes дают только чтение непрозрачного token;
открыть scope через прикладной API нельзя. Произвольный EventContext, прямой вызов
registry.onSave, before-хуки и afterCommit не предоставляют token. Проверяется также
managed persisted root, совпадение типа / ID, активная транзакция и Hibernate Session.

Изменение только записей регистра также продвигает optimistic version документа,
если текущий save ещё не продвинул её через шапку / секции / contribution.
Повторные процедуры одного callback не увеличивают версию повторно. Это относится
к lifecycle владельца; будущая ручная смена ключа строки документ не изменяет.

Каждая процедура использует PROPAGATION_MANDATORY. Ошибка внутри процедуры
помечает транзакцию rollback-only, даже если lifecycle перехватил исключение после clear.
Прикладной код не должен пытаться продолжать сохранение после такой ошибки.

Операции:

- `clear(type)` проверяет полный набор и возвращает число удалённых строк.
- `add(type, rows)` принимает новые экземпляры и возвращает сохранённые строки.
  Сервер назначает отсутствующий recorder, lineNumber и recordingOrder; чужой recorder
  и уже сохранённый ID отклоняются. Повтор одного экземпляра в списке также отклоняется.
- `delete(type, id)` удаляет одну строку только текущего регистратора. Чужой и
  отсутствующий ID дают одинаковый отказ. Остальные строки не перенумеровываются.

Номер добавляемой строки идёт после текущего максимального. При существующем наборе
add наследует его recordingOrder; старые ID / версии / порядок не меняются. Новый
набор получает новый порядок; последующие add наследуют его. Clear + add создаёт
новый набор. Пустой add не выделяет порядок.

Сериализация: документ, затем PESSIMISTIC_WRITE на существующем RecorderOrderClock
регистра. Очистка, добавление, одиночное удаление, прежняя replacement и удаление
документа используют этот mutex. При очистке / удалении он не продвигается.
Refresh clock выполняется после flush предыдущих изменений текущей транзакции.
Механизм retry остаётся снаружи транзакции владельца.

Весь набор читается внутренним RLS read scope. Авторизатор проверяет все удаляемые
и все добавляемые строки до записи. Add не требует delete прав на сохранённые строки.
Разрешение JPA callbacks при flush ограничено проверенными экземплярами, типом и
регистратором. ENTITY/RLS сохраняются; ATTR-проверок нет.

Прежние RecorderSetContribution / participant и поведение replacement сохраняются.
В частности, историческое продвижение clock при пустой replacement не меняется.

## Применение

```java
@Override
public void onSave(EntitySaveContext<MyDocument> context) {
    var records = registerRecords.forRecorder(context);
    records.clear(MyRegister.class);
    records.add(MyRegister.class, makeRows(context.entity()));
}
```

Или приложение вызывает только add / delete / не вызывает ничего. Платформа не
выбирает стратегию переформирования автоматически. Future posting lifecycle должен
получать такой же checked owner context; общий posting engine в этот пакет не входит.

## Последствия и оставшаяся работа

Новых таблиц и миграции данных нет. Установленный platform-core обновляется:
новые MODULE_API scopes фиксируются в реестре состава и signature baseline.

Default-off `RegisterMetadata.keyChangeAllowed` только объявляет будущую возможность.
На этом этапе JPA mapping ключей, команды их изменения и гранты пилотов не меняются.
Отдельное C5 право, команда смены ключа и её flush guard входят в следующий пакет.

Дополнение 2026-10-09: второй backend пакет описан в
[ADR-0021](ADR-0021-register-key-change-command.md). Он включает отдельную
команду / C5 право / snapshot guard; общий lock выделен в RegisterWriteMutex.
Правила процедур владельца и их полномочия остаются описанными выше.

Перенос формирования пилотного регистра из contribution в прикладной onSave и
подключение стандартной ListForm выполняются после реализации команды смены ключа.
Текущий participant продолжает работать; двойной генерации нет.

Приёмка первого пакета: H2 append / delete / clear-add / rollback / неподлинный и
истёкший context / узкий flush scope; регрессия canonical writes и состава модуля.
PostgreSQL гонки всего нового write контура проверяются до завершения итерации Р8.

Дополнение 2026-10-09: пилот перенесён на clear / add из прикладного onSave,
прежний participant снят. Стандартные списки и окно ключа описаны в
[ADR-0022](ADR-0022-standard-register-listform.md). Сам контракт RegisterRecords
остаётся прежним; стратегию переформирования определяет прикладной код.
