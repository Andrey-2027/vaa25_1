# ADR-0010: адрес типа в Entity Explorer — published-ключ, отдельная ветка host'а и один отказ

- Статус: принято (E3.0 — грамматика адреса, ветка host'а, гейт роли и история реализованы и
  проверены адресными тестами: `EntityExplorerAddressTest` 7/0, `FormRouteUrlBridgeTest` 25/0,
  `EntityExplorerRouteGateTest` 6/0, `EntityExplorerAddressWiringTest` 4/0,
  `DeepLinkRouteBaselineTest` 6/0, `platform-vaadin` 383/0/0. Живая приёмка по чек-листу §5
  плана среза выполняется на стенде, результат — в [`current-baseline.md`](../status/current-baseline.md))
- Дополнено E3.2.1 (§8.1–8.3a): якорь карточки — грамматика `?view=<tab>[/<section>]` в
  `EntityExplorerAddress` (там же 12/0), записи `view=` в baseline маршрутов, провод host ↔ вид ↔
  панель и сборка адреса окна из разобранного `Location` — §10
- Дата: 2026-09-27
- Область: публичный адрес **типа** (не записи), грамматика якоря карточки (`?view=`), ветка
  host'а и мост адреса, гейт диагностической роли и неразличимость отказа, резерв первых сегментов

  файл, вне Git), [`e3-configuration-studio-plan.md`](../../plans/e3-configuration-studio-plan.md)

- Опирается на: ADR-0009 (host адреса формы, кодек и каталог маршрутов, матрица `OpenResult`,
  dirty-контракт), ADR-0007 (таксономия экспозиции типов)

## Контекст

E2 дал приложению адрес **записи** («открыть эту карточку») и списка: `/records/{key}/{id}`,
`/lists/{key}`. Адреса **типа** нет: вход «Структура сущности» открывает вкладку без адреса, и
холодная ссылка на структуру типа невозможна. E3 отвечает на вопрос «что уже действует», и первый
его срез — научиться открывать карточку типа по ссылке, не подменяя адреса формы, не заводя второй
каталог ключей и не превращая карточку типа в фиктивную форму.

Ограничения, снятые измерением (E3.0, см. §0 плана среза):

1. `OpenResult.Opened` требует `FormRoute`; у карточки типа нет ни id записи, ни вида формы.
2. `FormRouteUrlBridge.historyChanged` игнорирует результат обработчика — типизированный результат
   нужен host'у, а не мосту.
3. `Workspace.open` для уже открытой вкладки только показывает её: повторный вход с новым ключом
   пришлось бы применять к тому же виду, а не открывать второй.
4. Дерево Explorer шире публикации: типы без published-ключа существуют (`NomAttributeValue`,
   `PrdSpecMtr`), и адрес для них выдумывать нельзя.
5. Проверка роли до этого среза была в трёх местах (пункт меню, вид, диалог подсистемы); route стал
   бы четвёртым.

## Решение

### 1. Адрес типа использует published-ключ E2

`/entity-explorer/{key}`, где `key` — published-ключ каталога маршрутов
(`PublishedFormRoute#entityKey()`), а грамматика ключа — та же `FormRoute.isKey`. Второго
пространства ключей не появляется: адрес типа и адрес формы ссылаются на один ключ, а различие —
только в разделе адреса.

Грамматика живёт в `EntityExplorerAddress` (`ROOT_SEGMENT`, `keyOf`, `format`, `claims`).
Ничего не нормализуется: регистр, лишний сегмент, query, фрагмент и percent-encoding дают отказ —
иначе у одной карточки было бы два адреса. `claims` отделён от `keyOf`: «адрес заявляет раздел» и
«адрес несёт ключ» — разные вопросы, и заявленный раздел без ключа получает отказ, а не тихую
главную.

Адрес типа **не наследует** linkability формы: наличие ключа не зависит от `NotLinkable` формы
(`LIST`/`ITEM`); legacy-ключи каталог принимает наравне с каноническими.

### 2. Раздел Explorer — отдельная ветка host'а, а не форма

Успех входа не выражается `OpenResult`: карточка типа не маршрут формы, и фиктивный `FormRoute`
ради `Opened` скрыл бы это. Мост получает второй, независимый обработчик
(`installExplorerEntryPoint(Consumer<String>)`), а `historyChanged` получает три ветки: Explorer →
свой обработчик, форма → `entryPoint`, иначе → главная.

`claimsAFormSection` **не** расширяется: он управляет выбором «домой или страницей состояния», и
explorer-адрес, никем не заявленный, активировал бы предыдущую безадресную вкладку (главную).
Успех рисует host: он открывает вкладку своим путём.

### 3. Гейт роли идёт до ключа, отказ один

`EntityExplorerAccess` — единственное место правила «диагностическую структуру видит только
`ADMIN`»: его спрашивают пункт меню, route-ветка, вид и диалог подсистемы. Порядок проверок —
часть контракта: роль → разбор ключа → каталог. Без роли каталог не спрашивают **вовсе**, поэтому
ответ не зависит от того, существует ли ключ.

Отказ по роли, по неизвестному ключу и по неразбираемому адресу — одно значение
`OpenResult.invalidRoute("Адрес не найден")`, без перечисления похожих ключей. В журнал идёт только
метка исхода (`outcome`): ни ключ, ни адрес — иначе отказ по роли отличался бы от отказа по
неизвестному ключу строкой в логе.

### 4. Адрес вкладки пишется до активации, история различает вход и выбор

Мост хранит адрес вкладки, не связанной с формой, отдельно от `FormRoute`:

- `tabAddressed(entryId, address)` — координатор сообщает адрес **до** активации. На холодном входе
  адрес уже стоит в окне, поэтому повторной записи нет; обратный порядок заставил бы мост записать
  «/» вместо адреса типа.
- `tabAddressChanged(entryId, address)` — выбор пользователя: непустой адрес пишется **немедленно
  шагом истории** (вкладка уже активна, события активации не будет), `null` — «у выбора адреса нет»:
  запись снимается, текущая запись истории **заменяется** на «/».
- Вход из истории (Back/Forward) применяет ключ к вкладке, но адрес не пишет: адрес уже изменён
  браузером.

### 5. Резерв первых сегментов — политика приложения, а не свойство URL

`entity-explorer` добавлен в `reserved` baseline маршрутов: ни один alias сущности не может занять
этот сегмент. Запрет в `FormRouteCatalog` не вводится: каталог о занятых сегментах не знает, а
хардкод трёх ключей был бы третьим, неполным местом знания (`login`, `api`, `ureport`, `VAADIN`
знает только приложение). Если появится второй host, каталог получит **вход** «занятые сегменты»
от него.

Технической коллизии при этом нет ни с `records`/`lists`, ни с `entity-explorer`: ключ типа всегда
**второй** сегмент адреса.

### 6. Тип без опубликованного ключа безадресен

Выбор типа, у которого каталог не публикует ключ, даёт `tabAddressChanged(entryId, null)`: адрес
заменяется на «/», вкладка остаётся, а карточка показывает причину строкой («ключ не опубликован
каталогом маршрутов»). Выдуманная ссылка открыла бы чужой адрес; полная перестройка карточки по
аспектам — предмет E3.2.

### 7. Legacy-ключ остаётся как запрошен

Каталог принимает прежние ключи наравне с каноническими, поэтому адрес с legacy-ключом
открывается и остаётся в окне как запрошен. Канонический ключ показывается шапкой карточки (E3.2).
Канонизация адреса заменой записи истории отложена: мост пишет адрес шагом истории, а
replace-семантика в E2 существует только для закрытия вкладки, и менять её ради косметики адреса —
отдельное решение.

### 8. Владелец вида и dirty-контракт

Вид Explorer — один UI-scoped бин. Вкладку открывает host через `openComponent` + `init(type)`,
а не через `open` с initializer'ом: для уже открытой вкладки `open` только показывает её и новый
ключ не применяет. Повторный вход (ссылка, вставка в строку браузера, Back) применяет ключ к
существующей вкладке — второй вид не появляется.

Открытие Explorer не теряет несохранённые правки и диалога не показывает; подтверждение остаётся
там, где уничтожается экран: закрытие вкладки, уход из host, выгрузка страницы (E2.4 не меняется).

### 9. Границы API

Публичными становятся: `EntityExplorerAddress` (платформа, `platform-vaadin`) и три метода моста
(`installExplorerEntryPoint`, `tabAddressed`, `tabAddressChanged`). API baseline `platform-vaadin`
перегенерирован намеренно, тем же шагом. E3.2.1 §8.1 добавил к тому же типу разбор якоря
(`anchorOf`) и запись адреса с якорем (`format(key, anchor)`) — тот же названный дрейф baseline.

Прикладными остаются: `EntityExplorerAccess` (правило роли — решение приложения), решение по адресу
и его результат (`MainLayout.decideExplorerEntry`, `ExplorerEntry`) и последовательность применения.
Платформа даёт адрес и мост, но не решает, кто и что видит.

### 10. Якорь карточки — `?view=<tab>[/<section>]`

Адрес типа может назвать место внутри карточки (E3.2.1 §8.1): вкладку (`?view=access`) или раздел
вкладки (`?view=access/rules`). Имя параметра одно — `view`: `?tab=…` остаётся отказом, потому что
второе написание того же места дало бы у карточки два адреса. Форму якоря знает платформа
(`EntityExplorerAddress.anchorOf`), а какое место он называет — словарь карточки приложения
(`CardTab`/`CardSection`): у платформы вкладок карточки нет, поэтому смысл имени якоря из грамматики
не выводится.

Грамматика якоря — та же грамматика ключа, применённая к каждой части: `<id>` либо `<id>/<id>`.
Якорь, выписанный вне грамматики или названный дважды, не разбирается вовсе: `keyOf` не даёт ключа,
а `anchorOf` — якоря; половины разобранного адреса не бывает. Исключение `?continue` не
расширяется: параметр переносится и рядом с якорем (`?view=access/rules&continue` открывает то же
место). Фрагмент не часть адреса (`#access` — отказ, как и раньше): `claims` он не меняет, но
ключа и якоря не даёт. Адрес без якоря работает как раньше — карточка открывается первым непустым
аспектом.

**Неизвестный якорь = неизвестный адрес.** Разбор якоря стоит после ключа и каталога (порядок
«роль → ключ → каталог → якорь» — часть контракта), а ответ — тот же единый отказ
`OpenResult.invalidRoute("Адрес не найден")`. «Ближайшей» вкладки, куда можно было бы повести,
не существует: неизвестный якорь отличается от неизвестного ключа только местом проверки, а не
ответом. Роль не-`ADMIN` отказывает до разбора якоря, поэтому отказ не различает ни роль, ни ключ,
ни якорь.

**Новый якорь появляется только с записью.** Словарь якорей — часть адресного контракта, поэтому
он живёт в `deep-link-baseline.txt` (записи `view=` для вкладок и разделов) и сверяется со словарём
карточки забором (`CardAnchorTest`) — та же дисциплина, что у alias и вариантов формы (ADR-0009
§3–§5): вкладка или раздел, которых нет в записях, публичным якорем не являются, а якорь
существующего адреса не переименовывается — это была бы сломанная ссылка, а не уборка.

**Адрес окна собирается из разобранного `Location` (E3.2.1 §8.3/8.3a).** `FormRouteUrlBridge.addressOf(Location)`
складывает `<path>?<name>[=value]&…` из `getPath()` и разобранных `QueryParameters`:
`Location.getPathWithQueryParameters()` кодирует `/` в значении query (`?view=reading%2Fpaths` —
измерено на стенде), а грамматика якоря кодирование отвергает осознанно, поэтому разделовый якорь не
доходил бы до словаря карточки. Тем же источником пользуется Back/Forward, а host делегирует мосту.
`%2F` в адресе окна остаётся допустимым: вход, refresh и Back/Forward читают уже раскодированные
значения `Location`, а канонический адрес платформы и записи baseline — в неупакованной форме.

**Место карточки сообщается целиком и только выбором пользователя (E3.2.1 §8.3).** «Где» из обзора и
узел табличной части называют host'у `<вкладка>/<раздел>`; ручная смена вкладки — вкладочный якорь;
применение якоря адреса не пишет адрес повторно, а смена вкладки внутри пользовательского фокуса не
сообщается отдельно — одно сообщение, один шаг истории.

### 11. Состояние текущего UI и отсутствующее место (E3.2.2 §9.3–9.4, 2026-10-02)

У Explorer одна видимая карточка. Выбранный тип и место, а также раскрытия дерева принадлежат
одному `ExplorerUiState` UI-scoped вида; host получает восстановленный выбор и вычисляет адрес
из опубликованного ключа. Первый вход из меню показывает пустую карточку. Повторное меню сохраняет
тип, место, поиск, фильтры и раскрытия. После закрытия Workspace-вкладки меню заново регистрирует
адрес до активации. Нажатие меню при уже активном Explorer не добавляет шаг истории.

Прямой адрес и программный запрос применяют названный тип и место, снимая мешающие фильтры.
Адрес без `view` возвращает карточку к первому доступному аспекту; пользовательский возврат к
ранее посещённому типу сохраняет его место вместе с соответствующим якорем адреса. Вход по адресу
не сообщает host'у новый пользовательский выбор. Выбор раздела другого типа сначала меняет
сохранённый тип, затем передаёт host'у один итоговый якорь.

Неизвестный словарю якорь по-прежнему получает единый отказ §10. Известный якорь, чьи вкладка
или раздел не нарисованы у конкретного типа, показывает сообщение «Раздел … отсутствует в
карточке этого типа» и действие «Открыть обзор». Запрошенный URL сохраняется до явного выбора
пользователя; сообщение не изображает успешное применение соседнего раздела. «Открыть обзор»
сообщает host'у `overview/summary`; если обзор недоступен, действие отключено.

Идентификатор owned-секции (`root + поле связи + FQN строки`) используется для дерева и поиска,
но не становится новым URL-якорем. Переход ведёт в существующий `fields/table-sections`; секция
и найденное поле уточняются текстом. Запись диагностики root-поля в форме и гриде предлагает
оба конкретных перехода (`fields/form`, `fields/grid`), оставаясь одной записью в счётчиках.

Снимок и кеш карточек пересоздаются при входе с изменившимся principal, набором authorities
или локалью; сохранённый выбор предыдущего контекста очищается. Новый UI получает отдельное
состояние. Поиск, фильтры, группировка и повторное меню используют готовый снимок; автоматическое
раскрытие поиска не заменяет пользовательские сворачивания.

### 12. Общий переход из форм и подсистем (E3.2.2 §10.1–10.2, 2026-10-02)

`EntityStructureNavigation` — optional APP_SPI в platform-vaadin. Реализация приложения
`EntityExplorerNavigation` хранит host в Vaadin UI scope и использует тот же снимок, что дерево
Explorer. ADMIN проверяется до чтения снимка и повторно при исполнении. MainLayout связывает
adapter с существующим `openExplorerTab(PROGRAMMATIC)`; поздний detach прежнего layout не
снимает новую привязку host. У каждого UI своя привязка. Без host возвращается `Unavailable`.

Root с опубликованным ключом получает только `EntityExplorerAddress.format(key, anchor)`;
root без ключа открывается программно без URL. Owned-тип определяется по полному классу строки
и подтверждённым секциям снимка; открывается root и `fields/table-sections`, подпись уточняет
секцию. Отсутствующий или неоднозначный владелец даёт отказ. Локальное уточнение секции не
создаёт новый шаг истории и не перекрывает статус отсутствующего места.

Общий helper подключает меню «Разработка» в FormCoordinator.createListForm, диалоговый путь
ItemForm и ItemFormWrapperView. Без SPI или доступа меню скрыто; при клике доступ проверяется
заново. Workspace-переход сохраняет исходный компонент, черновик и owned-строки. Диалоговый
переход отправляет опубликованный адрес в отдельную вкладку браузера; при отсутствии ключа
пункт отключён с причиной. Копирование ссылки типа не требует id записи и использует общий
clipboard helper с origin/context path. Сохранение и закрытие остаются за обычным dirty-guard.

`SubsystemStructureView.structureAction` использует этот SPI; отдельное создание диагностической
панели/диалога удалено. Поиск, выбор подсистемы и исходный компонент сохраняются. Живая приёмка
истории браузера, popup-поведения и двух пользователей остаётся в §11.1 плана E3.2.2.

## Последствия

- холодная ссылка, refresh, Back/Forward и повторный вход работают без второго вида; шаг истории
  появляется на выбор типа, а не на вход по адресу;
- адрес Explorer не подменяет `/records/**` и `/lists/**`; `/entity-explorer` без ключа получает
  отказ host'а (framework отвечает 404 только там, где адрес не совпал с алиасом);
- отказ неразличим по роли и ключу, журнал не содержит ключа; правило роли существует в одном месте;
- тип без ключа честно безадресен, причина видна на вкладке;
- якорь (§10) открывает то же место после refresh и Back/Forward, адрес без якоря работает как
  раньше, а неизвестный или дублированный якорь отказывает как неизвестный адрес;
- новое обещание платформы — три метода моста, грамматика адреса и грамматика якоря
  (`EntityExplorerAddress` вырос на разбор якоря и запись адреса с якорем).

## Рассмотренные альтернативы

### Выразить успех через `OpenResult.Opened` с фиктивным `FormRoute`

Отклонено: фиктивный маршрут потребовал бы либо нового вида `FormRouteKind`, либо фиктивных id, то
есть второго смысла у типа, который описывает адрес формы. `OpenResult` остаётся матрицей открытия
формы, а карточка типа получает собственный вход.

### Общий обработчик моста для форм и Explorer

Отклонено: подпись обработчика (`Function<String, OpenResult>`) заставляет изображать карточку типа
формой; возвращаемое значение в `historyChanged` не используется, поэтому второй обработчик не
создаёт ни второй подписки, ни второй записи адреса.

### Запретить ключи `records`, `lists`, `entity-explorer` в `FormRouteCatalog`

Отклонено в пользу списка `reserved` в baseline: запрет в каталоге смешивал бы устройство URL и
политику приложения, был бы неполным (занятые сегменты знает приложение) и отвергал бы допустимые
ключи, потому что ключ всегда второй сегмент.

### Канонизировать legacy-ключ в адресе

Отложено: replace-семантика в E2 есть только для закрытия вкладки; косметическая перезапись адреса
на входе — отдельное решение, а не побочный эффект E3.0.

### Взять ключ типа из FQCN

Отклонено (повторяет ADR-0009 §4): адрес должен переживать переименование класса и не становиться
второй точкой решения на каждый тип.

## Связь с другими решениями

- **ADR-0009** — host, кодек, каталог маршрутов, `OpenResult` и dirty-контракт: адрес типа
  пользуется ими, не меняя их.
- **E3 план среза** — происхождение фактов, lifecycle, единая карточка, вкладки аспектов и якоря
  остаются в E3.1/E3.2; проекция `EffectiveEntitySnapshot` и `snapshotSchemaVersion` вводятся вместе
  с потребителем (плагин IDE, этап I).

## Открытые пункты

1. Живая приёмка §5 плана среза на стенде (admin/manager): пункты 1–11, включая legacy-ключ и
   dirty-guard.
2. Канонизация legacy-ключа в адресе — если понадобится, отдельным решением с replace-семантикой
   истории.
3. Якоря карточки — решение §10; **провод якоря «host → вид → панель» закрыт в E3.2.1
   §8.2/8.3/8.3a** (применение при отрисовке, переключение вкладки карточки адресом, сборка адреса
   окна для Back/Forward из разобранного `Location`, точное место пользовательского фокуса).
   Открытым остаётся только пункт 1 — живая приёмка E3.0 по чек-листу §5 плана среза.
