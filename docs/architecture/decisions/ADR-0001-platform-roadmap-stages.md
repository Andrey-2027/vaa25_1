# ADR-0001: этапы стабилизации платформенного ядра

- Статус: принято; объём B3 уточнён ADR-0003
- Дата: 2026-09-11
- Область: roadmap, инженерный baseline, data security, модульность

## Контекст

Исходный JMIX-roadmap смешивал:

- уже реализованный, но незавершённый save/events WIP;
- будущие платформенные возможности;
- историю обсуждения;
- закрытые и повторно открытые вопросы;
- эксплуатационные долги.

При этом RLS enforcement и физическое выделение платформы рассматривались слишком поздно, а воспроизводимая сборка, production-конфигурация и реалистичные PostgreSQL-тесты не образовывали обязательного входного gate.

## Решение

Работы разделяются на независимые этапы:

1. **A — Engineering Baseline.** Зелёная проверка, корректность базовых контрактов, документация, воспроизводимая сборка, безопасные профили и управляемая схема.
2. **B — Aggregate save и events.** Завершение уже начатого WIP и замена его
   переходной save-specific обвязки metadata-driven default согласно ADR-0003.
3. **C — Data Boundary и RLS Enforcement.** Fail-closed защита всех каналов, FetchPlan/InstanceName и узкий data-access facade.
4. **D — Физическая платформизация.** Выделение API/SPI, Spring/Vaadin adapters, optional reports и reference application.
5. **E/F.** UI experience, интеграции и ERP только после обязательных gates.

RLS enforcement и физическая модульность не являются подпунктами этапа A:

- A делает архитектурные изменения воспроизводимыми и проверяемыми;
- C создаёт обязательную security boundary;
- D превращает логическую границу `org.ipro`/`org.ip` в поставляемые артефакты.

## Последствия

Положительные:

- следующий этап имеет измеримый вход и выход;
- текущий незавершённый код не объявляется готовой платформенной возможностью;
- security и module extraction нельзя бесконечно отодвигать функциональным backlog;
- обсуждения JMIX остаются источником идей, но не управляют реализацией напрямую.

Ограничения:

- до прохождения A не начинается новый широкий платформенный эпик;
- B-WIP стабилизируется без новых предметных функций; B3 вправе обобщить доказанную
  транзакционную механику, чтобы переходная обвязка не стала обязанностью приложения;
- schema changes требуют миграции;
- массовый перенос пакетов не совмещается с изменением поведения.

## Рассмотренные альтернативы

### Всё включить в этап A

Отклонено: этап становится многомесячным и смешивает baseline, security redesign и module extraction. У него исчезает проверяемая точка завершения.

### Сначала физически разбить Maven-модули

Отклонено: при нестабильных контрактах save/events и красной сборке такое перемещение создаст большой diff без доказанного улучшения поведения.

### Оставить RLS до появления REST

Отклонено: обходные каналы уже существуют в reports, projection queries, search и прямом persistence access.
