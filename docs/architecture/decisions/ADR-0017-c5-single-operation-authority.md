# ADR-0017: единый хозяин решения по операциям — C5, RLS остаётся за строки

- Статус: принято по решению владельца 2026-10-06; §3 уточнён владельцем 2026-10-13 в этапе П-U.
- Область: права на операции сущностей (чтение, создание, изменение, удаление),
  именованные операции владельцев, место RLS, семантика wildcard `'*'`, граница
  финальной проверки записи.
- План работ: [C5.4–C5.10](../c5-operation-permissions-plan.md).
- Связанные решения: ADR-0007 (canonical data path, capabilities, таксономия
  экспозиции), ADR-0013 и ADR-0015 (регистр сведений), ADR-0014 (report read),
  ADR-0016 (поля опубликованного REST-ресурса).
- Отклонённое предложение: вариант с новыми ключами `ENTITY:<FQN>:CREATE|UPDATE|DELETE`
  и миграцией грантов остаётся локальным черновиком в `docs/plans/` (каталог вне Git)
  и не принят.

## Контекст

Сегодня три разных вопроса решаются в двух местах, и это видно по коду.

**Право на операцию сущности выражено измерением.** Гейт объявляется как
`@RlsDimension(value = "ENTITY:AccountingObjectCorrection", kind = RlsDimensionKind.CHECK_ONLY,
custom = true)` — [AccountingObjectCorrection.java](../../../src/main/java/org/ip/model/AccountingObjectCorrection.java).
Решением служат флаги гранта: `RlsUiGate.canCreate/canUpdate/canDelete` спрашивают
`accessService.canUpdate(dimension, null, user)`. Тот же ключ участвует и в чтении:
[RlsReadGate.java](../../../platform-rls/src/main/java/org/ipro/rls/RlsReadGate.java)
требует «любой доступ» по каждому CHECK_ONLY-измерению, а
[CanonicalReadExecutor.java](../../../platform-core/src/main/java/org/ipro/data/CanonicalReadExecutor.java)
до этого уже требует C5 entity read. Чтение проверяется дважды: `ENTITY:<FQN>` и
`ENTITY:<SimpleName>`.

**Новый контракт покрывает только чтение.**
[C5PermissionEvaluator.java](../../../platform-rls/src/main/java/org/ipro/rls/c5/C5PermissionEvaluator.java)
знает API, entity read и attribute read. Запись авторизуется старым механизмом:
`CanonicalWriteExecutor.authorizeUpdate` вызывает `rlsPolicyEnforcer.requireUpdate`.

**Дефолты противоположны.** Чтение без гранта запрещено (роль ADMIN не заменяет
entity grant). Запись без измерений разрешена:
[RlsDimensionValue.java](../../../platform-rls/src/main/java/org/ipro/rls/RlsDimensionValue.java)
прямо говорит, что класс без `@RlsDimension` остаётся незащищённым. Для `Nomenclature`,
`GroupNom`, `Role`, `User`, `AttributeType`, `NomenclaturePrice` canonical CRUD
существует, а проверки «этому субъекту можно» нет вообще.

**Wildcard отвечает на гейты операций.** `AccessGrantRepository.findUserGrants` матчит
`g.dimension in (:dimension, '*')`, а `AccessService.hasAccess` считает такую строку
разрешением. Поэтому `grant("*")` в
[AccountingObjectPilotInitializer.java](../../../src/main/java/org/ip/config/AccountingObjectPilotInitializer.java)
покрывает и CHECK_ONLY-гейты документов. При этом C5 wildcard не принимает никогда:
[C5ReadDecisionService.java](../../../platform-rls/src/main/java/org/ipro/rls/c5/C5ReadDecisionService.java)
и [DefaultC5PermissionEvaluator.java](../../../platform-rls/src/main/java/org/ipro/rls/c5/DefaultC5PermissionEvaluator.java)
это документируют.

**Финальная граница записи зависит от RLS.**
[RlsWriteGuardBridge.java](../../../platform-rls/src/main/java/org/ipro/rls/RlsWriteGuardBridge.java)
и `RlsWriteEnforcementListener` проверяют flush, но выходят сразу при
`!policy.protectedEntity()` — то есть для типов без измерений финальной проверки нет.

**Приложение платит boilerplate.** `RlsCheckValue.of(null)` и `accessDimension()` в
[AccountingObjectDocument.java](../../../src/main/java/org/ip/model/AccountingObjectDocument.java),
ручные `rights.requireUpdate(document)` и `rights.requireUpdate(new NomenclatureAccountingObject())`
в [AccountingObjectSaveService.java](../../../src/main/java/org/ip/application/register/AccountingObjectSaveService.java).

Фактический состав грантов в рабочей БД при подготовке решения не проверялся.

## Принятые решения

### 1. Три вопроса, три владельца

| Вопрос | Владелец | Изменение |
| --- | --- | --- |
| Существует ли операция у типа | capability (`EntityDescriptor`, `DataOperation`) | нет |
| Разрешена ли операция субъекту | **C5** | становится единственным решателем |
| Какие строки видны и какие можно менять | RLS: FILTERABLE-измерения, значения строк, переход исходное → целевое | нет |

C5 не решает существование операции и не решает строки. RLS не решает право на
операцию.

### 2. Объём решаемых C5 определений

В этот срез входят: `ENTITY` READ / CREATE / UPDATE / DELETE, именованные `ACTION`
владельцев и существующие `ENTITY`/`ATTR`/`REST` read-ключи без изменения семантики.
Attribute read/write как политика предметных полей в срез не входит (§ «Границы»).

### 3. Хранилище и ключи

**Уточнение П-U от 13.10.2026 заменяет прежнее решение сохранять короткий ключ операций.**
Хранилищем остаётся exact/global строка `AccessGrant`. Сущность имеет одно определение
`ENTITY:<FQN>` с полным набором поддерживаемых READ/CREATE/UPDATE/DELETE. Для субъекта
все её флаги находятся в общей global-строке, а не в отдельных read/operation грантах.
Общий реестр — источник определения; реестр чтения является его представлением.
Короткий `ENTITY:<SimpleName>` не является алиасом и не разрешает операции.

База разработки не рабочая; владелец разрешил удалить старые гранты без переноса.
Очистка выполняется явно и однократно, не при обычном старте. Новая минимальная выдача
восстанавливает административную настройку; пользователи, роли, назначения и предметные
данные сохраняются. Поддержка старого формата грантов и старого редактора не требуется.

Отображение независимых флагов общей ENTITY-строки:

| Флаг строки | Смысл |
| --- | --- |
| `canUpdate` | разрешено создание и изменение |
| `canDelete` | разрешено удаление |
| `canRead` | разрешено чтение; создание/изменение/удаление не включают его автоматически |

**Изменение политики владельцем 14.10.2026:** UPDATE и DELETE существующей сущности
требуют также эффективного ENTITY READ. Чтение и операция могут поступать от разных
назначенных ролей или прямого субъекта. Флаги хранятся независимо; write-флаг не выдаёт
чтение автоматически. CREATE и ACTION EXECUTE не получают этой предпосылки.
На уровне RLS UPDATE/DELETE существующего значения требуют разрешающего флага и READ
того же значения. Bootstrap допустим только для создания нового значения без id,
не для изменения существующего или удаления. Предыдущее permissive bootstrap отменено.

Новые формы ключей вида `ENTITY:<FQN>:CREATE` не вводятся. ACTION/REST остаются
собственными определениями с EXECUTE/READ; RLS отвечает за область записей и не заменяет
C5. Права на поля отменены ADR-0018. Самостоятельные CREATE/UPDATE не вводятся этим
уточнением; §4 сохраняет силу.

Удаление старых CHECK_ONLY ENTITY-объявлений не снимает защиту flush: бывшие защищённые
типы включены в canonical write boundary, а владельцы записи регистра сначала проверяют
единое C5-определение, затем политики строк и фиксируют авторизацию для flush.

### 4. Независимость CREATE от UPDATE не вводится

Документированное следствие: пара «создание без изменения» и независимое удаление
невыразимы одной строкой. Условие пересмотра — конкретный потребитель или требование
другого ADR; пересмотр означает изменение схемы, а не формы ключа.

### 5. Регистрация определений

- `ENTITY` read — как сейчас, регистратором canonical roots.
- `ENTITY` CREATE/UPDATE/DELETE — выводятся из capabilities того же descriptor, что
  даёт canonical handle. Generic CRUD отсутствующего вида не публикуется.
- Определения, не выводимые из capabilities, регистрирует владелец подсистемы:
  гейт записи регистра, `REPORTS:JPQL_PREVIEW` как ACTION.
- Повтор определения идемпотентен; один ключ с разным смыслом — отказ при старте.
  Уникальность ключей проверяется той же проверкой, что у `RlsDimensionRegistry`.

### 6. Гейт операции перестаёт быть измерением

`@RlsDimension(kind = CHECK_ONLY)` на типе с canonical CRUD — отказ при старте.
Приложение перестаёт объявлять аннотацию, `accessDimension()`, `getRlsChecks()` с
пустым `RlsCheckValue` и вызывать `requireUpdate` вручную. Дублирующая CHECK_ONLY-проверка
чтения для таких типов снимается. Вид CHECK_ONLY сохраняется для не-сущностных гейтов;
его полное снятие — отдельное решение.

### 7. Wildcard `'*'` остаётся как семантика RLS

`'*'` продолжает означать «все построчные измерения» и сохраняется в фикстурах как
локальный обход построчного доступа. В решении C5 он не участвует: ни чтение, ни
операции. На гейты операций он перестаёт влиять не запретом, а развязкой: гейты
операций больше не являются измерениями. Магический ключ «полный доступ» не вводится;
полный доступ для роли — материализованные строки.

### 8. Порядок серверного решения

`корректность типа и intent → capability → C5-операция → загрузка доступного исходного
состояния → RLS (исходное/целевое состояние) → attribute-input (когда появится) →
numbering/validation/hooks/events → persistence`.

Для агрегата security preflight выполняется до `Saving`/`beforeAggregateSave`.

### 9. Финальная граница записи

Авторизация, зафиксированная на preflight, потребляется на flush для **всех** типов с
write-capability, включая типы без RLS, тем же механизмом, что применяет RLS сегодня.
Изменение managed-сущности или коллекции без зафиксированной авторизации отклоняется
на commit. Без этого требования дыра переименовывается, а не закрывается.

### 10. Отказ и причины

Причины: `UNAUTHENTICATED`, `ENTITY_PERMISSION_DENIED`, `ACTION_PERMISSION_DENIED`,
`RLS_DENIED`. Неизвестное определение и отсутствующий провайдер — ошибка конфигурации,
не allow; ошибка хранилища не превращается в пустой успешный результат. Отказ не оставляет
частичной записи, не выдаёт номер и не вызывает прикладные hooks.

### 11. Свежесть и отзыв

Следующий вызов после committed изменения грантов или назначенных ролей получает свежее
решение, включая вторую открытую сессию. Точка авторизации внутри уже начатой транзакции
документируется. Немедленная отмена начавшейся операции, распределённая инвалидация и
долговечный allow-cache в срез не входят.

### 12. Административное управление

Выдача грантов, назначение ролей и смена пароля — отдельные определения с действующим
ADMIN-prerequisite. `User` CRUD не даёт самоповышения. Предусматривается отчёт
«определение зарегистрировано, грантов нет», иначе новый тип молча закрыт для всех,
включая администратора. Первичная выдача идёт вместе с включением enforcement: без неё
возможен lockout.

### 13. Совместимость

ADR-0014 и ADR-0016 не меняются. C5 read-ключи не переименовываются. Уже выданные строки
продолжают действовать, потому что ключ операции не меняется. `'*'` не переносится ни в
read-ключи, ни в операции.

## Отклонённые варианты

| Вариант | Почему не принят |
| --- | --- |
| Новые ключи `ENTITY:<FQN>:CREATE\|UPDATE\|DELETE` с миграцией | Цена: переназначение уже выданных грантов, два гейта на одну сущность без правила приоритета, `canRead` в роли «разрешено создать», разбор формы ключа всеми потребителями общей таблицы. Потребителя независимого CREATE нет |
| Расширение CHECK_ONLY-семейства операциями | Оставляет wildcard отвечающим на операции и дублирующую проверку чтения; название «измерение» продолжает означать право на операцию |
| Снять вид CHECK_ONLY целиком в этом срезе | Излишний объём; достаточно запрета использовать его как гейт canonical-CRUD типа |
| Attribute read/write политики в этом срезе | Нет подтверждённого сценария ограничения поля; сохраняются три семантики одного поля (UI, report, REST) |
| Пересмотр точки авторизации на flush (отзыв посередине транзакции) | Меняет семантику работающей границы; в срез входит только распространение зафиксированной авторизации на типы без RLS |

## Проверяемые последствия

1. Тип без RLS (`Nomenclature`): CREATE/UPDATE/DELETE запрещены без гранта и разрешены
   с ним при отсутствии измерений.
2. Тип с RLS (`ReceivingDocument`): грант операции не открывает чужую строку; доступная
   строка без гранта операции не изменяется. Оба условия обязаны выполняться вместе.
3. Отказ не выдаёт номер, не публикует `Saving`/`beforeAggregateSave`, не выполняет SQL
   корня и секций.
4. Изменение managed-сущности и изменение коллекции без зафиксированной авторизации
   отклоняются на commit.
5. Чтение сущности проверяется один раз (C5); отказ без гранта сохраняется.
6. `'*'` не авторизует ни одной операции; построчный доступ по `'*'` сохраняется.
7. Старт падает при конфликте определений и при CHECK_ONLY на типе с canonical CRUD.
8. Приложение не регистрирует платформенные типы вручную; пустой `RlsCheckValue` и
   ручной `requireUpdate` в прикладном коде отсутствуют.
9. Администратор видит операции и построчные измерения раздельно; объяснение решения
   совпадает с серверным.
10. Новый тип появляется в отчёте определений без грантов.

## Границы и известный долг

- Attribute read/write как политика полей и query paths остаются открытым пунктом
  roadmap C5. Условие входа — конкретный прикладной сценарий ограничения поля.
- Вид CHECK_ONLY сохраняется для не-сущностных гейтов (`REPORTS:JPQL_PREVIEW` переводится
  в ACTION отдельным шагом плана).
- Два написания ключа (`ENTITY:<SimpleName>` для операций, `ENTITY:<FQN>` для чтения) —
  известный долг. Снятие — отдельным решением после стабилизации.
- Полная приёмка на PostgreSQL, публикация REST и физическое выделение модулей этим ADR
  не закрываются.
