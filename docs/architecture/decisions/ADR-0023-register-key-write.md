# ADR-0023: запись регистра по ключу — set / upsert / delete, конфликты и bounded retry

Дата: 2026-10-12. Статус: принято для реализации; PostgreSQL-спайк закрыт,
интеграция в canonical write pipeline — следующий пакет Р11.

- Область: самостоятельный (не подчинённый документу) регистр; запись ресурсов по полному
  естественному ключу, удаление по ключу, классификация конфликтов, бюджет повторов.
- Связанные решения: ADR-0013 (регистр v1), ADR-0015 и ADR-0020 (набор регистратора),
  ADR-0021 (отдельная команда смены ключа), ADR-0007 (canonical data path),
  ADR-0017 (единственный авторитет операции), ADR-0018 (прав на поля нет),
  ADR-0019 (операция строки принадлежит владельцу).
- Этап плана: [§15 Р11](../information-register-development-plan.md); протокол спайка —
  [Р11, PostgreSQL-спайк](../evidence/register-r11-key-write-spike-20261012.md).

## Что было и почему требуется изменение

Регистр v1 умеет читать (история, срез, точечное и batch-чтение) и писать только двумя
каналами: заменой полного набора владельца-документа (ADR-0020, `RecorderSetWriter`) и
отдельной командой смены ключа существующей строки (ADR-0021). У самостоятельного регистра
между тем есть обычный canonical CRUD, но нет операции «записать эти ресурсы для этого ключа»
с определённой семантикой вставки/замены, проверкой ожидаемой версии и классификацией
конфликтов. Поэтому прикладной код сам решает «создать или обновить», а на гонке отсутствующего
ключа получает сырой отказ уникальности (`23505`) и должен сам придумывать, что делать.

## Рассмотренные варианты

1. **Переиспользовать интернированный `NaturalKeyCreateSupport`.** Отклонено: у интернирования и
   регистра разные контракты (интернированный тип не имеет периода, ресурсов и среза), а общий
   retry-loop не оправдывает слияние. Переиспользуются только доказанно общие части описания и
   классификации ключа.
2. **Сделать поля ключа writable и оставить обычный canonical UPDATE.** Отклонено тем же
   аргументом, что в ADR-0021: managed dirty flush обходит canonical lifecycle, а «перенос» строки
   на другой ключ — это не замена ресурсов.
3. **Серверный `INSERT ... ON CONFLICT DO UPDATE` нативным SQL.** Отклонено: такая запись обходит
   canonical pipeline (lifecycle, C5/RLS, exposure, telemetry, durable audit), не покрывает
   удаление и проверку версии, а её семантика привязана к конкретной СУБД.
4. **Типизированные intents по ключу через canonical write pipeline; физический UNIQUE —
   авторитет гонки отсутствующего ключа; verdict-контракт; bounded retry на границе транзакции.**
   Выбран этот вариант.

## Контракт

**Intents.** `set(type, key, resources)` — безверсионная запись; `set(type, key, resources,
expectedVersion)` — проверяемая запись; `delete(type, key, expectedVersion)` — удаление;
`setAll(type, [key…], resources)` — набор ключей одной транзакцией.

**Ключ** — полный объявленный ключ строки: измерения (ссылки — сохранённые идентификаторы, тип
берётся из дескриптора) плюс нормализованный период для периодического регистра. Частичный ключ
или лишние поля — отказ до данных. Для подчинённого регистра контракт не применяется: там
строку задают регистратор и номер строки (ADR-0015/0020/0021), а `set`/`delete` по измерениям
не вводится вовсе.

**Verdicts** (результат операции, а не исключение): `CREATED`, `UPDATED`, `UNCHANGED`,
`DELETED`, `ABSENT`, `VERSION_REQUIRED`, `VERSION_CONFLICT`, `CONCURRENT_INSERT`,
`RETRY_EXHAUSTED`, `LOCK_TIMEOUT`, `SERIALIZATION_FAILURE`, `DEADLOCK`, `TRANSACTION_ABORTED`.

**Режимы.**

- Безверсионный `set`: отсутствует — INSERT; существует — замена ресурсов («записать такие
  ресурсы для ключа»). Это и есть upsert: отдельного имени для «создать или обновить» не
  вводится. Повтор с теми же ресурсами — `UNCHANGED` без UPDATE, без продвижения версии, без
  callbacks и аудита.
- Проверяемый `set`: отсутствует — `ABSENT` (не создаёт); версия не совпала — `VERSION_CONFLICT`.
  Слепой перезаписи чужого решения здесь нет по построению.
- Ключ этим контрактом не меняется: `set` на другом ключе создаёт другую строку и никогда не
  перемещает существующую. Перенос ключа остаётся командой ADR-0021 (она сохраняет ID и ресурсы).

**Отказы до данных (refusals)**: неполный или лишний ключ `KEY_WRITE_KEY`; неверный тип значения
ключа `KEY_WRITE_VALUE_TYPE`; неверный тип ресурса `KEY_WRITE_RESOURCE_TYPE`; тип, не объявивший
возможность, `KEY_WRITE_NOT_ALLOWED`; подчинённый регистр `REGISTER_NOT_INDEPENDENT`; пустой
набор `KEY_WRITE_EMPTY`; превышение размера набора `KEY_WRITE_BATCH_SIZE`; удаление без версии
`VERSION_REQUIRED`.

## Конфликты и классификация

Классификация выполняется по `SQLState`, а не по типу исключения фреймворка:

| SQLState | Класс | Что означает и что делает контракт |
| --- | --- | --- |
| 23505 | `CONCURRENT_INSERT` | Гонка вставки отсутствующего ключа: победил другой писатель. Только безверсионный путь; повторяется |
| 40001 | `SERIALIZATION_FAILURE` | Ошибка сериализации транзакции; ничего не закоммичено, повторяется |
| 40P01 | `DEADLOCK` | Взаимная блокировка; транзакция откатана целиком, повторяется |
| 55P03 / 57014 | `LOCK_TIMEOUT` | Ожидание блокировки истекло; не повторяется (повтор лишь удвоил бы ожидание) |
| 25P02 | `TRANSACTION_ABORTED` | Транзакция уже испорчена; работу в ней продолжать нельзя |
| — | `VERSION_CONFLICT` | Несовпадение ожидаемой версии; не повторяется никогда |
| прочее | без класса | Уходит вызывающему как есть: неизвестный отказ не «лечится» повтором |

**Почему пессимистическая блокировка не решает гонку отсутствующего ключа.** Блокировать нечего:
`SELECT … FOR UPDATE` по отсутствующей строке не оставляет ни блокировки, ни предикатной гарантии
в READ COMMITTED. Авторитет — физический UNIQUE `(измерения, период)`: он ровно один раз
пропускает вставку, а проигравший получает `23505`. Строки при этом не объединяются и не
затираются.

**Правило PostgreSQL.** Любая ошибка оператора завершает транзакцию: следующий оператор в ней
отказан (`25P02`). Поэтому «после unique violation продолжить» невозможно в принципе, и повтор
обязан начаться новой транзакцией. Спайк проверил это отдельной пробой на сервере и тем же
поведением через ORM.

## Retry

- **Владелец повтора — граница транзакции.** Участник внутри чужой транзакции не повторяет и не
  открывает `REQUIRES_NEW` (правило §15 плана): он возвращает verdict или типизированный отказ,
  а решение о повторе принимает вызывающая операция.
- **Автономная команда**: bounded retry, каждая попытка — новая транзакция (`TransactionTemplate`
  на попытку, никаких «продолжений» в испорченной). Бюджет по умолчанию 3; повторяются только
  `CONCURRENT_INSERT` (для безверсионного `set`), `SERIALIZATION_FAILURE` и `DEADLOCK`.
  `VERSION_CONFLICT` и `LOCK_TIMEOUT` не повторяются. Бюджет исчерпан — `RETRY_EXHAUSTED`, не
  исключение фреймворка. Бюджет в одну попытку — это не исчерпание: ответом остаётся
  классифицированный конфликт.
- **Побочные эффекты не удваиваются.** События публикуются после commit, durable-аудит пишется в
  транзакцию попытки, поэтому откатанная попытка не оставляет ни строки, ни записи аудита. Для
  интеграций и outbox команда принимает стабильный `commandId`, по которому сторона-получатель
  дедуплицирует доставку.

## Блокировки и порядок

Одиночная запись блокирует одну строку (`PESSIMISTIC_WRITE`). Набор `setAll` захватывает ключи в
каноническом порядке (измерения, затем период), потому что два набора одних ключей в разном
порядке иначе дадут deadlock. Порядок захвата — часть контракта, а не деталь реализации.

## Права, lifecycle и границы

- **Свои именованные операции**: `REGISTER:<FQN>:SET_KEY` и `REGISTER:<FQN>:DELETE_KEY`, объявляются
  отдельно от `CHANGE_KEY` (ADR-0021). Возможность opt-in и default-off на типе; регистрация
  операции грантов не выдаёт, EXECUTE назначается явно.
- Требуется ENTITY READ и (UPDATE для записи / DELETE для удаления) плюс RLS write values
  старого и нового состояния. Прав на поля нет (ADR-0018), полномочий документа не требуется:
  строка самостоятельного регистра владельца-документа не имеет (ADR-0019).
- Запись идёт через canonical write pipeline: фиксация canonical write, row lifecycle
  `beforeSave`/`beforeUpdate`/`onSave`, аудит через существующий durable `EventSink` с операцией
  `set-register-key:<entityName>` / `delete-register-key:<entityName>`. Новых таблиц нет.
- `RecordedRegisterEntryWriteGuard` и механизм ADR-0021 не ослабляются: подчинённые регистры
  по-прежнему пишутся только набором владельца и командой смены ключа. Generic managed flush
  остаётся не-каналом: поля ключа immutable.

## Что проверено спайком

Спайк — [RegisterKeyWriteConcurrencyPostgresIT](../../../src/test/java/org/ipro/register/RegisterKeyWriteConcurrencyPostgresIT.java):
тестовый прототип контракта работает с реальным PostgreSQL по объявленному регистру-фикстуре,
изолированная база создаётся [скриптом](../../../scripts/register-r11-postgresql.ps1).
Прогон 2026-10-12: **20 / 20**, failures 0, errors 0, skipped 0, BUILD SUCCESS
([протокол](../../plans/register-r11-postgresql-spike-20261012.log)).

| Проверено | Результат |
| --- | --- |
| Гонка вставки одного отсутствующего ключа | Один `CREATED`, проигравший `CONCURRENT_INSERT`; в базе одна строка версии 0 |
| Bounded retry проигравшего | `CONCURRENT_INSERT` → `UPDATED` за две попытки; аудит ровно один раз на попытку, откатанная попытка не оставила записи |
| Проверяемая версия | Победитель `UPDATED` (версия 1), проигравший `VERSION_CONFLICT` и **не** повторяется |
| Правило PostgreSQL | После `23505` следующий оператор отказан с `25P02` (проба на сервере, без ORM) |
| Откат попытки | Ни строки, ни записи аудита; продолжение через ORM тоже отказано |
| Resource-only | Повтор тех же ресурсов — `UNCHANGED` без роста версии; другой ключ — другая строка, ключ не переносится; проверяемый `set` на отсутствующем ключе — `ABSENT` |
| Удаление | Версия обязательна, конфликт не повторяется, повторное удаление отсутствующей строки — `ABSENT` |
| Набор ключей | Два набора одних ключей в обратном порядке — оба коммитятся без deadlock; разные ключи не мешают друг другу |
| Исчерпание бюджета | Конкурент забирает ключ перед каждой попыткой: два настоящих `23505`, `RETRY_EXHAUSTED`, ни строки, ни аудита |
| Классификация | 23505 / 40001 / 40P01 / 55P03 / 25P02 и `VERSION_CONFLICT` разобраны по SQLState; повторяются только транзиентные |

Без изолированной базы класс пропускается (20 skipped, BUILD SUCCESS) и в обычном прогоне
приложения инертен.

## Реализация (2026-10-13)

Контракт реализован в canonical pipeline и проверен на H2 и реальном PostgreSQL: команда
`RegisterKeyWrites` (`set`/`delete`), именованные операции `RegisterKeyWritePermissions`
(`SET_KEY`/`DELETE_KEY`, регистрация без выдачи грантов), декларация `keyWriteAllowed` на
дескрипторе с запретом для подчинённого регистра, независимый исходный снимок для `beforeUpdate`,
canonical-фиксация записи, row lifecycle, durable-аудит с операцией
`set-register-key:<Тип>` / `delete-register-key:<Тип>` и after-commit события. Пилот цен переведён на
этот контракт: «Цены номенклатуры» объявляют `keyWriteAllowed`, а `NomenclaturePriceService`
предлагает `setPrice` / `changePrice` / `removePrice` вместо прикладного решения «создать или
обновить». Протокол и границы — [реализация Р11](../evidence/register-r11-key-write-implementation-20261013.md).

## Что осталось и сознательно не входит в этот пакет

- **`setAll` (набор ключей).** Контракт набора с каноническим порядком подтверждён спайком, но
  потребителя с настоящим набором пока нет, поэтому батч-метод не вводится заранее.
- **Идемпотентность интеграций.** Стабильный `commandId` и outbox-дедупликация на стороне
  вызывающего в команде не появились: сейчас единственный потребитель — приложение.
- **`SERIALIZABLE`.** `40001`/`40P01` классифицируются, но сценарий на явном уровне изоляции не
  прогонялся; READ COMMITTED сериализационный конфликт не воспроизводит.
- **Другие серверные СУБД**: переносимость заявляется только с собственными измерениями.
- **REST-канал и отдельное действие формы** «записать цену на дату»: прикладной путь — сервис
  пилота, обычная карточка продолжает писать ресурс через canonical CRUD. Публичная поверхность
  регистра не расширялась, но reviewed-реестр границы приложение→платформа получил две строки API
  (`RegisterKeyWrites`, `RegisterKeyWritePermissions`); API-baseline'ы `platform-*` модулей не
  менялись — новых платформенных типов пакет регистра не добавил.

## Последствия

- Схема регистров не меняется, миграция не нужна: ключ уже физический UNIQUE.
- Новые ACTION не выдаются автоматически; прежние сценарии записи не расширяются.
- Прикладной сервис перестаёт сам решать «создать или обновить» и получает определённый ответ
  вместо сырого `23505`.
- Неизвестный отказ намеренно не повторяется: молчаливый retry «на всякий случай» запрещён, а
  поведение при исчерпании бюджета наблюдаемо (`RETRY_EXHAUSTED`).

## Приёмка реализации

Выполнена 2026-10-13: одна строка на ключ; определённый победитель и определённый отказ;
bounded повторы без дублей строки, события и аудита; отсутствие регрессий прежних каналов записи
(194 сценария на H2 без повторов: 69 регистров, 80 пилота и чтения, 12 новой команды, 9 прежней команды
смены ключа, 24 пилота цен); PostgreSQL-прогон
как обязательная часть приёмки — 24 / 24 на изолированной базе (H2 конкурентную проверку не
заменяет). Подробности и открытые пункты — [реализация Р11](../evidence/register-r11-key-write-implementation-20261013.md).
