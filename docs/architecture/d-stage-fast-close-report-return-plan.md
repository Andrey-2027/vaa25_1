# Этап D: ускоренное закрытие платформенной поставки и обязательный возврат к report add-on

Статус: рабочий план. Решение владельца: физический перенос отчётов временно отложен ради
быстрого выпуска платформы; к report add-on возвращаемся после первых удовлетворительных
результатов, которые высвободят ресурсы для переноса. Этот план не объявляет D3.7 выполненным.

## 1. Граница временного решения

1. `D3.6` заканчивает консолидацию существующего report UI **в приложении**. Новые функции
   отчётов и redesign модели сюда не входят.
2. `D3.7` (физический `report-*` add-on) остаётся открытой обязательной задачей `D-R`.
   Она не заменяется комментарием «позже» и не исчезает из roadmap.
3. В ближайшую поставку входят `D3.8` (BOM/starters/переключение приложения), минимально
   достаточный `D3.9` (границы и публичная поверхность) и `D4` (независимое reference app).
4. Целевое состояние: отчёты принадлежат приложению — его зависимости, persistence scan и
   `AutoConfiguration.imports` остаются в приложении; платформенные модули, BOM, starters и
   reference app не зависят от report-кода, движков и `org.ip`. JR persistence source boundary
   теперь отделена от `platform-persistence`; Maven-верификация этого изменения ещё впереди.
   Статическая сверка POM-графа показала: `platform-core`, `platform-numbering`, `platform-settings` и
   `platform-rls` зависят от `platform-persistence`, поэтому исключение артефакта из обычного
   backend starter не является рабочим обходом. Узкое отделение JR persistence реализовано
   в исходниках и описано в инвентаре; потребительский starter ещё предстоит проверить.
5. Формулировка результата — «платформа работает без отчётов; legacy-приложение сохраняет
   отчёты». Формулировка «optional report add-on готов» недопустима до реального D-R.

Первый documentation-срез при исполнении: изменить DoD/порядок D в roadmap и
`d3-core-extraction.md`, явно выделить временное исключение, ссылку на этот план и открытый
D-R. После закрытия D3.6 поправить ссылки «следующий D3.7» в его as-built и baseline;
фактические counts и результаты проверок записывать только после завершения прогонов.

## 2. Порядок работ и контрольные точки

### D-0. Зафиксировать фактическую исходную точку

- Считать текущую реализацию завершённой владельцем; не ждать дополнительного прогона.
- Быстро сверить текущий diff и as-built D3.6.4. Использовать уже имеющиеся результаты
  тестов, а неподтверждённые длительным прогоном критерии пометить для общего финального
  пакета. Работы, уже выполненные в D3.6.5–7, не повторять ради совпадения с нумерацией.
- Выписать только незакрытые дефекты с приоритетом: потеря/порча данных, RLS или иной
  server-side обход, сломанный save/dirty/route, затем остальные функциональные и визуальные.

Выход: короткий актуальный остаток D3.6 и список проверок для одного финального прогона.

### D-1. Закрыть D3.6 без расширения функциональности

Действующий детальный контракт — `docs/plans/d3.6-report-editor-consolidation-plan.md`.
Исполнять лишь оставшиеся пункты:

1. `D3.6.4`: USER/ADVANCED имеют одно поведение для полей, групп, сортировки, фильтров и
   итогов; view-level superset gate защищает переход; schema reconcile и orphaned items
   не теряют сохранённые данные.
2. `D3.6.5`: один редактор параметров и один CSS scope `.report-editor`, без глобального
   влияния на CRUD-формы.
3. `D3.6.6`: один каталог для UDR/JRXML/UReport3; старые URL становятся compatibility aliases,
   query parameters сохраняются, вторые экземпляры каталогов/редакторов не создаются.
4. `D3.6.7`: удалить variant-стеки лишь после parity gate; включить невакуумный
   consolidation guard и синхронизировать seam/surface/package-matrix реестры.
5. `D3.6.8`: выполнить быстрые статические проверки по мере изменений; длительные
   автоматические проверки собрать в общий финальный пакет после D3.8/D4. В пакет включить
   адресные D3.6 gates, один полный прогон и один random-order прогон по действующему
   контракту. Ручной smoke также провести в конце и ограничить критическими потоками:
   открытие старого URL, create/edit/save/reopen, dirty/failed save, параметры, USER/ADVANCED,
   запуск/экспорт и запрет неподдерживаемых engine actions.

Не принимать известные дефекты потери данных, безопасности или сохранения в обмен на
скорость. Косметический или редкий неразрушающий дефект может перейти в именованный
backlog с воспроизведением и владельцем; он не должен маскироваться зелёным gate.

Выход: один канонический report UI в приложении, старые маршруты совместимы, реестры и
baseline соответствуют коду. Физического переноса ещё нет.

### D-2. Заморозить границу будущего переноса

- Сохранить `src/test/resources/report-form-seam.txt` как проверяемый контракт
  Report → Form, обновив holders после удаления вариантов и комментарии о сроке переноса.
- Проверить source/POM/auto-configuration зависимости `platform-*` от `reportstudio`, JR,
  UReport и DynamicReports; сохранить отрицательный gate. Ранее найденная аномалия —
  `org.ipro.jr` entity/repository/scan внутри `platform-persistence` — устранена на уровне
  исходников и POM, но должна быть подтверждена финальной сборкой и проверкой D3.8 starter closure.
- Не превращать внутренние report-типы в публичный SPI платформы ради временного wiring.
- Оставить app-owned report registrations в приложении; не перетаскивать их в общий starter.
- Записать для D-R перечень report source roots, ресурсов, внешних forks, persistence
  registrations и тестов в [`d-r-report-addon-inventory.md`](d-r-report-addon-inventory.md).
  Это инвентарь переноса, не новая архитектурная работа.

Выход D-2: seam и перенос задокументированы, отрицательные границы проверяемы, JR persistence
владеет приложение, а `platform-persistence` оставляет только общую `BaseEntity`. Source-level
граница готова; сборочную и starter-поставку подтверждать только после соответствующего финального
прогона. Это не означает, что физический report add-on (D-R) уже поставляется отдельно.

### D-3. Выпустить минимальный состав платформы (`D3.8`)

Статус проверки на 2026-09-23: BOM и оба starter'а созданы; приложение использует
`platform-vaadin-starter`, который приносит `platform-vaadin`, backend-замыкание и
`vaadin-spring-boot-starter:25.1.6`. Фактический Maven dependency tree проверен: FilterGrid
модули управляются BOM, grouping приходит через projection, а UReport3, DynamicReports и
ReportUI остаются прямыми зависимостями приложения и не входят в platform closure. Backend
starter остаётся отдельной фасадной поставкой для backend-only потребителей.

Чистая компиляция на JDK 21, 18 целевых D3.8-тестов и `verify -DskipTests` прошли; последняя
команда выполнила Vaadin frontend/Vite build и Spring Boot repackage. В `JrPersistenceRegistrationTest`
подавлена инициализация корневым `data.sql`; после этого регистрация/запись JR entity прошла
все три теста. BOM, starters и platform POM не тянут report add-ons.

Полный `clean verify` завершился `BUILD FAILURE` на тестовой фазе (1318 тестов: 5 failures,
3 errors). Три D3.8-проверки состава starter/dependency были исправлены с учётом фасадной
модели, а JR slice исправлен и проверен целевым прогоном; полный набор после этих локальных
исправлений повторно не запускался. Оставшиеся известные красные проверки относятся к соседним
работам: `PlatformPublicSurfaceTest` (документ — 162 app-source-files, код — 154) и
`ReportEditorConsolidationTest` (контроль `bands` не подключён к дереву экрана). Их исправление
не включено в D3.8. Для bootstrap использован `-AllowSourceDrift`: расхождения fingerprints
внешних DynamicReports/UReport3 checkout требуют отдельной осознанной сверки.

1. Создать `platform-bom` с единым набором версий существующих `platform-*` артефактов.
2. Создать backend starter, который собирает нужные platform core/autoconfigure и
   backend-подсистемы, и Vaadin starter, который добавляет `platform-vaadin`. Точный
   dependency closure сверить по POM; report-зависимостей там быть не должно.
3. Зарегистрировать новые артефакты в `scripts/local-dependencies.json` в
   топологическом порядке. Корневого агрегатора нет: bootstrap/установка модулей
   проверяются через manifest и независимые Maven-проекты.
4. Переключить root application с ручного набора platform dependencies на BOM/starters,
   сохранив report-зависимости и registrations только у приложения.
5. Проверить dependency tree: platform starters не тянут отчёты, а приложение после
   переключения сохраняет свои отчёты и прежние ключевые сценарии.

Выход: приложение собирается на опубликованных platform artifacts; версия платформы
управляется отдельно от версии приложения.

### D-4. Минимальный governance (`D3.9`)

- Перечислить и закрепить тестами реально обещанные внешние API/SPI starter-поставки.
  `TEMPORARY_ALL_PUBLIC` не выдавать за стабильный контракт: оставшиеся модули явно
  пометить внутренними или оформить отдельный долг с owner и критерием снятия.
- Проверить невакуумность boundary/public-surface gates, отсутствие ссылок platform → app,
  строковых scan/pointcut contracts на app packages и отсутствие report-зависимостей.
- Обновить architecture index, status/baseline, bootstrap-инструкцию и release notes.
  Документация должна различать закрытый D-core и открытый D-R.

Выход: потребитель понимает, что является поддерживаемым контрактом, а что остаётся
внутренним или временным.

### D-5. Независимый reference app (`D4`)

Создать отдельный минимальный Maven-проект, который зависит от BOM/starters и не зависит
от root application, `org.ip` и report-библиотек. В первой поставке обязателен один
проверяемый вертикальный сценарий: test entity с list/detail/selection, автоматическое
подключение стандартных сервисов, разрешённый и запрещённый RLS-доступ, aggregate save
без ручной save-обвязки и smoke совместимости starter/autoconfiguration. Отдельно
проверить clean bootstrap и смену версии платформенных артефактов.

Развёрнутый каталог примеров D4 (включая варианты документа с 0/1/2 owned sections и
upgrade matrix) не считать автоматически выполненным одним smoke. Либо добавить его
сейчас, если готовые тесты делают это дешёвым, либо перечислить как открытый `D4-followup`
при пересмотре DoD. Не скрывать сокращение объёма под исходным названием D4.

Выход: независимый потребитель подтверждает главный результат этапа D — платформа
работает без приложения и без отчётов.

## 3. Экономный, но проверяемый режим работы

- Не запускать долгие тестовые прогоны по каждому срезу. Поддерживать короткий список
  затронутых наборов и один общий финальный пакет после завершения D3.6, D3.8 и D4:
  адресные gates, полный root-app набор, random-order gate и smoke. Повторять только ту
  часть пакета, которую затронуло исправление, если полный повтор не нужен для уверенности.
- Платформенные модули не переустанавливать, пока меняется только приложение. При
  изменениях POM/platform source ставить только изменённую dependency closure в нужном
  порядке; финальный clean bootstrap проверяет полный consumer graph.
- Каждый долгий Maven-запуск из IntelliJ выполнять один раз, писать вывод в файл и
  отслеживать завершение. Принимать результат только по `BUILD SUCCESS`, числу выполненных
  тестов и отсутствию пропущенных/ошибочных тестов сверх явно ожидаемых.
- Для диагностики сперва искать адресно `rg -n` с контекстом, а не читать целые логи и
  исходники. Таймаут интерфейса не является результатом сборки.
- На каждом cutover фиксировать commit/reviewable diff; не смешивать D3.6 UI-консолидацию
  с переносом пакетов или созданием нового report API.

## 4. Возврат к report add-on (`D-R`, бывший D3.7)

Контрольная точка возврата не привязана к запрету начинать E/F. После первых
удовлетворительных результатов текущих работ, которые позволяют выделить исполнителя и
время на перенос без срыва основного потока, провести короткий preflight:

1. Зафиксировать достигнутый результат и высвободившийся ресурс. Если перенос всё ещё
   невозможен, назвать конкретный блокер (например, утверждённый и датированный redesign
   модели отчётов, невоспроизводимый fork или юридическое ограничение публикации).
   «Модуль сырой» и «позже будет удобнее» сами по себе не блокеры.
2. Сверить зелёный D3.6 baseline, Report → Form seam, closure report dependencies,
   ресурсы/auto-configuration/persistence и воспроизводимость внешних forks.
3. Если ресурс выделен и технического блокера нет — начать физический перенос минимальными слоями:
   report core, report Vaadin и engine adapters/autoconfigure по фактической closure;
   подключить add-on обратно к приложению без redesign поведения.
4. Если ресурса или технической готовности пока нет — записать, чего именно не хватает,
   owner и условие следующей проверки. Возвращаться к D-R при каждом удовлетворительном
   результате, способном высвободить ресурс; не откладывать автоматически до конца E/F.

Definition of Done D-R: приложение подключает report add-on как зависимость; без add-on
платформа и reference app запускаются; report UI, движки, persistence и экспорт
проходят contract/regression tests; platform artifacts всё ещё не зависят от report;
публичный report API и версия add-on перечислены отдельно.

## 5. Оценка и критерий честного закрытия

Ориентир после текущей проверки D3.6: остаток D3.6 — 2–5 рабочих дней,
BOM/starters/app cutover — 3–5, governance и минимальный reference app — 3–6.
Суммарно около 8–16 рабочих дней при отсутствии новых блокеров сборки; это диапазон,
не обещание даты. D-R оценивается отдельно после preflight и **не включён** в этот срок.

Ближайшую поставку можно назвать закрытием **D-core с временным исключением D-R** только
после явной корректировки roadmap/DoD и прохождения D-1…D-5. Исходный DoD, где reports
подключаются опционально как готовый add-on, до выполнения D-R не достигнут.
