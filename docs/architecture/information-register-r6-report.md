## Пользовательский сценарий

В каталоге отчётов кнопка **«Создать отчёт о ценах»** создаёт новый DRAFT через штатный
`ReportTemplateService`, присваивает свободное имя и открывает его в редакторе.
При повторном создании существующий шаблон не заменяется. Действующий механизм
`requestEditTemplate` сохраняет проверку несохранённых изменений редактора.

Шаблон «Номенклатура и цена на дату» содержит код, название, дату записи и цену.
Дата запуска обязательна; форма показывает DatePicker из сохранённой visual-декларации DATE,
без эвристического defaultValue. LEFT JOIN сохраняет видимую номенклатуру без истории:
дата записи и цена пустые. Цена 0 остаётся числом, отсутствие цены не превращается в 0.
По умолчанию строки упорядочены по persistent id; фильтры и оформление меняются штатным редактором.

Один сохранённый шаблон запускается на разных датах. Граница включительная.
Например, история 150 → 90 даёт 150 на первую дату и 90 на вторую;
фильтр результата `price > 100` на вторую дату не возвращает старую запись 150.

## Реализация

`NomenclaturePriceReport` — прикладной рецепт: тип регистра, ссылочное измерение,
имя параметра `priceDate`, колонки справочника и подписи. CTE и ON прикладной код не пишет.

`RegisterSliceReportTemplates` — бин reportstudio и поддерживаемый recipe API.
Первый шаблон рассчитан на регистр с одним ссылочным измерением; остальные декларации
отклоняются явно. Общий генератор Р5 сохраняет поддержку нескольких измерений.
Корень справочника определяется из проверенного JPA mapping, поля проверяет существующий catalog/compiler.
Шаблон содержит обычные visual package JSON, JPQL для штатного guard/transfer,
FORM/SCALAR-параметр и DETAIL-бэнд. Изменений JPA-модели или миграции БД не требуется.

`generateParameterized(source, spec, names, dateParameter)` создаёт named DATE-параметр
в первой CTE и переносит его обязательную декларацию в main при композиции фрагмента.
В этом варианте `spec.asOf()` заменён runtime-параметром и не является запасной датой.
Обычный `generate` с literal LocalDate сохраняет контракт Р5.
Два named среза компонуются с отдельными параметрами; несовместимая декларация в consumer
и compiler-owned имя параметра отклоняются до исполнения.

## Исправления report pipeline

Compiler передаёт объявленные WHERE-параметры в ProjectionFilterCompiler как pending,
затем восстанавливает исходные runtime-имена за один проход. Необъявленный параметр
отклоняется. Учитывается случай, когда имя параметра содержит промежуточный compiler prefix.
Assembly не подменяет результат resolver pending-маркером; обычный текст `__PENDING__`
в literal binding сохраняется. DATE требует LocalDate, строка или отсутствие значения
отклоняются до data SQL.

Визуальный фильтр результата продолжает хранить имя колонки. Для исполнения assembly
строит отдельную копию дерева с проверенными исходными scalar paths; для visual query
это пути из скомпилированной проекции. Allow-list и типы берутся из guard schema.
Резолв одного псевдонима в SQL WHERE больше не подменяет путь проекции.
Значения, IN-списки и структура исходного дерева сохраняются.
Фильтрация произвольного вычисленного/агрегатного выражения через этот WHERE-адаптер
не поддерживается: неподдерживаемый expression отклоняется явно.

Bindings внешнего фильтра получают свободные имена при коллизии с CTE/основным запросом;
внутренние значения не перезаписываются. Итоговый запрос повторно проходит существующие
guard/authorizer/executor. Snapshot, сохранение и импорт шаблона не выдают прав.

Проверка настоящего PDF выявила два дефекта renderer: COLUMN caption не применялся,
а LocalDate преобразовывался в строку ISO до применения date pattern.
Теперь подпись DETAIL-колонки переопределяет caption схемы; LocalDate с явным форматом
проходит value formatter с сохранением пустого значения. В PDF проверяются человеческие
заголовки, дата `02.01.2026`, цена и отсутствие технических имён CTE.

## Архитектура

Общий `org.ipro.register` сохраняет независимость от reportstudio/UI.
Новый публичный recipe API подтверждён прикладным consumer и исполняемыми проверками;
compiler, AST и Source mapping не становятся прямыми зависимостями приложения.
Публичный реестр дополнен одним API-типом `RegisterSliceReportTemplates`.
Две новые явные ссылки на прежнюю editable-модель `ReportTemplate` (рецепт и форма запуска)
учтены в legacy-реестре. Это продолжение действующего report workflow; выделение owner-модуля
и полноценная стабилизация report-модели остаются долгом D-R.

Замеры D1: 167 app files, 145 platform tree files, 231 named types, 143 API,
26 SPI, 57 legacy types, 148 legacy usage links. Package matrix и register reach-back
не расширены. Owner-модули, signatures и fingerprints зависимостей в Р6 не изменялись.

## Приёмка и границы

Проверки включают сохранение через сервис, flush/clear и повторное открытие из БД,
независимый импорт, неизменность package JSON при смене даты, point/oracle parity,
нулевую цену и отсутствие истории, сохранение фильтра, сортировку, создание из каталога,
форму DatePicker, полноценное формирование PDF и чтение текста PDF.
Ролевые AccessGrant, реальные C5/RLS, смена subject в одной сессии и отрицательные
даты проверяются через report resolver/assembly/executor с отказом до SQL.
