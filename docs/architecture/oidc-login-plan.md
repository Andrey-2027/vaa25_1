# OIDC-вход в GitVaa: границы первого внедрения

Дата: 2026-10-26. Статус: предложение, не принято.

**Условие входа.** Есть заказчик с корпоративным IdP, и SSO входит в требования
внедрения. До этого OAuth2/OIDC остаётся условным пунктом этапа F
([roadmap §9](../../JMIX_GitVaa_Roadmap_v2.md)), а SSO без подтверждённой
потребности не копируется ([roadmap §1.3](../../JMIX_GitVaa_Roadmap_v2.md)).
Для автономной установки на несколько пользователей выгода не покрывает
стоимость поддержки IdP-конфигурации, привязок, сессий и диагностики входа.

**Область.** Заменяется только аутентификация — «кто вошёл». Модель прав C5/RLS
не меняется: субъектом остаётся локальный `User.username`, решения принимает
`C5PermissionDecisionService` по `access_grant`.

## 1. Что заменяется и что остаётся

| Слой | Заменяется | Остаётся |
|---|---|---|
| Кто пользователь | IdP: `(issuer, subject)` | строка `User`, её `username` — единственный субъект C5/RLS |
| Пароль, MFA, политика | IdP | локальный пароль только у аварийного администратора |
| Роли | — (режим A) | локальные `Role`; синхронизация — отдельный режим B |
| Решения о правах | — | `AccessGrant`, C5, `PermissionStateService` |
| Субъект для RLS | — | `SecurityRlsUser.username()` = `Authentication.getName()` = `User.username` |

Ключевое следствие: `*(issuer, subject) → локальный username*` должен быть
детерминирован и идемпотентен. Иначе существующие гранты, аудит и отчёты
начнут относиться к другому субъекту.

## 2. Два независимых контракта: вход и роли

Факт привязки OIDC **не меняет источник ролей**. Это свойство регистрации
провайдера, а не следствие первого входа.

### Режим A — локальные роли (значение по умолчанию и объём первого выпуска)

- Роли назначаются локально через существующие операции `USER:ASSIGN_ROLES`
  и экран прав.
- Claims из IdP читаются только для аутентификации; ролью не становятся.
- `sync-roles=false`; отсутствие групп в токене не влияет на вход.

### Режим B — синхронизация групп (отдельная поставка, по запросу заказчика)

- `sync-roles=true` — IdP объявлен источником групп для этого провайдера.
- Маппинг `claim/group → Role` — явная таблица; неизвестная группа не создаёт
  роль и не выдаёт прав.
- Отсутствие обязательной группы запрещает **новый вход**, но не удаляет
  выданные роли и персональные гранты (см. §4).
- Снятие группы снимает только те роли, которые дал маппинг; персональные
  гранты и локально выданные роли остаются и отзываются отдельно.

### Несколько провайдеров

Одна identity принадлежит ровно одному провайдеру. Конфликт
`(user_id, provider)` — отказ привязки, а не «последний выиграл». Одновременная
поддержка нескольких IdP в первый выпуск не входит.

## 3. Идентичность и привязка

Отдельная таблица `oidc_identity`: `issuer`, `subject`, `user_id`, `provider`,
`created_at`, `created_by`, уникальность `(issuer, subject)`.

Правила:

- связывание только с **заранее созданным** `User`; JIT-создания нет;
- e-mail не является ключом и не связывает учётку автоматически;
- `username` при входе не переименовывается: смена логина — отдельное действие
  администратора;
- `(issuer, subject)`, уже связанный с другим пользователем, — отказ;
  повторная привязка к тому же пользователю идемпотентна.

### Привязка — защищённая операция, а не следствие `UPDATE User`

- Именованное право `USER:LINK_IDENTITY` регистрируется через
  `C5OperationPermissionRegistry` — так же, как `USER:CHANGE_PASSWORD`
  и `USER:ASSIGN_ROLES`.
- Аудит: кто, когда, какой `issuer/subject`, к какому пользователю, результат.
- Запрет самоприсвоения по образцу `UserService.authorizeAdministration`:
  привязать identity к собственной учётной записи нельзя.
- Отсутствие `@EntityMetadata` скрывает таблицу из generic UI, но не заменяет
  проверку полномочий: привязка чужого `sub` к локальному администратору — это
  вход в его учётную запись.

## 4. Сессии и отзыв доступа: что именно обещаем

Три независимых обещания, их нельзя смешивать в «доступ отзывается сразу».

1. **Новый вход.** В режиме B группы проверяются при каждом входе; отсутствие
   обязательной группы — отказ. Это не закрывает уже открытую сессию
   и не удаляет выданные роли/гранты.
2. **Длительность.** Настраиваемые absolute lifetime и idle timeout сессии.
   По истечении — повторный вход. Absolute lifetime — верхняя граница для всех
   остальных механизмов.
3. **Принудительное завершение.** (a) реестр сессий приложения
   (`SessionRegistry` / реестр Vaadin-сессий) и административная операция
   завершения; (b) back-channel logout как уведомление IdP, если провайдер его
   поддерживает; (c) при недоступном back-channel действует только absolute
   lifetime.

Формулировка для приёмки: «уволен в IdP» = запрет нового входа немедленно,
завершение открытых сессий — не позже absolute lifetime или по back-channel.
Если заказчику нужен отзыв за секунды, back-channel становится обязательным
требованием, а не опцией.

В коде уже есть точечные обращения к `VaadinSession`, но общего реестра сессий
нет — его создание входит в объём внедрения.

## 5. Недоступный IdP и аварийный вход

- Discovery по `issuer-uri` выполняется при создании регистрации и ходит
  к провайдеру. Недоступный IdP **не должен валить старт приложения**.
  Решение фиксируется явно: либо статические/кэшированные metadata
  (`authorization-uri`, `token-uri`, `jwk-set-uri`), либо ленивое создание
  регистрации. «Как получится по умолчанию» — не решение.
- Локальная форма входа сохраняется. Аварийный администратор — локальный
  пользователь с паролем; при выключенном IdP корпоративная кнопка недоступна,
  локальный вход работает, UI сообщает причину.
- Проверка входит в приёмку: перезапуск приложения при выключенном IdP,
  успешный вход аварийного администратора.

## 6. Граница записи

Если позже появится `oidc-provisioner` (JIT или массовое создание), он пишет
через canonical `EntityDataAccess`, но обязан сохранять предметные проверки
`UserService`:

- `USER:ASSIGN_ROLES` при любом изменении набора ролей;
- `USER:CHANGE_PASSWORD` при установке пароля;
- запрет назначения ролей собственной учётной записи;
- обязательный пароль нового пользователя.

Список грантов у субъекта-провижинера даёт техническую возможность записи,
но не право обойти эти правила. Одного набора `AccessGrant` недостаточно,
чтобы считать контракт закрытым.

Отдельное следствие для JIT: «нет локального пароля» конфликтует с
`UserService.applyRawPasswordIfPresent` — новый пользователь без пароля
получает `ValidationException`. JIT потребует явного контракта (nullable
password и запрет локального входа для такой учётки), а не молчаливого
placeholder-пароля. В первый выпуск JIT не входит.

## 7. Технические уточнения

- **Цепочки безопасности.** `@Order(1)` — JPQL preview
  (`/api/report-jpql/**`, stateless Basic) в `SecurityConfig`; `@Order(2)` —
  REST read (`/api/v*/**`, stateless Basic) в `platform-rest-web`
  (`RestWebAutoConfiguration`). OIDC-регистрация не должна перехватывать
  `/api/v*/**`; UI-цепочка остаётся последней.
- **Зависимость.** Spring Boot 4.0.6: `spring-boot-starter-security-oauth2-client`
  (старый `spring-boot-starter-oauth2-client` объявлен deprecated).
- **Vaadin.** `oauth2Login` вместе с `VaadinSecurityConfigurer`; после обмена
  кода аутентификация должна нести локальный `username`, иначе
  `SecurityRlsUser` отдаст в RLS чужой субъект.
- **Тесты.** `MockMvc.oidcLogin()` подставляет готовую аутентификацию и не
  проверяет обмен кода и callback. Нужен минимум один тест с реальным входом
  через локальный OIDC-стенд (WireMock/embedded): код → callback → сессия,
  плюс отказ для неизвестного `subject`.

## 8. Приёмка первого выпуска

1. Локальный вход администратора работает без IdP; перезапуск при выключенном
   IdP проходит, приложение стартует.
2. Корпоративная кнопка: вход только для заранее созданного и связанного
   пользователя. Неизвестный `subject` — отказ с понятным сообщением,
   без создания учётки.
3. `Authentication.getName()` — локальный `username`; `RlsCurrentUser` видит
   его; решения C5/RLS совпадают с локальным входом того же пользователя.
4. Конфликт привязки `(issuer, subject)` — отказ; повторная привязка
   идемпотентна; аудит содержит актора и цель.
5. Режим A: вход не меняет роли. Режим B (если включён): роли меняются только
   по явному маппингу.
6. Absolute/idle timeout срабатывают; back-channel logout завершает сессию,
   если настроен; без него действует absolute lifetime.
7. `/api/v1/**` остаётся Basic и stateless: UI-сессия OIDC не даёт доступа
   к REST.
8. Полный verify зелёный.

## 9. Что не входит

JIT-провижининг, синхронизация групп в первом выпуске, несколько IdP
одновременно, SCIM, вход по e-mail, замена локальных ролей внешними
authority, изменение субъекта C5/RLS, отказ от локального входа.

## 10. Открытые решения владельца

- Значения absolute lifetime и idle timeout.
- Кто выполняет привязку identity: администратор в UI или заявка с ручной
  операцией.
- Обязателен ли back-channel logout для первого заказчика.
- Нужен ли режим B сразу или отдельной поставкой после первого внедрения.
