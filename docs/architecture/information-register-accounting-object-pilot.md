# Регистры сведений: пилот «Объект учёта номенклатуры»

- Дата: 2026-10-06.
- Статус: пилот, итерация 1, проверен пользователем; оценка положительная (2026-10-07).
- Режим: пилот, итерация 1; следующие итерации выбираются после практической пробы.
- Основание: [политика разработки](development-delivery-policy.md),
  [план регистратора](information-register-recorder-plan.md),
  [ADR-0015](decisions/ADR-0015-information-register-recorder.md).
- Удаление: повторная установка разрешена, если во всей сохранившейся истории
  больше нет записей пары «Цех + Номенклатура» (§5).

## 0. Режим и объём

- Цель / вопрос, который решаем: удобно ли объявлять и подключать подчинённый
  регистр к документам и пользоваться установкой, корректировкой и срезом на дату.
- Режим: пилот.
- Текущая итерация: 1; практическая проба завершена, пользователь оценил пилот положительно.
- Основание выбора: предметные правила согласованы; практическое удобство
  прикладного подключения и пользовательских форм проверено в локальной пробе.
- Пользователь или потребитель: прикладной разработчик и пользователь документов
  установки / корректировки объекта учёта.
- Рабочий сценарий: подготовить справочники и права → сохранить установку →
  просмотреть записи → подобрать номенклатуру на дату корректировки → сравнить
  текущий и новый тип → сохранить → проверить историю, срез и удаление.
- Входит в текущий пакет: два сценария §1, предметная модель и серверные правила
  §2–§5, формы и чтение регистра, схема и данные для пробы, применимые проверки.
- Отложено и почему: отчёты Preview/PDF, полный экспорт, дополнительные
  регистраторы и окончательная поставка не нужны для вопросов первой пробы.
- Окружение и зависимости: локальное приложение и отдельная тестовая схема;
  до записи пилотных данных фиксируем фактический профиль запуска и СУБД.
  Текущая конфигурация приложения задаёт PostgreSQL dialect; H2-проверки
  учитываем отдельно и не объявляем приёмкой PostgreSQL-сценария.
- Допустимые упрощения и ограничения: один новый периодический регистр,
  два типа регистраторов и выбранное окружение пробы; учётные алгоритмы не реализуются.
- Обязательные гарантии и применимые gates: серверные права и validation,
  независимость доступа к регистру и документу, запрет generic CRUD строк,
  атомарное сохранение / замена / удаление и согласованный порядок среза;
  применимые security/data gates определяем для выбранного запуска.
- Проверки выбранного сценария и его рисков: основной путь, повторное сохранение,
  отказы правил и прав, откат, конкуренция первоначальной установки одной пары,
  удаление, срез на дату и равные периоды; контроль самостоятельных цен.
- Критерий завершения текущего пакета: выполнены пользовательские шаги §7,
  необходимые проверки и подготовка; можно пройти сценарий по короткой инструкции.
- Практическая проба: предоставить команды запуска, учётку / настройку прав,
  пример данных, последовательность действий и ожидаемые результаты.
- Вопросы для обратной связи: удобство прикладного подключения, подбора,
  сравнения типов, просмотра истории и сообщений об отказах.
- Условия перехода к следующему пакету: результаты пробы и выбранное улучшение;
  объём следующей итерации заранее не назначается.
- Условия перехода к завершённому механизму: отдельное решение пользователя
  с подтверждёнными сценариями, целевым окружением и DoD завершения.

## 1. Цель и два сценария

Проверить использование регистра в прикладных документах, включая формирование
набора, самостоятельное чтение и подбор по срезу последних.

| Сценарий | Пилот | Проверяемый путь |
| --- | --- | --- |
| Без регистратора | Существующие «Цены номенклатуры» | Запись и чтение самостоятельного регистра сохраняют свой контракт |
| С регистратором | Новый «Объект учёта номенклатуры» | Установка и корректировка через два документа; история и актуальный тип учёта по цеху |

Новый сценарий использует два собственных DOCUMENT-типа. Подчинение существующих
цен и изменение предметного смысла `ReceivingDocument` в этот пакет не входят.

## 2. Модель

### Справочник «Тип учёта»

Обычный справочник с полями **Код** и **Наименование**. Начальные варианты:
**ФИФО, ЛИФО, СКЕ**. Тип учёта хранится и выбирается как ссылка на запись
справочника. Enum и реализация алгоритмов FIFO/LIFO в этом сценарии не требуются.

### Регистр сведений «Объект учёта номенклатуры»

- Периодический, подчинённый регистратору.
- Измерения: **Цех**, **Номенклатура**.
- Ресурс: **Тип учёта**, ссылка на справочник.
- Период: дата документа-регистратора.
- Разрешённые регистраторы: документы установки и корректировки.

Срез последних возвращает актуальный тип учёта для пары «Цех + Номенклатура»
на указанную дату. При равном периоде применяется принятый порядок
`period → recording_order → line_no` по ADR-0015.
Наличие регистратора не добавляет его в бизнес-измерения.

## 3. Документ «Установка объекта учёта»

**Шапка:** Номер, Дата, Цех.
**Табличная часть:** Номенклатура, Тип учёта.

Документ формирует первоначальные записи для номенклатуры, у которой **нет
ни одной записи в истории выбранного цеха**. Проверка относится к паре
«Цех + Номенклатура» и всей сохранившейся истории, включая записи позже даты документа.
Отсутствие записи в срезе на дату установки само по себе недостаточно. Исходное
требование «никогда не была зарегистрирована» уточнено пользователем: после удаления
всех записей пары повторная установка допускается (§5).

Перед сохранением сервер проверяет допустимость каждой пары. Подбор может
помогать выбирать подходящие позиции, но бизнес-проверка действует и при обходе UI.
Скрытая по правам существующая запись не делает пару допустимой для установки.
Две конкурентные установки одной пары не должны обе успешно создать первоначальные
записи. Конкретный способ обеспечить это зависит также от правила §5.

При редактировании установки проверка должна учитывать собственный заменяемый
набор: повторное сохранение ранее установленной этим документом пары не считается
новой независимой установкой. Для вновь добавленной пары проверяется вся история;
изменение цеха также создаёт другую проверяемую пару.
Повторы номенклатуры внутри одного документа отклоняются до записи набора.

## 4. Документ «Корректировка объекта учёта»

**Шапка:** Номер, Дата, Цех.
**Табличная часть:** Номенклатура, **Текущий тип учёта**, **Новый тип учёта**.

Подбор получает доступные пользователю номенклатуры выбранного цеха из среза
последних **на дату документа корректировки**. Пользователь выбирает позиции
и указывает новый тип учёта из справочника.

Текущий тип — справочная колонка для сравнения. В новые записи регистра попадает
новый тип. Подробный контракт пересчёта колонки при изменении даты/цеха и повторном
открытии документа фиксируется при подключении формы; видимое текущее значение
должно соответствовать выбранному цеху и дате.

Сервер повторно проверяет наличие подходящего объекта учёта на дату документа,
права и обязательность нового типа. Запись корректировки добавляет значение
от нового регистратора; предыдущие документы сохраняют свои записи.
Редактирование документа заменяет его собственный набор атомарно.

## 5. Удаление документа и повторная установка

Общий контракт ADR-0015 очищает записи регистра при удалении их документа.
Согласованное правило пользователя: **повторная установка разрешена, если
во всей сохранившейся истории больше нет записей этой пары**.

Удаление первоначальной установки само по себе не разрешает новую установку:
если остались записи корректировок или других документов, пара уже присутствует
в истории. После удаления всех её записей установка вновь допустима. Такая же
проверка применяется после удаления строки из заменяемого набора.

Отдельная постоянная память о когда-либо удалённых регистрациях не требуется.
Правило проверяется по полному существующему набору записей, включая будущие даты,
и не зависит от состава доступного пользователю среза.

## 6. Объём первой итерации

Включаем справочник типов, два документа и их табличные части, декларацию регистра,
прикладное формирование наборов через существующую aggregate transaction boundary,
просмотр истории и регистратора, подбор для корректировки и инструкцию запуска.

Проверяем сохранение, повторное сохранение, изменение и удаление документа;
отказы бизнес-правил и прав доступа; откат; срез на дату и порядок при равной дате.
Самостоятельные цены проходят контрольный сценарий без изменения их модели.
Перед пользовательской пробой нужны проверенная тестовая схема и данные для запуска.

Отложено: отчётный сценарий Preview/PDF и полный набор экспорта, дополнительные
типы регистраторов, окончательная поставка и выбор deployment backend. Реализация
учётных алгоритмов FIFO/LIFO, posting и ledger имеет отдельный предметный объём.

Обязательные проверки целостности, независимости прав регистра/документа и
серверного запрета generic CRUD подчинённых строк сохраняются.

## 7. Готовность к пробе и дальнейшие итерации

Первая итерация готова, когда пользователь может:

1. Выбрать типы учёта в справочнике.
2. Установить объекты учёта в цехе и увидеть записи с регистратором.
3. Получить подбор на дату корректировки, сравнить текущий и новый тип и сохранить.
4. Проверить историю и срез для двух цехов, нескольких дат и двух типов документов.
5. Получить понятный отказ повторной установки и проверить согласованное поведение удаления.
6. Выполнить контрольную запись/чтение «Цен номенклатуры» без регистратора.

Вопросы пробы: удобны ли подбор, сравнение типов и сообщения; хватает ли полей
и отборов; понятны ли история и правило актуальности.

| Итерация | Цель | Состояние |
| --- | --- | --- |
| Пилот 1 | Два сквозных сценария, установка и корректировка объектов учёта | Реализован и проверен; готов к пробе 2026-10-07. Обратная связь ожидается |
| Пилот 2 | Улучшения по результатам первой пробы | Объём выбирается после обратной связи |
| Пилот 3, при необходимости | Следующие подтверждённые сценарии, например отчёт | Отдельное решение |

К полному завершению Г6–Г8 переходим по отдельному решению: фиксируем подтверждённый
объём, оставшиеся ограничения, миграции и необходимые deployment/compatibility проверки.
Готовность первой итерации не означает закрытие всего трека регистратора.

## 8. План действий первой итерации

Каждый шаг ниже — часть одной итерации. Пользовательская проба проводится после
готовности всего выбранного пути; техническая готовность промежуточного шага
сама по себе не закрывает пилот.

### 1. Уточнить необходимые зависимости и условия запуска

- Сверить реализацию и evidence Г0–Г5 с нуждами этого сценария. Незакрытые
  критерии Г1/Г2, относящиеся к обязательным гарантиям пилота, включить в пакет:
  в частности, отказ startup при дубликате кода или недопустимом регистраторе.
- Зафиксировать профиль локального запуска, отдельную тестовую схему, способ
  её подготовки и доступные учётки; перечислить применимые gates.
- Перед подключением корректировки определить точность периода / даты,
  пересчёт текущего типа при смене даты или цеха и повторном открытии документа,
  а также учёт собственного заменяемого набора при проверке и подборе.

Результат: известны конкретные необходимые доработки и проверки; окружение
и правила формы позволяют реализовать первую итерацию без расширения до всего Г0–Г8.

### 2. Добавить предметную модель и схему

- Использовать существующие справочники `Workshop` и `Nomenclature`.
- Добавить справочник типов учёта, регистр, два документа и их табличные части
  по §2–§4; объявить стабильные коды двух регистраторов.
- Подготовить воспроизводимое создание новых таблиц, ограничений и необходимых
  индексов в тестовой схеме. `ddl-auto=update` не считать заменой миграции.

Результат: модель и схема поддерживают оба документа и историю регистра.

### 3. Подключить серверное поведение документов

- Формировать и заменять набор через существующую общую транзакцию сохранения
  документа; повторное сохранение не создаёт дубликатов.
- Проверять установку по полной истории с учётом собственного набора;
  обеспечить отказ второй конкурентной первоначальной установки той же пары.
- Проверять корректировку на дату документа и обязательность нового типа;
  отклонять повторы номенклатуры в табличной части.
- Применять согласованные права; сохранить атомарную очистку при удалении
  и правило повторной установки §5.

Результат: установка, корректировка, редактирование и удаление работают
через серверные операции с необходимыми гарантиями.

### 4. Подключить формы и просмотр результата

- Дать точки входа в справочник типов, оба документа и регистр.
- В корректировке реализовать подбор по цеху и дате, текущий / новый тип
  и согласованный пересчёт при изменении шапки.
- Сделать просмотр истории и среза с нужными отборами, подписью регистратора
  и переходом в доступный документ; сообщения об отказах должны объяснять правило.

Результат: пользователь проходит основной путь через интерфейс приложения.

### 5. Проверить выбранные сценарии и риски

- Пройти установку → корректировку → историю / срез → редактирование → удаление.
- Проверить два цеха, несколько дат, будущие записи,
  равные периоды и оба типа документов.
- Проверить отказы правил и прав, откат, конкуренцию установок одной пары,
  повторное сохранение и серверный запрет прямого CRUD подчинённых строк.
- Выполнить контрольный сценарий самостоятельных цен и необходимые
  проверки совместимости изменённых общих границ.
- Разделить результаты H2 и фактической СУБД пробы; учесть существующее evidence,
  повторяя проверки при изменениях или конкретных непроверенных рисках.

Результат: основной путь и существенные риски подтверждены в заявленном объёме.

### 6. Подготовить пользовательскую пробу

- Подготовить пример: два цеха, несколько номенклатур, ФИФО / ЛИФО / СКЕ,
  документы на разных датах; дать воспроизводимые шаги подготовки и запуска.
- Описать права, действия, ожидаемые результаты и ограничения.
- Сообщить «Пилот, итерация 1, готов к пробе» и предоставить пользователю результат.

Результат: выполнен критерий «можно пробовать» §7. Затем записываем обратную
связь в таблицу итераций и выбираем следующий пакет по результатам пробы.

## 9. Результат первой итерации — 2026-10-07

Реализованы справочник типов учёта, оба документа с табличными частями,
подчинённый периодический регистр, атомарная замена / очистка набора,
проверки первоначальной установки и корректировки, формы, подбор,
история и срез на дату с переходом к регистратору.

- [Инструкция для пользовательской пробы](accounting-object-pilot-user-guide.md).
- [Результаты проверок и технические границы](accounting-object-pilot-iteration1-evidence.md).
- Локальное окружение: PostgreSQL 17, база `accounting_object_pilot_local_v3`,
  профиль `accounting-pilot`, адрес `http://127.0.0.1:18080`.
- Проверки: 62 в пакете приложения, 18 сценариев пилота на PostgreSQL;
  ранее 476 проверок модуля Vaadin после добавления обновления строк таблицы.

Готовность относится к выбранному объёму пилота. Подбор ограничен 200 объектами
одного цеха; период без часового пояса с точностью до микросекунды; номер ручной;
минимум одна строка документа; запись сериализуется по цеху. Новые документы
и регистр используют независимые права на вид сущности, без построчного
ограничения регистра по цехам. Отчёты, экспорт и production-развёртывание
в эту итерацию не входят. План Г0–Г8 целиком не закрывается.
