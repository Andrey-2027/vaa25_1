# Как добавить действие: декларативные действия форм

Документ описывает прикладную сторону машины действий E1 (`org.ipro.form.action`): что нужно
сделать, чтобы действие появилось, чего делать не нужно и как это проверяется. Нормативные
формулировки самого контракта — в javadoc типов `platform-vaadin`; здесь — рабочее руководство.

## 0. Три вещи, которые нужно знать до чтения

1. **Доступность действия — данные, а не код.** Требование (`ActionRequirement`) описывает, что
   нужно действию (операция типа, выделение, обязательный контекст), и его считает одна общая
   политика (`ActionPolicy`) по уже вычисленным входам (capability типа + права + контекст).
   Своей формулы доступности в UI быть не должно.
2. **Объявление и исполнение — одна сущность.** Центральное действие — бин `ActionHandler`:
   `definition()` говорит *что* и *при каких условиях*, `execute(ActionInvocation)` — *как*.
   Объявление без исполнения неотличимо от опечатки, поэтому они вместе.
3. **Стандартный случай не требует ничего.** Обычная сущность с `@EntityMetadata` уже имеет
   generic-действия списка и карточки: они выводятся из capability типа. Добавлять код нужно только
   там, где поведение предметное (AppDev-first: инфраструктура не переезжает в прикладной
   boilerplate).

## 1. Пример 1: стандартная сущность — кода нет

Для типа с `@EntityMetadata` и обычным canonical data handle ничего объявлять не нужно:

| Тип | Что видит пользователь | Почему |
| --- | --- | --- |
| `Nomenclature` (полный CRUD) | Создать, Копировать, Изменить, Удалить, Обновить | `STANDARD_ROOT`: `LIST/DETAIL/LOOKUP` + `CREATE/UPDATE/DELETE` |
| `AttributeValue` (`CREATE` без `UPDATE`) | Просмотр, Обновить | `UPDATE` нет → «Изменить» неприменимо, «Просмотр» применимо (`UNAVAILABLE`) |
| `SklNomOpa` (`writes = {}`) | Просмотр, Обновить | операций записи нет → остаётся чтение |

Проверка на этот случай — не код, а тест состава (`ActionPolicyConfigTest`): он берёт реальные
прикладные политики и утверждает, что список действий следует из capability. Если для обычной
сущности понадобилось добавить действие — сначала проверьте, не выражается ли оно capability или
`suppress-override` (§4).

## 2. Пример 2: предметное действие с обязательным контекстом

Когда поведение предметное (в терминах проекта — «через `findOrCreate`, а не generic CRUD»),
действие объявляется явно. Скелет (полностью компилируемый, на настоящих типах; предметный путь
сегодня живёт в карточке типа атрибута — `AttributeTypeForm` → `AttributeValueService.getOrCreate`;
ниже показано, как тот же путь выглядит объявленным действием):

```java
@Component
public class AttributeValueAddAction implements ActionHandler {

    public static final ActionId ID = ActionId.of("attribute-value.add");

    /** Контекстный фильтр, без которого действие неприменимо: тип атрибута. */
    public static final String ATTRIBUTE_TYPE = "attrType";

    private final AttributeValueService values;

    public AttributeValueAddAction(AttributeValueService values) {
        this.values = values;
    }

    @Override
    public ActionDefinition definition() {
        return ActionDefinition.forEntity(ID, ActionSurface.LIST_TOOLBAR, AttributeValue.class,
            "Добавить значение", null, 10,
            // CREATE обязателен, выделение не нужно, обязательный контекст нужен:
            // без выбранного типа атрибута значение некуда интернировать.
            ActionRequirement.of(Level.REQUIRED, Level.ANY, Level.ANY, Level.ANY, false, true));
    }

    @Override
    public void execute(ActionInvocation invocation) {
        AttributeType type = (AttributeType) invocation.contextFilter(ATTRIBUTE_TYPE);
        if (type == null) {
            return; // контекст исчез между решением и кликом — штатный случай, не исключение
        }
        AttributeValue created = values.createEnumValue(type, rawCode(invocation), nameOf(invocation));
        if (invocation.canRefresh()) {
            invocation.refresh().run();
        }
    }
}
```

Что здесь существенно:

- **Идентичность — `ActionId`, не подпись.** Подпись можно менять, идентификатор — нет.
- **Поверхность и тип — часть ключа** `(surface, entityType, variant, actionId)`. `variant` — ключ
  варианта списка/карточки, а не фильтр применимости: «показывать в варианте X» выражается
  вариантом, «показывать при условии Y» — требованием.
- **Обязательный контекст — `requiredContextRequired`**, и незаполненный контекст даёт
  `CONTEXT_INCOMPLETE` с причиной, которую пользователь читает в подсказке.
- **Исполнение получает снимок** (`ActionInvocation`): строку, вариант, параметры открытия, значения
  контекстных фильтров, узкий `FormNavigator` и `refresh()`. Ни `ListForm`, ни
  `ApplicationContext` в исполнении нет — иначе доступность снова стала бы непереносимой в решение.
- **У исполнителя нет `isEnabled`.** Если действие применимо не всегда — это требование, а не
  предикат.
- **Строка/контекст, исчезнувшие между решением и кликом, — штатный случай**: действие просто не
  выполняется.

**Локальное действие одного составного view** объявляется на самой форме
(`ListForm#addAction`) и не требует ни Spring-бина, ни центральной регистрации: объявление
берётся у исполнителя, поэтому забытая регистрация не прячет кнопку молча.

## 3. Требования: что чем выражается

| Уровень | Значит | Пример |
| --- | --- | --- |
| `REQUIRED` | операция обязана быть: нужны и capability типа, и право пользователя | `crud.create` |
| `FORBIDDEN` | операции **не должно быть у типа** (только capability) | структурные условия |
| `UNAVAILABLE` | операция обязана быть **недоступна**: нет у типа **или** запрещена правами | `crud.open` |
| `ANY` | операция не участвует в решении | `crud.refresh` |

Плюс три флага: `selectionRequired` (нужна выделенная строка), `requiredContextRequired` (нужен
заполненный обязательный контекст) и `linkableRequired` (нужен публичный адрес формы, E2.1:
`ActionRequirement.linkable()`), и `rowStateSelectsOperation` — только для действий карточки,
где операция выбирается состоянием объекта (`crud.save`: новая запись — `CREATE`, существующая —
`UPDATE`).

Порядок проверок в политике фиксирован и объясним: подавление → применимость по типу/правам →
выделение → права на обязанную операцию → обязательный контекст → наличие адреса. Поэтому причина
в подсказке всегда называет ту проверку, которая действительно не прошла.

**`linkableRequired` — «действию нужна ссылка» (E2.1).** Так объявляется affordance, который без
публичного адреса не имеет смысла: у типа нет public handle, его сценарий чтения запрещён, вариант
требует необъявленного контекста или у записи ещё нет id. Отсутствие адреса делает действие
**неприменимым** (`NOT_LINKABLE`, скрыто), а не «видимым-но-серым»: серым оно было бы обещанием
ссылки, которой платформа не выдаст ни при каком состоянии экрана. Вход спрашивается **лениво** —
только у действия, объявившего это требование, — потому что первое обращение к каталогу адресов
строит его целиком.

## 4. Видимость и политика типа: `suppress-override`

Ситуация «generic-операция формально возможна, но правильный путь другой» выражается подавлением:

```java
@Bean
public ActionDefinition attributeValueWithoutGenericCreate() {
    return ActionDefinition.suppress(CrudAction.CREATE, ActionSurface.LIST_TOOLBAR,
        AttributeValue.class);
}
```

Правила подавления:

- это **UI-policy типа**, а не разрешение операции: capability типа не сужается, серверная граница
  не ослабляется (ADR-0007, ADR-0008);
- целевая регистрация обязана существовать — иначе старт падает с названной причиной, и опечатка
  в идентификаторе не превращается в молчаливо новое действие;
- требование у подавленной записи не вычисляется вовсе (решение останавливается на невидимости).

## 5. Чего не делать

1. **Не считать доступность в UI.** Вторая формула (предикат у кнопки, `setEnabled` по месту) — это
   шов, который E1 устранил: кнопка и серверная проверка расходились.
2. **Не прятать кнопку вместо подавления.** Скрытие в рендерере оставляет действие
   зарегистрированным для всех, кто о нём знает.
3. **Не сужать capability типа, чтобы скрыть кнопку.** Capability — про данные, а не про UI; для UI
   есть подавление.
4. **Не держать два владельца клика** (старый listener рядом с новым действием).
5. **Не тянуть форму или контекст Spring в исполнение.** Нужен снимок — он в `ActionInvocation`;
   чего в нём нет, того у действия быть не должно.
6. **Не выражать применимость вариантом.** Вариант — ключ, а не условие.

## 6. Как это проверяется

| Что | Чем |
| --- | --- |
| Семантические роли типов модуля | `platform-vaadin-surface.txt` + `PlatformVaadinSurfaceTest` (новый тип модуля обязан получить ровно одну роль) |
| Публичная подпись модуля | `platform-api-baseline/platform-vaadin.api` + `PlatformApiBaselineTest` (перезапись: `-Dplatform.api.baseline.write=true`) |
| Направления пакетов | `platform-package-matrix.txt` + `PlatformPackageDependencyMatrixTest` |
| Поведение решения | `ActionPolicyDecisionTableTest` (таблица решений), `ListFormActionDecisionTest` (кнопки и двойной клик на настоящем решателе) |
| Прикладная политика типа | `ActionPolicyConfigTest` (состав действий по типу на настоящих политиках) |
| Мёртвая поверхность | `FormDeadApiTest` (whitelist с обоснованием) |
| Полная проверка | `mvn verify` |

Прикладному действию в приложении отдельная запись в реестре ролей не нужна: реестр описывает
поверхность **модуля**, а действие приложения — потребитель этой поверхности.

## 7. Историческая справка (почему так)

До E1 доступность прикладной операции считалась предикатом внутри UI: у легаси-`ListCommand` были
`isEnabled(context)` и `appliesToVariant(variant)`, кнопка собиралась координатором, а серверная
граница проверяла права независимо. Расхождение между кнопкой и строкой (двойной клик открывал
карточку в обход проверки прав), причины отказов, которые нельзя было показать, и отсутствие пути
чтения у строки с отказом в правах — всё это следствия одной причины: у строки не было решения,
была вторая формула. Легаси-команды, их контекст, реестр и переходный адаптер сняты в E1.7.
