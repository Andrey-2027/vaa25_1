# E2.0 — spike host-стратегии и синхронизации адреса

> Статус: `DONE` (исследование); host реализован в E2.3 — подтверждён наблюдением, см. §6.
> Дата: 2026-09-25.
> Источник объёма: `docs/plans/e2-deep-linking-plan.md` §2.3, §5 (E2.0).
> Тип: результат проверки, а не реализуемая функциональность. Продуктовый код не изменён.

## 1. Вопросы spike

E2 должен уметь открывать форму по стабильному адресу. До публичного API и UI-интеграции нужно было
ответить на четыре вопроса:

1. Работают ли route templates в `@RouteAlias` на текущем `@Route("")`-компоненте (`MainLayout`)?
2. Пересоздаётся ли `MainLayout` при клиентской навигации, и вызывается ли повторно `openHome`?
3. Как менять адрес активной вкладки, не превращая переключение вкладок в route-entry?
4. Что происходит с Back/Forward и сохраняется ли состояние вкладок?

## 2. Метод

Spike выполнен на реальном приложении в dev-режиме (PostgreSQL `localhost:5432`, порт 8080), не на
моке. В `MainLayout` временно добавлены: два `@RouteAlias` с шаблонами, `BeforeEnterObserver`,
счётчики созданий и вызовов `openHome`, а также два триггера навигации (`UI.navigate` и
`Page.getHistory().pushState` + `setHistoryStateChangeHandler`). Сценарии прогонялись через реальный
браузер; наблюдения — серверные счётчики и `history.state` на клиенте.

Временная инструментация после прогона удалена: `git diff` по `MainLayout` пуст, следов `e2spike` в
дереве нет. Приложение остановлено.

**Фактическая версия Vaadin в сборке — 25.1.7**, тогда как `pom.xml` объявляет 25.1.6. Версии стоит
синхронизировать, чтобы ссылки на «25.1.6» в документах не были ложными.

## 3. Результаты

| # | Проверка | Результат |
| --- | --- | --- |
| 1 | Route templates в `@RouteAlias` на `@Route("")` | Работают: `/e2spike/:entityKey/:id` и `/e2spike-list/:entityKey` зарегистрировались и обслуживались |
| 2 | `/` → alias клиентски | Тот же экземпляр `MainLayout`; повторного `openHome` нет; тот же `Workspace` |
| 3 | Back после router-навигации | `BeforeEnter` для предыдущего пути; тот же layout и `Workspace`; без перезагрузки |
| 4 | Cold-загрузка deep URL | Работает; порядок `ctor → openHome → beforeEnter` |
| 5 | Auth redirect | Исходный URL сохраняется: после логина попадаем на deep URL; в адресе появляется `?continue` |
| 6 | Ручной `javascript history.pushState` | URL меняется без роутинга (`BeforeEnter` не вызывается), но Back с такой записи даёт **полную перезагрузку**: новый UI, новый `Workspace`, вкладки потеряны |
| 7 | Vaadin `History.pushState` + `setHistoryStateChangeHandler` | URL меняется без роутинга; Back/Forward приходят в Java-обработчик (`trigger=HISTORY`) тем же `Workspace` и без перезагрузки |
| 8 | Два UI (две вкладки браузера) | Независимые UI-scoped `Workspace`; URL одного не управляет другим |
| 9 | Существующие маршруты | `/report-catalog` alias'ом не затронут |

## 4. Принятые решения

1. **Host** — alias templates на существующем `MainLayout`. Прототипный scope не означает пересоздания
   на каждый переход: экземпляр route target переиспользуется при навигации внутри одного компонента,
   поэтому UI-scoped `Workspace` и состояние вкладок сохраняются. Отдельный app-owned shell и два route
   target не нужны.
2. **URL sync активной вкладки** — Vaadin `Page.getHistory().pushState/replaceState` с обязательным
   `setHistoryStateChangeHandler`. `UI.navigate` для этой задачи не годится: он запускает `BeforeEnter`
   на каждое изменение адреса.
3. **Back/Forward** — обрабатываются в `HistoryStateChangeHandler` (`trigger=HISTORY`); `BeforeEnter`
   остаётся для cold-входа и перезагрузки. Source guard различает программный pushState и
   пользовательский Back/Forward.
4. **Порядок cold-загрузки** — route-обработчик активирует целевую вкладку после `openHome`.

## 5. Остаточные риски и следующие проверки

- API `History` принимает Jackson 3 (`tools.jackson.databind.node.BaseJsonNode`), тогда как прикладной код
  использует Jackson 2. Транзитивно доступно, но это новая зависимость поверхности: инкапсулировать в
  `FormLinkService`/тонком адаптере и не протаскивать в прикладной код.
- После auth redirect в URL добавляется `?continue`; canonical URL обязан его переносить или отбрасывать,
  не считая ошибкой.
- Не проверено в этом spike: повторная проверка прав при Back к уже открытой вкладке, взаимодействие
  dirty-формы с history-переходами (E2.4), поведение при переходе alias → другой `@Route`
  (ожидаемо пересоздаёт shell).

## 6. Подтверждение реализации (E2.3, тот же стенд)

После E2.3 те же решения проверены на живом приложении (PostgreSQL, профиль `dev`, вход
`admin`), а не только тестами без UI. Результаты ниже — наблюдения, а не ожидания.

| # | Проверка | Результат |
| --- | --- | --- |
| 1 | Cold-загрузка `/records/nomenclature/1` без сессии | Redirect на `/login`, после входа — тот же адрес плюс `?continue`; кодек его переносит, форма открывается вкладкой `Workspace` |
| 2 | Cold-загрузка `/lists/nomenclature` | Список открывается вкладкой «Номенклатура», адрес — тот же |
| 3 | Повторная загрузка того же адреса | Та же вкладка и те же данные; повторный вход перечитывает строку |
| 4 | Реально отсутствующий id (`/records/nomenclature/2000000`) | Страница «Запись не найдена», **адрес не изменён**, вкладка не создана; в журнале `outcome=not-found` |
| 5 | Нарушение грамматики (`/records/Nomenclature/1`) | «Адрес не найден» (`entityKey вне грамматики`), адрес не изменён, вкладка не создана; `outcome=invalid-route` |
| 6 | Переключение на вкладку без адреса («Главная») | Адрес становится `/` — соответствие «видимое = адрес» держится |
| 7 | Route audit | Метка исхода и адрес пишутся в журнал с traceId и пользователем; id в метку не попадает, hidden и missing не различаются |

**Дефект, найденный только наблюдением.** `Location` из Vaadin отдаёт путь **без ведущего
слэша** (`records/nomenclature/1`), тогда как адрес формы — относительный путь, начинающийся
с `/`. Первая версия host'а поэтому показывала «Адрес не найден» на **каждой** корректной
ссылке. Отказ при этом вёл себя правильно (адрес не менялся, вкладка не создавалась) — то есть
дефект был виден как массовый 404, а не как обход защиты. Исправлено в host'е: слэш добавляет
host, всё остальное (`?continue`, регистр ключа, ведущие нули) остаётся делом кодека.

**Что наблюдением пока не проверено.** Ветка «переход между двумя адресуемыми вкладками»
(`pushState`) требует двух routable-вкладок в одной загрузке страницы, а сегодняшнее приложение
даёт не больше одной: каждый адрес приходит отдельной загрузкой, а обычные вызовы координатора
открывают вкладки без адреса (для них адрес — замена, а не шаг). Клиентская навигация
алиас → алиас (или открытие второй ссылки внутри сеанса) эту ветку включит; до тех пор она
покрыта только тестом моста. Back/Forward при переходе между загрузками — это обычная
навигация документа, то есть тот же cold-путь, что в строке 1.

## 7. Что это меняет в плане E2

Выбор host и способа URL sync закрыты. Дальше верны E2.1 (каталог/codec), E2.2 (безопасный
open-result), E2.3 (host + мост URL/Workspace на `History.pushState`) и E2.4 (dirty-navigation).
Локальный `docs/plans/e2-deep-linking-plan.md` — рабочий черновик; этот документ является
версионируемым результатом E2.0.
