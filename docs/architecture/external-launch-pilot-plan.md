# Запуск GitVaa из внешнего приложения: пилот «выбор записей для 1С»

Дата: 2026-10-27. Статус: предложение, не принято.
Ревизия 1 (2026-10-27) — по замечаниям владельца: доверие к переданному
пользователю, доступ по операции вместо полного входа, конфликт с существующей
сессией, определение профиля, серверное завершение выбора, восстановление после
сбоя и уточнение отказов.
Ревизия 2 (2026-10-27) — по ответам владельца: профиль зафиксирован —
**Номенклатура** (`id`, `code`, `name`), а операция должна выдерживать
**длительную работу** — список может быть открыт и «висеть» в браузере без выбора
(§9).

**Условие входа.** Есть внешняя система (пилот — 1С), из формы которой пользователь
уже работает, и он должен выбрать записи в GitVaa, а 1С — прочитать выбранное.
Механизм не строится «на будущее»: это первый подтверждённый потребитель, а не
универсальная шина. Формально канал относится к этапу F
([roadmap §9](../../JMIX_GitVaa_Roadmap_v2.md), `CONDITIONAL`), но пилот входит
по правилам политики — один полный сценарий первого потребителя
([policy §3](../development-delivery-policy.md)).

Пилот начинается, когда выполняется всё перечисленное:

1. список и поля названы: пилот — **Номенклатура**, в результат идут **`id`
   (ключ), `code`, `name`**;
2. есть **доверенный сервер 1С** — секрет интеграции хранится на сервере, а не в
   клиентской форме;
3. есть **явная привязка** «система + стабильный ID пользователя → локальный `User`»;
4. есть **форма 1С** (или её минимальная заготовка), на которой проверяется полный
   путь до применения результата: проба через `curl` подтверждает API, но удобство
   интеграции показывает только работающая форма.

**Область.** Пилот добавляет ровно один канал: запуск по одноразовому билету и
чтение результата вызывающей системой (вариант «1С забирает сама»). Билет даёт
**доступ, ограниченный конкретной операцией выбора**, а не полноценный вход в
приложение: полноценный вход по билету — отдельное свойство и отдельное решение.
Модель прав не меняется: субъектом остаётся локальный `User.username`, решения дают
C5/RLS. OIDC/SSO — другая задача ([oidc-login-plan](oidc-login-plan.md)) и пилоту
не нужен.

## Режим и объём

- Цель / вопрос: можно ли за один проход «1С → билет → выбор → результат» получить
  в 1С выбранные записи, не вводя пароль в браузере и не открывая 1С для входящих?
- Режим: пилот, одна итерация (первый полный сценарий).
- Основание выбора: [policy](../development-delivery-policy.md) §3 — «есть первый
  потребитель; нужны данные для выбора контракта».
- Потребитель: сотрудник, работающий в 1С; вызывающая система — сервер 1С
  (служебная учётка).
- Рабочий сценарий: сервер 1С просит билет → открывает URL у пользователя →
  пользователь отмечает строки номенклатуры в списке GitVaa и нажимает «Передать
  в 1С» → 1С опрашивает результат и получает `id`, `code`, `name` выбранных
  записей, собранные сервером.
- Входит в текущий пакет: API запуска (идемпотентный по `requestId`) и чтения
  результата, потребление билета и **сессия, ограниченная операцией**, экран выбора
  (множественная отметка, профиль Номенклатуры `id`/`code`/`name`,
  «Передать в 1С» / «Отмена»), серверное завершение выбора с повторной проверкой
  доступа, **длительная работа** (операция и сессия не рвутся по короткому простою),
  таблица операций со статусами и сроками, именованное право `INTEGRATION:LAUNCH`,
  честная ленивая чистка, аудит, сквозная приёмка с формой 1С.
- Отложено и почему: обратный вызов (callback) и outbox — не нужны для гипотезы и
  требуют открытого входящего 1С; полноценный вход в приложение по билету;
  OIDC/SSO; JIT-создание пользователей; несколько одновременных вкладок одной
  операции; несколько внешних систем и профилей; тысячи записей и постраничная
  отдача; сохранение уже сделанных отметок при возврате после закрытия вкладки;
  «живое» обновление формы 1С; гарантия «ровно то, что видел» без проверки версии.
- Окружение и зависимости: локальный стенд (PostgreSQL/H2, профиль `dev`), браузер
  пользователя, сервер 1С со служебной учёткой. Входящий доступ к 1С не требуется.
- Допустимые упрощения: один список и один профиль (Номенклатура); привязка —
  явный список в конфигурации; лимит выбранных записей; одна операция на браузерную
  сессию; значения собираются на момент подтверждения; сроки — параметры (билет
  3 минуты, операция — рабочая смена, результат — 15 минут после завершения) (§3).
- Обязательные гарантии: права и построчный доступ считаются на сервере от лица
  связанного локального пользователя (существующие C5/RLS); результат читает только
  инициировавшая система; повторная проверка доступа при завершении выбора; чистка по
  сроку; аудит без содержимого записей; новых путей к данным не появляется.
- Проверки: билет (одноразовость, срок, чужой билет, конфликт сессии), результат
  (свой/чужой, повторное чтение, истечение, `410`), идемпотентность запуска и
  завершения, повторная проверка доступа при завершении, двухпользовательская
  проверка RLS, `returnUrl` по allow-list, сквозная проба с формой 1С.
- Критерий завершения пакета: сквозной сценарий проходит с формой 1С на стенде,
  владелец может оценить формат результата, поведение при отказе и удобство запуска.
- Практическая проба: инструкция запуска, `curl`-примеры, минимальные шаги 1С
  (`ЗапуститьПриложение`, опрос, применение результата) и демонстрация на форме.
- Вопросы для обратной связи: см. §8.
- Условия перехода к следующему пакету: проба подтверждена и назван конкретный
  недостающий сценарий (второй профиль, размер выборки, несколько вкладок,
  сохранение отметок между заходами).
- Условия перехода от пилота к завершённому механизму: отдельное решение владельца;
  тогда — версии контрактов, несколько систем, надёжная доставка и эксплуатация.

## 1. Модель доверия

- API вызывает **сервер 1С** под служебной учёткой; секрет интеграции хранится на
  сервере 1С и не попадает ни в клиентскую форму, ни в ссылку, ни в 1С-клиент.
- Клиентская форма **не имеет доступа к API** и не может произвольно подставить
  `subject`. Если это условие нарушается на стороне 1С, модель ломается — это явное
  требование к интеграции, а не деталь реализации.
- Даже при доверенном сервере учётка интеграции умеет инициировать операцию от имени
  любого пользователя из привязок. Поэтому привязка — **явный список**
  `(система, стабильный ID пользователя) → локальный User`; «любой username сойдёт»
  не допускается, и расширить его может только администратор.
- Каждый запуск аудируется: какая система, какой внешний пользователь, какой
  локальный пользователь, какой профиль, результат операции. Без содержимого записей.
- Билет — транспорт входа, а не полномочие: он не даёт ни новых прав, ни выхода за
  пределы одной операции выбора.

## 2. Как это работает

```text
Сервер 1С ── POST /api/launch ─────► GitVaa: операция PENDING
   (повтор с тем же телом          (идемпотентно по requestId: повтор не создаёт
    возвращает ту же операцию)      вторую операцию, а отдаёт ссылку/статус)

Сервер 1С ── открывает URL у пользователя
Браузер ── GET /launch/{ticket} ──► проверка билета, конфликт с уже открытой
                                     сессией → явный отказ;
                                     иначе сессия, ОГРАНИЧЕННАЯ ОПЕРАЦИЕЙ,
                                     → 302 /launch/select

Пользователь: список номенклатуры (id, код, наименование, фильтры,
   множественная отметка); экран можно держать открытым долго
   «Передать в 1С» → серверное завершение: владелец, срок, статус, ключи,
     повторное чтение значений разрешённым путём → COMPLETED
   «Отмена»        → CANCELLED

Сервер 1С ── GET /api/launch/{requestId}/result (опрос по таймеру) ─► PENDING →
   COMPLETED {items[]} | CANCELLED | EXPIRED | 410 (результат истёк по сроку)
```

Операция и результат живут под `requestId`, который придумывает 1С; сессия браузера
привязана ровно к одной операции, поэтому два запуска не могут перепутать результаты.
Новых сетевых путей нет: 1С ходит в GitVaa, GitVaa к 1С не обращается.

**Длительная работа — часть пилота:** список может быть открыт и «висеть» в браузере
без выбора. Пока вкладка открыта, сессия выбора живёт (штатный heartbeat Vaadin, окно
сессии — параметр) и продлевает окно активности, но **не** абсолютный срок операции.
Операция в статусе `PENDING` живёт до абсолютного срока (пилот — рабочая смена, по
умолчанию 12 часов) и только потом становится `EXPIRED`. Если вкладку закрыли без
выбора, повторный `POST` с тем же телом, пока операция `PENDING`, выдаёт **новый
билет** — так пользователь возвращается в ту же операцию; прежний билет становится
недействительным, а живая сессия по нему закрывается. Уже сделанные отметки при
таком возврате не сохраняются (отложено, §7).

## 3. Контракты пилота

### `POST /api/launch` (служебная учётка сервера 1С, HTTP Basic, отдельная stateless-цепочка)

```json
{
  "requestId": "9f2c…",
  "profile": "nomenclature-select",
  "subject": "ivanov",
  "returnUrl": "e1cib://...",
  "filters": { "typeNom": "Товар" },
  "maxItems": 100
}
```

- **Идемпотентность.** Повтор с тем же `requestId` и тем же телом продолжает ту же
  операцию: если билет ещё не использован — возвращается рабочая ссылка, если
  операция ещё `PENDING` — выдаётся **новый билет** взамен прежнего, если операция
  уже завершена — её статус. Другое тело с тем же `requestId` — `409`. Это и
  восстановление после потерянного ответа, и возврат к «висящей» операции после
  закрытия вкладки.
- Отказы: `401` без учётных данных, `403` без права `INTEGRATION:LAUNCH`, `404`
  неизвестный профиль, `409` конфликт тела с существующей операцией, `422`
  неизвестная привязка, нет права чтения целевого списка (проверка на запуске, до
  открытия браузера) или `returnUrl` вне allow-list.
- `returnUrl` ограничен настройкой (например, `e1cib://` и адрес опубликованной базы
  1С); всё остальное отклоняется — ссылку показывают пользователю, и произвольный
  адрес превратил бы её в фишинговый переход.

### `GET /launch/{ticket}` (браузер)

Одноразовый вход: билет проверяется, помечается использованным, создаётся сессия
связанного локального пользователя, **ограниченная этой операцией**. Повторное или
просроченное открытие — страница «билет недействителен» без входа. Если в браузере
уже есть аутентифицированная сессия (в том числе другого пользователя) — явный отказ
с объяснением, без молчаливого переключения. Одна живая сессия на операцию: новый
билет закрывает прежнюю сессию по этой же операции.

### Завершение выбора (серверная операция экрана, без нового публичного API)

При «Передать в 1С» сервер проверяет владельца операции, её срок и статус `PENDING`,
принадлежность сессии, лимит `maxItems` и **перечитывает значения выбранных ключей
разрешённым путём чтения с повторной проверкой доступа** для связанного пользователя.
Ключ, который стал недоступен, отклоняется; запись снимка идемпотентна по операции —
повторное нажатие не создаёт второй результат.

Значения собираются **на момент подтверждения**: то, что уедет в 1С, — актуальные
данные. Совпадение «ровно с тем, что пользователь видел» без проверки версии не
гарантируется и в пилот не входит; `selectedAt` (серверное время подтверждения)
в результате позволяет 1С решить, достаточно ли этого.

### `GET /api/launch/{requestId}/result` (служебная учётка сервера 1С)

```json
{
  "schemaVersion": 1,
  "requestId": "9f2c…",
  "status": "COMPLETED",
  "selectedAt": "2026-10-27T12:30:12+03:00",
  "count": 2,
  "items": [
    { "key": "17", "fields": { "code": "…", "name": "…", "…": "…" } }
  ]
}
```

- `200` — `PENDING` (с `expiresAt`, чтобы 1С показывала ожидание и прекращала опрос
  по истечении срока) / `CANCELLED` / `EXPIRED` / `COMPLETED` с `items`;
- `410` — операция завершена, но результат уже удалён по сроку (`status: COMPLETED`,
  `resultExpired: true`): «поздно» отличимо и от «ещё не готово», и от «неизвестно»;
- `404` — неизвестный `requestId` или запрос от другой системы: существование чужих
  операций не раскрывается;
- `Cache-Control: no-store`.

Состав полей задаёт профиль, а не сущность целиком. Типы: даты ISO 8601; суммы и
количества строкой (точность); ссылки — ключ плюс представление; перечисления — код
плюс текст. Ключ — стабильный идентификатор записи GitVaa (и, если профиль его
объявляет, внешний код/GUID), чтобы 1С могла и сопоставить, и при необходимости
перечитать запись.

Чтение результата: только инициировавшая система; повторное чтение разрешено в
течение срока хранения результата (параметр, по умолчанию 15 минут; согласуется с
рабочим процессом 1С). Повторное чтение улучшает доставку, но её не гарантирует —
поэтому применение результата в 1С обязано быть идемпотентным по `requestId`.

Лимиты: `maxItems` пилота — 100; сверх лимита — отказ с понятным сообщением, а не
молчаливое усечение. Срок жизни операции — параметр (пилот: рабочая смена, по
умолчанию 12 часов) — рассчитан на список, открытый и «висящий» в браузере; после
срока — `EXPIRED`. Пока операция `PENDING`, ссылку можно перевыпустить (см. выше);
после завершения результат живёт 15 минут.

## 4. Что переиспользуется

| Нужно | Берём существующее |
|---|---|
| Пользователь и права | Локальный `User` + C5/RLS; `SecurityRlsUser` = `Authentication.getName()`; вход из билета не меняет модель прав |
| Экран выбора | Тот же путь чтения, что у списков (`BaseService`/`LookupService`, RLS-гейт) и та же сетка `FilterGrid`; маршрут `/lists/{entityKey}` (E2) — ориентир, но пилот делает отдельный `/launch/select`, чтобы не менять generic `ListForm` |
| Профиль пилота | Декларация по образцу `RestResourceDefinition` (`src/main/java/org/ip/config/rest/RestResourceDefinitionsConfiguration.java`): Номенклатура — `id` (ключ), `code`, `name`; проверка на старте |
| Транспорт и защита API | Отдельная stateless-цепочка Basic (`@Order(1)`), как у `/api/report-jpql/**` в `SecurityConfig`; JSON-ответ, разбор после гейтов |
| Право на канал | Именованная операция C5 (`NamedOperationOwner` + `C5OperationPermissionRegistry`) и CHECK_ONLY-измерение по образцу `REPORTS:JPQL_PREVIEW` (`ReportRights`) |
| Сохранение сессии | Штатные механизмы Spring Security: смена идентификатора сессии при входе и сохранение security context через репозиторий, а не только в потоке ([session management](https://docs.spring.io/spring-security/reference/7.0/servlet/authentication/session-management.html)) |
| Таблица операций | Обычная JPA-сущность приложения (`ddl-auto=update` в dev; прод-схема — отдельно) |
| Чистка по сроку | Ленивая (при запуске и чтении) — в приложении запрещены `@Scheduled`/`@Async` без typed executor (`ApplicationBackgroundBoundaryTest`); фоновый сборщик — отдельный шаг, если понадобится |

Профиль описывается типизированной строкой результата: стабильный ключ, поля с
типами и разрешённый источник. В пилоте источник — одна JPA-сущность `Nomenclature`,
результат — `id` (ключ), `code`, `name`. Список из расчётных строк или объединения
источников — отдельный случай: он меняет сборку значений и в пилот не входит.

## 5. Безопасность

- Билет: 256-битный случайный, хранится хэшем; одноразовый; TTL 3 минуты; привязан к
  конкретной операции. Привязка к IP не делается (прокси и мобильные сети ломают её),
  вместо неё — короткий срок и одноразовость.
- Сессия по билету **ограничена операцией**: доступны только экран выбора и служебные
  ресурсы; любой другой адрес приложения — вежливый отказ. Сессия живёт не дольше
  операции и закрывается при завершении, отмене или истечении срока; пока вкладка
  открыта, короткий простой её не рвёт (heartbeat Vaadin, окно сессии — параметр).
  Полноценного входа по билету нет.
- Конфликт сессий: уже открытая аутентифицированная сессия (в том числе другого
  пользователя) — явный отказ, без переключения и без переиспользования чужой сессии.
  Одна живая сессия на операцию: новый билет по той же операции закрывает прежнюю.
  Несколько одновременных вкладок и параллельные операции — отложены; каждая
  операция имеет собственный `requestId`.
- Пользователь: только уже созданный локальный `User`; привязка внешнего пользователя
  — явный список в конфигурации; JIT и автосвязывание по email отсутствуют.
- Права: экран показывает ровно то, что разрешено связанному пользователю; завершение
  выбора перечитывает значения и повторно проверяет доступ — «выбрал, потом отобрали»
  даёт отказ, а не утечку.
- Результат: читает только инициировавшая система; в данных результата нет токенов и
  ключей; в логах — только факт и счётчики, без содержимого.
- Чистка по сроку: **ленивая** — просроченный результат не выдаётся (гарантия), но
  физическое удаление происходит при следующем касании операции (запуск или чтение),
  а не ровно через 15 минут; отдельный сборщик — следующий шаг, если потребуется.
- Канал фиксируется новой строкой матрицы `DAC-23` «Внешний запуск по билету»: вход
  только через защищённый API приложения, билет — транспорт входа, обход прав не
  допускается ([матрица каналов](security-channel-matrix.md)).

## 6. Приёмка пилота

1. `POST /api/launch` возвращает `launchUrl`; без учётных данных — `401`, без права —
   `403`, неизвестный профиль — `404`, неизвестная привязка и `returnUrl` вне
   allow-list — `422`.
2. Повторный `POST` с тем же телом не создаёт вторую операцию (та же ссылка или
   статус), с другим телом — `409`.
3. `launchUrl` открывается в чистом браузере без формы входа и попадает в список; в
   URL нет ничего, кроме билета; повторное и просроченное открытие входа не дают.
4. Открытие билета при уже существующей сессии (другого пользователя) — явный отказ
   без переключения.
5. Из сессии по билету нельзя уйти на другие экраны приложения — отказ; после
   завершения операции сессия закрыта.
6. Список показывает `id`, код и наименование номенклатуры; фильтры, сортировка и
   страницы работают как в обычном списке.
7. Пользователь A видит ровно разрешённые ему строки (сверено с пользователем B).
8. «Передать в 1С» → `GET result` отдаёт `COMPLETED`, а `items` — значения на момент
   подтверждения; недоступный к моменту подтверждения ключ даёт отказ, а не данные.
9. Двойное нажатие «Передать» не создаёт второй результат; «Отмена» → `CANCELLED`;
   без действий — `EXPIRED`; после срока хранения — `410`, и это отличимо от `404`.
10. Чужой служебный аккаунт по чужому `requestId` получает `404`; в логах нет
    содержимого записей.
11. Полный путь на **форме 1С**: запрос билета, открытие, выбор, опрос, применение
    результата (идемпотентно по `requestId`) — пройден пользователем.
12. **Длительная работа:** экран оставлен открытым дольше короткого срока сессии —
    простой не выбивает пользователя, завершение проходит (в тесте — с сокращёнными
    значениями сроков).
13. Закрытая вкладка: повторный `POST` выдаёт новый билет, прежняя ссылка
    недействительна, операция остаётся той же; вторая живая сессия по ней не
    возникает.
14. Операция, «висящая» без действий дольше абсолютного срока, переходит в
    `EXPIRED`, и результат по ней не появляется.

## 7. Что пилот не доказывает

Полноценный вход в приложение по билету (это отдельное решение), одновременные
вкладки одной операции, сохранение сделанных отметок между заходами, совпадение
«ровно с тем, что видел» без проверки версии, гарантированное физическое удаление
результата к сроку, прод-нагрузку и работу через интернет (нужен TLS/прокси),
несколько систем и профилей, тысячи записей, поведение реального тонкого клиента 1С.
Это названные условия следующих итераций.

## 8. Открытые вопросы владельцу

Решено: список — Номенклатура (`id`, `code`, `name`), источник — одна сущность,
ключ — `id`. Остаётся уточнить:

1. Сколько записей за раз: десятки (лимит 100) или нужны тысячи?
2. Абсолютный срок операции: рабочая смена (12 часов) — подтвердить значение.
3. Нужно ли сохранять уже сделанные отметки, когда пользователь возвращается в
   операцию после закрытия вкладки (сейчас — нет)?
4. Источник привязки «внешний пользователь → локальный»: конфигурация или отдельная
   таблица с админ-экраном?
5. `returnUrl`: какие префиксы разрешены (тонкий клиент `e1cib://`, адрес
   опубликованной базы)?
6. Срок хранения результата под рабочий процесс 1С (по умолчанию 15 минут).
7. Возврат в 1С: тонкий клиент или веб-клиент?
