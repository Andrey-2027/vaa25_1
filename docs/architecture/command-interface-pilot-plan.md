- Дата: 2026-10-10.
- Статус: КИ-1–КИ-5 реализованы и проверены; Пилот 1 готов к пользовательской пробе.
- Результаты КИ-1: [каталог, resolver и проверки](evidence/command-interface-ki1-20261010.md).
- Результаты КИ-2: [хранение, назначения и проверки](evidence/command-interface-ki2-20261010.md).
- Результаты КИ-3: [единый снимок меню и плиток](evidence/command-interface-ki3-20261010.md).
- Результаты КИ-4: [административный редактор профилей](evidence/command-interface-ki4-20261010.md).
- Результаты КИ-5: [браузерная приёмка на PostgreSQL](evidence/command-interface-ki5-20261010.md).
- Пользовательская проба: [запуск, доступ и сценарий](command-interface-user-trial.md).
- Согласованный объём: рабочий пилот, только видимость, один назначенный профиль на пользователя.
- Уточнение по замечаниям: устойчивые ID, единая обработка пустых разделов, границы проекции и условие удаления старого построения меню.

## 1. Режим и результат

**Цель:** сохранить автоматический исходный интерфейс по подсистемам и позволить
администратору адаптировать его под рабочие задачи без изменения кода.

**Режим:** пилот, итерация 1. Предыдущей пользовательской пробы нет. Проверяем,
достаточно ли настройки видимости для создания удобных рабочих интерфейсов.

**Потребители:** разработчик приложения задаёт исходный состав; администратор
создаёт и назначает профили; пользователь получает назначенное меню.

**Рабочий сценарий:** администратор создаёт профили «Склад» и «Производство»,
скрывает разные разделы и пункты, назначает профили двум пользователям.
После обновления страницы пользователи видят разные меню при неизменных правах.
Снятие назначения возвращает интерфейс, заданный разработчиком.

**Входит:** автоматический каталог подсистем и пунктов открытия списков;
настройки разработчика; профили в БД; назначение пользователям; редактор
видимости; построение бокового меню и плиток из единого результата.

**Отложено:** изменение порядка, собственные разделы, перенос и дублирование
пунктов, кнопки внутри форм, отчёты и произвольные действия, персональные
настройки пользователя, несколько профилей с переключением, назначения по
ролям, массовое назначение, диагностика итогового меню конкретного пользователя,
наследование профилей, копирование и удаление профилей, экспорт/импорт
и применение изменений без обновления страницы. Эти возможности не нужны
для первой пробы видимости.

**Окружение:** существующий Java 21 / Spring Boot / Vaadin стек; H2 для
автоматических интеграционных проверок, отдельная локальная PostgreSQL БД
для браузерной пробы. Работа с реальной производственной БД не входит в пилот.

**Точка остановки:** оба пользователя проходят описанный сценарий;
автоматические проверки и браузерная приёмка выполнены; предоставлены
инструкция запуска, данные пробы и известные ограничения. Это означает
«Пилот 1 готов к пробе», а не завершение всего направления.

## 2. Поведение и границы

### Исходный состав и права

1. `SubsystemRegistry` остаётся источником принадлежности сущностей и дерева
   подсистем. Его содержимое не меняется при редактировании профиля.
2. На его основе строится неизменяемая проекция навигации. Узел представляет
   подсистему; пункт навигации представляет открытие списка сущности в её
   исходной подсистеме. В дальнейшем документе используется термин «пункт
   навигации»; действия внутри форм принадлежат существующему `ActionRegistry`.
   Нового сканирования классов и второго редактируемого реестра сущностей,
   форм или принадлежности подсистемам нет. Заголовки, иконки, порядок и
   принадлежность читаются из существующих источников; декларации навигации
   добавляют только устойчивую идентичность и исходную видимость.
3. При отсутствии настройки видимости все такие узлы и пункты видимы
   по умолчанию. Разработчик может изменить исходную видимость через Java SPI
   с явными ссылками на маркер подсистемы и класс сущности. Расширять
   `@EntityMetadata` и `@Subsystem` новыми флагами в пилоте не требуется.
4. В редакторе профиля доступны «По умолчанию», «Показывать», «Скрывать».
   «По умолчанию» наследует настройку разработчика, а не значение другого
   профиля. В БД хранятся только явные переопределения.
5. Итоговый пункт видим, если его разрешают настройка профиля/разработчика,
   вся цепочка родительских подсистем и существующий `RlsReadGate` текущего
   пользователя. «Показывать» не обходит скрытого родителя и проверку прав.
6. Настройка видимости не изменяет C5/RLS, открытие по прямой ссылке, поиск,
   формы выбора и программное открытие форм. При открытии списка используется
   существующий `FormNavigator` и действующие проверки доступа.

### Дерево и вложенные подсистемы

- Боковое меню и плитки страницы подсистемы используют один разрешённый
  снимок навигации, а не независимо фильтруют `SubsystemNode`.
- Родительская страница сохраняет показ пунктов потомков. Скрытый пункт
  или скрытая дочерняя подсистема исключается также из этой страницы.
- После фильтрации убираются пустые группы плиток и подсистемы без видимых
  пунктов во всём поддереве. Правило одинаково действует при назначенном
  профиле и без него. «Исходный состав» означает настройки разработчика,
  к которым затем применяются права и удаление пустых разделов. При включении
  пилота исходно пустые разделы исчезают у всех пользователей; это принятое
  изменение представления, а не настройка конкретного профиля.
  Полный каталог, включая пустые и скрытые узлы, остаётся в редакторе.
- Порядок, заголовки и иконки поступают из существующих метаданных.
- «Главная», «Администрирование», «Диагностика», диагностические структуры
  и legacy-меню сохраняют существующую логику и не настраиваются в пилоте.
  Доступный администратору вход в настройки нельзя скрыть профилем.
  В частности, скрытие новой плитки не скрывает независимый legacy-пункт.

### Назначение, обновления и сохранение

- Пользователю назначается не более одного профиля. Повторное назначение
  заменяет предыдущее; снятие назначения возвращает исходный состав.
  Автоматического назначения по ролям и отдельного глобального профиля нет.
- Настройки общие для всех пользователей профиля. На первом этапе профиль
  можно создать, переименовать, сохранить и сбросить; удаление не поддерживается.
  Сброс очищает его переопределения и сохраняет назначения пользователей.
- Ключ назначения — неизменяемый ID прикладного пользователя, представленный
  непрозрачной строкой. Для текущего приложения это `User.id`, не логин.
  Приложение разрешает текущую аутентификацию в этот ID; платформа не импортирует `User`.
- Подсистемы и пункты получают явные устойчивые ID через предусмотренный
  этим планом SPI `NavigationDefaultsContributor`: декларация связывает ID подсистемы с её
  маркером, а ID пункта — с исходной подсистемой и классом открываемого списка.
  Такая связь проверяется по `SubsystemRegistry` и не создаёт членство сама.
  Например, ID подсистемы — `directories`, ID пункта — `units-list`.
- ID задаются литералами ASCII lower-kebab-case, уникальны в пределах своего
  вида и сохраняются при переименовании Java-класса, переносе пакета, смене
  заголовка и перемещении пункта в другую исходную подсистему. В БД цель
  переопределения адресуется ключом `subsystem:<id>` либо `item:<id>`.
  Имена классов и текущая родительская подсистема в этот ключ не входят.
- Для каждого узла и пункта автоматического каталога требуется ровно одна
  декларация ID. Отсутствующая декларация, неизвестная цель, повтор ID или
  повтор декларации одной цели — ошибка запуска. Новый пункт требует одной
  декларации разработчика; администратору настраивать его заново не требуется.
  Удалённый ID не переиспользуется для другого назначения. Намеренная замена ID
  требует явной миграции сохранённых переопределений; автоматическое угадывание
  соответствий по названиям не выполняется.
- Backend навигации не зависит от `FormRouteCatalog`. Существующий alias E2
  можно осознанно использовать как литерал ID пункта, но вычисление ключа
  из текущего имени Java-класса и зависимость от UI-модуля не вводятся.
- Новые пункты без переопределений наследуют видимость разработчика.
  Удалённые из каталога ключи игнорируются при построении меню, сохраняются
  при обычном сохранении профиля и показываются администратору как устаревшие.
  Полный сброс профиля удаляет и их. Новый неизвестный пункт через редактор
  или сервис сохранить нельзя.
- Сохранение состава атомарно; версия профиля покрывает все переопределения.
  При конкурентном редактировании второе сохранение получает понятный конфликт
  и не перезаписывает чужие изменения. Создание и переименование требуют
  непустого уникального имени профиля.
- Изменения состава и назначения применяются после полного обновления
  страницы или нового входа. Открытые вкладки не закрываются принудительно.
  Между UI и пользователями нет общего изменяемого снимка меню.
- Отсутствие назначения означает исходные настройки разработчика с той же
  фильтрацией по правам и тем же удалением пустых разделов. Ошибка чтения настроек
  не означает отсутствие назначения: динамическая часть показывает сообщение
  о невозможности загрузить меню, служебные пункты сохраняются. Включённый
  механизм не подменяет ошибку молчаливым возвратом к исходному меню.

## 3. Этапы реализации

### КИ-1. Проекция навигации, идентичность и настройки разработчика

**Статус на 2026-10-10:** выполнен. Создан независимый модуль, объявлены ID
4 подсистем и 18 пунктов приложения. Пройдены 30 owner-side проверок и
прикладная проверка на реальном `SubsystemRegistry`; signature baseline
нового модуля проверен без перезаписи. Общий D1-gate сохраняет нарушения
соседнего UniDR-кода и устаревшие замеры; подробности в документе результатов.
Профили, автоконфигурация и изменение живого меню в этот этап не входят.

**Результат:** исходный командный интерфейс описан отдельно от метаданных
подсистем, имеет устойчивые ID и может разрешаться без Vaadin-компонентов.

- Создать необязательный backend-модуль `platform-navigation` в пакете
  `org.ipro.navigation`. Разрешённые зависимости: `platform-core` для готового
  дерева, `platform-persistence` для базы хранилища и необходимые Spring/JPA
  библиотеки. Импорты Vaadin, `org.ip` и отчётных подсистем запрещены.
  Основание отдельного модуля — повторное использование backend и проверяемая
  граница зависимостей. Публичные контракты ограничить текущим сценарием;
  предполагаемые расширения интерфейса в API пилота не добавлять.
- Ввести описания узла/пункта, неизменяемую проекцию, enum видимости профиля
  и SPI `NavigationDefaultsContributor`. Этот же SPI объявляет устойчивые ID
  и необязательную исходную видимость; отдельный SPI идентификаторов не нужен.
  Конфигурация адресует только существующие узлы/пункты. Проверить полноту
  ID, уникальность и известность целей независимо от порядка Spring-бинов.
  Объявить ID всех включённых в пилот подсистем и пунктов в прикладной конфигурации.
- Ввести чистый resolver: каталог + переопределения + предикат чтения сущности
  → неизменяемое итоговое дерево. Он централизует наследование, фильтрацию
  потомков, удаление пустых узлов и группировку плиток для родительской страницы.
- Сразу назначить роли API/SPI/MODULE_API/INTERNAL и добавить проверки
  композиции нового модуля. Каталог и разрешённое дерево — модели навигации;
  существующий `ActionRegistry` и исполнение действий форм не расширяются.
  Включение в каталог не выдаёт capabilities, маршруты или права; эти решения
  продолжают принадлежать существующим descriptor/route/security-каталогам.

**Приёмка этапа:** каталог строится на существующих подсистемах; тесты
разрешения покрывают настройки разработчика, профиль, права и вложенность.
Отдельный регрессионный тест подтверждает сохранность скрытия после смены
Java-типа/пакета и исходной подсистемы при неизменном ID пункта.

### КИ-2. Профили, назначения и защищённое хранение

**Статус на 2026-10-10:** выполнен. Профили и назначения хранятся во внутренних
JPA-таблицах; сервис проверяет администратора при каждом вызове, контролирует
версию состава и сохраняет устаревшие ключи до полного сброса. Добавлены
прикладные адаптеры `ROLE_ADMIN` и неизменяемого ID пользователя, условная
автоконфигурация и PostgreSQL DDL. Пройдены 57 проверок затронутого контура,
включая H2, PostgreSQL `validate`/перезапуск и запуск приложения с включённым
и выключенным флагом. Общий D1-gate сохраняет те же пять нарушений соседнего
кода/замеров, зафиксированных отдельно. Флаг по умолчанию выключен;
живое меню и административный экран остаются задачами КИ-3 и КИ-4.

**Результат:** профиль и его назначения переживают перезапуск приложения.

- Добавить внутренние таблицы профилей, переопределений и назначений.
  Переопределение уникально по профилю и ключу цели; назначение уникально по
  ключу пользователя. Профиль имеет версию; ссылки его внутренних таблиц
  защищены FK. Зависимости от таблицы `app_user` и изменения сущности `User` нет.
  Назначения моделируют только пользователей: резервный тип субъекта ROLE
  и правила выбора профиля по нескольким ролям в пилот не включаются.
- Эти JPA-типы являются `INTERNAL_STORE` без `@EntityMetadata`, generic CRUD
  и REST-публикации. Их транзакции обслуживает владелец подсистемы через
  именованные операции, в соответствии с ADR-0007.
- Предоставить сервис администрирования: список/создание/переименование
  профилей, чтение и атомарная запись состава с ожидаемой версией, сброс,
  назначение и снятие назначения. Отдельная read-модель возвращает состав
  назначенного профиля для построения пользовательского интерфейса.
- Все административные операции проверяют `NavigationAdministrationAccess`
  на сервере, включая прямой вызов сервиса. Приложение реализует этот SPI
  существующим правилом `ROLE_ADMIN`. Разрешающей реализации по умолчанию нет;
  при включённом модуле отсутствие адаптера является ошибкой запуска.
- Адаптер приложения проверяет существование выбранного пользователя и
  переводит его ID в ключ назначения. Поиск пользователей использует
  существующий canonical lookup с ограничением выдачи. Роли и grants не меняются.
- Зарегистрировать бины, сущности и репозитории собственной автоконфигурацией.
  Модуль уже добавлен в BOM, локальный порядок сборки и прямые зависимости
  пилотного приложения в КИ-1 для проверки прикладных деклараций.
  В общие starter-артефакты его пока не включать.
- Ввести `platform.navigation.enabled=false` по умолчанию. При выключении
  новая автоконфигурация, инфраструктура хранения и UI-вкладка не активируются.
  Для пилота флаг включается явно. Подготовить additive DDL для PostgreSQL
  и проверить запуск с `ddl-auto=validate`; внедрение нового migration framework
  не входит в задачу.

**Приёмка этапа:** реальное сохранение/перечитывание, конфликт версий и откат
проверены; неадминистратор не может менять профили или назначения.

### КИ-3. Подключение к пользовательскому интерфейсу

**Статус на 2026-10-10:** выполнен. `NavigationUiSnapshot` зарегистрирован в
Vaadin UI scope: при построении оболочки читает профиль текущего пользователя
и разрешает каталог через существующий `RlsReadGate`. `MainLayout` строит меню
из этого дерева, `SubsystemHomeView` получает тот же разрешённый узел.
Ошибка загрузки сохраняется в снимке и отображается в динамической части меню;
служебные пункты остаются доступными. Изменения применяются после обновления
страницы или нового входа. Флаг по умолчанию выключен; административный редактор
и браузерная пилотная приёмка остаются КИ-4 и КИ-5.

**Результат:** назначенный профиль одинаково влияет на боковое меню и плитки.

- Добавить прикладной UI-адаптер: текущая аутентификация → ID пользователя →
  назначенный профиль → resolver с существующим `RlsReadGate`. Снимок создаётся
  для текущего UI при построении оболочки; глобального кэша меню нет.
- `MainLayout` строит динамическую часть по разрешённому дереву.
  `SubsystemHomeView` получает разрешённый узел/группы того же снимка;
  прямой рекурсивный обход исходного дерева для плиток больше не используется
  во включённом режиме.
- Пункты продолжают открывать списки через `FormNavigator`. Настройки
  профиля не добавляются в форму выбора, deep-link, поиск или data path.
- При выключенном флаге сохранить существующий путь построения меню.
  При включении зарегистрированные адаптеры обязательны; отсутствие
  проводки не трактовать как отключение функции.
  Два пути построения допустимы только на время пилота; критерий перехода
  на единственный путь зафиксирован в разделе 5.

**Приёмка этапа:** два пользователя одновременно получают разные деревья;
скрытые потомки не появляются на родительской странице; выключение флага
возвращает прежнее поведение без удаления сохранённых настроек.

### КИ-4. Административный редактор

**Статус на 2026-10-10:** выполнен. В `AdminView` добавлена опциональная вкладка
«Интерфейс»: создание/переименование профилей, полное дерево, три состояния,
исходные настройки и итог с объяснением скрытого предка, предпросмотр через
общий resolver до применения пользовательских прав. Сохранение, подтверждаемый
сброс и назначения используют защищённый API КИ-2. Устаревшие ключи показаны
отдельно и не редактируются; конфликт или ошибка оставляет черновик.
При переключении/перечитывании профиля редактор предупреждает о потере локальных
изменений. Флаг оставлен выключенным; браузерная приёмка на отдельной PostgreSQL
базе остаётся задачей КИ-5.

**Результат:** полный сценарий настройки выполняется из приложения.

- Добавить вкладку «Интерфейс» рядом с существующими административными
  настройками. Сам экран и адаптер пользователей остаются прикладными;
  backend-модуль пригоден для повторного использования без этого экрана.
- Показать выбор профиля, создание/переименование, дерево подсистем и пунктов,
  три состояния видимости, исходное значение и итог по настройкам профиля.
  Для скрытого родителя показывать причину, по которой дочерний пункт
  не появится. Права конкретного пользователя оцениваются при построении
  его меню; редактор не выдаёт настройку профиля за проверку его прав.
- Предоставить «Сохранить», «Сбросить к настройкам разработчика» и отдельную
  область назначения/снятия назначения пользователям. Перед сохранением
  изменения локальны; ошибка или конфликт не теряет введённый состав.
- Предпросмотр дерева строить тем же resolver без открытия бизнес-данных;
  обозначить его как состав профиля до применения прав пользователя.
  В списке профилей показывать счётчик устаревших ключей; при открытии такого
  профиля — предупреждение и отдельный список без возможности включить
  неизвестный пункт. Сообщить, что изменения меню требуют обновления страницы.
- Проверка `ROLE_ADMIN` применяется как к доступности вкладки, так и к
  серверным операциям. Скрытие всех рабочих разделов оставляет администратору
  возможность вернуться во вкладку и сбросить профиль.

**Приёмка этапа:** администратор создаёт два профиля, сохраняет разные
настройки и назначает их пользователям без правки Java/SQL вручную.

### КИ-5. Приёмка и пакет пользовательской пробы

**Результат:** пилот воспроизводимо запускается и готов для оценки удобства.

Реализован отдельный launcher с новой локальной PostgreSQL-базой, canonical
подготовкой пользователей и явными grants. Выполнена браузерная приёмка разных
меню, вложенности, редактора/назначений, прямых ссылок, сброса и перезапуска с
`validate`, а также выключенного режима. См. [evidence](evidence/command-interface-ki5-20261010.md)
и [решение о границах](decisions/command-interface-pilot-boundary.md).

- Подготовить opt-in запуск/наполнение отдельной локальной БД: администратор,
  два пользователя с одинаковыми явно настроенными правами и разные профили.
  Использовать существующие разрешённые пути создания пользователей и grants;
  не вводить обход C5/RLS. Данные подготовки создаются только для пилота.
- Для предметной пробы использовать «Справочники» и «Производство»: например,
  разную видимость «Единиц измерения» и «Спецификаций». Вложенность дополнительно
  проверить тестовой иерархией с непустым дочерним узлом, поскольку существующая
  дочерняя «Документы / Производство» сейчас не содержит собственных сущностей.
- Выполнить автоматические проверки ниже и браузерный сценарий на PostgreSQL.
  Описать запуск, учётки/получение доступа, шаги, ожидаемый результат,
  ограничения и фактические результаты. Секреты не сохранять в документации.
- При реализации дополнить архитектурный индекс/roadmap ссылкой на план,
  коротким решением о границах навигации и evidence. Общие публичные baseline
  обновлять только для намеренно добавленных контрактов; чужие изменения
  текущего рабочего дерева в этот пакет не включать.

## 4. Проверки и критерии приёмки

| Группа | Обязательные сценарии |
| --- | --- |
| Исходный состав | Без назначения работают настройки разработчика с общей фильтрацией; скрытый разработчиком пункт может быть включён профилем при разрешённом чтении; неизвестная/дублирующая настройка разработчика даёт ошибку запуска. |
| Видимость | Все три состояния; скрытый родитель; скрытый дочерний узел на странице предка; одинаковое исчезновение пустых групп и разделов с профилем и без него; стабильный порядок. |
| Разделение с правами | SHOW при отказе `RlsReadGate` не выводит пункт; скрытие меню не запрещает разрешённые deep-link и selection; отказ C5 сохраняется при прямом открытии. |
| Изоляция | Два одновременно открытых UI с разными назначениями; изменение одного профиля не меняет другой; смена логина сохраняет назначение по ID. |
| Хранилище | Сохранение и перечитывание после перезапуска; уникальность назначения; замена/снятие назначения; сброс; две конкурирующие записи; откат без частично сохранённых переопределений. |
| Администрирование | Прямые вызовы операций неадминистратором запрещены; отсутствующий security-адаптер при включении даёт ошибку запуска; вход в администрирование сохраняется при скрытии всех рабочих пунктов. |
| Идентичность | Явные ID полны и уникальны; отсутствие/повтор ID даёт ошибку запуска; смена Java-класса, пакета, заголовка или исходной подсистемы при прежнем ID не сбрасывает скрытие; snapshot ID пилотных пунктов меняется только с объяснением совместимости. |
| Обновление каталога | Новый пункт с объявленным ID наследует developer default; удалённый ключ не ломает меню и сохраняется до сброса; счётчик и предупреждение об устаревших ключах видны администратору; возвращение прежнего пункта с тем же ID сохраняет явную настройку. |
| Проекция | Построение меню не мутирует исходные каталоги; профиль не меняет membership подсистем, capabilities или публикацию маршрутов; навигационный модуль не зависит от UI-каталога маршрутов. |
| Поставка и режимы | Независимая сборка модуля, API/composition gates, отсутствие зависимости на приложение/Vaadin; запуск выключенного режима; PostgreSQL DDL + validate; ошибка чтения профиля не подменяется исходным меню. |

Сначала выполняются тесты нового модуля, затронутой навигации и security/storage
интеграции; затем применимые архитектурные/API-проверки и smoke запуска приложения.
Широкий прогон расширяется при обнаруженном риске или требовании существующего gate.
Браузерная приёмка подтверждает оба меню после обновления, вложенную видимость,
снятие назначения, сброс, сохранение после перезапуска и сохранность прав.

## 5. Ограничения пилота и следующий пакет

Технические defaults этого плана: новые пункты с объявленными устойчивыми ID
наследуют исходные настройки; изменения применяются по обновлению страницы;
пустые разделы скрываются одинаково у пользователей с профилем и без него;
профили включаются явно флагом; интерфейс настройки пока принадлежит приложению;
идентичность подсистем и пунктов задана явными ID; назначение использует
стабильный ID пользователя. FQN остаётся технической ссылкой в коде и диагностике.

Для обратной связи проверяем: понятны ли три состояния и скрытие родителя,
достаточно ли видимости без изменения структуры, удобно ли назначать один
профиль, хватает ли объяснения источника итоговой настройки.

Первые кандидаты следующей итерации:

1. Диагностика итогового меню выбранного пользователя: какая настройка
   разработчика/профиля, скрытый родитель или отказ права чтения объясняет
   отсутствие пункта. Для пробы достаточно показать причины без открытия
   бизнес-данных и без изменения прав.
2. Массовое назначение одного профиля выбранным пользователям. Оно сохраняет
   правило «один пользователь — один профиль» и не требует назначения по ролям.

Затем по обратной связи рассматриваются порядок, охват служебных/legacy-пунктов
и дополнительные типы пунктов. Эти кандидаты не увеличивают пакет пилота 1.
Перед завершённым механизмом отдельно согласуем целевые приложения/СУБД,
миграции намеренных изменений ID, жизненный цикл удаления профилей,
экспорт/импорт и условия обновления интерфейса.

### Переход к единственному построению меню

Условие перехода: пользовательская проба подтвердила полезность; приёмка
профильного и исходного меню, вложенности и прав пройдена; принято отдельное
решение о постоянном включении механизма в приложении. В этом пакете перехода
удаляются прямое построение динамического меню из `SubsystemRegistry`/`SubsystemNode`
в UI и выбор между двумя реализациями по флагу пилота. Служебные и legacy-пункты
сохраняют отдельно согласованный объём. Для пользователей с профилем и без него
остаётся один resolver;
отсутствие назначения означает работу с настройками разработчика.

Если по результатам пробы принимается решение отказаться от функции,
пилотная интеграция удаляется из приложения; сохранение двух поддерживаемых
реализаций не является результатом завершения направления. Готовность
пилота к пробе сама по себе не запускает переход и дополнительный объём.
