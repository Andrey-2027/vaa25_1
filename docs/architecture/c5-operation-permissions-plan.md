# C5: права на операции — план работ C5.4–C5.10

Уточнение 2026-10-07: отдельные права на поля отменены во всех каналах по
[ADR-0018](decisions/ADR-0018-no-field-permissions.md). Упоминания сохранения
ATTR-контракта ниже относятся к старой модели; действуют права сущности,
операции и RLS. Расширять механизм на права полей не требуется.

- Дата: 2026-10-06, Europe/Moscow.
- Статус: C5.4–C5.9 выполнены; C5.10 (закрытие) выполнен — roadmap §2.2/§6/C5/§8/E0,
  status/current-baseline и архитектурный индекс приведены к результату 2026-10-10.
  Открыты PostgreSQL-шаг П09 (реальные flush-callbacks, коллекция `User.roles`,
  откат агрегата) и attribute read/write политика с записанным условием входа.
- Решение: [ADR-0017](decisions/ADR-0017-c5-single-operation-authority.md).
- Режим: завершённый механизм в согласованном локальном контуре приложения, для прав
  на операции и E1.2b. Attribute read/write политики в объём не входят.
- Политика выбора режима и объёма: [development-delivery-policy.md](development-delivery-policy.md).
- Опора: снимочные evidence [REST 4.7](rest-read-api-stage4-47-evidence-20261006.md) и
  [platform reactor](evidence/platform-reactor-install-20261006.md). Они не доказывают
  работу, описанную ниже.

## 0. Карточка решения

| Поле | Значение |
| --- | --- |
| Цель | Чтобы для текущих каналов приложения решение «разрешена ли операция этому субъекту» принималось в одном месте — C5 — одинаково для чтения, создания, изменения, удаления и именованных операций |
| Пользователь | Прикладной разработчик, администратор прав, пользователь форм |
| Рабочий сценарий | Администратор выдаёт права → пользователь открывает форму → выполняет разрешённую операцию → получает понятный отказ на запрещённой → после отзыва права следующий вызов в той же сессии отклоняется |
| Входит | Определения операций из capabilities; решение C5; применение на canonical read/write и агрегате; финальная граница записи для всех типов с write-capability; E1.2b; админский экран и первичная выдача; снятие ручного security-wiring из приложения |
| Не входит | Attribute read/write политики, query paths и inference, per-field restrictions, отзыв посередине транзакции, PostgreSQL subset как gate этого среза, REST write, новый IAM/SSO, распределённая инвалидация, физическая модульность, генератор и Studio |
| Сохраняется | RLS построчно, canonical data path, semantic capabilities, `ENTITY:<FQN>`/`ATTR` read-ключи, wildcard `'*'` как семантика RLS, ADR-0014, ADR-0016, действующая модель USER/ROLE |
| Допустимые ограничения | Allow-only без explicit deny; грубое отображение флагов (создание/изменение одним флагом); названия ключей не унифицируются; один application process для проверки отзыва |
| Городьба от разрастания | Новое определение появляется только вместе с прикладным сценарием, который его требует |
| Точка остановки | После DoD §6 механизм не расширяется без конкретного потребителя; включение границы (C5.6b) не растёт новыми типами без замеренного отказа по типу; attribute-политики открываются отдельным решением |
| Окружение | H2 для основного набора; для flush, collection и отзыва — целевая схема PostgreSQL, отдельным шагом |

## 2. Пакеты работ

Каждый пакет заканчивается проверкой, которую можно выполнить на текущем дереве.
Порядок: C5.4 → C5.5 → C5.6 → C5.6b → C5.7 → C5.8 → C5.9 → C5.10. Пары «enforcement + точечные
тесты» не разделяются.

### C5.4. Фиксация входов

Владельцы: документация, app/owner тесты.

- Зафиксировать HEAD, состояние незакоммиченных изменений, JDK/Maven, профиль и СУБД.
- Установить факт: какие строки грантов существуют в рабочей БД — точечные на
  `ENTITY:<SimpleName>` или только `'*'`. От этого зависит, меняется ли поведение пилота
  в момент включения.
- Перечислить фактических потребителей решений: canonical read/write, агрегат,
  `RlsUiGate`, `ActionContextProvider`, админский экран, регистр, report.
- Снять до-замеры: число security-запросов на чтение каталога, сохранение документа и
  решение по действию.

Выполнено 2026-10-06: [evidence](evidence/c5-4-inputs-20261006.md) — фактические гранты обеих баз, потребители решения, статический бюджет запросов. Runtime-замер отнесён к C5.6: в журнале нет SQL по грантам, `pg_stat_statements` не установлен.

**Gate.** Входы известны; поведение пилота при включении предсказано и записано.
Изменений в БД нет.

### C5.5. Определения и решение C5

Владельцы: platform-rls, platform-spring-boot-autoconfigure.

- Ввести виды определений: `ENTITY` READ/CREATE/UPDATE/DELETE, `ACTION`, существующие
  `ATTR`/`REST`. Один enum операций, один результат решения (allow/deny, причина,
  ключ, источники), один `require`-фасад. Абстракция каталога не вводится, пока нет
  второго семейства определений.
- Решение — только точный ключ и глобальная строка; `'*'` и value-scoped строки не
  участвуют.
- Сохранить совместимость существующего read-контракта: старые методы и конструкторы
  не меняют смысл.
- Регистрация: read — как сейчас; операции — вывод из capabilities; владельцы
  регистрируют `ACTION`. Конфликт ключей и неизвестное определение — отказ при старте.

Выполнено 2026-10-06: [evidence](evidence/c5-5-definitions-decision-20261006.md) — enum операций, реестр определений, решение и `require`-фасад в `platform-rls`, регистрация операций из capabilities, owner-тесты и проводка в приложении (59 + 35 + 29 тестов). Потребителя у решения ещё нет: применение — C5.6/C5.7. Подписной baseline `platform-rls.api` не перегенерирован, потому что дерево содержит чужие незакоммиченные изменения поверхности.

**Gate.** Одна строка даёт одно независимое решение об операции; read-поведение
не изменилось; `'*'` не авторизует операцию. Owner-тесты на allow/deny и на
fail-closed конфигурацию.

### C5.6. Применение: запись

Владельцы: platform-core, platform-autoconfigure, rls, register owner.

- `CanonicalWriteExecutor`: C5-проверка операции до numbering, validation, hooks и
  событий; `save` определяет операцию по существующему intent-контракту.
- UPDATE сохраняет проверку доступной исходной строки и RLS исходного/целевого
  состояния; DELETE даёт одинаковый отказ для отсутствующего и недоступного id.
- Агрегат: security preflight до `Saving`/`beforeAggregateSave`, включая секции и
  уже известные contributions.
- Финальная граница: зафиксированная авторизация потребляется на flush для всех типов
  с write-capability как механизм. Для типов без RLS это новая граница; для типов с RLS —
  распространение существующей.
- Register set replacement авторизуется отдельным именованным определением владельца
  (включение — C5.6b); generic CRUD строк регистра не открывается.
- `@RlsDimension(kind = CHECK_ONLY)` на типе с canonical CRUD — отказ при старте
  (включение — C5.6b).

Перенесено в C5.6b: первым шагом снять численный замер security-запросов на пилоте (тестовый `statement inspector`): статическая оценка C5.4 — не менее восьми запросов к `access_grant` на одно сохранение документа, потолки C5.9 без замера не с чем сравнивать.

Выполнено 2026-10-06: [evidence](evidence/c5-6-write-enforcement-20261006.md) — `CanonicalWriteExecutor` проверяет операцию до RLS, загрузки исходной строки, нумерации, валидации, хуков и событий; агрегат получил preflight через `AggregateOperationAuthorizer` до `Saving`; без явного операционного гранта запись закрыта, в том числе для `admin`. Из 44 отказов полного прикладного прогона (1856 тестов) 24 принадлежали срезу и закрыты явными операционными грантами в тестах, остальные 20 — чужие изменения рабочего дерева. `platform-spring-boot-autoconfigure.api` обновлён на две сигнатуры проводки; `platform-core.api` намеренно не перегенерирован: в него впитался бы чужой untracked seam. Финальная граница на flush сделана отдельным срезом и проверена ([c5-6-flush-boundary-20261007.md](evidence/c5-6-flush-boundary-20261007.md)), но по умолчанию снята явным переключателем `rls.write-boundary.enforced`: включение идёт вместе с миграцией мест прямой записи, а его цена измерена — 91 отказ по четырём типам и ~35 классов, включая production-путь `AttributeValueService` (это фронт замера, а не его итог: следующий слой — evidence §10). Миграция мест прямой записи идёт пошагово и по типам: свойство `rls.write-boundary.enforced-types` вооружает перечисленные типы, `enforced=true` остаётся состоянием её окончания. Миграция идёт шагами: демо-наполнение `DataInitializer` (`Role`, `User`) переведено на canonical path от собственного названного субъекта и проверено и пошагово, и глобально вооружённо (`DemoSeedingWriteBoundaryIT` 5/5, `TestProfileWithPropertyIT` под `enforced=true` — зелёный); затем пилотная фикстура `AccountingObjectPilotInitializer` (последняя прямая запись `Role`/`User` в production-коде) и `AttributeType` — тип с canonical write handle, у которого прямых записей в production не было вовсе, а прямые записи жили в фикстурах полного контекста (`NomenclatureAttributesIT`, `AttributeValueRefRlsIT` переведены на canonical path; slice-контексты границу не поднимают и переводу не подлежат). После этого `Role`, `User` и `AttributeType` названы в `rls.write-boundary.enforced-types` в main-properties: вооружение не меняет легальных путей (они проходят тот же preflight), но закрывает обход. Проверено: `PilotFixtureWriteBoundaryIT` 3/3, `AttributeTypeWriteBoundaryIT` 4/4 (включая запись через настоящий `ItemFormSaveDispatcher`), вооружённый прогон переведённых фикстур 11/0, production-список 29/0. Затем переведены фикстуры `Role`/`User` полных контекстов — семь классов (`RestReadHttpTestSupport` и его наследники, `RestReadPipelinePilotIT`, `RestReadRoleMatrixIT`, `RlsAutoConfigurationSmokeTest`, `C5GrantAdminParityIT`, `ReportJpqlPreviewControllerIT`): записи идут `EntityDataAccess.create/update/delete`, а фикстура получила названный вариант с read-ключами (`callAsSuperuserWithRead`), потому что canonical `update`/`delete` читает исходную строку. Вооружённые прогоны с ровно production-списком: мигрированные фикстуры 59/0, соседние полные контексты 85/0, весь срез вместе с фикстурами 109/0. Остаток — снятые типы и замеренный слой (`Nomenclature`, `GroupNom`, `AttributeValue`, `GridFormView`), вынесенный в C5.6b, и slice-контексты, где граница не поднята. Именованная операция замены набора регистратора, стартовый отказ для `CHECK_ONLY` на типе с canonical CRUD и численный замер security-запросов остаются остатком — C5.6b, evidence §5. Baseline `platform-rls.api` перегенерирован намеренно вместе с переносом реестра границы на принадлежность экземплярам: `RlsWriteGuardBridge.install(...)` → `recordCanonicalWrite/Delete(registry, entity)`, конструктор `RlsWriteEnforcementListener` — с реестром, в `RlsDimensionRegistry` — `registerWriteGovernedType`/`isWriteGoverned`, в `RlsPolicyEnforcer` — `recordCanonicalWrite/Delete`. Тем же переносом возвращена прикладная проверка вооружённого состояния (см. evidence §4/§5), поэтому `platform-core.api` не перегенерирован: чужой untracked seam там всё ещё есть.

**Закрыто по механизму 2026-10-08.** Задача закрывается механизмом: проверка операции,
агрегатный preflight и потребление авторизации на flush проверены (evidence §9). Включение —
перевод мест прямой записи, пошаговое вооружение и два именованных решения владельца —
вынесено в C5.6b: у остатка должен быть собственный DoD и точка остановки, а не приложение к
задаче о механизме.

**Gate.** Отказ не выдаёт номер, не вызывает hooks и не выполняет SQL мутации; изменение
managed-сущности и коллекции без авторизации отклоняется на commit; `Nomenclature`
закрыт без гранта и открыт с ним.

### C5.6b. Включение границы записи

Владельцы: app (места прямой записи), register owner, тестовые фикстуры.

Механизм границы сделан в C5.6; здесь закрывается **включение**. Типы с canonical write handle
называются при старте (WARN): их 20, и по умолчанию ни один не вооружён. Вооружение — не
переключатель «всё или ничего»: `rls.write-boundary.enforced-types` называет уже переведённые
типы, `enforced=true` — состояние окончания; оба свойства удаляются после.

- Переводить места прямой записи по типам: `EntityDataAccess`/canonical service вместо прямого
  `EntityManager`/repository, субъект — названный, с первичной выдачей прав, а не ослабление
  проверки. Шаг заканчивается вооружённым прогоном затронутых классов и именем типа в списке.
- Прикладной путь `AttributeValueService` (пять прямых `repository.save`): тип объявлен
  CREATE-only, generic update/delete запрещены by design, поэтому переименование значения
  требует **именованной typed-операции** — решение принято в
  [ADR-0019](decisions/ADR-0019-owner-named-row-operation.md): `ACTION:ATTRIBUTE_VALUE:RENAME`,
  мутация на загруженной строке, generic UPDATE не публикуется.
  Выполнено 2026-10-08: [evidence](evidence/c5-6b-named-row-operation-20261008.md) — шов
  `EntityDataAccess.executeNamed` на canonical path, определение операции регистрирует сам
  владелец (`AttributeValuePermissions`), создание значения — canonical create, кнопки формы
  отвечают тем же решением C5, тип назван в `rls.write-boundary.enforced-types` (прямой flush
  по нему отклоняется).
- Замена набора регистратора авторизуется отдельным именованным определением владельца;
  generic CRUD строк регистра не открывается.
- `@RlsDimension(kind = CHECK_ONLY)` на типе с canonical CRUD — отказ при старте.
- Численный замер security-запросов на пилоте (statement inspector): без него потолки C5.9 не
  с чем сравнивать. Выполнено 2026-10-08: 19 запросов к `access_grant` на первичное сохранение
  документа и 26 на повторное — статическая оценка C5.4 («≥8 запросов к `access_grant`») оказалась
  нижней границей, а один и тот же запрос повторяется до десяти раз внутри одного сохранения;
  см. [evidence](evidence/c5-6b-security-query-measurement-20261008.md).
- Когда список опустеет: `enforced=true` — единственное поведение, оба свойства и пошаговый
  инструмент удаляются.

**Объём берётся из замера, а не из числа имён.** Замер 2026-10-08 вооружил весь список,
кроме `UnitOfMeasurement` (он оставлен снятым намеренно: его 67 отказов уже известны и только
мешали бы читать следующий слой). Итог: 95 отказов границы в 21 классе, и они — по четырём
типам: `Nomenclature` 68, `GroupNom` 18, `AttributeValue` 8, `GridFormView` 1 (evidence §10).
Прежний замер («91 отказ, четыре типа») оказался **фронтом, а не итогом**: фикстуры, падавшие
в `setUp` на `UnitOfMeasurement`/`User`/`Role`, не доходили до записи `Nomenclature` и
`GroupNom`. Поэтому работа здесь идёт слоями, а замер повторяется после каждого.

- `Nomenclature` (68 тестов, 14 классов) и `GroupNom` (18 тестов, 4 класса HTTP-фикстуры) —
  только фикстуры: в `src/main` прямых записей этих типов нет вовсе.
- `AttributeValue` (8 тестов) — прикладной путь: [`AttributeValueService`](../../src/main/java/org/ip/service/AttributeValueService.java)
  пишет напрямую. Решение принято — [ADR-0019](decisions/ADR-0019-owner-named-row-operation.md):
  переименование идёт именованной операцией `ACTION:ATTRIBUTE_VALUE:RENAME`, а четыре пути
  создания — на canonical create. Переведено 2026-10-08 вместе с вооружением типа
  ([evidence](evidence/c5-6b-named-row-operation-20261008.md)): оставшиеся отказы по этому типу
  относятся к тестовым фикстурам, а не к production-коду.
- `GridFormView` (1 тест) — собственная проверка `CanonicalWriteBoundaryIT`, пишущая
  `gridFormViewRepository.saveAndFlush`; в `src/main` есть `GridFormViewService.save`.

Из 123 упавших тестов прогона границе принадлежат 95; остальные 28 — чужие (surface gates,
CTE/register-долг, deep-link baseline) и в счёт этого пакета не идут.

**Gate.** Замер с вооружённым всем списком не добавляет отказов ни по одному типу, кроме
названных; для каждого вооружённого типа прямой `EntityManager` отклоняется; `enforced=true`
для всего списка даёт тот же результат, что пустой список.

**Точка остановки.** Пакет не растёт новыми типами без замеренного отказа по этому типу;
attribute-политики и query paths сюда не входят (§7) — они открываются отдельным решением.

### C5.7. Применение: чтение и UI

Владельцы: platform-core, platform-vaadin, app.

- Чтение сущности — один раз через C5; дублирующая CHECK_ONLY-проверка снимается.
- `RlsUiGate` остаётся владельцем построчного ответа; решения об операциях для
  UI приходят из C5. Композиция «операция + строка» собирается в одном месте.
- E1.2b: `ActionPermission`/`ActionContextProvider` получают общий backend-ответ;
  объявленное действие не исполняется программно без требуемого права.
- Административные операции управления правами получают собственные определения.

Сделано 2026-10-09 (дублирующий гейт чтения):
[evidence](evidence/c5-7-read-ui-tile-gate-20261009.md) — чтение сущности решается один раз
C5 read-ключом `ENTITY:<FQN>`: `RlsReadGate` больше не читает флаг `canRead` короткого
`ENTITY:<Имя>`-ключа, плитка подсистемы спрашивает то же решение (`RlsReadGate#canRead`), а
столбец «Чтение» короткого ключа на админ-экране показывает ответ C5, а не флаг строки. Плитка
и список больше не расходятся с решением сервера; остальные пункты пакета не закрыты.

Сделано 2026-10-09 (E1.2b — общий backend операций в слое действий):
[evidence](evidence/c5-7b-e12b-action-operation-gate-20261009.md) — слой действий спрашивает
право на операцию типа тем же C5-движком, что и серверная граница (`OperationPermissionSource`
поверх `C5PermissionDecisionService`), и складывает этот ответ с построчным ответом RLS ровно в
одном месте (`ActionContextProvider`): строка, разрешённая построчно, больше не показывает
доступную кнопку без права на операцию, а причина отказа приходит из C5 и показывается раньше
построчной. Объявленное действие пересчитывает решение в момент клика, поэтому недоступное не
исполняется и программно. Первичная выдача операций в «обычной» базе — парный остаток C5.8, и
теперь его цена видна в UI: пока явные строки выдаёт только пилотный профиль, generic-запись
там будет отказана и администратору — это предсказание пункта C5.8, а не дефект проводки.

**Gate.** Отказы и причины UI совпадают с серверными; действие не запускается при
снятом праве после отрисовки; старт не зависит от `RlsUiGate` для операций.

### C5.8. Администратор и первичная выдача

Владельцы: app admin/security.

- Экран показывает операции из определений и построчные измерения раздельно; решение
  и его источники берутся тем же engine.
  Частично сделано 2026-10-08: [evidence](evidence/c5-8-named-operation-issuance-20261008.md) —
  именованная операция выдаётся админ-сервисом ровно объявленными флагами (у `ACTION:...`
  единственный флаг «выполнение» решает `EXECUTE`, «чтение» не записывается и не требуется),
  ключ объяснён названием владельца, а отказ на невыражаемый флаг назван, а не записан молча.
  Сделано 2026-10-09: [evidence](evidence/c5-8b-operation-effective-rights-20261009.md) —
  эффективные права операционных измерений собираются тем же engine, что решает сервер
  (`C5PermissionDecisionService.decideForSubject`, subject-aware форма с полным списком
  источников), а не RLS-свёрткой: `'*'` и value-scoped строки больше не показываются правом на
  операцию. Столбец «Чтение» короткого `ENTITY`-ключа до C5.7 названно оставался у RLS — это был
  прежний гейт видимости плитки; снят 2026-10-09 шагом C5.7
  ([evidence](evidence/c5-7-read-ui-tile-gate-20261009.md)), короткий ключ чисто операционный.
  Отчёт «определение зарегистрировано, грантов нет» и первичная выдача сделаны 2026-10-10:
  [evidence](evidence/c5-8c-ungranted-report-issuance-20261010.md) — отчёт показывает определения
  без единой решающей строки у кого угодно (включая администратора), а первичная выдача
  идемпотентно материализует плоскость сущностей названным ролям.
- Отчёт «определение зарегистрировано, грантов нет» — чтобы новый тип не оказался молча
  закрыт, включая для администратора. Сделано 2026-10-10: секция админ-экрана поверх
  `AccessGrantAdminService.ungrantedDefinitions()`.
- Первичная выдача грантов вместе с включением enforcement. По C5.4 операции пилота держатся только на `'*'`: нужны явные строки на все восемь типов пилота, а в обычной базе — на типы без измерений, иначе запись откажет и для `admin`; сценарий пилота
  (`Workshop`, `Nomenclature`, `UnitOfMeasurement`, `AccountingType`, документы учёта,
  регистр) получает явные строки; `'*'` остаётся как построчный обход. Сделано 2026-10-10:
  `InitialGrantIssuance` — условный стартер (`app.security-baseline.enabled`,
  `app.security-baseline.roles`), идемпотентно выдающий read-ключи и операции сущностей;
  `ACTION:`/`REST:` остаются точечной выдачей (C5.8).
- Самоповышение закрывается отдельными определениями назначения ролей и смены пароля,
  проверяемыми и на прямом вызове сервиса. Сделано 2026-10-10:
  [evidence](evidence/c5-8d-self-elevation-20261010.md) — владельцы `USER:ASSIGN_ROLES` и
  `USER:CHANGE_PASSWORD` решают и на серверном пути `UserService`, и в форме тем же ответом;
  чужая запись меняется только с правом, своя не расширяется никем (П13), а неизменённый набор
  ролей остаётся обычным обновлением.
- Обе эти операции — административный минимум первичной выдачи, а не предмет ручной выдачи.
  Сделано 2026-10-10: [evidence](evidence/c5-8e-admin-minimum-and-password-property-20261010.md) —
  `app.security-baseline.operations` по умолчанию называет `USER:ASSIGN_ROLES` и
  `USER:CHANGE_PASSWORD`, и условный стартер выдаёт их тем же ролям, что плоскость сущностей:
  иначе свежий контур закрыл бы управление пользователями и для администратора (предсказание C5.4).
  Названный, но незарегистрированный ключ или ключ без `EXECUTE` останавливает старт. Точечная
  выдача остаётся способом расширить минимум и выдать остальные `ACTION:`/`REST:`.
- Свойство типа, которое generic-запись не переносит, спрашивается владельцем в preflight записи.
  Сделано 2026-10-10: [evidence](evidence/c5-8e-admin-minimum-and-password-property-20261010.md) —
  шов `CanonicalWritePropertyPolicy` в `platform-core` (предсостояние + цель, отказ до нумерации,
  валидации, хуков и SQL) и владелец `UserPasswordChangePolicy` для хэша пароля: generic-запись
  `User` и именованная операция больше не переносят `password` без `ACTION:USER:CHANGE_PASSWORD`.
  Полевых прав при этом не появляется (ADR-0018).

**Gate.** Пилот проходит по короткой инструкции; администратор объясняет решение;
lockout невозможен; пользователь не может выдать себе ADMIN.

## 3. Матрица приёмки

Каждая строка проверяет и запрет, и отсутствие побочного результата. Число тестов
заранее не задаётся.

| ID | Сценарий | Что доказать |
| --- | --- | --- |
| П01 | Точечный грант есть и отсутствует | Независимость операций чтения, создания, изменения, удаления |
| П02 | Только `'*'` или value-scoped строка | Операция не разрешается |
| П03 | Тип без RLS (`Nomenclature`) | Операция проверяется без RLS |
| П04 | Тип с RLS (`ReceivingDocument`) | Грант операции не открывает чужую строку; доступная строка без гранта не меняется |
| П05 | Отсутствующий провайдер, аноним, неизвестное определение | Отказ конфигурации, не allow |
| П06 | Ошибка хранилища грантов | Ошибка сохраняется, allow не выдаётся |
| П07 | Запрещённая операция в агрегате | Отказ до событий, хуков, секций и SQL корня; до нумерации дело не доходит. Явного `never()` по номеру на агрегатном пути нет — номер закрыт на canonical-пути (`CanonicalWritePathIT.c5DenialStopsBeforeRlsNumberingValidationHooksAndEvents`) |
| П08 | Замена набора регистра без определения владельца | Отказ; права документа недостаточно; generic CRUD строк закрыт |
| П09 | Изменение managed-сущности и коллекции на commit | Отклоняется без зафиксированной авторизации. Коллекция `User.roles` и реальные flush-callbacks — отдельным шагом на PostgreSQL, пока не выполнены, и названы непроверенными, а не пропущенными |
| П10 | Чтение сущности | Отказ без гранта сохранён. «Одна проверка» утверждается устройством гейта (`RlsReadGate` решает по типу/виду, а не циклом по грантам), а не счётчиком `times(1)` — счётчика нет |
| П11 | Действие: allow/deny, программный вызов, снятие права после отрисовки | Не исполняется без права |
| П12 | Админ: эффективное решение и источники | Совпадает с серверным; операции и измерения раздельно |
| П13 | Пользователь меняет свои роли или чужой грант | Самоповышение запрещено на прямом вызове |
| П14 | Старт: конфликт определений; CHECK_ONLY-ключ на типе с canonical CRUD | Явный отказ старта: конфликт операций под одним ключом, имя типа без canonical write, конфликт метаданных, CHECK_ONLY-измерение с условием чтения. Совпадение CHECK_ONLY-ключа с ключом операций старт **не** останавливает — это принято ADR-0017 §3, иначе строка навсегда осталась бы непройденной по букве |

Пилоты: `Nomenclature` (тип без RLS), `ReceivingDocument` и `PrdSpec` (root + секции +
RLS), `Workshop` (опциональный филиал), `User` (роли, пароль), `NomenclaturePrice` и
регистр объектов учёта (независимость права регистра и документа).

## 5. Совместимость и выдача

- Ключ операции не меняется, поэтому уже выданные строки продолжают действовать; при
  этом операции, которые сейчас проходили только за счёт `'*'`, требуют явной выдачи —
  это и есть основное поведенческое изменение среза.
- `'*'` не переносится в операции и не участвует в C5; он остаётся построчным обходом.
- ADR-0014 и ADR-0016 не меняются; REST и report не получают новых обязательных грантов.
- Включение enforcement сопровождается первичной выдачей и, при необходимости,
  идемпотентным скриптом для выбранных субъектов. Данные в существующей таблице не
  переписываются.
- Выключатель «разрешить всё» не является способом отката.

## 7. Отложено с условием возврата

| Отложено | Условие возврата |
| --- | --- |
| Attribute read/write политика и ограничение полей | Первый прикладной сценарий, где поле должно быть скрыто или защищено от записи. **Сценарий вернулся и закрыт 2026-10-10:** [C5.8e](evidence/c5-8e-admin-minimum-and-password-property-20261010.md) защитил от записи поле `password` — не полевым правом, а тем же именованным определением владельца (шов `CanonicalWritePropertyPolicy`, ADR-0018); сам механизм произвольных полей остаётся отложенным и ждёт сценария, где поле нужно **скрыть** |
| Query paths и запрет inference через фильтр/сортировку/группировку | Требование того же сценария; до этого — консервативный полный допуск |
| Отзыв права посередине транзакции | Требование безопасности, которое не закрывается точкой авторизации |
| Независимость CREATE от UPDATE | Потребитель, которому нужен CREATE без UPDATE |
| Унификация написания ключей (`<SimpleName>` и `<FQN>`) | После стабилизации, отдельным решением |
| Полное снятие вида CHECK_ONLY | Когда не останется не-сущностных гейтов на этом виде |
| Полная PostgreSQL-приёмка и публикация REST | Отдельные gates, не условия этого среза |
| Ручная проба Gate C5.8 по короткой инструкции | Отдельный прогон на реальном контуре: администратор выдаёт и объясняет решение, lockout невозможен, пользователь не выдаёт себе ADMIN. Механизм уже закрыт тестами c5-8c/8d/8e; проба подтвердит удобство работы, а не наличие проверок |
