# Период и периодичность регистра сведений

Принято 2026-10-05; точность уточнена по решению пользователя 2026-10-07:
стандартный Vaadin DateTimePicker, достаточно миллисекунд.
Уточняет временной контракт ADR-0013 и этапов Р1–Р6.

## Контракт

Период записи и граница `asOf` используют `LocalDateTime`. `LocalDate` остаётся допустимым
типом обычных ресурсов/условий, но больше не является типом периода регистра.
`getLast`, `SliceSpec`, literal CTE bindings и runtime-параметры работают с датой и временем.
Обязательный параметр среза объявляется как `DATETIME`; `DATE` сохраняется для обычных
запросов по полям `LocalDate`. Передача даты без времени или строки вместо типизированного
`LocalDateTime` в runtime-параметр DATETIME отклоняется до выполнения запроса.

Новые периоды EXACT и границы canonical чтения используют миллисекунды:
дробная часть усекается до трёх знаков, без округления вперёд.
Например, `.123456789` становится `.123`. Общие mapped superclass нормализуют
период в setter; RegisterPeriodListener применяет то же правило при JPA-записи.
Регистр с собственным mapping обязан подключить listener либо обеспечить
ту же нормализацию своим write path. Прямые SQL / bulk DML также соблюдают это правило.
Физический TIMESTAMP(6) PostgreSQL допускает эти значения и не требует изменения типа.
Поля аудита и другие обычные даты не получают глобального усечения.

`LocalDateTime` описывает календарное время без часового пояса. В этом контракте записи
и запросы используют согласованное бизнес-время; автоматического перевода в UTC нет.

## Календарная настройка

`@RegisterMetadata.periodicity` задаётся для типа регистра:

| Режим | Сохранённый период для `2026-10-05T14:20:30.123456789` |
| --- | --- |
| EXACT — по умолчанию | `2026-10-05T14:20:30.123` |
| DAY | `2026-10-05T00:00` |
| MONTH | `2026-10-01T00:00` |
| YEAR | `2026-01-01T00:00` |

Это стабильное правило регистра, а не отдельный переключатель на каждом вызове save.
Нормализация идемпотентна. Смена режима существующего регистра может объединить прежние
ключи и требует проверки данных и отдельной миграции.

Календарные режимы требуют `@EntityListeners(RegisterPeriodListener.class)` на сущности
либо её mapped superclass. Startup validator проверяет наличие listener и поля периода.
JPA callback нормализует период перед INSERT/UPDATE. Для immutable ключа canonical lifecycle
применяет тот же нормализатор в `beforeSave`, до сравнения исходного и нового ключа.
Прямые SQL и bulk DML обходят JPA callbacks: импорт через них обязан сохранять нормализованный
период самостоятельно.

`NomenclaturePrice` объявляет DAY. Сохранение времени внутри одного дня даёт один дневной
ключ; новая дата остаётся новым ключом. Режим уникальности `(измерения, период)` текущего
независимого регистра не изменяется этим уточнением. Подчинение регистратору и альтернативная
уникальность набора — отдельная работа.

## Чтение и отчёт

Срез выбирает максимальный сохранённый период с `period <= asOf`. Граница включительная.
Календарные строки уже приведены к началу своего интервала, поэтому обычное сравнение
учитывает режим: строка октября действует с начала октября. `SliceSpec` и `getLast`
усекают дробную часть `asOf` до миллисекунд; преобразования в конец дня нет.

Отбор ресурсов/периода после среза применяется к выбранной последней строке; он не возвращает
предыдущую строку вместо последней. Уникальность текущего ключа исключает равные периоды
в одной группе. Разрешение совпадений в будущих регистрах потребует явного правила выбора.

DATETIME в форме, редакторе запроса, окне среза и форме запуска отчёта использует
стандартный Vaadin DateTimePicker с шагом 1 мс. Пустое поле не подставляет дату.
Обычный DATE-параметр по-прежнему использует DatePicker. Самописная композиция
DatePicker + TextField удалена. Дата документа пилота нормализуется до миллисекунд
перед проверками записи и при JPA-сохранении.

Календарные периоды в рецепте отчёта показываются как даты; EXACT показывает время и три
знаков дробной части. Jasper formatter поддерживает LocalDateTime и заданный date-time pattern.

## Переход существующего развёртывания

Для перехода на миллисекунды предварительно проверить записи с
`period_date <> date_trunc('milliseconds', period_date)` и возможное совпадение
ключей после усечения. Массовое преобразование существующих данных автоматически
не выполняется. В `accounting_object_pilot_local_v3` 2026-10-07 проверены только чтением
4 строки регистра, 2 установки и 2 корректировки; значений точнее миллисекунд нет.
Таблица цен пуста. Физическая схема и данные пилота не менялись.
Ранее приведённые ниже результаты тестов относятся к контракту на дату их запуска;
при этой смене выполнена компиляция, тесты не запускались.

1. Перевести `nomenclature_price.period_date` с DATE на TIMESTAMP без часового пояса.
   Пример для PostgreSQL: [`information-register-period-timestamp-postgresql.sql`](../../scripts/information-register-period-timestamp-postgresql.sql).
   Старые даты преобразуются в начало дня. 2026-10-05 SQL выполнен в локальной базе
   `DBVaa25`, схема `public`: тип TIMESTAMP(6), NOT NULL и прежние ограничения сохранены.
   Таблица была пустой. [Протокол перехода](evidence/register-period-timestamp-postgresql-20261005.md).
2. Обновить вызывающий код: тип периода, конструкторы/setters и `asOf` — LocalDateTime.
   Для прежнего дневного значения явно использовать `date.atStartOfDay()`.
3. Пересохранить прежние сохранённые рецепты среза: параметр DATE заменить на DATETIME,
   literal значения даты — на ISO дату и время. Новые черновики генератор создаёт в новом формате.
   Автоматической массовой правки пользовательских отчётов нет.
4. Повторить проверку временных границ на фактической СУБД и её точности TIMESTAMP.

Старые файлы evidence Р2–Р6 описывают принятый на соответствующую дату LocalDate-контракт
и не переписываются задним числом. Текущая проверка этого изменения фиксируется отдельно.
