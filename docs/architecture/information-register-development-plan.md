# Регистр сведений: план развития после первых трёх патчей

- Статус: Р1 реализован; код и сценарии Р2–Р3 подготовлены. Итоговый прогон Р1 и компиляция/прогон Р2–Р3 пропущены по просьбе пользователя; gates Р2–Р3 остаются открытыми. Остальные этапы запланированы.
- Дата: 2026-10-03.
- Текущий пилот: `NomenclaturePrice` («Цены номенклатуры»).
- Основное решение: [ADR-0013](decisions/ADR-0013-information-register-v1.md).
- Смежные решения: [canonical data path](decisions/ADR-0007-canonical-data-access-path.md), [lifecycle](decisions/ADR-0005-entity-lifecycle-and-application-behavior.md), [интернирование](decisions/ADR-0008-interned-entities.md), [план F-ERP](f-integration-erp-plan.md).

План относится к регистрам сведений и их потребителям. Проведение и регистры накопления включены как отдельный условный трек F-ERP-4. Он не начинается автоматически после завершения срезов сведений. Нумерация поздних версий ниже — предлагаемая группировка работ, а не объявленные версии платформы.

## 1. Исходное состояние

| Возможность | Что уже есть | Открытая часть |
| --- | --- | --- |
| Декларация | `@RegisterMetadata(dimensions, period, resources)` | Пока в прикладном `org.ip.register` |
| Проверка | Field access, поля ключа, `LocalDate`, nullability, неизменяемость, unique declaration; общий startup validator | Физическая схема H2 проверена поведением; внешняя БД требует отдельной проверки |
| Модель | `NomenclaturePrice`, ключ `(nomenclature_id, period_date)`, `BigDecimal(19,4)` | Второго предметного регистра нет; `EntityKind` остаётся `PLAIN` |
| Запись | Canonical CREATE/UPDATE, unique constraint, lifecycle guard | UPDATE managed-объекта без отдельного исходного снимка отклоняется |
| Чтение | `getLast(nomenclature, asOf)` и `priceOn(...)` через `EntityDataAccess` | Отдельный count-запрос; нет общего среза и batch API |
| Проверка чтения | Краевые случаи, 284 пробы случайной истории, detached-измерение, отказ C5 | Нет приёмки регистра с RLS-измерениями и нет PostgreSQL-замера |
| Отчёты / LIST | Компилятор уже имеет CTE, GROUP BY, MAX, параметры и составной ON | Срез регистра ещё не собран и не принят |

Последний прогон третьего патча: 67 целевых тестов прошли; в расширенном наборе 164 тестов осталось 6 ошибок других архитектурных проверок. Это историческое evidence по тому запуску. Перед новым этапом нужно повторно зафиксировать текущие исходники и локальные JAR, поскольку в проекте идут другие изменения.

## 2. Контракт, который сохраняется на всех этапах

1. Последняя запись на дату T — максимум периода среди записей данного полного набора измерений с `period <= T`. Граница включительная. Нет истории до T — нет записи; цена 0 не подставляется.
2. Точечный `getLast` требует все измерения. Частичный отбор относится к срезу нескольких групп и не должен возвращать одну произвольную группу.
3. Бизнес-ключ — измерения плюс период; технический `id` сохраняется. Один набор измерений и один период дают не более одной строки.
4. В первой версии среза отбор измерений входит в поиск максимального периода. Отбор ресурсов применяется к уже выбранной последней строке. Отбор самого периода сверх `asOf` тоже применяется после выбора, если он явно задан потребителем.
5. Все версии одного набора измерений должны иметь одинаковую видимость в рамках чтения. Скрытая свежая запись не должна превращать старую в ложную «последнюю».
6. Чтение проходит C5, RLS и проверки экспозиции; форма и отчёт не становятся отдельным обходным входом. Проверка допуска запроса и фильтрация строк — разные обязанности.
7. Запись проходит canonical validation/lifecycle/permissions. Нельзя заменить этот путь прямым `save`, bulk DML или SQL upsert без отдельного полного контракта.
8. `SliceSpec` описывает семантику. Исполнители для Criteria и report CTE могут различаться; `platform-core` не получает зависимость от reportstudio.
9. Оракул независим от генератора запросов. Один и тот же набор данных сравнивается с точечным чтением, срезом, count и batch по мере их появления.
10. День на `LocalDate` остаётся единственной поддерживаемой периодичностью до отдельного решения о других гранулярностях.

Пример для проверки отбора: цены 150, затем 90. Срез на последнюю дату с условием `price > 100` пуст. Значение 150 означает другую операцию — «последняя среди подходящих», которая позже получит отдельное имя.

## 4. Р0 — воспроизводимость и границы патча

Работы:

- Сохранить состояние затрагиваемых файлов; накладывать каждый внешний diff на текущие исправленные исходники, а не на исходную цепочку из песочницы.
- Зафиксировать фактические версии JDK, Boot, Spring Data, Hibernate и внутренние SNAPSHOT-артефакты. При изменении owner-модуля сначала проверить его, затем установить/подключить именно проверенный артефакт.
- Повторить целевой набор регистра. Расширять проверку на owner-модули, архитектурные границы, startup и потребителей при изменении соответствующих частей.
- Разделить дефекты нового патча и существующие несогласованности core/C5/REST/starter. Исправлять реестры после проверки роли и направления зависимости; массовая перезапись baseline не считается исправлением.

Приёмка: у каждого патча есть перечень затронутых контрактов, воспроизводимая команда и результат. Перед переключением общего платформенного или production-пути соответствующие архитектурные проверки зелёные; исследовательский спайк можно выполнять при документированных внешних долгах.

## 5. Р1 — закрытие v1.0

Работы:

- Запустить проверку по `ManagedEntityCatalog.managedEntityClasses()`, выбрать типы с `@RegisterMetadata`. Второй classpath scan сущностей не создавать.
- Построить проверенный immutable descriptor регистра: тип, измерения, период, ресурсы, типы полей и отображение ключа. Если descriptor ещё не нужен для Р1, начать с общего startup validator и добавить descriptor в Р4.
- Остановить старт до приёма запросов при ошибке любого регистра, включая регистр без читателя. Диагностика содержит тип, поле и код нарушения; ошибки можно собрать в один отчёт.
- Проверить реальный сценарий формы: создать две цены на разные даты, открыть историю, изменить ресурс, отклонить перенос ключа и дубль ключа с понятным сообщением.
- Отдельно проверить поведением схемы наличие unique и NOT NULL. Аннотационная проверка не подтверждает физическую схему развёрнутой БД.
- Зафиксировать ограничение managed UPDATE: неизвестный исходный ключ блокируется; до Р9 прикладной путь использует detached payload. Не снимать guard ради удобства.

Проверки: корректный контекст поднимается; неправильная декларация без `RegisterReader` ломает старт; не-регистры не проверяются как регистры; ошибочные JPA-модели не маскируются фикстурами без `@Id`; действующие write и oracle-тесты остаются зелёными.

Приёмка: все managed-регистры проверены автоматически, CRUD пилота принят, ограничения записи понятны. Выпуск: отдельный патч startup-проверки, затем небольшой патч диагностики формы, если она требует изменения.

Результат Р1 (2026-10-03): общий startup validator реализован; descriptor отложен до Р4.
Прошли 4 контекстных теста, 4 интеграционных сценария generic-формы, 7 persistence-тестов
(включая физические NOT NULL) и 21 целевой тест owner-модуля `platform-vaadin`.
Проверенный UI-артефакт установлен локально, его source fingerprint обновлён.
Итоговый объединённый прогон пропущен по просьбе пользователя; новый тест удаления версии
ещё не запускался. Ручная браузерная приёмка не выполнялась. Подробности и ограничения —
в [ADR-0013](decisions/ADR-0013-information-register-v1.md#evidence-завершения-р1-2026-10-03).

## 6. Р2 — спайк среза на существующем компиляторе

Вручную собрать обычный `VisualQueryPackage` на `NomenclaturePrice`. Пока не переносить пакеты и не вводить нового вида source в compiler AST.

Форма запроса, как схема проверки:

```text
mx:     dimension keys + MAX(period)
        WHERE period <= :asOf AND dimension conditions
        GROUP BY dimension keys

latest: register JOIN mx ON every dimension key AND period
        WHERE resource conditions after selecting the latest row

main:   nomenclature LEFT JOIN latest
```

Работы:

- Компилировать с настоящим `QueryBuilderMetadataCatalog`, затем анализировать через SQM/guard и выполнять на Hibernate. Мок guard не является приёмкой доступа.
- Проверить `MAX(LocalDate)`, ссылочное измерение через его id, составной ON, типы результирующих колонок и общий параметр даты.
- Добавить тестовый регистр с двумя измерениями в отдельном тестовом persistence-контексте. В production-модель ради проверки второй столбец не добавлять.
- Проверить LEFT JOIN: номенклатура без цены остаётся в отчёте с пустой ценой. Отбор внутри источника среза и WHERE потребителя после LEFT JOIN имеют разную семантику; зафиксировать оба сценария.
- Проверить сериализацию/повторную компиляцию пакета существующим codec. Если выявлен дефект, исправить минимальный механизм с отдельной регрессией.

Приёмка: один пакет выполняется, результат совпадает с оракулом для одной и двух размерностей. Дата одна на весь запрос. «Цена на дату каждого документа» требует корреляции или другого API и сюда не входит.

Подготовка Р2 (2026-10-03): добавлены семь сценариев на существующих VisualQueryPackage,
metadata catalog и настоящем SQM/guard: production mapping цен, отдельная двухмерная
модель, оракул, LEFT JOIN, отборы, codec и типы. Production compiler не менялся.
По просьбе пользователя компиляция и выполнение отложены; критерий выразимости ещё не подтверждён.
Состав, команда будущего запуска и ограничения описаны в [протоколе спайка](information-register-cte-spike.md).

## 7. Р3 — права и согласованная видимость

Текущий `ReportQueryGuard` проверяет RLS-допуск сущностей, включая CTE. Его `allowed()` сам по себе не доказывает наличие C5 и применение row filters. Для нового среза принять весь путь от допуска до выполнения.

Работы:

- Определить владельца C5-проверки report query: использовать общий evaluator и canonical семантику разрешений, без копирования логики AccessGrant в генератор.
- Проверять все сущности, участвующие в чтении: корни, CTE, JOIN, подзапросы и entity-параметры. Выявить также неявные чтения по путям ссылок.
- При отсутствии обязательного security provider или субъекта отклонять чтение. Пустой результат не должен скрывать ошибку конфигурации.
- Подключать RLS-фильтры в той же транзакции/сессии, где выполняется срез. Проверить actual SQL/результат, а не наличие вызова activator.
- Для поддерживаемых регистров доказать, что RLS зависит только от измерений или инвариантных для группы значений. Неподдерживаемую policy отклонять диагностикой; простого сравнения строк имён полей для вложенных путей недостаточно.
- Зафиксировать политику доступа к выводимым ресурсам и полям: использовать действующий attribute enforcement либо явно ограничить опубликованную проекцию до поддерживаемого набора.

Проверки: нет entity-read grant; запрещена сущность только внутри CTE; есть C5, но нет RLS; разрешена лишь часть наборов измерений; скрытые группы не попадают в data/count; свежая скрытая версия не вызывает выдачу старой. Cache/Session и порядок предыдущих чтений не меняют результат.

Приёмка: положительные и отрицательные сценарии проходят с реальным enforcement. Привилегированный bypass не используется в приёмочных чтениях. Если для отчётного канала требуется общее исправление, оно поставляется отдельным патчем до генератора.

Подготовка Р3 (2026-10-03): добавлены общий C5 authorizer, повторная проверка executor,
SPI проверки источника и прикладная проверка постоянной видимости регистра; подготовлены
12 security-сценариев с реальным хранилищем грантов и RLS. Компиляция и запуск отложены.
Проекция пока только scalar; необходимы ENTITY и ATTR grants всех persistent-атрибутов
участвующих типов. Это ужесточает общий report channel и требует приёмки текущих consumers.
Контракт — [проект ADR-0014](decisions/ADR-0014-report-read-authorization.md),
состав и ограничения — [протокол Р3](information-register-report-security.md).

## 8. Р4 — размещение общих типов

После спайка согласовать размещение. На v1.1 допускается временный общий пакет `org.ipro.register` в корневом модуле; это не новый артефакт `platform-register` и не повышение `EntityKind`.

Работы:

- Перенести общую декларацию, валидатор, descriptor/registry и reader; модель, lifecycle и предметный price service оставить в `org.ip`.
- Генератор report-фрагмента разместить рядом с reportstudio. Он принимает общий descriptor, не импортирует `NomenclaturePrice` и другие предметные классы.
- Сохранить исправленный reader через `EntityDataAccess`. Внешний патч переноса не должен возвращать исходный `JpaSpecificationExecutor`.
- Выделить shared semantic types так, чтобы core LIST executor позднее не зависел от reportstudio и его optional dependencies.
- Определить API/SPI/internal роли, обновить точные surface/matrix/measurement entries и затронутые модульные baseline. Проверить последствия для будущего D-R report add-on.
- Уточнить ADR-0013: перенос после спайка v1.1 заменяет прежнюю условную дату «после v1.2». F-ERP-3 и требование предметных production-примеров сохраняются.

Приёмка: направление `org.ipro → org.ip` отсутствует, canonical/security поведение неизменно, старт и все прежние тесты проходят. Package rename и новые capabilities не смешиваются в одном патче.

## 9. Р5 — SliceSpec и генератор

Первая спецификация: периодический регистр, `LATEST`, обязательная дата, типизированные условия измерений и отдельно условия после среза. Названия новых API окончательно выбрать по спайку, а не фиксировать преждевременно здесь.

Работы:

- Валидировать тип через registry/catalog, условия — по разрешённым полям, операторам и типам. Произвольные куски HQL/SQL и динамический `Class.forName` не принимать.
- Ссылочные измерения сравнивать по устойчивому persistent identity; составные/неподдерживаемые отображения отклонять явно до генерации.
- Генератор — чистая функция без БД: descriptor + spec + контекст имён → CTE-фрагмент, схема колонок, mapping имён и bindings.
- Выделить имена CTE, alias и параметров без коллизий с чужим пакетом. Проверить два среза одного регистра на разных датах в одном запросе.
- Поддержать перенос фрагмента в существующий пакет; потребитель соединяется со срезом как с виртуальной таблицей.
- Переиспользовать описание полей и семантику границы даты в reader, сохраняя его простой точечный запрос.

Проверки: типы и отказы входного контракта; отсутствие изменений исходного spec; коллизии имён; пустая история; точная дата; две размерности; несколько ресурсов; фильтр 150 → 90; неравенство point/slice/oracle не допускается.

Приёмка: потребитель не пишет GROUP BY/MAX/ON вручную; неизменённый compiler компилирует фрагмент. Если нужен compiler fix, он мал и подтверждён отдельным тестом Р2.

## 10. Р6 — приёмка v1.1 и измерения

Работы:

- Собрать сохраняемый отчёт «номенклатура плюс цена на выбранную дату»: включая номенклатуру без цены, несколько историй, фильтры, сортировку и повторное открытие шаблона.
- Проверить параметры через действующий report assembly/resolver и выполнение с реальными ролями. Генератор не выдаёт права на источник.
- Сравнить point read, CTE slice и оракул на одинаковых seeded histories, включая двухмерную модель и все граничные даты.
- Подготовить PostgreSQL-наборы: много групп/мало версий; мало групп/много версий; разные селективности измерений и разные даты среза.
- Проверить физические индексы и снять `EXPLAIN (ANALYZE, BUFFERS)` для CTE и коррелированного варианта. Сравнивать одинаковый результат, права, bindings и объём данных; security SQL учитывать отдельно.
- Зафиксировать план, строки/буферы, число запросов, время и условия измерения. Не выбирать вариант по универсальному утверждению «CTE всегда быстрее».

Приёмка v1.1: отчёт воспроизводим, разрешения соблюдены, point/slice/oracle совпадают. H2 подтверждает корректность JPA; без PostgreSQL-замера производительность на PostgreSQL остаётся непроверенной. PostgreSQL-протокол нужен до заявления о production-стоимости.

## 11. Р7 — срез в canonical LIST

Работы:

- Добавить ограниченное read intent/параметр среза в canonical путь. Он возвращает строки сущности-пилота, сохраняя FetchPlan, C5/RLS, telemetry и exposure checks.
- Использовать общий descriptor/spec, но самостоятельный Criteria executor. Report CTE generator не становится зависимостью core.
- Выделить predicate среза, одинаково применяемый к data и count. Отбор ресурсов строить снаружи поиска максимального периода.
- Для среза нескольких групп требовать pagination. Sort дополнять устойчивым tie-breaker; строки между страницами не повторяются и не пропадают из-за одинаковых sort values.
- Ограничить сортировки/фильтры поддерживаемыми путями; не допустить дублирования entity rows из collection joins.

Проверки: count parity для каждой комбинации фильтра и роли; первая/последняя/пустая страница; стабильный sort; точная дата; запрещённые группы; fresh persistence context; detached отображение без N+1.

Приёмка: обычный режим истории ведёт себя как прежде; новый режим даёт одну строку на видимый набор измерений и достоверный total. Страницы проверяются в фиксированном состоянии данных; snapshot consistency при конкурентных изменениях оговаривается отдельно.

## 12. Р8 — стандартный UI и UX источника

### ListForm

- Для периодического регистра вывести режимы «История / Срез последних» и параметр «На дату» из descriptor. Непериодический тип не получает бессмысленный переключатель.
- Начальная дата — бизнес-дата приложения; не читать её из случайной зоны клиента. Изменение даты/режима сбрасывает страницу и пересчитывает data/count.
- Определить, входят ли дата и режим в saved view и deep link. Сделать одинаковое поведение при повторном открытии.
- Команды редактирования работают с конкретной найденной строкой по id. «Установить новую цену на выбранную дату» — отдельная команда; до Р11 не выдавать обычное изменение ресурса за upsert.
- Ключ существующей строки показывать read-only, сохраняя server-side guard. Пустой срез объяснять обычным отсутствием записей, не подставлять нули.

### Конструктор отчёта

- Добавить выбор «Регистр → Срез последних → параметр даты», доступные измерения/ресурсы и понятное разделение отбора измерений и последнего значения.
- Преобразовать выбор пользователя в `SliceSpec` и обычный пакет. Сначала можно сохранять раскрытый пакет; сохранение намерения среза и повторная генерация требуют отдельного versioned формата.
- Проверить round-trip: сохранение, повторное открытие, редактирование и компиляция не теряют дату и положение фильтров.

Приёмка v1.2: прикладнику достаточно декларации регистра; не нужны отдельные формы, custom reader registration или ручной HQL. Принять UI/service parity прав и посчитать добавленный прикладной boilerplate.

## 13. Р9 — стоимость чтения и надёжный ключ

Этот этап содержит независимые изменения; каждое начинается своим патчем.

**Обновление.** Определить поддерживаемый write contract для managed и detached payload. Получать достоверные исходные значения ключа до изменения/merge либо использовать typed resource-only intent, который не принимает ключ для изменения. Способ не должен сравнивать managed instance с самим собой, очищать чужой persistence context или рассчитывать на непубличный `Session.getEntityEntry`. Проверить возврат результата после отказа, rollback, optimistic version и работу других lifecycle callbacks.

**Bounded read.** После измерения отдельного count в `getLast` добавить общий bounded/first read intent в canonical API. Он сохраняет permissions, FetchPlan, exposure и telemetry. Ограничение — одна data-строка; permission SQL измеряется отдельно и не обещается как «один SQL на весь вызов». Текущий reader переключить после parity tests.

**Batch.** Для страницы номенклатуры/строк документа добавить чтение по ограниченному набору полных ключей на одну дату. Один set-based data query или документированное chunking, без point read на каждую строку. Установить лимиты ключей и параметров, обработку дублей, отсутствие/запрет записи. Произвольная дата у каждого ключа — другой контракт, не скрытое расширение этого метода.

Приёмка: ресурс корректно изменяется в заявленных каналах, ключ защищён; одиночное чтение не делает count; batch совпадает с oracle и не имеет линейного N+1. Остальные каналы canonical read/write не регрессируют.

## 14. Р10 — предметный пилот и повышение до платформенной возможности

Первый кандидат — реальный периодический регистр `ИзмененияКомпонентовПоРаспространениям`. Его фактические измерения, ресурсы, даты и связи сначала сверить с предметной конфигурацией. Тестовую двухмерную сущность и песочницу цен не считать вторым production-примером.

Работы:

- Описать предметный сценарий независимо от Java API: кто записывает, что означает период, как корректируется история, что запрещено и как задаётся видимость.
- Принять сначала простой point/slice read, затем составной запрос с распространениями/диапазонами. Проверять каждую часть отдельным оракулом; не связывать все проблемы в одном тесте.
- Сравнить минимум два подтверждённых production-сценария с общим контрактом. Если второго нет, сохранить pilot status и не повышать kind.
- Отдельным ADR решить необходимость `INFORMATION_REGISTER`, metadata facts, public API и владельца артефакта. Перенос Java package и повышение semantic kind — разные решения.
- При физическом выносе разделить контракты, engine и optional report/UI adapters без обратных зависимостей; принять starter composition, startup registration, API baseline и внешний reference consumer.

Приёмка: F-ERP-3 явно подтверждён или уточнён новым ADR; общий механизм сокращает реальный прикладной код. Не вводить новый базовый класс только ради названия типа.

## 15. Р11 — запись по ключу, upsert и конкуренция

Начать с отдельного ADR и PostgreSQL-спайка. Непериодический регистр тоже может использовать этот контракт, когда появляется реальный потребитель.

Решения до реализации:

- `set` создаёт/изменяет ресурс для ключа; различить вставку, замену ресурсов и корректировку. Определить delete по ключу, идемпотентность и правила исправления прошлых периодов.
- Запись участвует в транзакции вызывающей операции. Конфликт уникальности, optimistic lock, deadlock/serialization error классифицируются отдельно; владельцем retry является граница транзакции.
- Для самостоятельной команды вне чужой транзакции возможен отдельный transactional entry point с bounded retry. Свой `REQUIRES_NEW` внутри обычной записи регистра не вводить.
- Определить конфликтную политику: проверка ожидаемой версии или сериализованная замена. Пессимистическая блокировка найденной строки не решает гонку вставки отсутствующего ключа.
- Побочные эффекты не повторяются при retry: события/интеграции имеют определённую after-commit/outbox/idempotency семантику.

Спайк: N транзакций пишут один отсутствующий ключ; N обновляют существующий; конфликт внутри сохранения агрегата; полный rollback; resource-only изменение; истечение retry; разные ключи; блокировки в устойчивом порядке. После unique violation не пытаться продолжить испорченную PostgreSQL-транзакцию.

Реализация идёт через canonical write pipeline и общую lifecycle/security семантику. Из интернирования переиспользуются только доказанно общие части описания/классификации ключа; `NaturalKeyCreateSupport` и регистр не объединяются ради одного retry-loop.

Приёмка: одна строка на ключ, определённый победитель/конфликт, не частично сохранённый агрегат, bounded повторы и согласованные события. H2 не заменяет PostgreSQL-конкурентную проверку. Другие серверные СУБД добавляются только с собственными измерениями и тестами.

## 16. Р12 — дополнительные семантики

Каждая возможность добавляется при конкретном сценарии и отдельном принятом контракте:

| Возможность | Что решить | Приёмка |
| --- | --- | --- |
| Срез первых | `earliestAtOrAfter(T)` или первая запись среди `period <= T` — разные операции; имя и направление границы явные | Oracle на обеих сторонах даты; нельзя просто заменить MAX на MIN и оставить неоговорённый смысл |
| Отбор до среза | Отдельно названная «последняя подходящая»; не менять смысл `latest` | Пример 150 → 90 даёт разные ожидаемые результаты для двух режимов |
| Месяц/секунда | Тип периода, нормализация, зона, точность выбранной БД, бизнес-граница | Нормализация одинакова при записи, поиске, миграции и проверке unique |
| Интервалы действия | `validFrom/validTo`, перекрытия и закрытие интервала | Это самостоятельная модель; отсутствие новой версии не равно окончанию действия |
| Неактивность/нулевые ресурсы | Явный ресурс-флаг и место его фильтрации | Нулевая цена и отсутствие цены остаются разными состояниями |
| Разные даты в одной таблице документов | Корреляция либо batch с датой на каждый ключ | Не выдавать один параметр CTE за дату каждой строки |

Приёмка этапа — не все строки таблицы сразу, а подтверждённый потребитель и point/slice/oracle parity для каждой добавленной операции.

## 17. Р13 — диагностика, генерация и эксплуатация

- Explorer показывает измерения, период, ресурсы, business key, гранулярность, доступные read/write intents, источник каждого факта и понятные ограничения. Значения грантов и пользовательские решения по строкам в type facts не включать.
- Метаданные читателя, генератора, UI и Explorer получаются из одного descriptor/registry; параллельную reflection-модель для Studio не заводить.
- Рецепт создания регистра генерирует entity declaration, key mapping/constraint, resources и требуемые migration changes. До изменения файлов выдаёт plan/diff, сохраняет ручной код и не требует boilerplate registration.
- Отдельно выбрать канал рецепта: сначала CLI/Maven/шаблон, IDE-плагин — после устойчивого round-trip на реальных потребителях.
- Перед развёртыванием иметь schema migration, проверку данных на дубли/NULL, physical index validation и rollback/совместимость версии приложения. `ddl-auto=update` остаётся удобством песочницы, не доказательством миграции.
- Добавить измерения стоимости/отказов на существующей telemetry-границе. Кеш истории/среза вводить только по профилю с корректной инвалидацией записей и учётом permission context.

Приёмка: новое приложение использует регистр без внутренних пакетов и ручного инфраструктурного wiring, миграции воспроизводимы, проблемы декларации диагностируются до запроса.

## 18. Р14 — регистратор, проведение и регистр накопления

Этот трек выполняется по F-ERP-4 после его собственных предпосылок: capability-aware actions, предметные owner/composition/business fact сценарии и границы записи. Готовый срез сведений является полезным инструментом, но не доказательством готовности ledger.

Последовательные части:

1. **Регистратор сведений, если нужен.** Определить владельца производных записей, атомарное создание/замену, коррекцию и отказ обычного CRUD. Не смешивать текущие значения и аудиторский журнал; выбрать модель истории явно.
2. **Posting capability документа.** `DRAFT/POSTED`, разрешения post/unpost/repost, optimistic concurrency, запрет обычного изменения/удаления проведённого документа.
3. **PostingBatch и неизменяемые движения.** Команда идемпотентна по command id; состояние документа, batch и движения меняются атомарно. Отмена создаёт reversal batch, а не удаляет историю — сохранить решение действующего F-ERP-плана.
4. **Временная модель.** Разделить `effectiveAt` и `recordedAt`, правила проведения задним числом, закрытых периодов и исправлений. Не переносить автоматически LocalDate-контракт цен на хозяйственные движения.
5. **Read API.** Остатки на дату и обороты за интервал; видимость и resource permissions применяются до агрегации. Проверять арифметику независимой моделью движений.
6. **Конкурентные ограничения.** Контроль отрицательного остатка — отдельный сценарий с сериализацией по ключу и PostgreSQL-тестом нескольких проведений. Явно выбрать источник блокировки и порядок захвата.
7. **Производительность.** Материализованные остатки — производные данные после измерений; они полностью восстанавливаются из движений. Цель и допустимая задержка refresh определяются отдельно.
8. **Предметная приёмка.** Первый кандидат `ЗапускВПроизводство`; измерения и ресурсы сверяются до schema migration. FIFO, себестоимость и пересчёт хронологии получают собственные предметные алгоритмы.

Приёмка каждой части включает rollback, retry/idempotency, запреты обходных каналов, RLS/C5, backward-date cases и восстановление. Общий «полный аналог регистров 1С» не является критерием завершения.
