# Разбор замечаний к плану реестра сущностей

Дата: 2026-11-10. Редакция разбора 2 — с учётом файла `СтруктураСущностей_ЗамечанияКПлану_Часть2.txt`.

Источник замечаний: предоставленный пользователем файл `СтруктураСущностей_ЗамечанияКПлану.txt`.
Первоначально проверенный документ: [план, редакция 1](entity-registry-ux-plan-rev1.md). Результаты перенесены в [актуальный план, редакция 2](entity-registry-ux-plan.md).

Статус: замечания проверены, основной план обновлён. Пользователь отдельно подтвердил границу: общие компоненты представления — в платформе, навигация и рабочие вкладки — в приложении. Положения приложенных текстов не считаются автоматически новыми требованиями: конкретные решения и уточнения ниже явно отделены от описания существующего кода.

## 1. Основные выводы

Большинство технических замечаний стоит принять. Наиболее существенны точный состав каталога, сохранение административных фильтров, механизм создания отдельных карточек, зависимости потребителей общего снимка и явный контракт истории/закрытия вкладок.

В исходном плане выпуск реестра излишне связан с добавлением нового рецепта `PLAIN`. Это следует разделить: готовность каталога и навигации проверяется самостоятельно; создание простой сущности получает отдельный генераторный план. Пользователь явно запросил четыре пункта меню, поэтому изменение видимости четвёртого пункта требует отдельного продуктового решения.

Есть фактические уточнения к самим замечаниям:

- Активация безадресной вкладки уже вызывает `replace("/")`, а не `push`. Переход на адресованную вкладку обычно добавляет шаг, закрытие активной вкладки использует замену, Back/Forward повторно адрес не записывает. Для реестра сначала нужно зафиксировать существующие правила и проверить несколько безадресных карточек.
- `showStructureDetail()` относится к сообщению в открытой карточке, в частности при переходе к подтверждённой табличной части. Это не показ общих диагностик каталога. Оба получателя нужно назвать отдельно.
- В действующем интерактивном макете есть общие диагностики, сброс активных фильтров и пустое состояние. Узкий вариант также уже отрисовывался. В плане, однако, закреплён только широкий снимок и не перечислены все состояния.
- Рефакторинг и новый экран уже разделены как R1 и R2. Не хватает явного требования сохранить прежнее поведение на R1, отдельного флага внедрения и периода до удаления старого пути.
- Приведённые числа инвентаря не следует использовать как актуальный состав Explorer без измерения и проверки области охвата. Сохранённый ET0-инвентарь от 2026-10-21 содержит 44 managed-типа (21/7/16 по экспозициям), а не 37 (16/5/16). Это исторический снимок managed entities, не замена актуальному `ExplorerSnapshot`.
- `GridFormView` нельзя автоматически считать `INTERNAL_STORE` по назначению или имени. В его исходнике есть `@EntityMetadata`, а в сохранённом инвентаре — `STANDARD_ROOT`; отнесение его к служебным явно отложено комментарием класса. Классификацию берём из descriptor, UI её не переопределяет.

## 2. Технические замечания

Нумерация T1–T10 соответствует первому нумерованному перечню в файле замечаний.

| Пункт | Оценка | Что предлагается зафиксировать |
|---|---|---|
| T1. Единица списка | Принять | Запись реестра — самостоятельный тип из каталога Explorer. Owned-строка не становится отдельным объектом основного списка; её открывают через подтверждённого владельца. Типы с ошибкой сборки/неизвестным descriptor не исчезают молча. Точные количества измеряются на текущем снимке. |
| T2. Служебные типы и группировка | Принять уточнение политики | По умолчанию скрывать типы, которые действующий descriptor относит к `INTERNAL_STORE`/`UNCLASSIFIED`; показывать их явной дополнительной опцией. После включения группировать по выбранной оси, без неописанной третьей иерархии. Неизвестная экспозиция не равна служебной. |
| T3. Название группы `PLAIN` | Принять как требование к реализации | «Простые сущности» в выбранном макете — осознанная новая подпись. Менять общий словарь представления и его проверки; не заводить отдельный перевод только в новом renderer. Смена подписи не меняет семантику `PLAIN`. |
| T4. Утрата фильтров | Принять | Три согласованных поля оставить основными. Существующие «Только ошибки», показ служебных типов и технический фильтр экспозиции сохранить в компактных дополнительных настройках. Их состояние, индикацию и сброс определить явно. «Только ошибки» не заменять условием «Есть замечания»: WARNING и ERROR — разные условия; действующая обработка `BUILD_FAILED` тоже сохраняется. |
| T5. Область ADR | Принять | Обновление касается §8 и §11 ADR-0010; в §4 зафиксировать применение правил к отдельным entry id и сценарии истории. Новые результаты проверки обозначить отдельно от исторических измерений прежнего среза. |
| T6. Зависимости и получатели сообщений | Принять с уточнением | `EntityDraftProjectCatalog.current()/refresh()` подключается к общему каталогу. Refresh инвалидирует снимок и кеши read-only панелей, как прежнее очищение `panels/pilotPanels`, сохраняя ввод редакторов. Общие диагностики имеют отдельную платформенную панель и прикладную вкладку; сообщение о секции доставляется целевой карточке. |
| T7. Создание экземпляра карточки | Конкретный механизм выбран | `Workspace.open(EntityExplorerCardView.class, entryId, title, initializer)` создаёт компонент через `WorkspaceManager` / `beanFactory.createBean`. Прикладной `EntityExplorerWorkspace` держит карту ссылок на живые карточки, как существующий `EntityModifyWorkspace`. Явный запрос к существующей карточке применяется через эту карту до активации; новый компонент получает его в initializer. Закрытие удаляет ссылку. API Workspace расширять и читать его кеш обходным `getOrCreate` не требуется. Подробный алгоритм — в матрице входов. |
| T8. Несколько безадресных карточек | Принять как обязательную проверку | Карта адресов уже per-entry; поле последней безадресной вкладки — общее. Проверить последовательности «реестр → карточка без ключа → другая карточка → Back/Forward/закрытие». Не обещать восстановление точного безадресного entry из одного `/` без подтверждения действующей семантики. Патч платформенного моста обосновывать результатом проверки. |
| T9. История при возврате к реестру | Уточнён контракт нового экрана | В старом совмещённом Explorer выбор мог назначить адрес единственной вкладке. Новый самостоятельный реестр остаётся `/` и без выбора, и с выбором; URL типа принадлежит отдельной карточке после её открытия. Две строки реестра записаны в матрицу с `replace` при смене URL; выбор в реестре историю не меняет. |
| T10. Закрыть и снова открыть реестр | Владелец выбран | Нейтральный `EntityExplorerRegistryState` — часть платформенного представления. Его прикладной владелец `EntityExplorerUiSession` — UI-scoped и переживает закрытие компонента. Восстанавливаются фильтры, группировка, раскрытия и допустимый выбор; новый UI/контекст применяет очистку. Аннотация UI-scope на прежнем смешанном `ExplorerUiState` не является обязательным механизмом. |

## 3. Замечания к интерфейсу

Нумерация U1–U10 соответствует ненумерованному перечню интерфейсных замечаний.

| Пункт | Оценка | Предложение |
|---|---|---|
| U1. Повтор вида/подсистемы | Принять | Показывать вид и подсистему один раз: например, сохранить строку над заголовком и убрать две повторяющиеся строки свойств. |
| U2. Разные макеты/состояния | Пробел передачи устранён | Прежняя ссылка на файлы чата не делала исходник доступным из проекта. Теперь в `docs/plans/mockups/` сохранены исходный фрагмент, самостоятельный HTML и шесть именованных снимков с манифестом SHA-256. Начальное значение — «По видам»; сброс и пустой результат показаны отдельными состояниями. Старое сравнение вариантов не является текущим эталоном. Визуальная основа и уточнения после ревью различены в актуальном плане. |
| U3. Пять систем счётчиков | Принять упрощение, сохранить смысл | Без фильтров достаточно «N сущностей», с фильтрами — «Найдено N из M». Число типов в группе, количество диагностик у типа и непривязанные диагностики имеют разный смысл. Убрать повторяющийся агрегат, а не смешивать число сущностей с числом сообщений. |
| U4. Бейджи и длинные имена | Уточнить критерий приёмки | В текущем CSS текст переносится, отдельный flex-элемент счётчика не сжимается. Наезд не подтверждён одной лишь длиной имени. Закрепить отсутствие пересечения и читаемость на 736 px, полное доступное имя при любом сокращении. Native `title` не считать единственным способом получить имя с клавиатуры. |
| U5. Стрелка у реквизитов | Не относится к текущему варианту | В текущем обзоре реквизиты — обычный текст, экспортной стрелки нет. Для длинного состава достаточно текстового «ещё N»; возвращать отдельный переход к разделу пользователь уже решил не делать. |
| U6. «Открыть список» | Отдельная возможность, не обязательное исправление | Проверенный вызов в `EntitySummaryPanel` открывает список ссылающегося типа из строки обратной ссылки. Это не готовое действие списка выбранного root. Такой переход может быть полезен, но частоту использования мы не измеряли. При добавлении нужны реальная доступность списка и штатный навигатор. До отдельного решения не превращать его в третью основную кнопку принятого обзора. |
| U7. Заголовки вкладок | Одно правило для обоих режимов | Общий прикладной helper формирует заголовки просмотра и изменения из одной подписи, с различением режима и доступным кодом/FQCN. В перечень изменений включён `EntityModifyWorkspace`; проверяются одинаковые подписи и ограниченная ширина. |
| U8. Узкая компоновка | Снимки добавлены | Узкий список и узкий обзор добавлены к [набору состояний](mockups/entity-registry-states.md). Container queries полезны для реализации; сама ширина 820 px из карточки не обязана подходить реестру. |
| U9. Недоступная простая сущность | Техническая проблема верна, решение о скрытии отдельно | Причину недоступности нужно читать без hover и с клавиатуры. Пользователь явно включил четвёртый пункт в меню; скрывать его автоматически по рекомендации из файла не следует. Предпочтительный вариант для обсуждения — сохранить пункт с явным доступным пояснением до отдельной реализации генератора. |
| U10. Строка группировки | Небольшое улучшение | Разместить компактное управление в шапке самого списка, без дополнительной полосы на всю ширину. В текущем варианте оно уже находится над деревом; доработка касается плотности этой шапки. |

## 4. Замечания к границам и этапам

| Пункт | Оценка | Решение для предлагаемой редакции |
|---|---|---|
| S1. Вынести рецепт `PLAIN` | План разделён | Создан [отдельный генераторный план](plain-entity-creation-plan.md). Выпуск реестра не зависит от него; четвёртый пункт остаётся с доступным пояснением недоступности до поддерживаемого рецепта. |
| S2. Рефакторинг, флаг, откат | Принять с уточнением | R1/R2 уже разделены. Для R1 требовать сохранения поведения старого экрана и целевых регрессий; новый реестр включать отдельным флагом, например `app.entity-explorer.registry.enabled`. Не использовать для этого существующий `ux-pilot.enabled`, который влияет также на компактные карточки и допуск черновиков. Удаление старого пути выполнять после проверки нового и отдельного завершения периода отката. |
| S3. Имена классов | Принять как соглашение | Новые компоненты называть в существующем семействе: `EntityExplorerRegistryView/State/Model`. Уже работающие классы не переименовывать ради симметрии. |
| S4. Матрица R0 отдельным файлом | Создана | [Матрица входов](entity-registry-entry-matrix.md) содержит entry id, создание/активацию, URL, запись истории, состояние и guard, алгоритм доступа к открытой карточке, закрытие/повторное открытие и ограничение нескольких безадресных вкладок. |

## 5. Что перенесено в редакцию 2 плана

1. Сначала определить состав списка по данным `ExplorerSnapshot`, поведение служебных/owned-типов и неизменность семантической классификации.
2. Сохранить три основных поля и административные условия в дополнительных опциях; явно описать их сброс и индикацию.
3. Зафиксировать создание карточек через `Workspace.open(Class, …)`, независимость состояний и применение явного якоря при повторном входе.
4. Добавить всех потребителей снимка, включая генератор, и разнести адресные сообщения карточки и общую диагностику.
5. Записать матрицу истории и жизненного цикла; дополнить ADR-0010 в соответствующих частях.
6. Вынести создание `PLAIN` из критерия готовности реестра; явно сохранить вопрос четырёх пунктов меню из пользовательского требования.
7. Разделить безопасный рефакторинг, включение нового экрана и последующую очистку старого пути. Новый флаг не меняет существующие правила допуска.
8. Сохранить выбранную компоновку, убрать дубли фактов и избыточный агрегат, закрепить широкий/узкий режимы, пустой результат и активные фильтры как состояния одного эталона.

Дополнительно по второй части замечаний: назван прикладной владелец состояния; refresh включает кеши read-only карточек; правило подписи симметрично для просмотра и изменения; критерий непересечения длинного имени и бейджа на 736 px включён в приёмку. По прямому решению пользователя платформенными становятся повторно используемые панели, их нейтральные состояния/модели и ресурсы, а прикладными — UI-session, защищённые адаптеры, навигация и Workspace-host.

С пунктом второй части «выбранный реестр адресован» есть различие области: это верно для старого совмещённого экрана, но не для принятого здесь нового самостоятельного реестра. Новый контракт явно сохраняет `/` при выборе и назначает URL только отдельной карточке. Само ограничение общего `addresslessEntryId` остаётся в проверках и не объявлено устранённым документацией.

## 6. Проверенные источники и пределы разбора

- [ExplorerTreeModel](../../src/main/java/org/ip/views/admin/ExplorerTreeModel.java): словарь, фильтры, определение служебного типа и обработка неизвестной диагностики.
- [EntityDraftProjectCatalog](../../src/main/java/org/ip/views/admin/EntityDraftProjectCatalog.java): потребление и обновление каталога через `EntityExplorerView`.
- [EntityExplorerNavigation](../../src/main/java/org/ip/views/admin/EntityExplorerNavigation.java), [EntityExplorerView](../../src/main/java/org/ip/views/admin/EntityExplorerView.java): открытие владельца owned-строки и доставка сообщения в карточку.
- [Workspace](../../src/main/java/org/ip/views/workspace/Workspace.java), [WorkspaceManager](../../src/main/java/org/ip/views/workspace/WorkspaceManager.java): создание компонента на entry id и активация уже открытого.
- [FormRouteUrlBridge](../../platform-vaadin/src/main/java/org/ipro/form/host/FormRouteUrlBridge.java): карта адресов, последняя безадресная вкладка и правила записи истории.
- [ADR-0010](../architecture/decisions/ADR-0010-explorer-type-address.md): адреса, владельцы состояния и одна карточка в прежнем контракте.
- [Историческое измерение ET0](entity-types-appdev-first-et0-inventory-evidence.md), [инвентарь](entity-types-appdev-first-et0-inventory.md), [GridFormView](../../src/main/java/org/ip/model/GridFormView.java): ограничения чисел baseline и недопустимость классифицировать тип по имени.
- [EntitySummaryPanel](../../src/main/java/org/ip/views/admin/EntitySummaryPanel.java): действие открытия списка из обратной ссылки.

Это проверка текста, исходников и сохранённых артефактов. Приложение и тесты исполнения для этого разбора не запускались; актуальное количество типов и поведение нескольких безадресных вкладок требуют соответствующей проверки при подготовке матрицы.
