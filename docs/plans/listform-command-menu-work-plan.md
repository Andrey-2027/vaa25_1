# Меню команд ListForm и SelectionForm: детальный план работ

Дата: 07.11.2026, Europe/Moscow. Статус: **план уточнён по «Замечаниям1» и «Замечаниям2» и поручению владельца; согласованные умолчания сохранены; реализация не начата**.
Основание: [предварительная сверка](listform-command-menu-precheck.md), последние указания владельца по составу меню и поручение составить детальный план. При составлении HEAD — `8b0d9f36`; в рабочем дереве есть отдельные изменения автоформ/генератора. Перед реализацией повторно сверить затрагиваемые файлы.

## 1. Результат и границы

Результат для пользователя — одна компактная панель с предсказуемым переполнением в полное «Ещё». Команды и настройки списка сгруппированы; служебные инструменты находятся в подменю. Пользовательский режим компактности ListForm удалён.

Результат для прикладника — умолчания работают без кода; в конфигурации формы можно независимо задать состав команд, состав панели, вид кнопок и порядок. Требования и исполнители действий повторно не объявляются. Старые публичные входы сохраняются.

Входит: общий рендерер команд, настройки формы, все выявленные источники команд ListForm, общий механизм меню настроек для SelectionForm, совместимость, целевые и визуальные проверки. Интеграция настоящего ListForm выполняется в CM3, **после готовности общей части CM1–CM2**, и относится к реализации.

Не входит: новые права или операции данных, изменение запросов и загрузки, новый механизм печати, мультивыделение, контекстное меню строк, горячие клавиши предметных действий, перенос в заголовок Workspace, встроенные списки AF6, переделка карточек и Explorer. Существующие Tab/Enter/Esc и стрелки меню сохраняются. Настройки команд не записываются в пользовательские сохранённые виды.

## 2. Зафиксированные умолчания

Полное «Ещё» содержит включённые в данную форму применимые команды. Временно недоступные команды остаются отключёнными с причиной; неприменимые и исключённые из состава не показываются. Иконка на панели всегда имеет доступное имя и tooltip; в меню есть текстовая подпись.

| Команда / ключ | Панель | «Ещё» |
| --- | --- | --- |
| Создать — `crud.create` | Иконка и подпись, основной акцент | Рабочие команды |
| Копировать — `crud.copy` | Иконка | Рабочие команды |
| Изменить — `crud.edit` | Иконка и подпись | Рабочие команды |
| Просмотр — `crud.open` | Нет | Рабочие команды |
| Удалить — `crud.delete` | Нет | Рабочие команды |
| Обновить — `crud.refresh` | Иконка | Рабочие команды |
| Виды — `ui.list.views` | Иконка | Рабочие команды |
| Печать — `report.print` | Иконка и подпись | Рабочие команды; при наличии модуля/объявления |
| Изменить ключ записи — `change-register-key` | Иконка и подпись | Рабочие команды формы регистра |
| Общий поиск — `ui.list.quick-search` | Нет | Настройки, включаемый пункт |
| Условия — `ui.list.conditions` | Нет | Настройки; по возможностям грида |
| Условное форматирование — `ui.list.formatting` | Нет | Настройки |
| Группировка — `ui.list.grouping` | Нет | Настройки; обычный пункт без галочки, по возможностям грида |
| Скопировать ссылку — `crud.copy_link` | Нет | Служебные |
| Разработка — `ui.list.development` | Нет | Служебные → Разработка → существующие инструменты |
| Компактный вид | Удалён | Удалён |

Рабочая последовательность панели: Создать → Копировать → Изменить → Изменить ключ записи (если есть) → Виды → Печать (если есть) → Обновить → остальные объявленные действия → Ещё. Это техническое умолчание плана, переопределяемое формой. Остальные объявленные действия по умолчанию сохраняют вывод на панель с подписью и в полное меню **после основных команд**, поэтому при сужении сворачиваются первыми; их взаимный порядок — существующий `ActionDefinition.order`, затем ActionId. Сохранение такого default — осознанный компромисс совместимости. Форма может явно ограничить состав панели. Итоговое размещение и порядок задаются данными, а не временем регистрации.

В «Ещё» рабочие команды, настройки и служебное подменю разделены визуально. Порядок меню не меняется при изменении ширины. Пустые группы и разделители не показываются. Служебные команды не дублируются отдельной строкой над формой.

Переполнение: убирать кнопки панели справа налево, сохранять префикс установленного порядка, возвращать слева направо при расширении. Кнопка «Ещё» остаётся доступной; второй строки штатных команд и второго overflow-меню нет. Поле/панель отборов и режим истории/среза регистра остаются вне переполнения команд.

## 3. Технические решения для реализации

### 3.1. Настройки принадлежат форме

Выбран вариант отдельного описания настроек формы. **Публичный record ActionDefinition не меняется**, placement в него не добавляется. Существующие ActionId, ActionSurface, требования, provenance, фабрики и исполнители сохраняются. Так прикладное размещение переопределяется без новых бинов действий и без изменения конструктора, используемого ReportPrintAction.

Проектируемые типы в `platform-vaadin`:

- `org.ipro.form.builder.ListCommandLayout` — неизменяемое описание с Builder, режимами состава/панели и переопределениями представления; APP_API.
- `org.ipro.form.builder.ListUiCommand` — типизированные ключи штатных UI-команд из таблицы §2; APP_API. Используется существующий ActionId, но UI-команды не становятся обязательными Spring-бинами и не получают фиктивных требований прав.
- `org.ipro.form.CommandBar` и её модель зарегистрированной команды — INTERNAL. Класс не возвращается из публичного `getToolbar()` и не становится обязательным прикладным входом.
- Внутренние адаптеры соединяют стандартные/объявленные действия, состояния грида и служебные операции с рендерером. У них нет второй формулы прав.

Проектируемые входы: `ListFormVariants.commands(Consumer<ListCommandLayout.Builder>)` для default, `commands(String variant, Consumer<ListCommandLayout.Builder>)` для именованного варианта; default-метод `FormTypeCustomization.configureListCommands(Class<?> type, ListCommandLayout.Builder commands)` для семейства; `ListForm.configureCommands(Consumer<ListCommandLayout.Builder>)` для экземпляра, включая прямое создание и составной host. Существующий `ListForm.addAction(ActionHandler)` остаётся входом объявления/исполнения. Ниже зафиксирован эскиз APP_API до CM1; при реализации он получает javadoc и компилируемые примеры, а не проектируется заново по ходу рендера.

Ссылки на необязательные предметные команды задаются по ActionId. Новый код platform-vaadin не импортирует классы platform-report-vaadin/platform-register-vaadin и не создаёт обратной зависимости этих модулей. Специфические настройки семейства задаются через family-hook.

### 3.1.1. Эскиз API настроек

У Builder начальное состояние всех свойств — INHERIT. `build()` возвращает неизменяемое описание. Consumer-вход изменяет слой соответствующего источника, а не общий изменяемый Builder всех форм.

| Вход Builder | Семантика |
| --- | --- |
| `inheritCommands()` / `allCommands()` | Унаследовать состав / явно выбрать AUTO |
| `commands(ActionId... ids)` | EXPLICIT со строгими статическими ссылками; пустой массив означает явно пустой состав |
| `commandRefs(ListCommandLayout.Ref... refs)` | EXPLICIT со строгими, необязательными или локальными ссылками |
| `inheritPanel()` / `defaultPanel()` / `allOnPanel()` | Унаследовать режим панели / вернуть платформенные правила панели для текущего состава / вывести все рабочие команды |
| `panel(ActionId... ids)` / `panelRefs(Ref... refs)` | Явный перечень панели; пустой перечень оставляет включённые команды в «Ещё» |
| `command(ActionId id)` / `command(Ref ref)` | Переопределения одной команды: `iconOnly()`, `iconAndText()`, `onPanel()`, `inMore()`, `order(int)`, `included(boolean)`; приоритет слоя сохраняется |
| `exclude(ActionId... ids)` / `include(ActionId... ids)` | Переопределить включение отдельных известных команд на данном слое, не превращая AUTO в EXPLICIT; для локальной/optional-ссылки — `command(ref).included(...)` |

Вложенный `ListCommandLayout.Ref` имеет фабрики `required(ActionId)`, `optional(ActionId)`, `local(ActionId)`. Это намерение проверки ссылки, а не новое требование прав. Штатный UI передаёт `ListUiCommand.*.id()`, CRUD — `CrudAction.*.id()`. `report.print` и `change-register-key` **не становятся** значениями ListUiCommand: первый — ключ другого модуля, второй — семейное локальное действие.

`null` вместо Consumer, variant у variant-overload, массива, элемента, Ref или ActionId — ошибка конфигурации; для default есть отдельный overload без variant. Отсутствие вызова означает INHERIT; пустой перечень не означает ни null, ни AUTO. Переопределения отдельных команд сливаются по свойствам; `inheritCommands()` меняет только режим состава, а `included(...)` остаётся независимым свойством и переопределяется более конкретным слоем.

Эскиз использования, подлежащий компиляции в CM1:

```java
variants.commands(c -> {
    c.allCommands();
    c.panel(CrudAction.CREATE.id(), CrudAction.COPY.id(), ListUiCommand.VIEWS.id());
    c.command(CrudAction.COPY.id()).iconOnly();
});
variants.commands("journal", c -> {
    c.commandRefs(ListCommandLayout.Ref.required(CrudAction.CREATE.id()),
        ListCommandLayout.Ref.optional(ActionId.of("report.print")),
        ListCommandLayout.Ref.local(ActionId.of("materials")));
    c.panelRefs(ListCommandLayout.Ref.required(CrudAction.CREATE.id()),
        ListCommandLayout.Ref.optional(ActionId.of("report.print")));
});
```

### 3.2. Независимые настройки и приоритеты

| Настройка | Режимы / правило |
| --- | --- |
| Состав | INHERIT / AUTO / EXPLICIT. INHERIT не меняет нижний слой; AUTO отменяет унаследованный явный перечень; EXPLICIT задаёт свой перечень, включая явно пустой |
| Панель | INHERIT / DEFAULT / ALL / EXPLICIT. В EXPLICIT остальные включённые команды остаются в «Ещё» |
| Вид | Иконка или иконка с подписью; настройка не замораживает состав |
| Порядок и группа | Явная последовательность/переопределения порядка; прочие команды упорядочены детерминированно; меню отделяет рабочие, настройки и служебные |

Приоритет: платформа → семейство → default-конфигурация сущности → именованный вариант → экземпляр/место использования. Переопределяются только явно заданные свойства. Перечни EXPLICIT заменяют унаследованный перечень, не объединяются с ним. Явный состав не расширяется новыми действиями; автоматический расширяется с учётом отдельных included-правил. Вызов Resolver не затирает настройку, уже заданную фабрикой экземпляра.

«Все на панели» относится к рабочим исполняемым командам. Настройки и служебные команды сохраняют свою группу, если форма явно не задаёт им другое место. Структурные подменю не превращаются автоматически в кнопки. Исключение из состава убирает команду и с панели, и из «Ещё»; это настройка UI, не изменение серверных полномочий.

Настройки и окончательный состав проверяются по стабильным ключам; дубли и конфликтующие правила дают адресную ошибку с сущностью/вариантом/источником. Различаются три вида ссылок:

- REQUIRED: известный статический UI-ключ или действие реестра данной поверхности/типа/варианта; проверяется при старте без построения UI. Неизвестный ключ — ошибка, а не молчаливое исчезновение.
- OPTIONAL: отсутствие действия допустимо, например report.print без модуля печати. Наличие необязательности задаётся явно в конфигурации; универсального «игнорировать все неизвестные ключи» нет. Если действие появится, для него действуют обычные решения прав и настройки.
- LOCAL: синтаксис и конфликты проверяются сразу, разрешение откладывается до завершения композиции данного открытия. Ссылка может находиться в конфигурации до `addAction`, включая добавление после возврата `createListForm`.

Конечная граница LOCAL — `UI.beforeClientResponse` перед первым ответом, показывающим форму, после attach и регистрации локальных действий текущего цикла. До неё ссылка находится в pending и не создаёт ложную кнопку. На границе неразрешённый обязательный локальный ключ даёт адресную ошибку. Для показанного экземпляра изменения проверяются перед следующим ответом: configure/addAction в одном цикле допустимы, бесконечное ожидание регистрации между ответами не допускается. При необходимости отсутствия команды до произвольного будущего момента используется явная OPTIONAL-ссылка. Копирование состояния открытия не обходит эту проверку.

Платформенные умолчания для optional-модуля не требуют наличия его объявления. Ссылка REQUIRED из прикладной конфигурации — требует. Эти случаи не смешиваются.

### 3.3. Состояние и исполнение

Рендерер получает для команды ключ, подпись, иконку, представление, текущее решение/состояние и делегат исполнения. Решение вычисляется один раз на обновление и применяется к кнопке и меню. Checked-состояние поиска и других включаемых настроек читается из актуального грида/формы, в том числе после применения вида. Группировка — обычный пункт без checked-состояния.

Направление синхронизации одно: настройки/решение команды → Button и MenuItem. Стандартные Button-геттеры поддерживают инспекцию и программный click. Прямые setVisible/setEnabled/setText/setIcon этих Button не являются способом конфигурации команды, не зеркалятся автоматически в меню и могут быть перезаписаны штатным обновлением. Для согласованного изменения используется API команды/формы. Это явное ограничение поведенческой совместимости, отражаемое в release notes; произвольный перехват мутаций Button, двусторонние observers и polling не входят в задачу. Прикладные компоненты в дополнительной области остаются обычными Vaadin-компонентами с обычными setter-ами.

Позднее добавление команды до/после ActionResolver поддерживается. Компоненты и состояние разных открытий не разделяются. Изменение выделения/прав/контекста обновляет состояния без пересоздания всей формы. Само клиентское скрытие кнопки по ширине не меняет `ActionDecision.visible`.

Кнопка, пункт меню и программный `getDeleteButton().click()` вызывают один путь исполнения с повторной проверкой текущего решения, принадлежности команды составу формы и актуального выделения/контекста. **Исключённая команда через эту форму не исполняется**, в том числе через устаревший MenuItem или программный click; исполнение отклоняется с объяснимой причиной NOT_APPLICABLE. Серверные полномочия этим не изменяются: другой разрешённый host или серверный API применяет свои прежние проверки. Сохраняются generic host-gate readOnly и отдельные требования/availability объявленных действий. Просмотр остаётся самостоятельным действием; двойной щелчок сохраняет существующий выбор между изменением и чтением.

### 3.4. Совместимость

- Сохраняются точные сигнатуры конструкторов ListForm/SelectionForm, `getToolbar(): HorizontalLayout`, публичных геттеров CRUD-кнопок, `installMoreMenu(): void`, `addAction()` и `FilterGridMoreMenu.create()`.
- `getToolbar()` предоставляет дополнительную область совместимости ниже основной строки, до отборов/грида. Пустая область не занимает место. Поддерживаются поздние add/remove, произвольный Span, поле или Button; автоматических пунктов меню для них нет.
- CRUD-геттеры связаны с реальными командами и сохраняют программный `.click()`. Если команда размещена только в меню, её Button-совместимость не создаёт скрытый обход проверки. Прямые мутации этих Button не входят в договор синхронизации (§3.3); новый постоянный override прав не вводится.
- Вложенность toolbar меняется. Поиск стандартных кнопок через `getToolbar().getChildren()` не сохраняется как контракт. Такие тесты переводятся на семантические проверки без ослабления проверок прав/исполнения.
- `installMoreMenu()` остаётся идемпотентным входом совместимости. Внутренний spacer/anchor и лишний вызов координатора могут быть удалены.
- Ключи видов, отборы, данные, ActionSurface и public ActionDefinition сохраняются. ItemForm использует прежние affordance и поведение.

Договор операций старого toolbar:

| Операция | Поведение после переноса |
| --- | --- |
| `add` / `remove` прикладного Component | Добавить/удалить компонент дополнительной области; обычные правила родителя Vaadin сохраняются |
| `remove(form.getDeleteButton())` и другие штатные CRUD-геттеры | Через адаптер сопоставить объект Button с ключом команды и установить included=false на слое экземпляра; убрать из панели и меню, запретить click через форму. AUTO не превращать в замороженный EXPLICIT |
| `remove(Component...)` / `remove(Collection)` смешанного набора | Сначала проверить весь набор, затем применить удаление; не оставить частично изменённое состояние при ошибке родителя |
| `removeAll()` | Очистить только дополнительную область. Для отключения всех команд используется явный пустой состав `commands()` |
| `addComponentAtIndex`, `indexOf`, `getChildren` | Индексы и обход только дополнительной области. Управлять порядком основной панели через них нельзя; штатные команды настраиваются через configureCommands |

Адаптер работает по идентичности штатной Button, не по подписи. Чужая кнопка другой формы не исключает одноимённую команду. Договор не обещает прежнего плоского DOM или полного поведения HorizontalLayout как главной панели; это изменение семантики явно отмечается в release notes и проверяется в consumer, наряду с бинарной совместимостью.

Компактность удаляется из ListForm полностью: команда, переключение, чтение/запись `filtergrid.compact*`, восстановление по старому ключу и относящийся только к режиму обход компонентов. Старые ключи остаются неиспользуемыми; массовой очистки хранилища нет. Библиотечный `FilterGrid.setCompact()` и его сторонние потребители не удаляются. Новый список использует обычный вид, остальные настройки сохраняются.

## 4. Порядок и контрольные точки

## 9. Визуальная приёмка и критерий завершения

- Обычный список и регистр: 1280×900 и 760×900; диалог выбора 700 px и ширина, ограниченная viewport. Нет второй строки штатных команд, «Ещё» доступно, поповер не обрезан.
- Совпадают подписи/иконки/состояния команды в обоих представлениях при обновлении через поддерживаемую модель. Иконочные кнопки объяснимы без знания кода. Причину disabled можно узнать, открыв меню с клавиатуры: через проверенный штатный focus/tooltip либо fallback с причиной в тексте/доступном описании пункта (CM0.4). Один недоступный hover-tooltip не закрывает критерий.
- Сужение/расширение, шрифты, длинный перевод/подпись, масштаб 125%/150%, скрытая вкладка, повторное открытие не теряют команды и фокус. При фокусе на скрываемой кнопке переход на «Ещё» предсказуем.
- Меню всегда полное для состава формы. Служебные операции только в соответствующем подменю; при отсутствии доступных инструментов пустой контейнер не виден.
- Область совместимости не занимает места, когда пуста; непустая расположена под основной панелью и не ломает отборы/грид.
- Просмотр, печать и ключ регистра выполняют прежние операции с прежним контекстом. Пользовательский режим компактности отсутствует и не включается старой настройкой.
- Изменённые экраны соответствуют §3.2 плана автоформ: единообразие Lumo, компактность, понятные состояния и клавиатура. Приложить снимки и отмеченный чек-лист; приёмку владельца учитывать отдельно от проверки исполнителя.

**Готово (КМ3):** выполнены CM0–CM6 и матрица §8, проверены все семь источников команд и оба host-а, нет новых ошибок совместимости/поставки, визуальные критерии приняты. Оставшийся несвязанный дрейф и ограничения перечислены; полный прогон не заявлен выполненным. Простое совпадение макета или успешная работа demo не заменяет этот критерий.
