# platform-contracts

Первый extraction slice этапа D2: стабильный слой контрактов платформы, вынесенный
в отдельный Maven-проект.

## Что здесь лежит

`org.ipro.metadata.annotation` — 12 типов (7 аннотаций и 5 enum'ов), которые читают
и приложение, и платформенные реализации. У этих типов **ноль внешних зависимостей**:
только `java.lang.annotation`, поэтому слой собирается сам по себе, без Spring, JPA
и Vaadin.

## Зачем отдельный проект

D1 зафиксировал границу картой и исполняемыми правилами. D2 делает её физической:
приложение больше не содержит этих типов в своём дереве исходников и получает их как
зависимость. Граница обеспечена не договорённостью, а сборкой — у модуля нет и не может
быть класса приложения на пути компиляции.

Пакеты сохранены намеренно (`org.ipro.metadata.annotation`): режется **тип**, а не
пакет, поэтому перенос не потребовал ни одной правки в коде. Разделение пакета между
модулями в этом проекте уже существует (`org.ipro.crud` и `crudui-core`).

## Сборка и потребление

```bash
mvn -o -f platform-contracts/pom.xml clean install   # артефакт в локальный репозиторий
mvn -o verify                                        # приложение потребляет его как зависимость
```

Порядок важен: `mvn verify` в корне артефакт не собирает, он его потребляет — так же, как
уже потребляются `filtergrid-*` и `crudui-core`. Проект зарегистрирован в манифесте
воркспейса `scripts/local-dependencies.json`, поэтому бутстрап-скрипт собирает его
до сборки приложения.

## Что сюда не попадает

- платформенные реализации (metadata resolver, executors, telemetry — это не контракт);
- всё, что знает имя прикладного пакета `org.ip` (это единственное жёсткое правило D1);
- типы, нужные только одной стороне: контракт — это то, на что опираются обе.

Добавление типа в этот модуль — отдельное решение (политика D1 §6.3), а не следствие
удобства: случайное попадание реализации в публичную поверхность считается дефектом.
