# platform-contracts

Первый extraction slice этапа D2: стабильный слой контрактов платформы, вынесенный
в отдельный Maven-проект.

## Что здесь лежит

34 типа, у каждого — обе стороны: и приложение, и платформенные реализации.

| Пакет | Типы | Что это |
|---|---|---|
| `org.ipro.metadata.annotation` | 12 | декларации метаданных (7 аннотаций, 5 enum'ов) |
| `org.ipro.lifecycle` | 6 | SPI lifecycle: `EntityLifecycle<T>` и контексты save/update/delete/aggregate |
| `org.ipro.events` | 10 | контракты событий жизненного цикла и `EventContext` |
| `org.ipro.data` | 5 | нейтральные identifiers и декларации (`DataOperation`, `SearchFields`, exposure/capability overrides) |
| `org.ipro.fetch.plan` | 1 | `FetchScenario` — часть ключа FetchPlan |

Ни один из этих типов не знает Spring, JPA и Vaadin. Внешние зависимости модуля — ровно две,
и обе объявлены в `pom.xml`:

- `org.slf4j:slf4j-api` — внешний API-артефакт (`EventContext` читает `traceId` из MDC);
- `org.ipro.crudui:crudui-core` — нейтральный identifier `org.ipro.crud.IdentifiableEntity`,
  уже опубликованный в другом платформенном артефакте. `crudui-core` объявляет Vaadin как
  `provided`, поэтому UI в потребителей контрактов не течёт.

Набор зависимостей и состав типов — reviewed: их сравнивает с зафиксированными списками
`PlatformContractsModuleTest`, поэтому новая зависимость здесь не может появиться «по пути».

## Зачем отдельный проект

D1 зафиксировал границу картой и исполняемыми правилами. D2 делает её физической:
приложение больше не содержит этих типов в своём дереве исходников и получает их как
зависимость. Граница обеспечена не договорённостью, а сборкой — у модуля нет и не может
быть класса приложения на пути компиляции.

Пакеты сохранены намеренно: режется **тип**, а не пакет, поэтому ни один из срезов не
потребовал правок в коде. Плата за это — разделённые пакеты: сейчас их два
(`org.ipro.data`, `org.ipro.fetch.plan`). Список зафиксирован в тесте и только сокращается:
`org.ipro.events` и `org.ipro.lifecycle` были разделены после срез 2, а после срез 3 ушли
целиком — SPI остался здесь, а runtime уехал в `platform-events`.

`IdentifiableEntity` тоже должен жить здесь, но он опубликован в другом репозитории
(`crudui`), поэтому пока остаётся объявленной зависимостью.

## Сборка и потребление

```bash
mvn -o -f platform-contracts/pom.xml clean install   # артефакт в локальный репозиторий
mvn -o verify                                        # приложение потребляет его как зависимость
```

Порядок важен: `mvn verify` в корне артефакт не собирает, он его потребляет — так же, как
уже потребляются `filtergrid-*` и `crudui-core`. Проект зарегистрирован в манифесте
воркспейса `scripts/local-dependencies.json`, поэтому бутстрап-скрипт собирает его
до сборки приложения.

## Где runtime

Исполнение контура (`EntityEventPublisher`, `EntityLifecycleRegistry`, их авто-конфигурация) —
в соседнем артефакте `platform-events`, который зависит на этот модуль. Направление
`runtime → contracts` одностороннее: контракты о runtime не знают.

## Что сюда не попадает

- платформенные реализации (metadata resolver, executors, telemetry — это не контракт);
- всё, что знает имя прикладного пакета `org.ip` (это единственное жёсткое правило D1);
- типы, нужные только одной стороне: контракт — это то, на что опираются обе.

Добавление типа в этот модуль — отдельное решение (политика D1 §6.3), а не следствие
удобства: случайное попадание реализации в публичную поверхность считается дефектом.
