# IG0 baseline review: MetadataDrivenAggregateSaveService is the supported atomic command API
# used by application save services; AggregateSaveContribution is their payload SPI.
# Participant dispatch and rollback implementation remain platform-owned.
# D3.3: семантическая классификация production-типов platform-core (FQN -> базовая роль).
#
# Формат: <role> <fqn>  и отдельно  test-usage <fqn> <файлы тестов приложения>
# Роли (ровно одна на production-тип): APP_API | APP_SPI | MODULE_API | INTERNAL
#   APP_API     — поддерживаемый API: приложение называет тип либо платформа явно экспортирует
#                 его для внешних приложений (ET4 Standard*); использования в host-модели не требуется.
#   APP_SPI     — приложение реализует или расширяет тип; платформа вызывает обратно.
#   MODULE_API  — контракт между platform-модулями: production-код будущих autoconfigure/Vaadin/
#                 report-модулей (сегодня это платформенные классы, ещё лежащие в дереве).
#   INTERNAL    — реализация без compatibility promise: менять и удалять можно свободно.
#
# Зачем второй реестр. D1-реестр (`platform-public-surface.txt`) описывает только потребление
# приложением. Тип, который приложение не называет, не получал никакой роли: обещание «internal
# можно менять свободно» нельзя было проверить, а 44 типа, образующих контракт между модулями,
# не были зафиксированы вовсе. Здесь роль есть у каждого из 108 production-типов, и полнота
# проверяется тестом `PlatformCoreSurfaceTest`, а не глазами. Бюджет разделов (32/4/43/16)
# сверяется с числом записей под заголовком: расхождение — ошибка сборки, а не тема для
# комментария. 92 -> 94 — D3.5.1: `EntityLookup` и `EntityServiceResolver` (APP_API 28 -> 30).
# 94 -> 95 — E3.2.0 шаг 2: `FetchPlanInspection` (MODULE_API 43 -> 44) — владелец плана
# публикует сценарии и пути наружу, потому что `FetchPlan` в этом реестре INTERNAL.
# 95 -> 95 — E3.2.0 шаг 5.1: `FacetKind` MODULE_API -> APP_API (APP_API 31 -> 32, MODULE_API
# 44 -> 43): карточка рисует строки фактов аспектов и делит их по видам факта, а вид строки
# возвращает `FacetRow.kind()`. Роль MODULE_API расходилась с употреблением так же, как раньше у
# `ResolvedValue`: соседние типы того же словаря (`FactSource`, `ResolvedValue`) уже APP_API.
# 109 -> 109 — D-R S4: `EntityReadAccess` и `EntityPresentationService` APP_API -> MODULE_API
# (APP_API 36 -> 34, MODULE_API 51 -> 53). Роль APP_API держалась на одном прикладном файле —
# адаптере форм стандартного интерфейса регистра: показ регистратора читал пачками через
# fixed-graph границу, а подписи собирал `EntityPresentationService`. Файл уехал в
# platform-register-vaadin, поэтому оба типа — по правилу 3 контракт между модулями: их
# называет production-код платформенных модулей (UI-адаптер регистра, form-слой, reportstudio —
# платформенный код, всё ещё лежащий в дереве приложения), а прикладной main — нет. Бюджет API
# от этого сократился, а не вырос; D1-реестр снял свои записи по той же причине.
# 109 -> 111 — S5(б) плана выноса (ADR-0026): `AggregateCommandPayload` (APP_API 34 -> 35) —
# объявление payload'а команды, который читают lifecycle-хуки её сущности (`beforeSave` — вето,
# `onSave` — генерация строк); `CallbackScope` (INTERNAL 16 -> 17) — общая дисциплина
# callback-scope'ов crud-пути: package-private механизм, у которого нет compatibility promise,
# потому что приложение пользуется только операциями конкретных scope'ов, а не базой.
# 111 -> 114 — ET2 (2026-10-23): `StructuralAttribute` (APP_API 35 -> 36),
# `JpaFieldFacts` (MODULE_API 53 -> 54), `StructuralAttributeScanner` (INTERNAL 17 -> 18).
# Число production-типов в шапке (108 -> 109) — не рост: полнота проверяется тестом
# `everyCoreProductionTypeHasExactlyOneReviewedRole`, который сверяет реестр с исходниками
# platform-core в обе стороны, и 114 — то, что он измеряет сейчас.
#
# Роли — reviewed-решение, а не вывод теста: если бы список строил сам тест, проверялось бы то же
# правило, которым он построен. Черновик воспроизводится скриптом
# `node scripts/analyze-platform-surface.mjs --core-registry`, решения по спорным типам записаны
# ниже явно.
#
# Правила классификации (в порядке применения):
#   1. D1-роль API -> APP_API, SPI -> APP_SPI: текущие роли сохраняются.
#   2. Явные решения по спорным типам — см. ниже.
#   3. Тип, который называет production-код будущих autoconfigure/Vaadin/report-модулей -> MODULE_API.
#   4. Остальные -> INTERNAL.
#   5. Public nested type наследует роль owner-типа, если для него нет отдельной записи.
#   6. Каждый новый production-тип обязан получить роль сразу — полнота проверяется тестом.
#
# Явные решения (механически не выводятся):
#   NaturalKeyCreateSupport -> APP_API: generic механизм, намеренно используемый прикладными
#       interned use cases. Роль legacy-internal не сходилась с употреблением.
#   EntityDataAccess -> APP_API (значит, и его сигнатура входит в API closure).
#   ResolvedValue -> APP_API: карточка Explorer показывает происхождение факта, а значение
#       приходит этим типом из опубликованной `EntitySummary` (platform-vaadin). Прежняя роль
#       MODULE_API расходилась с D1-реестром и была устаревшим решением: приложение называет
#       тип, а его собственный компонент `source` (`FactSource`) уже APP_API. Правило 1.
#       Шаг 5 E3.1 сделал происхождение видимым — вместе с ним видимой стала и эта граница.
#   FacetKind -> APP_API: карточка делит строки аспекта по видам факта (объявление/исполнитель,
#       сценарий/путь, измерение/правило), поэтому называет сам словарь видов. Прежняя роль
#       MODULE_API расходилась с употреблением: вид строки возвращает публичный `FacetRow.kind()`
#       из APP_API-типа `EntitySummary`. Роль SPI не подходит — это словарь, который карточка
#       читает, а не механизм, который она подстраивает. Правило 1.
#   LookupService, ServiceLocator -> MODULE_API: контракт между core и будущим form/vaadin-слоем.
#       Приложение называет их напрямую — это фиксирует legacy-запись D1-реестра, а не роль.
#   JpaGlobalSearchProvider -> INTERNAL: реализация registry по умолчанию, выбирать её явно
#       приложение не должно (временная legacy-ссылка в D1-реестре).
#   CurrentUser -> удалён до D3.4 (§4 плана): единственный platform-потребитель
#       (CanonicalReadExecutor) получает RlsCurrentUser через конструктор, прикладные потребители
#       — Spring-бин RlsCurrentUser (SecurityRlsUser) или прямой чтением SecurityContext.
#
# Отклонение от механического среза ревью. Срез предполагал, что 13 типов, названных только
# тестами приложения, останутся INTERNAL. Замер по production-источникам показал другое: 12 из них
# называет production-код metadata/data/fetch-конфигураций и form/reportstudio-слоя, то есть по
# правилу 3 они MODULE_API. Legacy-доступ от этого не меняется: приложение (main) их не называет,
# а ссылки тестов заморожены отдельной записью test-usage и не превращают типы в API.
#
# test-usage overlay — ортогональная запись, а не пятая роль: тип может быть MODULE_API и
# одновременно иметь замороженные ссылки из тестов приложения. Список только сокращается: снятая
# ссылка обязана исчезнуть из реестра, новая ломает сборку.
#
# ET4: Standard* bases are explicit external APP_API exports. TableSectionService and
# EntityDescriptorCatalog are host application API; their previous MODULE_API role was stale.
