# D3.5.0: семантическая классификация production-типов будущего модуля platform-vaadin.
#
# Формат: <role> <fqn>
# Роли (ровно одна на production-тип): APP_API | APP_SPI | MODULE_API | INTERNAL
#   APP_API    — поддерживаемый API приложения: приложение называет тип, платформа не наследует.
#   APP_SPI    — приложение реализует или расширяет тип; платформа вызывает обратно.
#   MODULE_API — контракт между platform-модулями (wiring модуля и будущий report-модуль),
#                а также тип, публично видимый через сигнатуру API приложения: приложение его
#                не называет сам, но менять его свободно уже нельзя (D3.5.8).
#   INTERNAL   — реализация без compatibility promise: менять и удалять можно свободно.
#
# Зачем реестр появился до самого модуля. Порядок «сначала перенести 83 public-класса, потом
# разобраться» уже был опробован в D3.3 и дал `TEMPORARY_ALL_PUBLIC`: состав зафиксирован,
# а решения о том, что именно является контрактом, не принято ни по одному типу. Здесь роли
# назначаются до физического переноса, поэтому переезд не зацементирует текущую поверхность.
#
# Замер до изменений (D3.5.0): 90 production-типов — `org.ipro.form` 80, `org.ipro.vaadin` 7,
# `org.ip.telemetry.vaadin` 3. D3.5.4 (физический перенос): три telemetry-типа переехали
# в модуль со сменой пакета — `org.ip.telemetry.vaadin` → `org.ipro.vaadin.telemetry`
# (пакет приложения в платформенном артефакте — нарушение границы, а не деталь адресации);
# FQN в реестре обновлены, роли и бюджеты не изменились.
# D3.5.1: +`org.ipro.form.coordinator.FormNavigator` (APP_API) —
# 91 тип. D3.5.2: +`org.ipro.form.LookupComboHelper` — 92 типа. D3.5.2b: +`org.ipro.form.FilterLookupOptions`
# (INTERNAL) — 93 типа. D3.5.3: `LookupComboHelper`
# повышен с INTERNAL до APP_API — прикладные конфиги полей намеренно используют его лимиты и
# autocomplete-хелпер, а INTERNAL-роль противоречила употреблению. Число типов не меняется,
# бюджет — меняется.
# D3.5.8: API closure измерен впервые — 14 из 42 типов APP_API/APP_SPI отдавали наружу
# INTERNAL-тип (24 публичных члена, 12 различных типов: словарь DSL и wiring формы). Роли
# приведены в соответствие с сигнатурами: эти 12 типов переведены INTERNAL -> MODULE_API,
# потому что приложение их не называет (в D1-реестре ни одной такой строки, в `src/main`
# приложения — ноль ссылок), но и свободными к изменению они уже не являются: прикладные
# конфиги передают в них лямбды, то есть компилируются против этих сигнатур.
# E1.1: +11 INTERNAL-типов (`org.ipro.form.action.*`) — контракт действия, чистое решение,
# реестр с ключом (surface, entityType, variant, actionId) и переходный адаптер `ListCommand`.
# App-facing SPI ещё не объявлен, поэтому роли не повышаются: promotion до APP_SPI и обновление
# `.api` baseline выполняются вместе с первым потребителем в приложении (E1.6).
# E1.7: −4 типа легаси-команд (`ListCommand`, `ListCommandContext`, `ListCommandRegistry`,
# `ListCommandActionAdapter`). Адаптер был переходным и потребителя не получил; реестр команд
# и его контекст держали вторую формулу доступности в UI (`isEnabled`/предикат), которую
# вытеснило решение (E1.3–E1.6).
# E1.2a: +1 INTERNAL-тип (`ActionContextProvider`) — провайдер входов решения: capability из
# `EntityDescriptorCatalog` и права из `RlsUiGate`. Потребителя пока нет (граница среза), рóли
# остаются INTERNAL: app-facing контракт появляется вместе с фактическим употреблением (E1.3).
# E1.3: ListForm стал потребителем машины действий, поэтому два её типа — `ActionResolver`
# (передан в публичный сеттер формы) и `ActionDecision` (его возвращаемый тип) — повышены
# INTERNAL -> MODULE_API по правилу раздела MODULE_API: они видны через сигнатуру APP_API-типа,
# значит свободно меняться больше не могут. App-facing роль по-прежнему не присваивается:
# приложение действий не объявляет, promotion до APP_SPI ждёт D3.9/E1.6.
# E1.5: +1 MODULE_API-тип (`ReadOnlyReason`) — типизированная причина режима просмотра. Он виден
# через сигнатуру APP_SPI-типа `ItemForm` (`setReadOnly(ReadOnlyReason)`, `readOnlyReason()`),
# поэтому правило MODULE_API, а не INTERNAL. Состав INTERNAL не менялся: карточка перешла на
# уже объявленные `ActionDecision`/`ActionResolver`, а `Savable` получил однострочный default
# `isReadOnly()` — Workspace по нему не предлагает закрытие с сохранением в режиме просмотра.
# E2.1: +2 типа — `CopyLinkButton` (APP_API: app-facing affordance «скопировать ссылку»,
# которым прикладное представление может воспользоваться так же, как список и карточка) и
# `ItemFormLinkAffordance` (INTERNAL: один код встраивания кнопки в подвал карточки для диалога и
# для вкладки Workspace — адрес не должен зависеть от того, каким путём открыли запись).
# E2.1: +1 INTERNAL-тип (`RouteLinkability`) — вход решения «построима ли ссылка на форму».
# Роль INTERNAL, а не APP_API: тип стоит в сигнатуре `ActionContext.linkability()`, а сам
# `ActionContext` — INTERNAL (правило 7 не срабатывает: публичной сигнатуры APP_API/APP_SPI он не
# касается). Приложение адресный вход не собирает — его привязывает провайдер, — а объявить
# действие, которому нужна ссылка, можно требованием `ActionRequirement.linkable()` без нового типа.
#
# Бюджет ролей: APP_API 51, APP_SPI 11, MODULE_API 15, INTERNAL 48.
#
# Забор — `PlatformVaadinSurfaceTest` в дереве приложения: каждый production-тип модуля
# `platform-vaadin` обязан иметь ровно одну роль, лишняя запись так же ломает сборку, как
# пропавшая. Полнота проверяется, а не подразумевается. До D3.5.4 забор смотрел на три
# каталога-кандидата в дереве, после переноса — на исходники самого модуля; состав проверяется
# в обе стороны третьим забором — `PlatformVaadinModuleTest` (копий типов в дереве нет).
#
# Роли — reviewed-решение, а не вывод теста: если бы список строил сам тест, проверялось бы то же
# правило, которым он построен. Черновик воспроизводится скриптом
# `node scripts/analyze-platform-surface.mjs --vaadin-registry`, решения по спорным типам
# записаны ниже явно.
#
# Правила классификации (в порядке применения):
#   1. D1-роль API -> APP_API, SPI -> APP_SPI: текущее потребление приложением сохраняется.
#   2. Явные решения по спорным типам — см. ниже.
#   3. Тип, который называет production-код другого platform-модуля -> MODULE_API.
#   4. Остальные -> INTERNAL.
#   5. Public nested type наследует роль owner-типа, если для него нет отдельной записи.
#   6. Каждый новый production-тип обязан получить роль сразу — полнота проверяется тестом.
#   7. D3.5.8: тип, стоящий в публичной сигнатуре типа с ролью APP_API/APP_SPI, не может быть
#      INTERNAL — он получает MODULE_API (или APP_API, если его называет приложение). «INTERNAL
#      можно менять свободно» в этой позиции означало бы скрытую ломку совместимости для тех,
#      кто уже скомпилирован против сигнатуры.
#
# Явные решения (механически не выводятся):
#
#   * FormCoordinator -> INTERNAL. D1 зарегистрировал его как legacy-internal (13 файлов
#     приложения), и это верный сигнал: класс несёт ApplicationContext, ServiceLocator,
#     mutable Workspace и режим открытия. Повышение до APP_API заморозило бы именно ту
#     поверхность, которую D3.5 обязан расчистить (D3.5.1: FormContext без ApplicationContext,
#     D3.5.3: UI-scope). Публичным контрактом должен стать узкий типизированный
#     FormNavigator/FormComposer, а сам координатор — реализацией.
#
#   * ItemTable -> APP_API. Приложение получает его из SPI-точки `TableSectionCustomization`
#     и вызывает на нём `applyPersistedRows`/`markDirty`, а также использует nested
#     `ItemTable.AddOption` (org/ip/views/forms/PrdSpecMtrTableCustomization.java:36-37).
#     Тип, который платформа передаёт в SPI, обязан быть публичным API: иначе SPI не
#     реализуем. Роль исправляет D1-запись legacy-internal: там измерялся reach-through,
#     а здесь это осознанная точка расширения.
#
#   * ListForm -> APP_API. Приложение строит на нём свои list-views (12 файлов в D1-реестре),
#     но не наследует его — то есть потребляет как компонент. Альтернатива (оставить INTERNAL)
#     означала бы, что прикладные list-views опираются на незаявленный контракт: формально
#     верно, практически — запрет пользоваться штатной формой списка. Узкий view-контракт
#     для list-форм — предмет D3.6, а не повод не назначать роль сейчас.
#
#   * LookupComboHelper -> APP_API. Прикладные конфиги полей (`UserFormConfig`,
#     `NomenclatureItemFormConfig`) намеренно берут его `DICTIONARY_LIMIT` и lazy-автокомплит:
#     INTERNAL сделал бы их зависимыми от незаявленного контракта, а дублирование лимита
#     литералом в приложении разъехалось бы при первом изменении политики загрузки.
#
#   * Explorer DTO и assemblers -> APP_API. `EntitySummary`/`EntitySummaryAssembler`/
#     `SubsystemSummaryAssembler` читаются прикладными views (`EntityExplorerView`,
#     `SubsystemStructureView`, `EntitySummaryPanel`, `JpqlRunService`). План D3.5 (D3.5.4)
#     переносит весь `org.ipro.vaadin` в модуль, поэтому «оставить в дереве» не вариант:
#     DTO обязан получить роль, и это роль API — приложение их только читает.
#
#   * MODULE_API был пуст до D3.5.8 — и это тоже был измеренный факт, а не недосмотр: ни один
#     platform-модуль не называл тип из этих трёх корней, а Report пользовался `EntityField` и
#     `SelectionFormAssembler`, которые уже APP_API. D3.5.8 добавил второе основание для роли:
#     тип, публично видимый через сигнатуру APP_API/APP_SPI (правило 7). Список в разделе —
#     результат замера, а не вкуса: 14 типов-владельцев отдают наружу 12 различных
#     INTERNAL-типов. В MODULE_API, а не APP_API, они переведены по факту употребления:
#     приложение их не называет, но прикладные конфиги передают в них лямбды и потому
#     компилируются против этих сигнатур. Граница честная: это поверхность модуля, а не
#     приглашение приложению её называть. Если D3.7 выделит report-core и ему понадобится
#     платформенный тип, которого нет в APP поверхностях, запись появится здесь и будет видна
#     в диффе.

# E1.6a: +1 APP_SPI (`ActionHandler`) и +3 APP_API (`ActionId`, `ActionRequirement`,
# `ActionInvocation`) — приложение впервые объявляет действие, а не только подавляет готовое.
# `ActionHandler` — SPI: его реализует приложение. Остальные три — часть той же подписи (id,
# требование и снимок списка обязано называть всякое объявление), поэтому они APP_API, а не
# MODULE_API: прежняя роль была верна лишь до появления первого потребителя. `ActionHandlerRegistry`
# — INTERNAL: приложение в него ничего не кладёт и его не называет.
#
# E1.4: +3 APP_API (`ActionDefinition`, `ActionSurface`, `CrudAction`) — первый потребитель
# app-facing контракта: приложение объявляет предметный override платформенного действия
# (`ActionDefinition.suppress(...)` в app-конфиге), то есть вызывает эти типы, а не наследует их.
# Роль APP_API, а не APP_SPI: приложение не реализует машину действий и платформа не вызывает
# обратно его код через эти типы. `ActionId` и `ActionRequirement` при этом видны через сигнатуры
# APP_API-типа (`id()`, `requirement()`, канонический конструктор) — правило 7 переводит их
# в MODULE_API, а не оставляет INTERNAL.

# E2.2: +2 APP_API (`org.ipro.form.link.*`) — исход открытия по адресу:
# `OpenResult` (Opened/NotFound/Forbidden/InvalidRoute/NotLinkable/Unavailable + метка
# `outcome()` для route audit) и `FormRouteOpener` (каталог → навигатор, порядок проверок §6 ADR).
# Роль APP_API: host маршрута в приложении принимает решение по исходу и показывает страницу
# состояния, то есть **называет** эти типы. Зависимость `FormRouteOpener` — от APP_API
# `FormNavigator`, а не от INTERNAL `FormCoordinator`: подпись обещания платформы не может
# называть класс реализации (та же норма, что у `FormContext`).
# Интерфейс `FormNavigator` расширен двумя routed-методами тем же срезом: без этого новому
# APP_API-типу нечего было бы вызывать, а обход через координатор потребовал бы INTERNAL
# в публичной подписи.

# E2.1: +10 APP_API (`org.ipro.form.link.*`) — публичный адрес формы как контракт
# приложения: `FormRoute`/`FormRouteKind` (типизированный адрес), `FormRouteCodec`
# (грамматика), `FormRouteCatalog`/`PublishedFormRoute` (публикуемые типы, варианты и причины),
# `FormLinkService`/`FormLinkResult`/`NotLinkableReason` (генерация ссылки), `FormRouteParseResult`
# (разбор с причиной отказа), `FormRouteAliasDeclaration` (декларация ключа приложением).
# Роль APP_API, а не APP_SPI: приложение **называет** эти типы (host маршрута и кнопка ссылки),
# платформа через них обратно не вызывает. Декларация (`FormRouteAliasDeclaration`) — тот же
# случай, что `ActionDefinition`: приложение конструирует значение и отдаёт его списком в wiring.
# Внутренних типов срез не добавил: бины живут в `FormAutoConfiguration`, а парсер/форматтер —
# один класс (`FormRouteCodec`), без отдельного INTERNAL-слоя. Baseline `.api` обновлён этим же
# срезом.
#
# E2.3 добавил host адреса и его мост с вкладками: `RouteStatePage` (то, что видно при 403/404)
# и `FormRouteUrlBridge` (соответствие адреса активной вкладке) — обе роли APP_API, потому что
# host пишет их в приложении. `BrowserHistory` — INTERNAL: это шов для проверки моста без
# браузера, а не контракт; менять его можно свободно. Алиасы маршрутов и сам host живут в
# `MainLayout` приложения, поэтому `@RouteAlias` в реестре модуля не появляется.
#
# Доделки ревью E2 добавили `ApplicationBasePath` — INTERNAL по той же причине, что и
# `BrowserHistory`: приложение его не называет и через подписи APP_API он не виден, а нужен он
# двум местам модуля сразу (запись истории и копирование ссылки), потому что базовый путь
# развёртывания у них обязан быть один. Публичность класса здесь — не обещание потребителю,
# а способ не дублировать формулу; менять его можно свободно.
#
# E3.0: +1 APP_API (`org.ipro.form.link.EntityExplorerAddress`) — грамматика адреса типа
# Explorer (`/entity-explorer/{key}`). Роль APP_API: host маршрута в приложении называет этот
# тип, читая ключ из адреса и различая «адрес раздела» и «ключ типа»; платформа через него
# обратно не вызывает. Второго описания ключа срез не завёл: грамматика берётся у
# `FormRoute.isKey`, а корень раздела — константа этого типа, потому что видом формы
# (`FormRouteKind`) он не является. Запрета занятых ключей в каталоге нет: ключ всегда второй
# сегмент, а резерв первого сегмента — политика приложения (список `reserved` в baseline
# маршрутов), не свойство URL. Baseline `.api` обновлён этим же срезом.
