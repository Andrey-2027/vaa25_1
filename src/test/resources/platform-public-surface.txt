#   дескриптор поля запроса org.ipro.reportstudio.data.QueryField — ту же связь отчётного UI с
#   отчётной моделью, что и канонический ReportStructureEditor (уже в этой строке). Решение
#   осознанное: панель рисует списки и подписи полей, а резолвер визуального отбора строится
#   из этой схемы. Вопрос «становится ли дескриптор API/SPI вместо internal» относится к D3.7,
#   где проектируется шов report-модулей, и здесь он не решается молчанием.
#
# D1: reviewed реестр публичной поверхности платформы (FQN -> роль).
# Формат: <role> <fqn> [файлы приложения, которые называют тип — только для legacy-internal]
# Роли: API | SPI | legacy-internal; критерий и забор — в PlatformPublicSurfaceTest.

# Бюджет legacy-internal: 74 -> 67 (число записей ниже; то же число измерено в
# docs/architecture/d1-surface-measurements.md как legacy-internal-types).
#   73 -> 75 — это исправление измерения, а не новое разрешение. Забор читал только строки
#   `import`, поэтому пять production-типов приложения, записанных fully-qualified или через
#   wildcard-импорт пакета, в реестр вообще не попадали (WorkspaceGateway, JpqlDatasetRunner,
#   SectionRlsPolicy, JrxmlTemplateService, ServiceParams). Два из них действительно внутренние
#   на сегодня, и честный бюджет — 75.
#   75 -> 74 — осознанное решение: NaturalKeyCreateSupport признан поддерживаемым API. Это не
#   generic-внутренность, а механизм, намеренно используемый прикладными interned use cases;
#   роль не сходилась с употреблением.
#   74 -> 70 — D3.5.1/D3.5.3: снят reach-through к LookupService (16 файлов приложения) и
#   ServiceLocator (4 файла), плюс со строки FormCoordinator сняты 2 файла. Записи удалены

#   70 -> 69 — D3.5.3-fix: приложение больше не называет конкретный координатор (все вьюхи
#   переведены на типизированный FormNavigator, а сам навигатор берёт UI-scoped область через
#   провайдер). Ссылок стало ноль, и строка удалена целиком, а не оставлена с пустым списком.
#   69 -> 67 — D3.5.4: Vaadin-адаптеры телеметрии уехали из дерева в platform-vaadin
#   (org.ip.telemetry.vaadin → org.ipro.vaadin.telemetry), и вместе с ними снялись
#   legacy-строки MdcKeys и TelemetryBridge — их называл только адаптер. Тогда же ушли три
#   API-строки (EventSink, EventType, TelemetryEvent): у них тоже не осталось ни одного
#   потребителя в приложении. Это не ослабление границы, а её честность: реестр описывает
#   поверхность, которую приложение действительно называет, и обязан совпадать с фактом в обе
#   стороны — иначе он превращается в перечень желаний. Типы никуда не исчезли: EventSink и
#   EventType — публичный API platform-telemetry, MdcKeys/TelemetryBridge питают её же
#   адаптер, просто и то и другое теперь внутри платформы, а не в дереве приложения.
#   67 -> 57 — D3.5.7: сняты 10 записей, у которых роль не сходилась с употреблением. Реестр ролей
#   UI-платформы (platform-vaadin-surface.txt, D3.5.0) объявляет ItemTable, ListForm и три типа
#   explorer'а (EntitySummary/EntitySummaryAssembler/SubsystemSummaryAssembler плюс пять вложенных)

#   ItemTable — параметр
#   callback'а кастомизации, EntitySummary возвращается assembler.summarize(). Строки D1 были
#   написаны до D3.5.0, когда эти типы лежали в дереве приложения, и их замороженные списки
#   называли те самые report-файлы, которые поедут в D3.6: забор сообщал бы о нарушении границы
#   на легальном переезде. Дисциплина не ослаблена, а перенесена туда, где она проверяема:

#   javadoc), поэтому бюджет ссылок сократился не только переклассификацией.
#   57 -> 60 — D3.6: покрывающий забор everyPlatformTypeTheApplicationNamesHasAReviewedRole был
#   вакуумным (собирал unclassified, но не имел терминального ассерта), поэтому четыре типа,
#   которые приложение называло, в реестр не попали: FormNavigator (роль API — он объявлен

#   внутренних типа — LookupComboHelper (D3.5.2a) плюс ReportCatalogItemFactory и

#   INTERNAL, а лимит становится собственным решением экрана, либо это осознанный API.

#   целиком, а не осталась с обновлённым списком файлов.
