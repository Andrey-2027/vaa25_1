# platform-metadata — позвоночник метаданных

**D2 → D3.** Артефакт `org.ipro:platform-metadata:1.0-SNAPSHOT` содержит два типа:

| Тип | Роль |
|---|---|
| `org.ipro.metadata.AnnotationClassScanner` | единая точка сканирования классов по аннотации в base package (её используют все платформенные каталоги) |
| `org.ipro.metadata.ReferenceIndex` | индекс обратных ссылок: кто и каким полем ссылается на сущность |

## Почему именно эти два типа, а не пакет `org.ipro.metadata`

Срез определялся не удобством переноса, а замером: для каждой подсистемы считалось
замыкание — типы дерева, достижимые транзитивно от её пакета. Модуль не может ссылаться на
дерево (приложение зависит от модуля, обратная ссылка замкнула бы сборку), поэтому именно
замыкание, а не число прямых импортов, показывает, что мешает выносу.

Замер показал, что весь упор подсистем в метаданные — это ровно два типа:

| Подсистема | Тянула из дерева до этого среза |
|---|---|
| `org.ipro.numbering` | `AnnotationClassScanner` |
| `org.ipro.settings` | `AnnotationClassScanner`, `ReferenceIndex` |

Пакет `org.ipro.metadata` целиком (37 классов) — это движок метаданных со своими
резолверами, реестрами секций и компонентами форм; он выносится по мере того, как этого
потребует замыкание следующей подсистемы, а не «за компанию». Реестр замыканий —
`PlatformSubsystemClosureTest`, он shrink-only: рост записи означает новый импорт подсистемы
в приложение, сокращение — состоявшийся срез, зафиксированный сознательно.

## Что модуль не содержит и почему

- **Авто-конфигурации.** Бин `ReferenceIndex` объявляет `MetadataAutoConfiguration`
  приложения (с `@Value("${platform.subsystem-scan-package:org.ip}")`), поэтому потеря
  артефакта ломает сборку, а не проявляется позже как «каталог молча пуст». Если модулю
  когда-нибудь понадобится собственная авто-конфигурация, он обязан нести свой imports-файл
  — по образцу `platform-events` и `platform-persistence`.
- **Реализаций платформы** (`data`, `crud`, `rls`, `telemetry`, `form`). Разрешённые
  зависимости — только `platform-contracts` (аннотации метаданных) и `spring-context`
  (сканер классов и bean-контракт). Набор reviewed и проверяется
  `PlatformMetadataModuleTest`.
- **Знания о подсистемах.** `ReferenceIndex.ReverseReferenceSource` — интерфейс для
  источников ссылок из подсистем (направление `settings → metadata`), поэтому модуль
  остаётся ниже их и может быть зависимостью подсистем, а не наоборот.

## Сборка

Модуль — самостоятельный Maven-проект, собирается до приложения
(`mvn -f platform-metadata/pom.xml -DskipTests clean install`), зарегистрирован в
`scripts/local-dependencies.json` (`dependsOn: platform-contracts`). Приложение получает его
как обычную зависимость и не перечисляет его пакеты ни в `@EntityScan`, ни в
`@EnableJpaRepositories`, ни в component scan.
